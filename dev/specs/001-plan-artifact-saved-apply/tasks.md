## Four test-design traps

Each makes a criterion silently unsound if missed. Each is encoded in a task rather than left as
advice.

1. **SC-006 (T041)** compares two consecutive plan runs byte-for-byte. The engine may switch to
   incremental extraction on the second run, and `delete_operations_computed` is inside the
   checksum and is **not** one of the two masked fields. The test MUST pin the same extraction mode
   on both runs and both sides, and MUST assert the pinning held before comparing.
2. **SC-002 / SC-003 / SC-008 (T074)** ride on the destination kind's human-friendly ID being
   declared in the destination schema **and** fully supplied by the plan's identity. A fixture
   lacking it produces duplicates that read as a product bug. The integration fixture MUST assert
   the precondition and fail as a fixture error when it does not hold.
3. **SC-008 (T079)** exercises apply-time peer resolution — but if every referenced peer is created by
   the same plan, dependency-tier ordering fills the resolver's memo and the destination-query path
   **never runs**, so the test passes while the requirement it measures is broken. The fixture MUST
   include at least one referenced peer that **pre-exists at the destination and is absent from the
   plan**, and MUST assert that the query path was taken for it.
4. **The conformance harness against a mock (T081, T046, T051) — AD054.** Two assertions cannot fail
   for the right reason if the harness is built the obvious way. **(a)** Keyedness is a property of the
   **rendered mutation**, not of the assembled `data`: by the time `data` is complete a
   relationship-crossing HFID component is a resolved node-id **string**, so "every component present in
   `data`" can hold while the mutation goes out with neither `id` nor `hfid`. The harness MUST build a real
   `InfrahubNodeSync` from a **committed `NodeSchemaAPI` fixture** and assert the rendered input
   (`.venv/…/infrahub_sdk/node/node.py:295-298`, upsert render `:1843-1846`). **And the assertion must be
   split (AD067)**: the harness is *required* to include a kind whose HFID crosses a relationship, and that
   kind cannot render keyed today (V39), so a universal "every operation renders keyed" asserts an outcome
   the artifacts' own facts say must fail. All-direct-HFID kinds MUST render keyed; the
   relationship-crossing kind carries the same assertion under `xfail(strict=True)`. **(b)** The replace-set
   reconciliation MUST **re-read** the destination peer set before comparing. A relationship manager sets
   `self.initialized = data is not None` (`.venv/…/infrahub_sdk/node/relationship.py:264`) and `fetch()`
   returns immediately once initialized (`:286-299`), so on a node built from the write payload
   `peer_ids` **is** the desired set: `compare_lists` finds nothing to remove and the reconciliation is a
   guaranteed no-op that passes against a mock and removes nothing against a server. **And "fetch first" is
   not the fix (AD065)** — the `client.get` lives inside that guard (`:290-296`), so the manager must be
   forced cold (AD075 withdraws the second-node variant: the node saved must be the node whose manager was
   reconciled), and the observable is that a destination **read was issued**, because
   a no-op `fetch()` satisfies "was fetched before `peer_ids` was read". **(c)** A mock holds
   no destination state, so **"two applies produce one create" cannot fail at all** and asserting it at the
   invocation count does not rescue it — two applies simply issue two creates, there is no operation-level
   dedup in this design and none is wanted. Assert **byte-identical rendered mutation inputs** across the two
   applies instead (AD068): that can fail, it is decidable offline, and it is the property convergence rests
   on.

## Scope guardrails

Carried from the brief's Out of Scope and the spec's. No task below the line, and any task that
starts to grow one is wrong:

- No delete is ever executed against a destination.
- No new CLI command **group**, and under AD005 no new command either.
- No durable per-operation apply ledger — applied identifiers live on the run result only.
- No configuration-version registry, validation or interpretation — the value is opaque.
- No load-path reference-scan replacement and no batched destination writes.
- No destination freshness check, plan expiration or conflict policy.
- No v1 migration and no second apply path.
- **No change to the live `sync` write path. No exception (AD070).** The zero-match and multi-match refusals
  belong to the new apply-path resolver only; the existing warn-and-continue stays exactly as it is
  (AD048). And `_replace_relationship_set` is **new code on the planned-write path**, not an extraction
  shared with `update_node`: an earlier draft corrected `update_node`'s additive ordering "while we were
  there", which would have made `infrahub-sync sync` start **removing** destination relationship peers
  absent from the source. `update_node`'s only caller is the live write path
  (`infrahub_sync/adapters/infrahub.py:625`), so that is a data-removing change to an existing command,
  unauthorized here and contradicted by T044 and T053 in the same phase. **`update_node`'s additive ordering
  is a recorded pre-existing defect for a later outcome to own**, and the eight lines of duplication that
  leaves are the deliberate price of this guardrail being literally true.
- **No new run state, and no run failure for a recorded delete.** The vocabulary stays
  `pending | running | dry-run | applied | failed`; a delete-bearing apply ends `applied` with a recorded
  skipped-delete count and a warning naming it. Introducing a distinct state for "applied with skips"
  would be the compatibility change AD010 declines (AD055).
- **No repair of unreachable code.** The schema-subhash refusal path cannot execute (corrected V22), so
  T060 is dropped rather than implemented, and nothing in this run makes that check live (AD063).
- **No `--run-id` overload.** Review takes its run identifier as `--from-plan <run-id>`; the existing
  `--run-id` keeps exactly one meaning (AD057).
- **No error-tolerance option added to `diff`.** Derivation failures there are hard failures; adding a
  `--continue-on-error` to the non-mutating command would be new user-facing surface the brief does
  not carry (AD047).
