# Critique: Approve a plan without applying it, and a `verify` that checks the destination

**Date**: 2026-11-10 | **Spec**: [spec.md](../spec.md) | **Plan**: [plan.md](../plan.md)

## Executive Summary

The problem is real and sourced: a customer report and two V3 cards (INFP-653, INFP-647) describe the same gap.
The scope is small and each user story ships alone. The plan reuses the existing pre-write gate instead of copying
it, which makes the `verify`/`apply` parity requirement (SC-004) true by construction.

One gap must be closed before tasks: the plan says the approval and its idempotency receipt "commit together" but the
receipt machinery is built around submitting a flow run. The plan must name the store operation that records both in
one transaction. Four recommendations follow; none changes scope.

**Verdict**: ⚠️ PROCEED WITH UPDATES. Fixes applied to `plan.md`, `research.md` and `contracts/cli.md` in the same
commit as this report.

## Product Lens Findings

### 3a. Problem validation

- The need is evidenced (customer message, INFP-653, INFP-647). Scope is bounded by an explicit out-of-scope list.

### 3b. User value

- **P1 (💡)**: `approve` prints the run but not what is being approved. An operator who pastes the wrong run ID
  approves a plan they did not review. Suggestion: `approve` prints the plan's summary counts (creates, updates,
  recorded deletes) next to the approval, so the operator sees what they accepted. **Applied** to
  `contracts/cli.md` and `plan.md`.

### 3c. Alternatives

- Folding `verify` into `approve` was considered during the grilling and rejected by the user. No new alternative.

### 3d. Edge cases and experience

- **P2 (💡)**: `verify` now fails when the destination is unreachable or its credentials are missing. Before this
  change it succeeded without them. A script that runs `verify` where the destination is not reachable changes
  result. Suggestion: record the change as a `changed` changelog entry, and state it in the "Running a sync" page.
  **Applied** to `plan.md` (documentation notes).
- **P3 (🤔)**: no way to withdraw an approval in v1. Already recorded as the spec's open question; left for the
  user.

### 3e. Success measurement

- SC-001 to SC-005 are testable. No change.

## Engineering Lens Findings

### 4a. Architecture

- **E1 (🎯)**: Approval idempotency. `_resume_or_replay` replays an `accepted` receipt and otherwise submits a flow
  run; approval submits none. The plan must define a store operation that, in one transaction, runs the conditional
  approval update and completes the reserved receipt with its stored response, so a retry after a lost response
  replays the same body and a concurrent approve cannot record twice. Also check that `mutation_receipts.operation`
  accepts a new value `approve` (constraint or literal type). **Applied** to `plan.md` and `research.md` (R8).
- Validated: the gate split keeps the single artifact read in `apply_plan` and gives `verify` a function with no path
  to the write loop.

### 4b. Failure modes

- Validated: a failed `verify` writes back with `ExecutionMergeWriteback` (`flow.py`, `_record_failure`), so the
  phase does not change (FR-012) and the run stays approvable and applicable.
- Validated: `resolve_destination_lineage` on Infrahub runs one `AccountProfile` query and writes nothing, so
  including it in the gate keeps `verify` read-only.
- **E2 (💡)**: Approve while a `verify` execution is active is refused by the "no active execution" rule. That is
  safe but surprising. Suggestion: the refusal message names the active stage. **Applied** to
  `contracts/http-api.md` wording in `plan.md` notes.

### 4c. Security

- Validated: the approval-required check at admission cannot be bypassed from the Prefect UI, because a worker only
  runs an execution the API recorded (`_claim_current_execution`). Worker-side enforcement stays a later
  defence-in-depth change (research R9).
- The approval reason is operator text, stored like other audit reasons; no secret enters it.

### 4d. Performance

- No concern: approval is one row read and one conditional update; `verify` adds the reads `apply` already does.

### 4e. Testing

- **E3 (💡)**: SC-004 parity needs one test per check where the same fixture makes both `verify` and `apply` refuse
  on the same check name. Suggestion: a parametrized test over the check list in `data-model.md`. Carried into
  tasks.

### 4f. Operations

- Nullable columns are additive; an older service ignores them. Rollback is to unset
  `INFRAHUB_SYNC_REQUIRE_APPROVAL`.

### 4g. Dependencies

- Spec 017 (run events) is not on the base; the `approved` event is a follow-up (research R10).

## Cross-Lens Insights

- **X1**: P1 and E1 meet at the approve response: the stored response the receipt replays should carry the summary
  counts, so a replayed approval shows the same thing the first one did.
