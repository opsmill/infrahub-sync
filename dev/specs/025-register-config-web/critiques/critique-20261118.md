# Critique: Register a configuration package from the web interface

**Date**: 2026-11-18
**Artifacts reviewed**: [spec.md](../spec.md), [plan.md](../plan.md), [research.md](../research.md),
[contracts/](../contracts/), [constitution](../../../../docs/docs/development/constitution.md)

## Executive summary

The problem is real: today a configuration can only be registered from a terminal, and a version
can only be checked against the destination after it becomes permanent. The plan solves both with
one read-only route and changes in the web interface, with no new dependency.

One finding blocks implementation. The access rule chosen for the new route would let a token that
is not an administrator token send the service's destination token to a server of its choice. The
other findings are completions to the contracts and the spec.

**Verdict**: ⚠️ PROCEED WITH UPDATES. All updates are applied in the same commit as this report.

## Product lens

### 3a. Problem validation

- The need comes from the maintainer (grilling session, 2026-11-18). No customer request is cited;
  this is recorded in the spec's Input. No change.

### 3b. User value

- Story 1 has value on its own for CLI users (`configs check`). Story 4 can be dropped without
  changing Stories 1 to 3 (FR-022). The order delivers value early. No change.

### 3d. Edge cases and user experience

- **P1 (💡)**: drag and drop alone excludes keyboard and assistive technology users. The web
  interface contract has a "choose a file" button, but no requirement asks for it. **Applied**: FR-007
  now requires a way to choose the file without dragging.
- **P2 (💡)**: validation against an unreachable destination can take up to the SDK timeout of 60
  seconds for each read (`capabilities.py`, `_resolved_client_settings`). The spec does not say what
  the operator views meanwhile. **Applied**: FR-009 now requires a visible "validating" state and
  that Cancel stays available while validation runs.

### 3e. Success measurement

- SC-001 (under 2 minutes) holds when the destination answers. When it does not, two 60-second
  timeouts approach the limit. Accepted: SC-001 describes the normal case; User Story 4 covers the
  outage. No change.

## Engineering lens

### 4c. Security

- **E1 (🎯)**: with a branch, validation builds an Infrahub client from the package's
  `destination.settings.url` and resolves the package's `token` credential reference from the
  service environment (`_resolved_client_settings` in
  [`capabilities.py`](../../../../infrahub_sync/configuration/capabilities.py), line 194). For a
  registered version this is safe, because only an administrator registers. For a package sent by
  the caller, a token that is not an administrator token could declare its own URL and receive the
  service's destination token. Research R10 and FR-005 gave the new route the access rule of the
  existing validate route, which accepts any authenticated token. **Applied**: the new route requires
  an administrator, like registration, and records a refused attempt in the audit log as
  registration does. FR-005, research R10, the Sync API contract and the constitution check are
  updated.
- **E2 (💡)**: `document` is parsed with `yaml.safe_load`, which expands aliases; a crafted
  document can consume memory. After E1 only administrators reach the parser, the same people who
  can register any package. Accepted risk, recorded in the plan.

### 4b. Failure modes

- **E3 (💡)**: `destination_read` in the data model and contract lists `timeout`, `unreachable`,
  `unauthorized`, `forbidden` and `nobranch`. `_resolved_client_settings` also raises the reasons
  `unconfigured` (no destination URL) and `credentials` (the token reference does not resolve).
  **Applied**: both values added; both block registration like other findings.

### 4e. Testing

- **E4 (💡)**: the review step must show every finding, but the route returns a page of at most 256
  findings, like the existing route. **Applied**: the web interface contract states that the review
  step requests the largest page and, when `total_findings` is larger, says how many more findings
  exist and that `infrahub-sync configs check` lists them all.
- The parity test for FR-002 (same findings before and after registration) needs a destination for
  the branch case. The unit tier can use the existing destination schema test doubles; the live
  check is in quickstart Scenario 1. No change.

### 4f. Operational readiness

- The new table is created with `CREATE TABLE IF NOT EXISTS`. Rolling back the code leaves an
  unused table, which is harmless. No change.

### 4g. Integration risks

- Spec 022 (local accounts) is in progress and touches the same files; recorded in the plan's Risks.
  No change.

## Cross-lens insights
