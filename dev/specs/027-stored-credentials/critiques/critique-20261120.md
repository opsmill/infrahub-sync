# Critique Report: Stored credentials managed through the Sync API

**Date**: 2026-11-20 | **Spec**: [spec.md](../spec.md) | **Plan**: [plan.md](../plan.md)

**Reviewed at**: commit `c0178ca0`

## Executive Summary

The problem is real and stated with evidence: the brief traces each pain point to the code and to ADR
0039. The design follows two patterns that already exist, the `admin` account defined by the
environment and Infrahub's shared `agent` account, and it removes a mechanism instead of adding a
second one.

Two findings must be fixed before tasks:

- **Redaction.** Today the Sync API and the worker build their redaction lists from the process
  environment (`execution.py:416`, `service.py:373`, `apply_guard.py:303`, `schedules.py:322`). Once
  values come from the database, a value that the Sync API decrypts for the schema read is in no
  redaction list. On the worker, a value released before `flow.py:1166` is also in no list.
- **Timeouts and retries on the worker's call.** Constitution principle II requires explicit handling
  of timeouts and transient failures, and the plan does not define it for the new call.

The other findings are recommendations that can be applied to the plan now.

**Verdict**: ⚠️ PROCEED WITH UPDATES

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 💡 | Revisions restart at 1 when a credential is deleted and created again with the same name. A run record "netbox-lab revision 1" is then ambiguous. | `run_credential_uses` also records `credential_id`. The run detail route keeps returning the name and the revision. |
| E2 | 💡 | Research R5 releases only the destination to apply, resume and verify. If a write stage builds the incremental store, it also needs the `store` block. | Release the `store` block to every stage that builds the store. A task checks which stages build it. |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E3 | 🎯 | The worker's call to the Sync API has no timeout or retry rule. A short restart of `sync-api` would fail every run that starts during it. Constitution principle II. | The client uses a 10-second timeout and retries connection errors and `502`, `503` and `504` three times with backoff (1, 2 and 4 seconds). It does not retry other refusals. After the last attempt, the cause is `api-unreachable`. |
| E4 | 💡 | Deletion and registration can race: a registration can check that a credential exists while a deletion removes it. | Both run in one transaction that locks the credential row (`SELECT … FOR UPDATE` on PostgreSQL). Run start checks again (FR-008), so the race cannot reach a worker. |
| E5 | 💡 | Rolling back to an earlier build is not described. | ADR 0054 says that an earlier build ignores the new tables, needs `INFRAHUB_SYNC_CREDENTIAL_*` again, and cannot run versions that name stored credentials. |

### Security & Privacy

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E6 | 🎯 | Redaction lists come from the environment. A value that the Sync API decrypts in its own process for the schema read is in no list, so an error from the Infrahub SDK that repeats the token would reach a log or a response. On the worker, a value released before `flow.py:1166` is in no list. | The decryption function returns values in a type that registers them with the process's redaction list at once, for the Sync API (per request) and for the worker (from the moment of release). A test raises an error that holds the value at each point and checks the output. |
| E7 | 💡 | The worker token travels to `sync-api` over plain HTTP in Compose, as the values do in the answer. | Document it. The worker client trusts `INFRAHUB_SYNC_CA_DIRECTORY` and accepts `https://` for `INFRAHUB_SYNC_API_URL`. |
| E8 | 💡 | The worker token's format is not defined. The `admin` token refuses the `ifs_pat_` and `ifs_ses_` prefixes and has a minimum length (`settings.py:162-171`). | Apply the same rules to `INFRAHUB_SYNC_WORKER_TOKEN`, and refuse a value equal to the `admin` token. |
| E9 | 💡 | Any signed-in account can call validate on a registered version with a branch, which makes the Sync API send the destination token to the registered destination. | No change: an administrator registered that address. Record it beside the "not bound to an address" assumption. |
