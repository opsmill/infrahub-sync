# Critique Report: Read state for each side of a Plan

**Date**: 2026-11-09
**Inputs**: [spec.md](../spec.md), [plan.md](../plan.md), [research.md](../research.md),
[data-model.md](../data-model.md), [contracts/](../contracts/), the constitution
(`docs/docs/development/constitution.md`).

## Executive Summary

The problem is real and comes from a request by the frontend team. The scope is small: one observer in Potenda,
two columns, one response field and two CLI fields. The design reuses the store's column migration and the
engine's private seams.

Two findings must be addressed before tasks are generated:

- A registered run holds its `verify` and `apply` executions after its Plan execution. "The latest execution",
  which the spec and the CLI use, is then an execution with no read state, so the read state disappears from the
  run's page and from `runs show` once the operator verifies the plan (M1).
- When the worker fails to record a side's end but the stage succeeds, FR-009 shows the side as `interrupted`,
  which is false (M2).

**Verdict**: ⚠️ PROCEED WITH UPDATES.

## Product Lens Findings

### Problem Validation

The frontend team reported the problem, and the grilling confirmed the user and the pain. No finding.

### User Value Assessment

- **M1 (Must-Address).** The service records a run's `verify` and `apply` stages as new executions of the same run
  (`RunService` calls `_owned_run(run_id, ..., "verify")` and `_owned_run(run_id, ..., "apply")`,
  `infrahub_sync/service/service.py:341,370`). After an operator verifies a Plan, `resource.orchestration[-1]` is
  the `verify` execution, whose `reads` is `null`. The spec's Key Entities say that the UI and the CLI show "the
  latest execution's read state", and FR-012 says `runs show` prints the read state "of the latest execution". The
  read state would vanish exactly when the operator reviews the plan.
  **Suggestion**: show the read state of the latest execution that read the sides, meaning the latest `plan` or
  `sync` execution, in the spec (Key Entities, FR-012, User Story 2) and in the CLI design (research R11).

### Edge Cases & User Experience

- **R1 (Recommendation).** The spec does not say what the operator views for an execution that is still in the
  queue, before the worker starts it. With R4 the sides appear only when the worker starts the stage.
  **Suggestion**: state in the edge cases that a queued execution has no read state yet.

### Success Measurement

- **Q1 (Question).** SC-001 rests on a UI refresh interval that the frontend team has not confirmed. It is recorded
  as an assumption. No change.

## Engineering Lens Findings

### Architecture Soundness

The observer keeps Potenda free of service imports, and the private seam leaves the pinned factory shape alone. The
principle VII exception is recorded. No finding.

### Failure Mode Analysis

- **M2 (Must-Address).** FR-007 lets a failed write pass without changing the outcome. If the end write of a side
  fails and the stage then succeeds, the side stays `reading`, and FR-009 returns it as `interrupted` for an
  execution whose `terminal_state` is `completed`. A completed `plan` or `sync` execution read both sides
  successfully, so `interrupted` is false.
  **Suggestion**: for an execution whose `terminal_state` is `completed`, return a side still stored as `waiting`
  or `reading` as `null` (no read state recorded) and log one WARNING, instead of `not_started` or `interrupted`.
  Keep FR-009's rule for every other terminal state. Update FR-009, the edge cases, R6, the data model and the
  contract.
- **R2 (Recommendation).** On SQLite, the two read threads and the main thread write through separate connections.
  `sqlite3.connect` waits 5 seconds on a locked database by default (`store.py:2915`), so a write rarely fails, and
  FR-007 covers the case. **Suggestion**: add a unit test that runs both reads concurrently on SQLite and checks
  both end documents.

### Security & Privacy Review

Only fixed states, times, counts, kind names and class names are stored. Kind names come from the configuration's
schema mapping, as the plan summary's `by_kind` already does. No finding.

### Performance & Scalability

- **R3 (Recommendation).** With DiffSync's Redis store, `count(model)` scans the store's keys for each kind
  (`diffsync/store/redis.py:210`), and `get_all_model_names` scans them all once. On a large configuration with
  many kinds, counting adds one key scan for each kind after each read. **Suggestion**: count once over the store's
  objects when the store is Redis, or measure the cost on the largest example before choosing; record the result in
  the implementation report.

### Testing Strategy

- **R4 (Recommendation).** Tests that compare a full run response or an `OrchestrationSummary` dictionary will see
  a new `reads` key. **Suggestion**: a task to find and update those tests, separately from the new tests.

### Operational Readiness

- The columns are additive and nullable. Code from before this feature selects explicit columns and ignores them,
  so a rollback to the previous image works without a migration. No finding.

### Dependencies & Integration Risks

- **R5 (Recommendation).** `docs/docs/reference/durable-product-records.mdx` describes what a stage execution
  records. **Suggestion**: include it in the documentation task if it lists execution fields.

## Cross-Lens Insights

- M1 and M2 both concern which read state the operator sees after the stage. Both are fixed in the response and
  CLI rules, with no change to the stored data.
