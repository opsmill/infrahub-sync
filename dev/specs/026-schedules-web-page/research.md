# Research: Manage schedules from the web interface

Every path below is relative to the repository root. Frontend paths are under `frontend/src/`.

## R1. Whether the Sync API covers every page

**Decision**: The existing routes cover the list, the schedule page and the actions. Two additions
are needed after the maintainer's review: a cadence preview route (R12) and a newest-first order
for `GET /events` (R13).

**Findings**:

- The schedule routes `GET /schedules`, `GET /schedules/{id}` and `POST /schedules/{id}/change`,
  `/pause`, `/resume`, `/delete` and `/take-over`, and `POST /schedules`, are in
  `frontend/src/api/types.generated.ts:320-457`, with `ScheduleResource`, `SchedulePage`,
  `CreateScheduleRequest` and `ChangeScheduleRequest`.
- `GET /runs` accepts `schedule_id` and `trigger_type` (`types.generated.ts:2455-2456`). A run has
  `trigger_type`, `schedule_id` and `scheduled_start_at` (`types.generated.ts:1825-1829`).
- `GET /me` returns `actor`, `administrator` and `approval_required`.
- Both write targets are available in this build: `DELIVERED_SCHEDULE_WRITE_TARGETS` in
  `infrahub_sync/service/serve.py` holds `branch-review` and `default-branch`.
- The Sync API replaces account identifiers with account names in `owner` and `left_out_set_by`
  (`ACCOUNT_FIELDS` in `infrahub_sync/service/presentation.py:27`).

**Alternatives considered**: Computing previews in the browser and reading the history oldest
first. Both are rejected in R12 and R13.

## R2. Where the pages sit and how they are routed

**Decision**: Two file routes, `routes/schedules.index.tsx` and
`routes/schedules.$scheduleId.tsx`, following `routes/runs.index.tsx` and
`routes/runs.$runId.tsx`. Page components in a new `features/schedules/` directory. A
"Schedules" navigation entry after "Runs" in `routes/__root.tsx`, with a new case in
`sectionOf`.

**Rationale**: The runs pages already solve the list, the detail page, search parameters and
prefetching. Each route's loader prefetches its query and never throws (`frontend/README.md:72-84`).
`routeTree.gen.ts` is regenerated by the TanStack Router Vite plugin and is committed.

**Alternatives considered**: Schedules only on the configuration page. A configuration has at most
one schedule, but an operator who asks "what runs on a schedule?" would have to open every
configuration. Rejected (spec SC-001).

## R3. Reading schedules

**Decision**: Add to `api/queries.ts`:

- `schedulePagesQuery({state, config})`, an infinite query on `GET /schedules` copied from
  `runPagesQuery` (`queries.ts:127-153`), polled every `LIST_REFRESH_MS`.
- `scheduleQuery(scheduleId)` on `GET /schedules/{id}`, polled every `LIST_REFRESH_MS`.
- `configScheduleQuery(configId)`: `GET /schedules?config_id=…&limit=1`, for the configuration
  page. Without a `state` filter the Sync API leaves deleted schedules out, and a configuration has
  at most one other schedule.
- `runPagesQuery` gains an optional `schedule` filter, sent as `schedule_id`, and its query key
  includes it.

**Rationale**: Same polling and paging behavior as the runs pages (spec edge case "An action and
a refresh cross"). `poll()` already stops polling after a failed first read.

## R4. Writing schedules and retry keys

**Decision**: Add one mutation hook per route to `api/actions.ts` with `$api.useMutation` and
`onSettled: invalidate`, as the run actions do. Each dialog creates a key with
`useIdempotencyKey()`, renews it when a field changes, and sends it as `Idempotency-Key`, as
`StartRunDialog.tsx:138-193` does. After a success, the page writes the returned schedule
resource into the cache of `scheduleQuery` with `setQueryData` before the invalidation reloads it.

**Rationale**: Pressing the button again after a lost answer resends the same key, so the Sync
API returns the first answer instead of creating a second schedule (FR-021, SC-005). Writing the
returned resource first means the page shows the state the action produced, even when a poll that
started before the action answers later (FR-022). After a refusal, the same `onSettled`
invalidation reloads the schedule: a resume refused with `schedule-stopped` can store the
schedule as stopped with a new reason, and the page then shows it.

**Change form**: the dialog keeps the schedule's values from when it opened and builds the request
with `changeRequest(opening, form)` in `domain/schedules.ts`. The Sync API has no version check on
a change (`ChangeScheduleRequest` has no version field), so comparing with a later poll could send
back a field that another person changed. A later poll that differs from the opening values shows
a notice with a reload (FR-023).

**Alternatives considered**: `sendSecret` (`actions.ts:99-110`), which keeps values out of the
query cache. No schedule field is a secret, and a credential in a field is refused by the Sync API
with `secret-parameter-refused`, so `useMutation` is enough.

## R5. Refusal messages

**Decision**: Add a `describeScheduleError` next to `describeAccountError` (`queries.ts:526`),
with a title and a detail for each schedule refusal code. The forms map the codes listed in
`data-model.md` ("Refusals mapped to a field") to the field they concern. Every other code is shown
with `MutationError` (`features/runs/form.tsx:78-109`).

`describeScheduleError` maps `forbidden` itself ("Only the owner of this schedule or an
administrator can do this"). It falls back to `describeError` only for codes it does not know,
because `ACTION_ERRORS.forbidden` (`queries.ts:304-307`) names "the actor that started this run".

**Rationale**: `describeAccountError` is the precedent for a table per area. `describeError`
already handles 401, no answer, timeouts and unknown codes.

**Secret refusal**: for `secret-parameter-refused` the form shows the title and detail of the
table, not the Sync API message, so no value entered in a field is repeated (spec edge case).

## R6. Permissions

**Decision**: A pure function `scheduleActions(me, schedule)` in `domain/schedules.ts` returns, for
each action, whether it is shown, whether it is available, and the text when it is unavailable,
per `data-model.md` ("Permissions"). The page renders from that result. While `GET /me` has not
answered, every action is shown as available and the Sync API decides, as `RunPage.tsx:454` does.

**Rationale**: One function holds the whole rule, so it can be tested without a browser.

## R7. Cron helper and time zone input

**Decision**:

- The cadence field is a helper with seven forms: "Every N minutes", "Every hour", "Every N
  hours", "Every day", "Every week", "Every month" and "Custom" (data-model "Cadence helper forms";
  the interval forms were added by the clarification of 2026-11-20). The first six are built from
  a fixed list of intervals, a minute, a time, days of the week and a day of the month; the helper
  writes the cron expression and shows it under the form, so the person learns the notation.
  "Custom" is a text field with a label for each of the five fields.
- `cronFromForm(form)` and `formFromCron(cron)` in `domain/cadence.ts` convert both ways.
  `formFromCron` recognizes only the exact patterns of the table; anything else is "Custom", so
  the helper never rewrites an expression.
- The words for the six built forms are produced by the helper itself. A custom expression gets no words:
  describing every cron expression in words needs a parser (for example the `cronstrue` library)
  whose reading can differ from Prefect's in edge cases, such as a day of month and a day of week
  both set. The preview of R12 shows what the expression does.
- GitLab's pipeline schedules offer a similar choice of common cadences and a custom cron
  expression; this design follows that idea. GitHub was not checked.
- The time zone is a `Select` filled from `Intl.supportedValuesOf("timeZone")`, with `UTC` added
  when missing. The browser's time zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`) is
  selected by default. When `supportedValuesOf` is not available, the field is a text field. The
change form adds the schedule's stored time zone to the choices when the browser's list does not
have it (an alias such as `Europe/Kiev`), so the stored value is never shown as empty.

**Rationale**: The spec decides that the interface does not compute start times (Decision 3). The
browser's list uses IANA names, which the Sync API's time zone check accepts. A name the Sync API
does not know is refused with `schedule-timezone-invalid` and shown under the field.

**Alternatives considered**: A cron library in the browser to describe the expression in words.
Rejected: a second cron reading that can differ from the Sync API's.

## R8. The schedule on the configuration page and on runs

**Decision**:

- `ConfigurationPage.tsx`: a "Schedule" line under the header state line (`:251-297`) with the
  schedule's name, state badge and next start, linked to the schedule page. Without a schedule it
  shows "No schedule" and a "Create schedule" button that opens the create dialog with the
  configuration and its latest version filled in.
- `RunsTable.tsx`: a "Scheduled" mark in `IdLine` (`:174`) for a run with `trigger_type`
  `scheduled`, linking to `/schedules/$scheduleId`.
- `RunPage.tsx`: a line "Started by schedule <name>, scheduled for <time>" with a link. The
  schedule's name is read with `scheduleQuery(run.schedule_id)`.
- `RunsPage.tsx`: the search parameter `schedule` (validated like `config`), shown as a removable
  filter "Schedule: <name>", passed to `runPagesQuery`.

## R12. Cadence preview route

**Decision**: Add `POST /schedules/next-starts` (contracts/http-api.md) to
`infrahub_sync/service/schedule_routes.py`, with a method `next_starts(cron, timezone, count)` on
`ScheduleService` in `infrahub_sync/service/schedules.py` that calls
`schedule_cadence.starts_between(cron, timezone, now, now + 5 years, count)` with the service clock.
`InvalidCadenceError` maps to `schedule-cron-invalid` or `schedule-timezone-invalid` with the same
message as the create path (`schedules.py:1081-1083`), raised with `_error`, not `_refusal`, so no
event is recorded. A response model `ScheduleNextStarts` is added to `infrahub_sync/client/models.py`, next to `ScheduleResource`. The credential check reuses `_refuse_secret_values` without recording an event. The
form calls the route 400 ms after the last change and ignores answers to older requests (TanStack
Query keyed by `cron` and `timezone`).

**Rationale**: `schedule_cadence` uses Prefect's `CronSchedule`, the class Prefect's scheduler
uses, including at daylight-saving changes. Any computation in the browser can disagree with the
starts that happen. The values travel in a JSON body, not in the query string, because uvicorn's
access log writes the query string; a credential typed into the field by mistake must not reach a
log (spec 021 FR-025). It takes no retry key because it stores nothing, like
`POST /configs/{config_id}/versions/{registry_version}/validate`.

**Alternatives considered**:

- A cron library in the browser. Rejected: a second computation that can disagree with Prefect.
- `POST /schedules` with a "dry run" flag. Rejected: every `POST` needs a retry key and writes an
  event, and a create needs a name and a configuration the person may not have chosen yet.
- A preview inside `GET /schedules/{id}` only. Rejected: the create form has no schedule yet.

## R13. Newest-first events

**Decision**: Add an `order` query parameter (`asc` default, `desc`) to `GET /events` in
`infrahub_sync/service/app.py:282`, carried through `RunService.list_events`
(`infrahub_sync/service/service.py:1511`) to `ProductStore.list_events`
(`infrahub_sync/product_store/store.py:3306`), which uses `ORDER BY created_at DESC, event_id DESC`
for `desc`. The protocol at `store.py:1031` and every implementation of it get the parameter with
the default `asc`. The schedule page fixes `until` to the time of its first read, so older pages
do not shift when new events arrive (contracts/http-api.md).

**Rationale**: The events are listed oldest first, paged by offset. A schedule that starts every 5
minutes records about 860 events a day with its run events. Showing the newest events would mean
reading every page first. Sorting in the store is one clause.

**Alternatives considered**:

- Reading every page in the browser and reversing it. Rejected: unbounded reads.
- A `since` window (the last 7 days) read oldest first. Rejected: the newest event is still on the
  last page, and a quiet schedule can have its last event older than the window.
- A route `GET /schedules/{id}/events`. Rejected: `GET /events?related=schedule:<id>` already
  selects the right events; only the order is missing.

## R14. History texts

**Decision**: `eventText(event)` in `domain/schedule-events.ts` maps `event_type` and `outcome` to
the texts of data-model "History entries", and returns the type and outcome as given for anything
else. The frontend has no event texts today (no use of `event_type` in `frontend/src`), so the
run events shown with "Show all events" get three texts of their own: `infrahub_sync.run.accepted`
"Run started", `infrahub_sync.run.synced` "Run wrote its changes" and `infrahub_sync.run.failed`
"Run failed". Any other run event shows its `operation` and `outcome` as returned.

## R9. Tests

**Decision**: Python: pytest unit tests for the preview route (starts equal to
`schedule_cadence.starts_between`, a daylight-saving case in `Europe/Paris`, `count` bounds, both
refusals, no event recorded on a refusal, the route not read as a schedule identifier) in
`tests/service/test_schedule_next_starts.py`, and for `order=desc` (order, ties on `created_at`,
default unchanged, invalid value) in `tests/service/test_events_route.py`. Frontend: add Vitest
for the pure functions in `domain/cadence.ts` (both directions, every form, the patterns that must
stay "Custom") and `domain/schedule-events.ts`, and for those in `domain/schedules.ts`: the
permission rule, the state and stop-reason texts, and the change request built from the opening
values and the form, including the case where a later read differs from the opening values. Add
`pnpm test` to the `frontend-lint` job in `.github/workflows/workflow-linter.yml`. Check the pages
by hand with `quickstart.md` against the development stack.

**Rationale**: The frontend has no tests today (no Vitest, no Playwright). The rules most likely to
be wrong in a way a reviewer misses are the permission rule and the change request, which are
pure functions. Vitest runs on the existing Vite configuration and adds one development
dependency. Browser tests would need a running Sync API and are not justified for one feature.

**Alternatives considered**:

- No automated test, as today. Rejected: constitution principle V asks for tests of behavior that
  can break.
- Node's built-in test runner. Rejected: it needs a TypeScript loader setup that Vitest provides
  from the Vite configuration.

## R11. Writing rules for page text

**Decision**: Page text follows `AGENTS.md` "Sync frontend" (account names only) and the style of
`ACTION_ERRORS`: the title says what happened, the detail says what to do next. Stop-reason texts
follow `_STOPPED_ACTIONS` in `infrahub_sync/cli.py` and the table in
`docs/docs/orchestration.mdx` ("A stopped schedule"), so the CLI, the docs and the web interface
give the same instruction.
