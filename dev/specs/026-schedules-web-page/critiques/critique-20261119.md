# Critique Report: Manage schedules from the web interface

**Date**: 2026-11-19

**Spec**: [spec.md](../spec.md) | **Plan**: [plan.md](../plan.md)

**Verdict**: ⚠️ PROCEED WITH UPDATES

## Executive Summary

The spec fills a gap that spec 021 left open on purpose: schedules exist in the Sync API and the
CLI but not in the web interface. The plan adds no Sync API route and reuses the runs pages'
patterns. Two must-address items were found, both in the change form:

- The spec assumed that `schedule-changed` reports a change made by another person after the form
  opened. It does not. The Sync API has no version check on a change, and `schedule-changed` is
  returned only when another writer changed the schedule during each of three save attempts. A
  form that compares its values with the latest polled schedule could undo another person's
  change without telling anyone.
- The shared `forbidden` message in `ACTION_ERRORS` (`frontend/src/api/queries.ts:304-307`) talks
  about "the actor that started this run". Reused on a schedule page, it would give the wrong
  instruction.

Both are resolved by the edits listed under "Applied changes". The other findings are
recommendations, applied where the fix was clear.

## Engineering Lens Findings

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | `ChangeScheduleRequest` has no version or `updated_at` field, so the Sync API cannot detect that the schedule changed after the form opened. User Story 5, scenario 8 and FR-023 assume it can. If the form compares its values with the latest polled schedule, a field the person did not touch, but another person changed meanwhile, differs and is sent back with the old value. That undoes the other person's change. | Compute the change request against the values the form opened with, not the latest poll. When the polled schedule differs from those values while the form is open, show "This schedule changed since you opened this form" with a reload. Restate `schedule-changed` as a refusal after three save attempts that the person can send again. Applied to the spec (User Story 5, FR-018, FR-023), data-model and research R4. |
| E2 | 🎯 | `describeError` maps `forbidden` to "Only the actor that started this run, or an administrator, can do this" (`queries.ts:304-307`). A schedule page that falls back to it gives the wrong instruction. | `describeScheduleError` maps `forbidden` and every schedule code itself, and falls back to `describeError` only for codes it does not know. Applied to research R5. |
