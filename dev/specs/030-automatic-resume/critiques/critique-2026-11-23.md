# Critique Report: Automatic resume of an interrupted apply

**Date**: 2026-11-23
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ PROCEED WITH UPDATES

---

## Executive Summary

The spec solves a real problem that INFP-650 names: a run stopped by a lost worker waits for a person for no reason
related to its data. The plan reuses the existing admission paths (`verify_run`, `resume_run`) and the receipts for
exactly-once submission, which keeps the new code small and keeps every existing check in force. One finding must be
fixed: rule 6 as planned would resume a run whose worker raised a failure but could not record it, which goes against
FR-002. The other findings are recommendations: write no decision row while the setting is off, state in the spec how
a person takes over a waiting row, avoid an import cycle between the service and the reconciler, and keep
submissions out of request-time reconciliation.

## Engineering Lens Findings

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E2 | 💡 | `service.py` imports from `liveness.py` (`select_cancellable_execution`). A reconciler that calls `RunService` would import it back, a cycle. The plan also names `app.py` as the place that wires them, but the reconciler is built in `serve.py`. | Define a narrow protocol in `liveness.py` (`AutomaticResumeSubmitter`, with `submit_check` and `submit_resume`) that `RunService` satisfies, and wire it in `serve.py`. |
| E4 | 💡 | `reconcile_execution` also runs at request time (`reconcile_run`, before a run is rendered). If the row step ran there, a `GET` request would submit Prefect flow runs. | The interruption insert may happen at request time (it is part of the store transaction), but the step of rows runs only in `reconcile_once`, the background loop. |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | Research R2 counts rule 6 when Prefect reports `crashed` or `failed`. In Prefect, `failed` means the flow raised an exception: the worker was running and reported a failure, but its failure record did not reach the store, for example because the store was unreachable. Resuming then contradicts FR-002 ("a failure that the worker reported itself"). `crashed` is the state Prefect gives when the process or its infrastructure ended. | Count rule 6 only for `crashed`. Update research R2, the spec's background and FR-001, and the plan's summary. |
| E3 | 💡 | When the pool snapshot is unavailable (`pool.detail_available` false), the plan does not say whether a row may be submitted. | Treat an unavailable snapshot as "no live worker": the row waits. Log one structured event per row move, with the run identifier and the state, never a value. |
