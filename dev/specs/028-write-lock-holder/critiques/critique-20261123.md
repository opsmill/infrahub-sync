# Critique Report: Name the run that holds a configuration's write lock

**Spec**: [spec.md](../spec.md) | **Plan**: [plan.md](../plan.md) | **Date**: 2026-11-23

**Mode**: critique extension (`speckit-critique-run`), run by the prep agent itself.

## Executive Summary

The problem is real and narrow: INFP-647 acceptance criterion 7, and a known weakness of the guess on branch
`fix/write-guard-names-active-run`. The design (a session label read through `pg_locks` and `pg_stat_activity`)
has no stale state and no migration. Two failure modes in the lookup itself are not bounded in the plan: a lookup
that hangs, and a query that returns more than one row. Both are resolvable in the plan. Verdict: ⚠️ PROCEED WITH
UPDATES.

## Product Lens Findings 🎯

### Problem Validation

- The need is stated in the INFP-647 acceptance criteria and in the review of the earlier branch. No finding.

### User Value Assessment

- P1 💡: The "ended" next action asks the operator to contact the administrator, but the operator may be the
  administrator. Suggest the next action also say what the administrator does: the lock is released when the
  holding session ends, so the worker of that run must be stopped or restarted.

### Alternative Approaches

- Owner row in a lock table (as ShedLock or Liquibase do) and fencing tokens were compared in the session before
  the spec; the label approach avoids stale rows. No finding.

### Edge Cases & UX

- P2 💡: The spec says nothing about the web interface. It reads the same failure record through the API, so it
  gets the same fields; say so in the spec's assumptions.

### Success Measurement

- P3 💡: SC-001 says "100% of repetitions" without a count. Suggest a fixed number (for example 20 repetitions in
  the integration test).

## Engineering Lens Findings 🔬

### Architecture Soundness

- E1 💡: `hold_apply_guard(run_id=None)` keeps an unlabelled path. Only `flow.py` calls it in production. Keep the
  parameter optional for the existing integration tests, but have `_configuration_write_guard` always pass it, and
  test that it does.

### Failure Mode Analysis

- E2 🎯: The holder lookup runs on a session that has just timed out. If the server is slow or the network
  drops, the query can wait without limit, and the failure record is not stored until it returns. Set a short
  `statement_timeout` for the lookup (for example 2 seconds, with `set_config` as `_SET_DEADLINE` does) and treat
  a timeout as "not known".
- E3 🎯: The plan's query can, in principle, return several rows (for example a session that holds the key and
  another that was granted it during a race). Read at most two rows; accept a candidate only when exactly one row
  is returned.
- E4 💡: The label is set with one more statement before `lock_timeout`. If that statement fails, the plan maps
  it to `ApplyGuardUnavailableError`. State that this fails the write before any lock request, and add a unit
  test.

### Security & Privacy

- E5 💡: Any session of the service's database account can set a label that names a real run of the same
  configuration. The run-record check limits this to real runs of that configuration, and only the service uses
  that account. Record this residual risk in the secret-redaction guideline correction and in the ADR 0021
  amendment.

### Performance & Scalability

- One query, only on a failed wait. No finding.

### Testing Strategy

- E6 💡: The scripted fake session in `tests/service/test_apply_guard.py` checks the exact statement order. Adding
  the label statement changes every existing acquisition script. List this in the tasks so the change to existing
  tests is deliberate, not incidental.
- E7 💡: `pg_stat_activity` depends on `track_activities` (on by default). Add the server setting to the
  integration test's recorded output, so a "not known" result can be explained.

### Operational Readiness

- E8 💡: Log the lookup outcome at debug level with the class of the outcome only (named, not known: no row, label
  rejected, run not confirmed, lookup failed), never the label. This helps explain a "not known" in support
  cases.

### Dependencies & Integration

- No new dependency. The API shape is unchanged. No finding.

## Cross-Lens Insights 🔗

- X1: E2 and the spec's FR-006 meet: a lookup must never delay or replace the contention failure. Bounding the
  lookup with a timeout serves the operator (the failure appears promptly) and the engineering rule.
