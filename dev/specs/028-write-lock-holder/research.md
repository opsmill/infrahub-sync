# Research: Name the run that holds a configuration's write lock

All facts below were checked on branch `028-write-lock-holder` (from `fix/write-guard-names-active-run` at
`a50d5780`) or in the PostgreSQL 16 documentation, linked for each item.

## R1. Where the label is written and read

- **Decision**: Write and read the label in `infrahub_sync/service/apply_guard.py` only. Pass the run ID from
  `_configuration_write_guard` in `infrahub_sync/service/flow.py`.
- **Rationale**: Both lock requests are inside `_execute_stage(run_id, ...)` (`flow.py:1254` for an apply,
  `flow.py:1311` for a sync), so every caller has the run ID. The guard owns its session, which is never handed to
  an adapter or to the product store (`_configuration_write_guard` docstring, ADR 0010).
- **Alternatives considered**: Setting `application_name` in the connection string in
  `service_guard_session` (`service/storage.py:180`). Rejected: `connect` is a no-argument callable built once
  per hold, and changing the connection string touches the redaction of the DSN (`dsn_secret_values`).

## R2. Run ID format and the label length

- **Decision**: Label is `infrahub-sync-guard:` (20 bytes) followed by the run ID. Write the label only when the
  whole label is at most 62 bytes; accept a label only when it is at most 62 bytes. A label of 63 bytes may have
  been cut short and gives "not known".
- **Rationale**: Run IDs generated by the service come from `generate_run_id` in `infrahub_sync/cache/paths.py`:
  `YYYYMMDDTHHMM-<8 hex>`, 22 characters, so the label is 42 bytes. The run records accept any identifier of up
  to 128 characters (`_IDENTIFIER_PATTERN = ^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$` in
  `infrahub_sync/product_store/models.py`), so a longer run ID can exist and must not be shortened. PostgreSQL:
  "The `application_name` can be any string of less than `NAMEDATALEN` characters (64 characters in a standard
  build)" and "Only printable ASCII characters may be used in the `application_name` value. Other characters are
  replaced with C-style hexadecimal escapes"
  ([PostgreSQL 16, runtime-config-logging](https://www.postgresql.org/docs/16/runtime-config-logging.html)). The
  run ID pattern allows only ASCII letters, digits, `.`, `_` and `-`, so no character is replaced.
- **Alternatives considered**: Hashing a long run ID into the label. Rejected: the label then needs a reverse
  lookup, and generated IDs already fit.

## R3. Reading the holder

- **Decision**: On the failing session, after the `55P03` lock timeout and before `_discard`, join `pg_locks` to
  `pg_stat_activity` on `pid`, filter `locktype = 'advisory'`, `granted`, the same key halves as `_OWNERSHIP`
  (`_lock_columns`), `objsubid = 1`, `database` equal to the current database's OID, and `pid` different from the
  session's own.
- **Rationale**: `pg_locks` lists the locks of the whole server; its `database` column is the "OID of the
  database in which the lock target exists"
  ([PostgreSQL 16, pg_locks](https://www.postgresql.org/docs/16/view-pg-locks.html)). The advisory key is derived
  from the configuration ID only, so the same key in another database on the same server is a different lock.
  A lock timeout in autocommit mode leaves the session usable.
- **Alternatives considered**: A second, new session for the lookup. Rejected: it adds a connection to a path
  that has already failed (SC-004).

## R4. Who can read the label

- **Decision**: Assume the guard sessions and the reading session use the same database account (the one service
  database setting). Treat a label that cannot be read (empty or null) as "not known". Cover a label that cannot
  be read in the real PostgreSQL test.
- **Rationale**: "Ordinary users can only see all the information about their own sessions (sessions belonging
  to a role that they are a member of). In rows about other sessions, many columns will be null. Note, however,
  that the existence of a session and its general properties such as its sessions user and database are visible
  to all users. Superusers and roles with privileges of built-in role `pg_read_all_stats` can see all the
  information about all sessions"
  ([PostgreSQL 16, monitoring-stats](https://www.postgresql.org/docs/16/monitoring-stats.html)). The
  documentation does not say whether `application_name` is among the columns set to null for another account's
  session, so this is not known from the documentation. The test with two accounts records what the server does,
  and the code must give "not known" or the correct run, never a wrong run.
- **Alternatives considered**: Granting `pg_read_all_stats` to the service account. Rejected: it widens what the
  service account can read, and the service uses one account anyway.
- **Correction, 2026-11-23**: The integration test
  `test_a_holder_of_another_account_is_named_correctly_or_not_known` showed that, on PostgreSQL 16 with
  `track_activities` on, a waiting session of another account that is not a superuser reads the holder's
  `application_name` and names the holder correctly. The label is therefore readable by any account that can
  connect to the Sync service's database, not only by the same account. A run ID is not a secret, and the label
  holds nothing else. A holder without a label shows `application_name` as an empty string, which the parser
  rejects, so the run is "not known".

## R5. The label is untrusted

- **Decision**: Any session of the same account can run `SET application_name`. Accept the label only with the
  exact prefix and a run-ID-shaped value (R2), then confirm in the run records that the run exists and has the same
  `config_id` as the failing run (`ProductProjection.write_holder_state`, R6). Never accept the failing run's own ID. Store
  only the run ID.
- **Rationale**: Spec FR-003, FR-005. The run records are the authority for run IDs; the label is only a pointer.

## R6. A holder whose write has ended

- **Decision**: Replace `other_write_in_progress(config_id, *, run_id)` with
  `write_holder_state(run_id, config_id) -> HolderState | None`. One query returns `None` when the run does not
  exist or belongs to another configuration; otherwise it applies the same rule (an execution of a write purpose
  that a worker claimed and that has no terminal verdict) to that one run and reports whether the write is still
  open. When it is not, the template says the run's write has ended. Do not add a stored field for this; the
  cause and the next action carry it. (Clarification 2026-11-23: one read of the run records, SC-004.)
- **Note (2026-11-23, review)**: The same read also returns `write_ended_at`, and the run counts as ended only when the run records have no claimed, open write for the run and its latest claimed write ended (`HolderState.write_ended_at`) before this write started waiting (the time the guard took immediately before it sent the lock request, stamped as `ApplyGuardContentionError.wait_started_at`). A holder that released the lock and recorded its verdict during the wait gets the "writing" variant. The causes say which run held the guard when the wait ended, not "for the whole wait".
- **Rationale**: `ProductRun.finished_at` is not a safe signal: a run that was interrupted and is now being
  resumed already has a record from its earlier stage. The open-write rule is what commit `a50d5780` already used.
  Keeping the record's field list to `active_run_id` keeps ADR 0021's field list change minimal.
- **Alternatives considered**: An `active_run_ended` boolean field. Rejected: one more field in the API and the
  record for a rare case that the template text already covers.

## R7. ADR 0021

- **Decision**: Amend ADR 0021 with a dated amendment (as ADR 0029 does): the fixed list grows by
  `write_guard_contended`, and the allowed fields gain `active_run_id`, a run ID confirmed in the run records and
  read from the label of the session that holds the configuration's write lock.
- **Rationale**: ADR 0021 states "a failure type from a fixed list of 17 names" and lists the allowed fields
  exhaustively (`dev/adr/0021-a-failure-record-holds-a-structured-cause.md`, Decision). Its Consequences say that
  adding a failure type means adding a typed attribute or an error class and a template, which this change does.
  Leaving the ADR unchanged would make its list wrong.
- **Alternatives considered**: A new ADR. Rejected: the decision of ADR 0021 stands; only its lists change.

## R8. Real PostgreSQL tests

- **Decision**: Extend `tests/integration/test_apply_guard_integration.py` (opt-in `-m integration`,
  `APPLY_GUARD_TEST_POSTGRESQL_DSN`). It already runs a holder in a separate OS process and terminates backends on
  a disposable database. Add: A holds with label, B and C wait with short deadlines, C's
  `ApplyGuardContentionError.holder_run_id` is A's run ID; a holder without a label gives `None`; a holder with a
  63-byte label gives `None`; a holder in another account gives either `None` or A, never another value.
- **Rationale**: The unit tier uses a scripted fake session, which cannot prove what PostgreSQL returns.

## R9. Earlier branch content kept

- `failure_type` `write_guard_contended`, `active_run_id` in `FAILURE_RECORD_KEYS`, `StageFailureResource`, the
  CLI line `active run: <run_id>` (`cli.py:1588`) and the `runs resume` hint variant stay as they are.

## R10. Running the PostgreSQL tests on every pull request

- **Decision**: Reuse the "Product store on PostgreSQL" job of `.github/workflows/workflow-tests.yml`. It runs on
  every pull request that changes Sync files (`needs.files-changed.outputs.sync`), starts a `postgres:16-alpine`
  service container, sets `PRODUCT_STORE_TEST_POSTGRESQL_DSN`, and runs `invoke tests.tests-product-store-postgresql`,
  which fails on any skip, an unset DSN or an empty selection (`tasks/tests.py`). Set
  `APPLY_GUARD_TEST_POSTGRESQL_DSN` to the same server in that job, and add
  `tests/integration/test_apply_guard_integration.py` to the task's selection and its DSN check. The nightly job
  (`.github/scripts/nightly_e2e.py`) keeps setting the DSN for its own run.
- **Rationale**: Clarification 2026-11-23 (FR-013). The job already has the container, the gate against silent
  skips and the trigger; a second job would duplicate them. The existing write-lock integration tests use a
  disposable database and terminate only their own backends, so they can share the server with the product store
  tests.
- **Alternatives considered**: A separate job only for the write lock. Rejected: a second PostgreSQL container
  and a second skip gate for the same trigger. Running the tests only when service files change (option C of the
  clarification). Rejected by the clarification.

## R11. Showing the holder in the web interface

- **Decision**: `failureDetail` (`frontend/src/domain/run-state.ts`) reads `active_run_id` from the failure record
  into `FailureDetail.activeRunId`, only when it is a non-empty string. The failure notice
  (`frontend/src/features/runs/run-notices.tsx`) shows the existing "Open run" link
  (`<Link to="/runs/$runId">`, already used by the notice that names another run) when `activeRunId` is set. The
  cause and the next action are the texts the service stores, so the "not known" and "has ended" cases need no
  web-only wording, and the web interface shows the same meaning as the CLI.
- **Rationale**: Clarification 2026-11-23 (FR-014). The web interface already shows the failure's cause and next
  action; the only missing part is the link. Reusing the existing link keeps one style for "go to another run".
- **Alternatives considered**: A new `active_run_ended` field so the web interface can word the "ended" case
  itself. Rejected (R6): the stored cause already says it. A prototype round with `emil-prototype`. Not planned:
  this is one link inside an existing notice, not a new screen.
