# Critique: 024-demo-ready-netbox

**Date**: 2026-11-18 | **Inputs**: spec.md, plan.md, research.md, contracts/, quickstart.md

## Executive summary

The scope is right and small: most pieces exist, and the plan composes them. One design flaw
blocks implementation as written: the development stack mounts the source tree over the installed
`infrahub_sync` package, so `demo prepare` run inside the development `sync-api` container finds
neither the wheel's bundled assets nor the repository paths (E1). Two smaller defects follow:
the idempotency key reuse across two different routes (E2), and a feedback destination that could
put customer details in a public tracker (P2).

**Verdict**: ⚠️ PROCEED WITH UPDATES. All must-address items have a clear fix, applied below.

## Product lens

### 3a. Problem validation

- The need comes from the maintainer's design conversation; the evidence is the 9-step,
  30-minute "Run a first sync". Scope is narrow and matches it. No finding.

### 3b. User value

- **P1 (💡)**: SC-003 (3 colleagues send feedback) cannot be checked by the build. That is
  correct for a round measure, but the spec should say it is measured after delivery, so tasks do
  not try to "implement" it. → Add a note to SC-003.

### 3c. Alternatives

- A script in `scripts/` instead of a CLI command would serve P1, but not the Styrmin driver, which
  runs the image. The CLI command is the simplest shape that serves both. No finding.

### 3d. Edge cases and experience

- **P2 (🎯)**: R-8 sends feedback to public GitHub issues. Solution architects try the demo with
  customers in mind and may write customer names or environments into feedback. → The page asks
  for feedback through the channel named in the invitation to the round, and lists what to
  include; it names no public tracker.
- **P3 (💡)**: `dev.demo` keeps an existing NetBox's data. A NetBox that holds the `seed` dataset
  (from the integration tests) gives a different plan with no explanation. → `dev.demo` says which
  dataset it found when it can tell, and always prints the command that reloads the `demo` dataset.

### 3e. Success measurement

- SC-001 to SC-005 are measurable. No finding beyond P1.

## Engineering lens

### 4a. Architecture

- **E1 (🎯)**: the development stack bind-mounts `../infrahub_sync` read-only over the installed
  package (`development/docker-compose.yml`, `x-sync-source`). Assets bundled into
  `infrahub_sync/demo/assets/` by the wheel build are hidden, and `examples/` and `tests/data/` are
  not mounted, so the source-tree fallback fails too. → `dev.demo` runs `demo prepare` on the host
  (`uv run`, source tree, fallback paths present) against the published loopback ports:
  `--infrahub-address http://localhost:8000` for the schema load, the worker addresses written into
  the package. The image path is proven separately by an image test (assets present in the built
  image) and quickstart scenario 3, which runs the built `infrahub-sync:dev` image with
  `docker run` and no source mount. FR-005 still holds: both paths run the same command.

### 4b. Failure modes

- **E2 (🎯)**: one idempotency key per package checksum is reused for `register_config` on the
  first run and `create_config_version` on a later run. The service rejects a key "already used by
  this actor for different content" with 409, so the second run could fail. → Derive the key from
  the operation and its target: `demo-prepare-register-<sha12>` and
  `demo-prepare-version-<config_id>-<sha12>`.
- **E3 (💡)**: a schema convergence timeout leaves the schema possibly loaded. The contract already
  says a second run completes the work; state the timeout (120 seconds, overridable with
  `--schema-timeout`).

### 4c. Security

- Tokens are environment-only; `dev.demo` passes the Infrahub admin token to a host process through
  its environment, not its arguments. No new finding.

### 4d. Performance

- Not relevant beyond SC-001.

### 4e. Testing

- **E4 (💡)**: the editable-install fallback and the wheel path are two code paths; test both
  (unit test for the source-tree path, wheel build test for the bundled path, image test for the
  image).

### 4f. Operational readiness

- Not a deployed service change. No finding.

### 4g. Dependencies

- `infrahub-sdk` schema API: `schema.load` returns `schema_updated` and `errors`; pinned
  `>=1.18,<2`. No finding.

## Cross-lens insights

- **X1**: E1's fix (run on the host in `dev.demo`) also gives colleagues clearer error output in
  their own terminal, with no container `exec` wrapping.

## Findings summary

| ID | Lens | Severity | Category | Finding | Suggestion |

## Remediation applied

All three must-address items and all four recommendations were applied to spec.md, plan.md,
research.md, the CLI contract, the task contract and quickstart.md in the same commit as this report.
