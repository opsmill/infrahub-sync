# Critique: spec 018, a Helm chart to run Infrahub Sync 3.x on Kubernetes

**Date**: 2026-11-16

**Reviewed**: [spec.md](../spec.md), [plan.md](../plan.md), [research.md](../research.md),
[data-model.md](../data-model.md), [contracts/](../contracts/)

**Verdict**: PROCEED WITH UPDATES. Six findings must be addressed; all six are applied in the
same commit as this report.

A first critique agent stopped on a rate limit before it wrote a report. This report was written
afterwards, from checks against the code, the images and `infrahub-helm`.

## Must-address findings

### M-1. The default image of the chart cannot be pulled today

- **Evidence**: on 2026-11-16, `docker manifest inspect registry.opsmill.io/opsmill/infrahub-sync:3.0.0a5`
  answered "artifact opsmill/infrahub-sync:3.0.0a5 not found" with this machine's registry login,
  while `registry.opsmill.io/opsmill/infrahub:1.11.12` resolved. The unreleased fragment
  `changelog/+prefect-from-sync-image.changed.md` says the Prefect server moved into the Sync
  image after `3.0.0a5` was cut, so an older image would not hold
  `infrahub_sync.service.prefect_server` either.
- **Change**:
  - `appVersion` follows the package version in `pyproject.toml`, as the Compose pin does (ADR 16).
  - Local verification uses an image built from this worktree.
  - The plan states that the chart is published only after the first Sync release that contains
    this code is in the registry.
  - The end-to-end test fails, rather than skips, when the image was pulled and a pod does not
    become ready.

### M-2. User Story 2 promises that state survives a change of Sync version

- **Evidence**: `docs/docs/compose-deployment.mdx:1180-1206`: "This alpha promises no in-place
  state migration and no backup or restore."
- **Change**:
  - The chart keeps the volumes across `helm upgrade` and runs the bootstrap again. That is what
    it can promise.
  - Whether packages and runs survive a change of Sync version is decided by each Sync release
    and its release notes, and is not promised during the alpha.
  - Scenarios 2 and 3 of User Story 2 and SC-003 are corrected to say so.

### M-3. A Job named after the release revision breaks tools that render the chart

- **Evidence**: tools that apply `helm template` output (Argo CD, for example) render
  `.Release.Revision` as 1 every time. After an image change, the Job keeps its name and gets a
  new pod template, and Kubernetes refuses the change because a Job's template is immutable.
- **Change**:
  - The Job name ends with a short hash of what the bootstrap reads: the image reference, its
    settings, and the checksum of the Secret and ConfigMaps the chart creates.
  - Helm deletes the Job of the previous name on upgrade, because it is no longer in the
    manifest, and a GitOps tool prunes it.
  - An upgrade that changes none of these leaves the completed Job in place. That is equivalent
    to running it again, because the bootstrap is safe to repeat and writes nothing on a converged
    deployment (`bootstrap.py:5-6`).
  - FR-007 and RR-34 are corrected.

### M-4. `helm lint` with no values fails on the required credentials

- **Evidence**: `infrahub-helm/Makefile:23-28` runs `helm lint` on every chart with no values. The
  `helm-lint-*` jobs in `ci.yml` do the same. The chart refuses to render without credentials
  (FR-012).
- **Change**:
  - Add `charts/infrahub-sync/ci/lint-values.yaml`, which names an existing Secret, and exclude
    `ci/` from the packaged chart in `.helmignore`.
  - Pass the file in the lint job and in the Makefile loop.
  - The file must not be named `values.<x>.yaml` at the chart root:
    `package-helm-chart.yml:94` publishes each such file as a chart flavor.

### M-5. Kubernetes service links put `INFRAHUB_SYNC_*` and `PREFECT_SERVER_*` variables into the pods

- **Evidence**: by default Kubernetes adds `<SERVICE>_PORT=tcp://…` and similar variables for each
  Service in the namespace. With a release named `infrahub-sync`, the Sync API Service is
  `infrahub-sync-api`, which gives `INFRAHUB_SYNC_API_PORT` and `INFRAHUB_SYNC_API_SERVICE_HOST`.
  A Prefect Service named `prefect-server` in a namespace shared with Infrahub gives
  `PREFECT_SERVER_*` variables, the prefix of Prefect's server settings. The Sync code refuses
  some settings when they are set to an unexpected value (`storage.py:158-166`,
  `settings.py:26-34`).
- **Change**: set `enableServiceLinks: false` on every pod (new RR-23).

### M-6. Two Prefect servers can run at the same time during a rolling update

- **Evidence**: the Prefect server runs its database migration when it starts
  (`service/prefect_server.py:36-37`). With the default `RollingUpdate`, the new pod starts while
  the old one still serves.
- **Change**:
  - The Prefect server and the worker use the `Recreate` strategy.
  - The worker uses it to keep one worker, the only tested value.
  - The Sync API keeps `RollingUpdate`, because its schema initialization runs under an advisory
    lock (`product_store/store.py:417`).
  - New RR-24.

## Recommendations

- **R-1. Write the gate with the Prefect client, not with raw HTTP.**
  - `prefect.client.orchestration.get_client()` already applies `PREFECT_API_URL` and the Basic
    authentication from `PREFECT_API_AUTH_STRING` (`prefect/client/orchestration/__init__.py:266-274, 357`).
  - The gate reads the deployment `infrahub-sync-service/run` (`service/orchestration.py:33-34, 49-51`)
    with `read_deployment_by_name` and checks its `work_pool_name`. This is the same call that
    `service/deploy.py:33` makes.
  - Applied to plan.md.
- **R-2. Mount the PostgreSQL init script with mode 0555.**
  - The entrypoint sources an `.sh` file that is not executable, rather than running it
    (`docker-entrypoint.sh:180-187` in `postgres:16-alpine`).
  - When it is sourced, the script's `set -eu` stays in force in the entrypoint.
  - During initialization the server listens only on its local socket
    (`docker-entrypoint.sh:297`). The container must therefore set `PGUSER` and `PGDATABASE` to
    the administrator role and must not set `PGHOST`.
  - Applied to plan.md.
- **R-3. Make the end-to-end upgrade check wait for the new Job.**
  - On an upgrade the gate passes at once, because the deployment of the previous release still
    exists (research R-2).
  - The test therefore waits for the new Job with `kubectl wait --for=condition=complete` before
    it checks the Sync API.
  - Applied to quickstart.md.
- **R-4. State how `helm --wait` treats the Job.**
  - Helm 3 waits for Jobs only with `--wait-for-jobs`.
  - Whether Helm 4's default wait treats a Job as ready only when it completes is not verified.
    Check it during implementation, then document it.
- **R-5. State what an upgrade does to a run in progress.**
  - Replacing the worker pod ends any run it is executing.
  - The documentation tells the operator to check `infrahub-sync runs list` before an upgrade,
    and points to "When the outcome of a write is uncertain" (`compose-deployment.mdx:1208`).
  - Added to FR-031 and the edge cases.

## Checked and found correct

- **Worker without a work pool.** On each sync it reads the pool again and logs "not found"; it
  does not exit (`prefect/workers/_worker_channel/_sync.py:298-336`, Prefect 3.8.6).
- **The bundled-store check of the bootstrap.** It resolves `object-store.` as an absolute name
  (`bootstrap.py:109-136`), so in Kubernetes it always concludes that the bundled store is left
  out. It only refuses an endpoint whose host is exactly `object-store`. A Service named
  `<fullname>-object-store` passes (research R-3).
- **`$(VAR)` in container variables.** Kubernetes expands a reference to a variable defined
  earlier in the same list, a `secretKeyRef` variable included. It leaves an undefined reference
  as literal text, so the order of the list is part of the contract (plan, design point 1).
