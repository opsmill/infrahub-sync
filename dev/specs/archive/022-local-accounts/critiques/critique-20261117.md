# Critique Report: Sign in to Sync with a local account

**Date**: 2026-11-17 | **Spec**: [spec.md](../spec.md) | **Plan**: [plan.md](../plan.md)

**Reviewed**: `spec.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`
at commit `6897d538`, against the code at `7987596f` and the constitution.

**Method**: an independent reviewer read the artifacts and checked their claims in the code. The
reviewer ran one command, `hashlib.scrypt`. The rest is from reading.

## Executive Summary

**Verdict: ⚠️ PROCEED WITH UPDATES.**

The problem and the scope are sound. Nine findings block task generation. Four of them (E1, E2,
X2, E7) come from one design choice: records hold the account name as text, and a deletion
rewrites it. The update replaces that choice: records hold an account identifier, and the API
turns it into a name when it answers. The other blocking findings are a sign-in refusal that a
stranger can keep in place, a way to test guesses of the `admin` password, the memory cost of
password hashing, a first step that cannot be released alone, and two inaccurate statements.

All blocking findings and all recommendations are applied in the commit that adds this report.
The "Resolution" column says how.

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion | Resolution |
| --- | --- | --- | --- | --- |
| Q1 | 🤔 | Records could hold an account identifier and not the name. The research rejected it on a wrong fact ("start-up does not alter existing tables"). The rewrite also changes `approved_by`, which ADR 0037 says is never changed. | Reconsider before tasks. | **Adopted.** Records hold an identifier. No existing table changes: the existing text columns hold the identifier. Research R1 and R7 are rewritten. The maintainer should confirm this choice. |
| E1 | 🎯 | A deletion left the name in `mutation_receipts.response_body`: stored run and configuration responses hold `actor`, `approved_by` and `registered_by`, and the `already-approved` refusal holds the name in its message. | Rewrite the stored JSON, or stop storing the name. | Resolved by Q1. Stored responses hold identifiers. The `already-approved` message no longer names the account. |
| E8 | 💡 | `resolve` returns `Principal` or nothing, so it cannot express an expired token, and `Principal` has no session identifier. | State that the protocol gains a result type. | Applied in research R4. |
| E7 | 💡 | The code writes `unknown` and `unauthenticated` as actors, and both match the name rule. | Reserve them. | Resolved by Q1: rights compare identifiers, so a name cannot match them. Both are still refused as names, for clarity on display. |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion | Resolution |
| --- | --- | --- | --- | --- |
| E2 | 🎯 | The deletion race covers every request in progress, not only the worker: about 50 writes in `service.py`, and `liveness.py` and `resume_view.py`, carry a name resolved earlier. A late write would keep the old name, and a new account with that name would own the run. | Check the account in each write. | Resolved by Q1. A late write carries the identifier of the deleted account, which displays as the placeholder and gives no right to anyone. |
| E10 | 💡 | Applying the `admin` variables from two processes at once can fail on the unique digest. | An upsert, or the advisory lock of schema initialization. | Applied in research R5. |

### Security & Privacy

| ID | Severity | Finding | Suggestion | Resolution |
| --- | --- | --- | --- | --- |
| X1 | 🎯 | The refusal after repeated failures is keyed by name and stored. Anyone can keep a known name refused, including `admin`, with five requests every 15 minutes. | A growing delay, or ways to clear the refusal. | Applied. The maintainer's rule stays. Added: a refused attempt does not extend the refusal; a restart of `sync-api` clears it for `admin`; an administrator clears it for another account; tokens are not affected. The remaining limit is stated under "Assumptions". |
| E3 | 🎯 | `collect_secret_values` collects every variable whose name contains `PASSWORD`, and a `reason` that contains a collected value is refused. Every `reason` gets a maximum length. |
| E6 | 🎯 | With digests, the service cannot list the tokens, so a token pasted into a `reason` or a package is not caught. | Detect values by their prefix. | Applied in research R4: a free-text value that contains `ifs_pat_` or `ifs_ses_` is refused, and the `admin` token cannot start with either. |
| E5 | 🎯 | The Constitution Check row for principle VI said no value is printed or returned. A token value is displayed once. | Record the deviation, or amend the principle. | Applied: the row is corrected, the deviation is in "Complexity Tracking", and the feature amends the sentence of principle VI (FR-040). |
