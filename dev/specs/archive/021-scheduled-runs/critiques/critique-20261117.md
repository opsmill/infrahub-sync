# Critique Report: Scheduled runs that write without a person present

**Date**: 2026-11-17

**Artifacts reviewed**: `spec.md` (`c7b4cfc5`), `plan.md`, `research.md`, `data-model.md`,
`contracts/`, `quickstart.md` (`82d0cb34`), `.specify/memory/constitution.md`. The engineering
findings were checked against the code of `feature/v3-develop` at `7987596f` by a reviewer that
had not written the plan.

## Later change

After this report, the product owner asked for Prefect to hold the cadence. Research R1, R2, R3,
R10 and R14 were rewritten: each Sync schedule has one Prefect schedule on the existing
deployment, and the worker admits the flow run that Prefect's scheduler creates. The findings
below that name a loop in the Sync API (E1, E2 in part, E11, E12) describe the earlier design. The
other findings still apply. The new design was not reviewed by a second reviewer.

The product owner then answered the four questions at the end of this report: this specification
builds the two capabilities of INFP-655 (P1), a schedule waits while one of its proposed changes
is approved and not merged (P2), constitution principle I is amended for both write targets
(E13), and a run with branch review always writes the remaining records (P3).

## Executive Summary

The specification answers a decision that was left open: how a run that nobody watches passes the
write gates. Its answer, review in Infrahub through a branch and a proposed change, removes a
second approval procedure from Infrahub Sync.

The first version of the plan had six design errors against the code and three contradictions in
the specification. All nine are corrected in the artifacts of this commit:

- A plan made on the default branch cannot be applied to another branch (E4).
- A repeated attempt of one start would have been refused, or would have created a second run
  (E1).
- A receipt that nothing resolves could block a schedule for ever (E2).
- A configuration that declares its own branch would have been written with no review (E3).
- A failed run could leave a branch that no record names (E5).
- The event plan did not fit the store and the event model in four places (E6).
- A run with branch review that stops or is interrupted had no path for a person (P3).
- The schedule showed a late-start duration of one hour while one minute applied (P4).
- A schedule could stop in user story 1 with no way to start it again before user story 3 (P5).

Four questions need the product owner. None of them blocks the tasks.

**Verdict**: PROCEED WITH UPDATES. The updates are applied.

## Engineering Lens Findings

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E4 | Must-address | The plan's manifest records the destination branch, and the apply step refuses another one with no override (`plan/verify.py:462-515`). The worker also uses one branch for the schema read, the plan and the apply. The first design planned on the default branch and wrote to a new one. | **Applied.** The branch is created first, and the run plans, verifies and applies on it. It is deleted when the plan holds no operation. FR-022 now says that no branch remains. |
| E3 | Must-address | `effective_destination_branch` puts a branch that the configuration declares before the run's branch (`configuration/runtime.py:27-30`). A schedule with branch review on such a version would write to the declared branch with no Sync approval. | **Applied.** FR-027 refuses it with `schedule-branch-declared`. |
| E6 | Must-address | Four mismatches with the event code: the store methods take one event and the worker needs up to three; the start time and the left-out count were put in `reason`, which is read from the receipt before the plan exists; the kind order and the primary resource were not listed; the `events` command has no related filter. | **Applied.** Research R9: a typed `details` field, event sequences on the store methods, the schedule added in `run_event`, and `--schedule` listed as new work. |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | Must-address | A receipt replays only when the request body is the same (`service/service.py:1734-1771`). The branch name had a random suffix, so a repeated attempt got `idempotency-conflict`. A take-over changes the actor, so the key no longer matched and a second run was created. | **Applied.** Research R2: the run holds `scheduled_start_at`, a unique index on `(schedule_id, scheduled_start_at)` allows one run, the fingerprint holds the schedule and the start time only, and the branch suffix is derived from them. |
| E2 | Must-address | Nothing resolves a receipt that has no execution. A start that could not be handed to Prefect for more than 60 seconds was recorded as missed and left a run in phase `accepted`, which then counted as "in progress" at every later start. | **Applied.** Research R2 and R7: such a run is retried until it is submitted, with a wait that grows, and is never recorded as missed. An unresolved receipt counts as "in progress" only for an operation that starts a stage, and only up to the admission time limit. |
| E5 | Must-address | The record of a run's branch was written from the result of a successful stage, so a failed, interrupted or cancelled run left a branch that no record names. Opening the proposed change sat inside the scope whose failures make a write ambiguous. | **Applied.** The service writes the record in the state `pending` when it creates the run. The proposed change is opened and earlier ones are replaced after the write is committed, and a failure there does not change the verdict of the write. |
| E11 | Recommendation | Write guard, liveness and cancellation work on a scheduled run with no change. Two API processes are a test case, not a deployment case. | No change. |
