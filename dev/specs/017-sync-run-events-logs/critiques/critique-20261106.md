# Critique Report: Sync run events and logs, read from the Sync API

**Spec**: [spec.md](../spec.md) | **Plan**: [plan.md](../plan.md) | **Date**: 2026-11-06

## Executive Summary

The need comes from an observed failure (the 2026-11-06 plan on the missing branch `demo-test`) and from ADR 0019's
stated direction, and the user confirmed every product decision in the brief. The plan reuses existing seams: the
audit table, the store's one-transaction writes, `RunLoggerBridge`'s prefix, `operator_cause`, and the per-call
Prefect client in `serve.py`.

Three items must be fixed before tasks are generated:

- FR-006 cannot be tested as written: three Sync API error messages name Prefect today, and the brief's test
  ("search responses for `prefect`") would also match field names and the operator's own link;
- the worker's events name the run's initiating actor, which is wrong when another account requested the apply;
- the plan does not say which existing tests change when a known failure stops raising.

Verdict: ⚠️ PROCEED WITH UPDATES. All three were applied to spec.md, plan.md and data-model.md in this phase.

## Engineering Lens Findings

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | data-model.md gives a worker event the run's initiating actor. An apply requested by another account (an administrator) would then show the wrong actor next to `run.applied`. `complete_mutation` stores the `flow_run_id` on the accepted receipt (`store.py:2054-2075`), so the worker can find the account that requested its flow run. | The worker event's actor is the actor of the accepted request whose receipt holds this flow run ID; the run's actor only when no receipt holds it. **Applied** to data-model.md. |
| E2 | 💡 | Events from the API and the worker are ordered by `created_at` from two containers. Clock skew between them can reorder a `run.accepted` and the stage's result. | Note the dependency on synchronized clocks in the deployment page; order by `created_at`, then `event_id`, as the store does. **Applied** to plan.md (documentation item). |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E3 | 🎯 | Returning `Failed` instead of raising changes what callers see. Tests that expect `service_sync_run` to raise for a known failure, and any caller of the flow outside the worker, will see a returned state, or an exception raised by Prefect from that state (research R1). The plan does not list them. | Add a plan section that names the test files to update (`tests/service/test_flow_and_prefect.py`, `tests/service/test_run_log_next_step.py`, `tests/service/test_service_worker.py`) and states that the unknown-class path and the refused claim still raise. **Applied.** A later change made the refused claim return `Failed` as well (plan.md, "Failure exit for known error classes"). |
| E4 | 💡 | A Prefect timeout on `read_logs` must not hold a request open. | Use the client's existing timeout; map a timeout to 503 `log-unavailable` (already in the plan's log reader, step 2). No change. |

### Performance & Scalability

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E6 | 💡 | Each log request reads every line of the run's flow runs (research R9). `--follow` repeats this every 2 seconds. | E7 | 💡 | Two log lines with the same timestamp have no defined order. | Order by timestamp, then Prefect's log ID. **Applied** to data-model.md. |
