# Critique Report: Health of the Sync API and each worker

**Date**: 2026-11-23
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ PROCEED WITH UPDATES

---

## Executive Summary

The spec follows a clear requirement (INFP-663 requirement 3) and a reference design (Infrahub PR
opsmill/infrahub#11473). Its scope is narrow, and the plan reuses existing code: `pool_status`,
the liveness rule, `s3_client_arguments` and the Prefect probes, which Prefect 3.8.6 leaves open
when an auth string is set (`prefect/server/api/server.py:522-535`). This review checked the plan
against the code. Five problems must be fixed before tasks are written:

- In Compose, the product database and the Prefect database run in the same PostgreSQL container.
  Several expected results in the spec, the contract and the quickstart cannot happen with that
  setup, including the worker healthcheck scenario US2-3.
- The plan does not say when the age of a round is measured. If the age counts from the start of
  the round, every caller that waits during an outage runs its own round.
- The "anything else is `unknown_error`" rule needs a broad `except`, which constitution
  principle IV forbids in touched code.
- With psycopg 3.3.6, an unknown host raises the text `failed to resolve host …`, which none of
  the markers in research R-3 matches, so a stopped PostgreSQL container would be reported as
  `unavailable` instead of `name_resolution_failed`.
- Several readers of `/api/status` are missing from the plan, among them `tasks/dev.py`, which
  would report a 503 as "start `dev.api`".

The remaining findings are smaller corrections. None of them questions a product decision that
was already taken.

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | Round sharing. The data model sets `timestamp` to "when the round of checks started", and plan step 2 says that "a caller that waited re-checks the age". If the age is measured from the start of the round, a 3-second round is already too old when it ends. Each caller that waited on the lock then runs its own round, one after the other, and the last caller waits for N × 3 seconds. This breaks FR-004 and SC-006 during an outage, which is when monitoring tools poll. Infrahub records the age when the round ends (`self._latest = (self._clock(), report)` after `gather`). | In plan.md, Design, step 2: "The age of a report is measured from the end of its round (monotonic clock read after `gather`). `timestamp` in the response stays the start time." Add a unit test with a fake clock, 10 callers and a check that lasts longer than 1 second, and assert that it runs exactly one round. |
| E2 | 🎯 | Constitution principle IV: "a broad `except Exception:` is prohibited in touched code". Research R-3 ends with "Anything else → `unknown_error`", and Infrahub's `_run_check` uses `except Exception` for this. The plan's Constitution Check marks IV as "Pass" and does not say how a check catches its errors. | In plan.md, add under Design a list of the exceptions that each check catches: `OSError`, `TimeoutError`, `psycopg.Error`, `botocore.exceptions.BotoCoreError`, `botocore.exceptions.ClientError` and `httpx.HTTPError`. State that any other exception escapes to `contain_unhandled_error` (`app.py:494-510`), which answers with the 503 envelope. As an alternative, record the broad `except` with its reason under Complexity Tracking, following the precedents at `app.py:397` and `app.py:500`. In that case, change the Constitution Check row for IV to "Pass with justification". |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E3 | 🎯 | The psycopg markers of research R-3 do not match psycopg 3.3.6, the locked version. psycopg resolves the host name in Python (`socket.getaddrinfo`, `psycopg/_conninfo_attempts.py:102`) before libpq runs. Tested with the project's virtual environment, an unknown host raises `OperationalError` with the text `failed to resolve host '<host>': [Errno 8] nodename nor servname provided, or not known` and no `__cause__`. That text does not contain the marker `could not translate host name`, so a stopped Compose container would be classified `unavailable`, not `name_resolution_failed`, which contradicts the contract's PostgreSQL example and quickstart scenario 4. A refused port gives `connection failed: … could not receive data from server: Connection refused`, which the `Connection refused` marker does match. A connect timeout raises the typed `psycopg.errors.ConnectionTimeout` (`errors.py:404`). Other points: the connect timeout applies to each address attempt separately (`psycopg/connection.py:102-111`); the `getaddrinfo` call and `SELECT 1` are not bounded by it, so "the thread also ends" (R-4) is not guaranteed. | In research.md R-3: add the marker `failed to resolve host` → `name_resolution_failed`, classify `ConnectionTimeout` by its type before any text, and require one unit test per marker with the exact psycopg 3.3.6 text. In R-2 and R-4: run the database check with `psycopg.AsyncConnection.connect(..., connect_timeout=limit)`, which resolves the name through asyncio and can be cancelled by `asyncio.timeout`, so no thread is left behind, and set `options='-c statement_timeout=<limit ms>'`. For the object store, state that the timeout and retry settings are merged into the `Config` returned by `s3_client_arguments` (`storage.py:251-264`) with `Config.merge`, so that the addressing style is kept. |
| E4 | 💡 | One worker record that does not match the expected shape (for example `heartbeat_interval_seconds` set to `None`, or a status outside `WorkerStatus`) makes `_pool_worker` raise `ValueError`. `pool_status` then returns `detail_available=False` for the whole pool (`orchestration.py:464-467`, `:714-727`). Today this only changes a label. With this feature, it sets `workers.state` to `unknown` and the answer to 503, which raises an alert, possibly because of a 23-hour-old record from another process. | In research.md R-5, state that a record that cannot be parsed is left out of the list and logged once, and does not make the pool `unknown`. Keep `unknown` for a pool that cannot be read. Add a unit test with one malformed record next to one live worker. |

In plan.md, add a unit test for a worker name that contains a host name. |

| X1 | In Compose, the product database and the Prefect database run in the same PostgreSQL container, and the worker heartbeat goes through the Prefect server to that database. When `postgres` stops, `database`, `task_manager_db` and the worker read all fail. The worker's heartbeats then fail too, so the file-based healthcheck marks the worker `unhealthy` after about 50 to 60 seconds (the 30-second threshold, then 3 failed checks 10 seconds apart), and Prefect's backoff can stop the worker process. | US2-3 ("the result depends only on the worker's own heartbeats, not on PostgreSQL") cannot pass as designed. The contract's "503, PostgreSQL stopped" example (`task_manager_db` up, workers `known`) and quickstart scenario 4 tell operators to expect a result they will not see. SC-003 recovery times also depend on the worker's backoff (P3). | Choose one rule and write it into spec.md. (a) The file records that the worker's event loop runs: a separate task in the worker writes it on a fixed timer, independent of the Prefect call, so the healthcheck detects a hung or stopped process only and US2-3 holds. Writing the file after every heartbeat attempt is not enough, because Prefect's backoff spaces the attempts 20, 40 and 80 seconds apart during an outage. Or (b) keep "successful heartbeat" and rewrite US2-3 and FR-011: "the healthcheck depends on the Prefect server and its database, and not on the product database, the object store or the Sync API". In both cases, fix the contract's PostgreSQL example (`task_manager_db` down, workers `unknown`) and the expected results of quickstart scenario 4. |
