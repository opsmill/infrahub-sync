`verify` now runs every check that `apply` runs before its first write, against the destination, and writes nothing. It connects to the destination, so it fails when it cannot reach it. A run with no registered configuration binding cannot be applied by the service, so `verify` checks only its saved files and records `destination_checked: false`. The run records the checks that passed under `results.verification.checks`, and the CLI prints one `check: NAME passed` line for each. When `verify` or `apply` fails on a check that runs before the first write, the service records the name of each failed check under `failed_checks`, and the CLI prints one `failed_check: NAME` line for each name and the recorded next action before the `run-terminal` error. Some failures record no check name, such as a destination that cannot be reached or a destination schema that cannot be read; the CLI then prints no `failed_check:` line. Earlier, `verify` checked only the files the plan run saved, and a refused `apply` recorded no check name. `apply` now refuses every run in phase `cancelled` with `run-cancelled`, including a run whose `verify` stage was cancelled while it ran.
