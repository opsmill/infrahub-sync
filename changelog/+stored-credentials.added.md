An administrator can now store the tokens and passwords of sources and destinations in the Sync API, with `infrahub-sync credentials create`, `set` and `describe`, and delete one with `credentials delete`, which is refused while the latest version of a configuration or a schedule that is not deleted names the credential; every signed-in account can list them and view one with `credentials list` and `credentials show`, and no command or route for accounts returns a value. A configuration package names a stored credential in each adapter block with `credential: <name>`. The Sync API stores each value encrypted with `INFRAHUB_SYNC_ENCRYPTION_KEY`, and each worker gets the values of a run in progress from the Sync API with the token of the new `worker` account, `INFRAHUB_SYNC_WORKER_TOKEN`, at the address in `INFRAHUB_SYNC_API_URL`, so a worker needs no credential variable and no restart when a value changes. The Sync API refuses to start without `INFRAHUB_SYNC_ENCRYPTION_KEY` or `INFRAHUB_SYNC_WORKER_TOKEN` and names the missing variable, and the Compose deployment requires both in `.env`. Changing the key is not supported; if the key is lost, an administrator sets the value of every credential again. The web interface has a "Credentials" page with the same actions, and the details page of a run shows the credentials and revisions that each stage read. Creating a schedule, or changing it to pin another version, is refused with `422 credential-not-found` when that version names a stored credential that does not exist. See the "Manage stored credentials" guide.
