When a `sync`, `apply` or `runs resume` cannot start its write because another write of the same configuration holds the configuration's write lock when the wait ends, the run's failure record now has the failure type `write_guard_contended`. It names, in `active_run_id`, the run whose database session held the lock when the wait ended, and only when the run records hold that run for the same configuration; otherwise the cause says that the run holding the lock is not known. When the named run's write had already ended before the wait began, the next action says to stop or restart that run's worker. The CLI prints `active run: <run_id>`, and the web interface's failure notice links to that run with **Open run**. A run whose ID is longer than 42 characters, or a run on a worker that does not have this change yet (during an upgrade), is never named.
