---
title: Move from V2 to V3
---

V3 turns Infrahub Sync from a local command-line synchronizer into a deployed service. The
command-line client still carries the familiar verbs, but the service owns registration, run
admission, saved plans, and every write to a destination.

There is no in-place state migration between V2 and V3. To switch, you start a fresh V3
deployment, register your configuration again as a V3 package, and review a new plan before
anything is written. [Before switching](#before-switching) lists these steps. The table
below compares the two lines, and [Where each action lives now](#where-each-action-lives-now)
links the current procedure for each task.

The V2 documentation stays published as its own version. Reach it from the version menu in
the top navigation; every page on this line describes V3 only.

## What changed

| Area | V2 | V3 | Sources |
| --- | --- | --- | --- |
| Installation and runtime | The package was installed into a virtual environment, and that one process read the source, computed the difference, and wrote to the destination. | A service runs the Sync API, a worker, Prefect, PostgreSQL, and object storage, either from the release image through the root `docker-compose.yml` or built from source. The command-line client talks to that API and executes no synchronization itself. | [V2](/v2/installation) · [V3](./installation.mdx#two-ways-to-run-v3) |
| Configuration and credentials | A project directory holding a `config.yml`, whose token settings named environment variables the local process read. | One package file with a `format_version`, a `configuration` object, and a `credentials` block. Credential-bearing settings hold `$credential` references, and the worker resolves them from the deployment's `.env` where it runs. | [V2](/v2/creating-a-sync-project) · [V3](./reference/config.mdx) |
| Adapter code | A generation step emitted Python adapter and model code beside the configuration before a run. | No generation step. The worker loads installed adapter classes for the registered package version. | [V2](/v2/running-a-sync#generating-sync-adapters-and-models) · [V3](./reference/config.mdx) |
| Registration and validation | There was no registry. Each command re-read the files on disk, addressed by project name and directory. | Registration returns an immutable configuration identity, version, and package checksum, and the registry is append-only. A registered version can be re-validated later against the adapter declarations installed at that moment, and mutations accept an idempotency key. | [V2](/v2/reference/cli) · [V3](./reference/sync-http-api.mdx#routes) |
| Planning and apply | `diff` wrote a Parquet plan into a local cache directory and logged a run identifier. `apply` replayed that cached plan from disk and refused it when the destination schema shape had drifted. | `plan` admits a service plan run. The saved plan is reviewed through the service, which issues its checksum, and `apply` is bound to that checksum. `sync` submits a confirmed run. A plan records deletes, and apply never executes them. | [V2](/v2/running-a-sync#reviewing-and-applying-a-cached-plan) · [V3](./reference/cache-layout.mdx#saved-plan-review) |
| Adapters | The loader accepted built-in names, dotted paths, filesystem paths, and entry points. | A registered package resolves its source adapter against capability declarations, and only the adapters bundled with Infrahub Sync carry one. Filesystem targets are refused in a registered package. Loading a local filesystem plugin remains development-only behavior. | [V2](/v2/adapters/local-adapters#adapter-resolution-paths) · [V3](./development/guides/adding-an-adapter.md) |
| Operations | There was no service to operate. A run was whatever the operator started locally, and there were no durable run records. | The deployment has documented status, log, stop, restart, reset, and replacement procedures, a reconciliation procedure for a write whose outcome is unknown, and durable run records the client reads back. | [V2](/v2/reference/cache-layout) · [V3](./operations/compose-troubleshooting.mdx) |
| Contributor workflow | Install the development dependencies, format, lint, type-check, and run the tests. | The same loop, plus the extras the service and orchestration imports need, a local Preview stack for the API and worker, and named test tiers that state what each one requires. | [V2](/v2/contributing#development-workflow) · [V3](./development/knowledge/quality-gates.md) |

Two boundaries are worth reading before you plan work around them. A package that names an
adapter Infrahub Sync does not bundle is refused at registration, so a V2 setup that relied on
a filesystem or third-party adapter has no complete registered route today. And a recorded
delete stays recorded: reviewing a plan shows what the destination holds that the source does
not, but applying it never removes those objects.

## Before switching

- **Start from fresh deployment state.** Use a new directory and let the deployment generate a
  new identity and empty state. Do not copy an older deployment's instance files, operator
  environment, or secrets, and do not point the new deployment at the old data.
- **Register the configuration again.** A V2 `config.yml` is not a registered V3 version.
  Convert it into a package with `configs convert`, supply the credential values on the
  deployment, and register the package. See
  [Move a V2 configuration to V3](#move-a-v2-configuration-to-v3).
- **Delete any `store` block.** V3 keeps sync data in memory during a run and refuses
  configurations that declare a sync store, including Redis. If you already registered
  the package, register a new version without the block and run that version. Editing
  the local file does not change an existing registered version.
- **Review a new plan before you apply anything.** Treat the first V3 plan as the record of what
  the run would change, whatever a previous V2 run did.

No in-place state migration, rollback, backup, or restore procedure has been verified between
the two lines, and starting a fresh deployment neither migrates nor cleans up anything an earlier
version wrote.

That is not the same as leaving your destination alone. The plan reads the destination as it finds
it, so it can propose creates and updates against objects a V2 run wrote: an update carries the
destination identity recorded when the plan was built, writes the mapped fields its payload
carries, and replaces each relationship set it names rather than merging into it. Apply executes
every reviewed operation except a delete — recorded deletes are never executed. Read the plan
before you apply it. See
[Planned writes and apply](./development/knowledge/planned-write-and-apply.md) for what one operation
does at the destination.

## Move a V2 configuration to V3

`infrahub-sync configs convert` reads a v1 or v2 `config.yml` and writes a V3 configuration
package next to it. You run it on your own machine: it needs no Sync API URL or token, and it
does not read the adapter and model files that V2 generated. It never reads or prints a
credential value. It opens no network connection unless you pass `--live-schema`.

### Prefixes and IP addresses: `--live-schema`

V2 configurations did not map the IP namespace, so V2 wrote every prefix and IP address into
Infrahub's `default` namespace. Infrahub identifies a prefix or an address by its value and its
namespace, and V3 does not plan a kind unless the configuration maps every part of that identity.
Without a change, the first V3 plan of such a configuration fails with
`UnwritableConvergenceIdentityError`.

With `--live-schema`, the command reads the schema of the destination Infrahub, without a token,
and finds each mapped kind whose uniqueness constraint names an IP namespace that `config.yml`
does not map. For each one, it:

- sets the namespace to `default`, as a reference to the namespace kind
- makes the identifiers of that kind the fields of the uniqueness constraint, for example
  `prefix` and `ip_namespace`
- adds a mapping for the namespace kind with no source endpoint, which loads nothing from the
  source

The report lists each change under `Notes`. When Infrahub refuses an anonymous schema read, the
report says so and the command changes nothing. Without `--live-schema`, edit the package by
hand in the same way.

### Convert the file and read the report

1. Run the command on the `config.yml` you used with V2:

   ```bash
   infrahub-sync configs convert config.yml
   ```

   The package is written to `package.yml` next to `config.yml`. To write it somewhere else,
   pass `--output <path>`. The command does not replace an existing file unless you pass
   `--force`.

2. Read the report. For the V2 NetBox example, with no V2 variable set in the shell, the report
   is:

   ```text
   Converting config.yml (v1 or v2 configuration "from-netbox")

   Credentials (set these in the Sync deployment's .env file):
     source.settings.token        NETBOX_TOKEN (v2) -> INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN
     destination.settings.token   INFRAHUB_API_TOKEN (v2) -> INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN

   Settings taken from the environment or the file:
     source.settings.url          https://demo.netbox.dev   from config.yml
     destination.settings.url     http://localhost:8000     from config.yml
     warning: destination.settings.url is a loopback address; the Sync worker runs in a container and may not reach it
     no v2 variable (NETBOX_ADDRESS, NETBOX_URL, INFRAHUB_ADDRESS, INFRAHUB_URL) is set here; values come from config.yml or the flags

   Notes:
     V3 has no generation step; the generated adapter and model files are not needed
   ```

   The report has these sections, in this order. A section with nothing to report is left out.

   - `Credentials`: each credential setting, where V2 took its value from, and the
     `INFRAHUB_SYNC_CREDENTIAL_` variable the Sync worker reads in V3. A warning follows when
     `config.yml` still holds a literal value, and when the `docker-compose.yml` shipped with
     this version does not pass the variable to the Sync worker. The shipped file passes only
     `INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN`, `INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN` and
     `INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN`.
   - `Settings taken from the environment or the file`: each address, and each other setting
     that V2 read from an environment variable, with the value written and where it came from.
     A warning follows for a `localhost` or `127.0.0.1` address, and for an address taken from a
     generic variable name such as `URL`. The last line names the V2 variables that are set in
     your shell, names only.
   - `Dropped`: each key left out of the package, and why.
   - `Notes`: other information, for example that V3 uses its bundled adapter when `adapter:`
     names the bundled module, or that a credential setting is not referenced because the V2
     authentication method did not use it.
   - `Warnings from the package checks`: the warnings that registration would report for the
     package.

3. Confirm. The command asks `Write package.yml? [y/N]`. Answer `y` to write the file. Any
   other answer writes nothing and exits with status 0. Pass `--yes` to write without the
   question. Without a terminal and without `--yes`, the command writes nothing and exits with
   status 1.

4. Follow the next steps that the command prints after it writes the file:

   ```text
   Next steps:
     1. Set INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN and INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN in .env
     2. Restart the deployment so the Sync worker receives them
     3. infrahub-sync configs register package.yml
   ```

   Then review the first plan before you apply it. When the Sync API requires approval, approve
   the plan with `infrahub-sync approve` before `apply`; `sync` is refused in that mode. See
   [Run a sync](./running-a-sync.mdx).

Before it writes, the command runs every registration check that needs no connection. A
package it writes registers without edits, as long as the addresses are ones the Sync worker
can reach.

### Addresses and other settings that V2 read from the environment

V2 read some settings from environment variables, for example `NETBOX_ADDRESS` or
`INFRAHUB_ADDRESS`, and for most adapters a variable took precedence over the file. V3 reads
only the registered package. The command writes the value that V2 would have used where you run
it, and the report names where that value came from:

- `--source-url` or `--destination-url`, when you pass it. A flag takes precedence over the
  file and the variables.
- Otherwise the V2 variable, when it is set and V2 read it before the file. For IP Fabric, V2
  read the file first, and the command does the same.
- Otherwise the value in `config.yml`.

The command reads only the variable names that V2 itself read for each adapter. It does not read
a variable that `config.yml` names in a `${NAME}` placeholder or in a `*_env_vars` setting, and
it says so in the report. V2 did not expand `${NAME}` placeholders. When a placeholder names one
of the variables that V2 read for that setting, the command treats the setting as empty in the
file and reads the variables in V2's order. For example, with `url: ${NETBOX_URL}` and both
`NETBOX_ADDRESS` and `NETBOX_URL` set, the command writes the value of `NETBOX_ADDRESS`, as V2
did. When a `*_env_vars` setting replaces V2's variable names for a
setting, V2 did not read its default names either, so the command takes that setting from
`config.yml` or a flag only.

Run the command in the shell where V2 ran, or pass the addresses as flags, so that the package
holds the addresses V2 used. Then check that the Sync worker can reach them.

- The Observium and Slurpit examples hold placeholder addresses that are not absolute URLs.
  Pass `--source-url`.
- When `config.yml` holds `${CISCO_APIC_VERIFY}`, set that variable where you run the command;
  no flag sets `verify`. Set the APIC address with `CISCO_APIC_URL` or `--source-url`.

### Credentials that the package references

V3 does not run a sync when a credential reference points to a variable that is missing or
empty. So the package references only the credential settings that your V2 configuration used:

- For `genericrestapi` and `peeringmanager`, the `auth_method` setting decides. Its V2 default is
  `token`. The methods `token`, `x-auth-token`, `api-key` and `key` use `token`, `basic` uses
  `username` and `password`, and `none` uses no credential.
- For `prometheus`, the `auth_method` setting decides. Its V2 default is `none`, which uses no
  credential. `bearer` uses `token`, and `basic` uses `username` and `password`.
- For `slurpitsync`, V2 used only `api_key`.
- Every other adapter uses all of its credential settings: `token` for `infrahub`, `netbox` and
  `nautobot`, `username` and `password` for `aci`, and `auth` for `ipfabricsync`.

A credential setting that holds a value or a `${NAME}` placeholder in `config.yml` is also
referenced, even when the authentication method does not use it. Each credential setting that
the package does not reference is listed under `Notes`, for example
`not referenced: source.settings.token (auth_method basic does not use it)`.

When `auth_method` holds a value that V2 did not accept, the command refuses the configuration
and names the setting.

### How the command handles each v2 key

| v2 key | What the command does |
| --- | --- |
| `name` | Copies it. |
| `source.name`, `destination.name` | Copies a bundled adapter name. Refuses any other name. The destination must be `infrahub`. |
| `source.adapter`, `destination.adapter` | Drops it with a note when it names the bundled adapter's own module. Refuses any other value. |
| Credential settings, such as `token` or `password` | Replaces the value with a `$credential` reference and declares the reference in the `credentials` block, for each setting that the V2 authentication method used or that holds a value. Leaves out the others with a note. |
| `auth_method` | Copies a value that V2 accepted. Refuses any other value. |
| `url` and other settings that V2 read from the environment first | Writes the value from the flag, the variable or the file, and reports its origin. |
| `genericrestapi` and `peeringmanager` settings that end in `_env_vars` | Drops them and lists them under `Dropped`. The command does not read the variables they name. |
| An address that holds a user name or password | Refuses it, without printing the address. |
| `destination.settings.source`, `destination.settings.owner` | Writes a V2 group name as `{kind: CoreAccountGroup, name: <name>}`, the kind V2 looked up, and adds a note. V2 fell back to the account named after the source adapter when no such group existed; V3 stops the run before any write. A `{kind, name}` value is copied. |
| Other settings that the bundled adapter accepts | Copies them. |
| Other settings | Refuses them. |
| Other keys of `source` or `destination` | Drops them, because V2 did not read them. |
| `store` | Drops it with a warning: V3 keeps sync data in memory during a run. |
| `adapters_path` | Drops it with a warning: V3 runs only its bundled adapters. |
| `incremental` | Copies it for `infrahub`, `nautobot` and `netbox` sources. Drops it with a warning for other sources. |
| `order`, `diffsync_flags`, `schema_mapping` | Copies them. |
| Other top-level keys | Drops them, because V2 did not read them. |
| `format_version` | Refuses the file, because it is already a V3 package. |

### Configurations that the command refuses

When the command refuses a configuration, it writes nothing, prints every reason to standard
error and exits with status 1. A refusal never prints the value of a credential setting. In
this release the command refuses:

- An adapter that is not bundled with Infrahub Sync. The reason lists the bundled adapters.
- A custom adapter: an `adapter:` value that is a file path, a dotted path or an entry point.
  Custom adapters are planned for 3.0 (INFP-654).
- A destination other than Infrahub, including Peering Manager. This release writes only to
  Infrahub.
- A setting that the bundled adapter does not accept.
- An `auth_method` value that V2 did not accept.
- A `${NAME}` placeholder in a setting that V2 did not read from the environment. V2 used the
  placeholder text as the value, so write the value in `config.yml`.
- An address that the command cannot find in the file, a V2 variable or a flag.
- An address that holds a user name or password, in the file, in a V2 variable or in a flag.
  The reason names the setting and where the address came from, and does not print the address.
- A `${NAME}` placeholder in a setting that V2 read from the environment, such as
  `verify: ${CISCO_APIC_VERIFY}`, when the V2 variable for that setting is not set where you run
  the command.
- A package that would fail a registration check.

For the V2 example that writes to Peering Manager, the refusal is:

```text
error: config.yml cannot be converted (1 reason)
  destination.name        peeringmanager                      V3 does not write to peeringmanager yet; this release writes only to Infrahub
```

### Check of the first V3 plan against data that V2 wrote

A release check compares the first V3 plan with the data V2 wrote. On a local NetBox loaded with
the pinned `demo` dataset, V2 `2.0.1` synchronizes the NetBox example of the `2.0.2` tag into an
empty Infrahub. The same `config.yml` is then converted with `configs convert --live-schema --yes`,
registered, and planned on the same Infrahub branch, with no NetBox change in between. The check
passes only when that plan holds no creates and no updates. The records it leaves out, its
problems and its deletes must be on reviewed lists, or follow from a listed record: they are
records that Infrahub identifies by fewer fields than NetBox, which V2 merged into one node.

On the NetBox example and the `demo` dataset, the first V3 plan holds no creates and no
updates. It leaves out the racks, VLANs and devices that V2 merged, and the records that depend
on them, and it records deletes of the nodes V2 wrote for those records. Apply never executes a
delete. Read the first V3 plan of your own configuration before you apply it: your data can
differ from the example.
