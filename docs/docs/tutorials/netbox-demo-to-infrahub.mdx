---
title: Sync the public NetBox demo to a local Infrahub
description: Start a local Infrahub and the Sync service, load a data model, and synchronize infrastructure data from the public NetBox demo.
---

By the end of this tutorial you will have run a local Infrahub and the Sync service, loaded a
schema that covers locations, devices, interfaces, IPAM, and organizations, and imported data
from the [public NetBox demo](https://demo.netbox.dev) into an Infrahub branch that you can
review as a proposed change. Sync runs in containers built from a checkout of Infrahub Sync.
You start with no Infrahub instance and no schema.

:::tip Other routes

- For an existing NetBox and Infrahub with a Compose Sync deployment, follow
  [Preview NetBox data in an existing Infrahub](netbox-to-existing-infrahub).
  That tutorial ends with a saved preview; this local demo continues through an import.
- To import the same data from a local NetBox with a fixed dataset, which gives the same
  result on every run, follow [Run a first sync](../development-stack.mdx#run-a-first-sync).

:::

**Time**: ~30 minutes

**Prerequisites**:

- [Docker](https://docs.docker.com/get-docker/) installed and running (Docker Desktop or OrbStack)
- [Git](https://git-scm.com/downloads)
- [uv](https://docs.astral.sh/uv/getting-started/installation/) (Python package manager)
- [Python](https://www.python.org/downloads/) 3.11 to 3.13

:::warning Public demo data
Anyone can edit the public NetBox demo, so object counts, names, and sample data differ from
the examples in this tutorial. Other users also add records that stop a run, such as two
devices with the same name or two identical addresses with no VRF.
[When a run fails](#when-a-run-fails) shows how to find the record that caused it.
:::

## Start Infrahub

Infrahub publishes a Docker Compose file for a local instance. Put it in a directory of its
own, outside the Infrahub Sync checkout that you clone in the next step, because that
checkout already holds a `docker-compose.yml` of its own.

1. Download the Compose file and start Infrahub:

```bash
mkdir -p ~/infrahub-local && cd ~/infrahub-local
curl https://infrahub.opsmill.io > docker-compose.yml
docker compose -p infrahub up -d --wait
```

The first start takes a few minutes while Docker downloads the container images.

2. Open your browser and go to [http://localhost:8000](http://localhost:8000).

3. Log in from the bottom-left corner using the default credentials:

    - Username: `admin`
    - Password: `infrahub`

:::success Verification
You should see the Infrahub web interface with a navigation menu on the left side.
:::

## Get Infrahub Sync

The checkout provides the `infrahub-sync` command, `infrahubctl`, the Sync service image, and
the example package this tutorial uses.

1. Clone the V3 branch beside the Infrahub directory and install the development environment:

```bash
cd ~
git clone --branch feature/v3-develop https://github.com/opsmill/infrahub-sync.git
cd infrahub-sync
uv sync --extra dev --extra prefect --extra service
```

The repository's default branch is `main`, which is V2. Clone the V3 line explicitly, as
shown above, or a pinned V3 tag once one exists. Run every remaining command from the
`infrahub-sync` directory.

2. Verify the `infrahub-sync` command is available:

```bash
uv run infrahub-sync --help
```

## Load a schema into Infrahub

Infrahub stores data according to its schema. Before Sync can import anything, Infrahub needs
the kinds of objects that the sync creates.

The schema for this tutorial covers DCIM and IPAM features similar to NetBox's. It is
not a copy of NetBox's data model. A real migration can keep the parts of NetBox that
matter to you and adapt the model to your own workflows.

1. Export the local Infrahub address and API token for `infrahubctl`:

```bash
export INFRAHUB_ADDRESS="http://localhost:8000"
export INFRAHUB_API_TOKEN="06438eb2-8019-4776-878c-0941b1f1d1ec"
```

This is the default admin token that Infrahub's Compose file creates. Do not reuse it for an
internet-facing or shared Infrahub instance.

2. Download the schema. It is published on the
[Infrahub Marketplace](https://marketplace.infrahub.app/collections/infrahub/traditional-infrastructure-sot)
as the `infrahub/traditional-infrastructure-sot` collection:

```bash
uv run infrahubctl marketplace get infrahub/traditional-infrastructure-sot \
  --collection --output-dir .netbox/schemas
```

The command writes the collection's 16 schema files into `.netbox/schemas/`. Git ignores the
`.netbox/` directory.

The command can fail with `Marketplace request failed: ReadTimeout`. If it does, skip it and
load the copy of the same 16 files that the nightly tests use, in the next step.

3. Load the schema into Infrahub:

```bash
uv run infrahubctl schema load .netbox/schemas --wait 120
```

If you skipped the download, load the copy from the checkout instead:

```bash
uv run infrahubctl schema load tests/data/nightly_schema/traditional-infrastructure-sot --wait 120
```

Refresh [the local Infrahub web interface](http://localhost:8000). You should see additional
schema objects in the left navigation. You can also open the schema view in the UI to explore
the kinds and relationships that were loaded.

## Create a NetBox API token

Create a token in the public NetBox demo instance so Infrahub Sync can read data from NetBox.

1. Open the [public NetBox demo](https://demo.netbox.dev).
2. Log in with username `admin` and password `admin`.
3. Open your user profile.
4. Create an API token.
5. Copy the complete generated token value.

Export the token locally:

```bash
export INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN="nbt_..."
```

Export the complete `nbt_...` token value. Do not include an authorization prefix such as `Bearer`, and do not copy only the short **Key** field.

## Start the Sync service

The Sync service is a Sync API, a worker that connects to NetBox and Infrahub, a Prefect
server, PostgreSQL, and object storage. The development stack builds the service image from
your checkout and starts all of them in containers.

1. Give the worker the Infrahub token. The worker reads both credentials from its environment
   when its container starts:

```bash
export INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN="${INFRAHUB_API_TOKEN}"
```

2. Build the image and start the stack:

```bash
uv run invoke build
uv run invoke start
```

`start` waits until every service is healthy, then prints the Sync API address, its bearer
token, and the Prefect UI address.

3. Point the CLI at the Sync API and check the service:

```bash
export INFRAHUB_SYNC_API_URL="http://127.0.0.1:8030"
export INFRAHUB_SYNC_API_TOKEN="infrahub-sync-dev-token"
curl -sf -H "Authorization: Bearer ${INFRAHUB_SYNC_API_TOKEN}" "${INFRAHUB_SYNC_API_URL}/status"
```

The response reports `"service": "ready"` when the worker is running. The API token
authenticates the CLI to the Sync API. It is separate from
`INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN`, which the worker uses to access Infrahub.

If you change either credential later, export the new value and run `uv run invoke start`
again. It recreates the worker with the new environment.

For the addresses, the image rebuild after a code change, and the other stack commands, see
[Local development stack](../development-stack.mdx#run-from-source).

## Create the sync project

A sync project is a directory containing a `package.yml` file. Its `configuration` key names the source and destination adapters, maps source fields to destination fields, and includes references that let Infrahub Sync compute write order.

1. Copy the example NetBox to Infrahub package, and set its Infrahub address to one the
   worker can reach:

```bash
mkdir -p .netbox
sed 's#url: "http://localhost:8000"#url: "http://host.docker.internal:8000"#' \
  examples/netbox_to_infrahub/package.yml > .netbox/from-netbox.yml
grep -n 'url:' .netbox/from-netbox.yml
```

The `grep` prints the two addresses: `https://demo.netbox.dev` for the source and
`http://host.docker.internal:8000` for the destination.

The worker runs in a container, and inside a container `localhost` is the container itself,
not your machine. Docker Desktop and OrbStack resolve `host.docker.internal` to your machine,
where Infrahub publishes port 8000. On Linux, the worker's Compose service maps
`host.docker.internal` to the host's internal IP address (Docker's `host-gateway` value);
this route has not been tested on Linux yet.

The worker reads `source.settings.url` and `destination.settings.url` from the registered
package itself, not from the environment. `INFRAHUB_ADDRESS` is used only by `infrahubctl`.
Only the two credentials come from the worker's environment, resolved through the
`credentials` block at the bottom of the file.

The copied configuration is named `from-netbox`. Open `.netbox/from-netbox.yml` in an editor
and scan the top-level keys under `configuration`:

- `name` identifies the sync project.
- `source` configures the NetBox adapter.
- `destination` configures the Infrahub adapter.
- `schema_mapping` defines how NetBox API resources become Infrahub objects.

This tutorial registers the package, uses `diff` to create a service plan, reviews that
plan, and then applies it by its checksum, so the writes are exactly what you reviewed. See
[Run a sync](../running-a-sync.mdx) for the one-step `sync` alternative, which calculates
and writes a new plan in the same run instead of applying a plan you already reviewed.

For a fuller explanation of this file, see [Create a sync project](../creating-a-sync-project.mdx) and the [schema mapping reference](../reference/schema-mapping.mdx).

## Register the configuration package

Register the package with the Sync API.

```bash
uv run infrahub-sync configs register .netbox/from-netbox.yml \
  --reason "register NetBox demo import"
```

Record the returned `config_id` and `registry_version`. If you edit the package later, use
`configs version <config-id> .netbox/from-netbox.yml` to create another immutable registry
version.

For more about the command flow, see [Run a sync](../running-a-sync.mdx).

## Create a branch

Infrahub tracks changes through branches, so you can review a batch of imported data as a proposed change before it lands on `main`. Create a branch to hold this import:

```bash
uv run infrahubctl branch create netbox-import
```

The rest of this tutorial runs `diff` and `apply` against this branch with
`--branch netbox-import`, so you can inspect the destination changes before merging the
Infrahub branch. For more about branches and proposed changes, see
[Infrahub version control](https://docs.infrahub.app/topics/version-control/).

## Preview the changes

Run a dry-run diff against the `netbox-import` branch before writing any data to Infrahub.

```bash
uv run infrahub-sync diff \
  --config-id <config-id> \
  --version <version> \
  --branch netbox-import \
  --reason "review NetBox demo import"
```

The service worker loads NetBox and Infrahub, compares both sides, and publishes a saved
plan. The CLI waits by default and prints its summary, including the plan's checksum.
Review it again with `infrahub-sync runs plan <run-id> --detail`.

Review the output before continuing. On a first run against an empty branch, most planned changes should be creates. Exact counts depend on the current public NetBox demo data.

If the CLI prints `phase: plan-failed`, see [When a run fails](#when-a-run-fails).

## Apply the reviewed plan

Apply the reviewed plan with its checksum, so the writes are exactly what you reviewed:

```bash
uv run infrahub-sync apply <run-id> \
  --expected-checksum <checksum> \
  --branch netbox-import \
  --reason "import NetBox demo data"
```

The apply writes the imported objects and relationships into the `netbox-import` branch —
`main` is untouched until you merge the resulting proposed change. Because this configuration
omits `order:`, Infrahub Sync derives the write order from the mapping references.

`infrahub-sync sync --config-id <config-id> --version <version> --branch netbox-import
--reason "..."` is the one-step alternative: it calculates and writes a new plan in the
same run, with no stop for review. Choose it once you trust the mapping and no longer need
to review each plan before it writes.

Run the same `diff` again to confirm the branch matches NetBox. After a successful import,
the plan lists no creates, apart from records that other users added to the demo in the
meantime. It records one delete of the built-in `default` IP namespace, and `apply` never
runs deletes.

## When a run fails

The CLI prints the run's final phase and outcome, but not the error that ended it. The error
is recorded on the run's Prefect flow run.

1. Print the run record, which includes the flow run ID:

```bash
uv run infrahub-sync runs show <run-id>
```

2. Open the flow run in the Prefect UI, at `http://127.0.0.1:4230/runs/flow-run/<flow-run-id>`.
   Its name says what it was doing, for example `Plan sync of from-netbox`. The state
   message of a failed flow run contains the error. **Runs** in the Prefect UI lists every
   flow run.

The same error is in the worker's log:

```bash
docker compose -f development/docker-compose.dev.yml logs sync-worker
```

[Troubleshooting](#troubleshooting) lists the errors the public demo data produces and what
each one means.

### When an apply stops partway

An apply can stop after it has written earlier operations. Nothing is rolled back: those
writes stay on the branch. The run ends with `phase: apply-failed` when the failed operation
is known not to have written, and with `phase: apply-interrupted` and `outcome: ambiguous`
when the service cannot tell, in which case the failed operation may have written part of its
change.

To finish the import, remove the cause, then run `diff` again on the same branch and apply
the new plan. The new plan compares NetBox with what the branch now holds, so it contains only
what is still missing or different.

## Verify the imported data

The imported data lives on the `netbox-import` branch, not on `main`. Open [the local Infrahub web interface](http://localhost:8000):

1. Use the branch selector in the top-left corner to switch from `main` to `netbox-import`.
2. Browse the left navigation for imported objects from the NetBox demo. Depending on the current demo data and the example mapping, you may see objects such as:

   - tags and organizations (manufacturers, providers, RIRs)
   - sites and racks
   - devices and interfaces
   - IP namespaces, VRFs, VLANs, and VLAN groups
   - prefixes, IP addresses, and aggregates
   - circuits

   NetBox has no IP namespace of its own, so the example creates one Infrahub IP namespace per
   NetBox VRF name, and puts prefixes and addresses with no VRF in Infrahub's built-in
   `default` namespace. Infrahub identifies a prefix or an address by namespace plus value, so
   the same address in two VRFs stays two objects. The
   [schema mapping reference](../reference/schema-mapping.mdx#key-the-namespace-on-the-vrf-id-instead-of-its-name)
   explains the recipe and what to do when two VRFs share a name.

   :::info This is a minimal mapping
   Some records and relationships may be missing — that doesn't mean the sync failed.

   Three exclusions keep this mapping working against the current demo data. VLAN names in
   NetBox are only unique within a VLAN group, but Infrahub's `IpamVLAN` identifies a VLAN by
   name alone. The mapping puts the VLAN group's name and its length before the VLAN name
   (for example, `Data` in group `Site A` becomes `6:Site A:Data`). The length keeps pairs
   with hyphens or colons in their names distinct. `DcimDevice` also identifies
   a device by name alone. The demo names its patch panels with a `PP:` prefix, so the
   mapping skips devices and their interfaces when the device name contains `PP:`. If your
   NetBox data uses other patch-panel names, adapt both device and interface filters.

   Racks can share a name across sites in NetBox. The demo has a `Comms closet` rack at
   several sites. The mapping prefixes each Infrahub rack name with the length of the site
   name and the site name (for example, `6:Site A:Comms closet`). The length keeps pairs
   with separators in their names distinct. Device references to racks use the corresponding
   NetBox rack ID and resolve to the renamed rack.
   :::

3. Once you're happy with the data, open a proposed change in the Infrahub UI: select
   **Proposed changes** in the left navigation, click **+ Create a proposed change**, set
   `netbox-import` as the source branch and `main` as the destination, add a name and
   description, and click **Create**. See [Infrahub version control](https://docs.infrahub.app/topics/version-control/)
   for how proposed changes and branch merges work.

If you switch back to `main`, none of this data is there yet — that's expected, since it's still isolated in the branch.

## What happened

You used Infrahub Sync to move data from NetBox into Infrahub in a controlled sequence:

1. Infrahub provided the destination graph and schema.
2. NetBox provided the source data.
3. A branch isolated the import from `main` so it could be reviewed first.
4. `package.yml` described the adapters, field mappings, references, filters, and Transformations.
5. The Sync API registered the configuration and issued the run identity.
6. `diff` asked the worker to compare the source and destination without writing changes.
7. `apply` wrote the exact reviewed plan, bound to its checksum, to the branch.

The same pattern applies to larger migrations: start with a clear schema, map a small set of objects, condition source data where needed, review the diff inside a branch, and then apply the reviewed plan before opening a proposed change toward `main`.

## Stop the local services

Stopping and deleting are separate steps, so you can keep the imported data for later.

To remove the Sync service and its data (registered packages, runs, and plans), from the
`infrahub-sync` directory:

```bash
uv run invoke destroy
```

The image built from your checkout is kept, so the next `uv run invoke start` does not
rebuild it.

To stop Infrahub and keep its data, from the Infrahub directory:

```bash
cd ~/infrahub-local
docker compose -p infrahub down
```

To stop Infrahub and delete its data, including the `netbox-import` branch, add `--volumes`:

```bash
docker compose -p infrahub down --volumes
```

## Troubleshooting

### `infrahub-sync` fails with `Both url and token must be specified`

```text
ERROR | infrahub_sync.cli | Failed to initialize the Sync Instance: Error initializing InfrahubAdapter: Both url and token must be specified!
```

The service worker cannot resolve a credential reference declared by the package. The
package contains credential references and declarations, but secret
credential values belong only in the worker environment. The package names
`INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN` and `INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN`, and the worker reads
their values when its container starts. Export both, then run `uv run invoke start`, which
recreates the worker with the new values:

```bash
export INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN="<your-netbox-token>"
export INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN="06438eb2-8019-4776-878c-0941b1f1d1ec"
uv run invoke start
```

This error names whichever adapter (NetBox or Infrahub) is missing its variables — the same message is raised for either one.

### A plan run reports destination models missing from the schema

```text
ERROR | One or more models are not present in the schema - ['LocationSite', ...]
```

The destination does not have the schema collection this configuration maps to. Download
and load every file listed in [Load a schema into Infrahub](#load-a-schema-into-infrahub),
then submit a new `diff` run. Use a fresh Infrahub instance or branch if an existing
`InfraDevice` or another overlapping kind prevents that collection from loading.

The similarly named `models/examples/netbox/netbox.yml` file in the Infrahub source
repository is not a replacement: it uses a different set of destination kinds.

### `infrahub-sync` fails with `Object ... already present`

Two source records resolved to one identifier while NetBox was being read. The run stops
there — before a plan exists and before anything is written to Infrahub — so the state at the
destination is whatever the last successful run left. The kind in the message says which of
two different problems you have.

The public NetBox demo is shared. Other visitors can create duplicate records, such as
two identical prefixes in one VRF. If the error names `IpamPrefix` and shows the same
prefix and namespace, inspect those prefixes in NetBox, and remove or rename the duplicate
in the demo if you can identify it.

#### Two IP addresses or prefixes in one namespace

```text
ValueError: An error occurred while loading Netbox: ('Object 172.16.0.2/24__default already present', IpamIPAddress "172.16.0.2/24__default")
```

The part after `__` is the IP namespace the object landed in, so two NetBox IP addresses share both an address and a namespace. That happens when they sit in the same VRF, when neither has a VRF and both went to `default`, or when one has no VRF and the other sits in a VRF actually named `default`.

That does not mean one of them is wrong. NetBox can hold the same address more than once on purpose — a shared VRRP or HSRP address, for example. It can also be an accidental duplicate. Open both rows in NetBox (**IPAM > IP Addresses**, search the address from the message) and compare their VRF, tenant, role, assigned object, and description before you change anything.

What you find points to one of two fixes:

- The source record is wrong. Correct or remove the entry that should not be there in NetBox.
- Both records are correct, and the mapping is collapsing a distinction Infrahub needs to keep. That needs the namespace mapping or the destination schema to change so the two addresses resolve somewhere different — editing `identifiers` alone will not help, since Infrahub identifies the address by namespace plus address either way. Two genuinely identical addresses inside one namespace refuse under any namespace recipe.

#### Two VRFs with the same name

```text
ValueError: An error occurred while loading Netbox: ('Object MGMT already present', IpamNamespace "MGMT")
```

The example names each IP namespace after a NetBox VRF, so two VRFs called `MGMT` produce that namespace record twice and the second is refused. They are separate objects in NetBox, each with its own `rd` value, and the sync does not merge them — it stops. The same source also collides at `IpamVRF`, which is keyed on the VRF name as well; namespaces load first, so the namespace is the one the message names.

Renaming one of the VRFs in NetBox resolves it, but you do not have to touch NetBox: [key the namespace on the VRF ID instead of its name](../reference/schema-mapping.mdx#key-the-namespace-on-the-vrf-id-instead-of-its-name), which uses an identifier NetBox cannot repeat. That recipe covers namespaces, prefixes and addresses; the full example's `IpamVRF` entry is still keyed on the name and needs its own transform before the whole example runs against such a source.

Re-run the command once NetBox or the mapping reflects what you intend. Deleting a row purely to clear the message can destroy real data.
