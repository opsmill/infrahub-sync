---
title: Preview Nautobot data in an existing Infrahub
---

Preview the locations and devices from your existing Nautobot instance in an
existing Infrahub. You will:

- load two destination kinds, the Infrahub schema types that receive the data, into
  an Infrahub branch. A branch holds changes apart from `main` until you merge them.
- store a Sync configuration package in Infrahub.
- review a saved plan: the list of creates, updates, and deletes that the Sync
  service calculates and stores before it writes anything.

This tutorial writes no inventory data. It ends with the saved plan. For a
fresh local Infrahub and the public NetBox demo, follow the
[local demo tutorial](netbox-demo-to-infrahub) instead.

## Before you start

- Complete [Start a Compose deployment](../quickstart-compose.mdx) and confirm
  that the worker reports `ready`.
- Have Nautobot and Infrahub running, with API tokens for each. The worker
  container must be able to reach both servers; the Docker host must also reach
  Infrahub to load its schema.
- Have Python 3 with `venv` and `pip` on the Docker host for the separate
  Infrahub schema tool. The Sync CLI is already included in the deployment.
- Choose an Infrahub branch where you can load the example schema. Loading the
  schema changes that branch's types; the later preview does not import data.
  If `TestingSite` or `TestingDevice` already exists there with a different
  definition, choose another suitable branch or adapt the schema and mapping
  together before continuing.
- Every Nautobot Location and Device you plan to sync needs a `status`, and
  every Device needs a `role`, even though this tutorial's destination schema
  does not map them. That is a Nautobot data requirement, not a `package.yml`
  field, and a record missing either fails the run.

Run all commands on the Docker host, from the deployment directory that holds
`docker-compose.yml` and `.env`.

The two YAML files have different purposes:

- `schema.yml` defines the types and fields in Infrahub. Load it with
  `infrahubctl`.
- `package.yml` declares the Sync source, destination, mappings, and credential
  references. Register it with the deployment's `cli` service.

## Measured scenario

The measured run used Nautobot 2.4.41 with `depth: 1` and Infrahub 1.10.6. It
verified five devices and their location/model relationships, matching this
tutorial's sites-and-devices mapping. Saved run records survived deployment
restart. These measurements do not establish compatibility with other server
versions.

`depth: 1` requests nested objects. Without it, Nautobot 2.4.41 returns a
shallow `device_type` reference and the required `device_type.model` field is
missing.

## Set Nautobot and Infrahub credentials

Open `.env` and add the source and destination tokens:

```dotenv
INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN=<your Nautobot token>
INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN=<your Infrahub token>
```

Paste the Nautobot API token exactly as issued under your user profile's API
tokens; it has no special prefix like a NetBox token. For Infrahub, use an API
token created under your account settings; a login password does not work here.
Use source credentials that can read the mapped objects and an Infrahub token
that can load schema and read those destination kinds on your chosen branch.

The bundled CLI contacts Sync with your own Infrahub API token, `INFRAHUB_SYNC_TOKEN`, which
you exported in the quickstart; `INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN` is the token
the worker uses to write to the destination Infrahub.
Do not run `source .env`: that file also contains the deployment's
internal credentials.

## Prepare the destination schema

Save the following as `schema.yml` in the deployment directory. Each device
has a name, model, serial number, and a relationship to its site. This example
requires unique site names and unique device names in the mapped data.

```yaml
version: '1.0'
nodes:
  - name: Site
    namespace: Testing
    human_friendly_id: [name__value]
    uniqueness_constraints: [[name__value]]
    attributes:
      - name: name
        kind: Text
        optional: false
  - name: Device
    namespace: Testing
    human_friendly_id: [name__value]
    uniqueness_constraints: [[name__value]]
    attributes:
      - name: name
        kind: Text
        optional: false
      - name: model
        kind: Text
        optional: false
      - name: serial
        kind: Text
        optional: false
    relationships:
      - name: site
        peer: TestingSite
        kind: Attribute
        cardinality: one
        optional: false
```

Install the Infrahub SDK's schema tool in a host virtual environment:

```sh
python3 -m venv .schema-tools
.schema-tools/bin/python -m pip install 'infrahub-sdk[ctl]'
.schema-tools/bin/infrahubctl version
```

The version command must complete successfully before you continue. Replace
`https://infrahub.example.invalid` below with the address the **Docker host**
uses to reach Infrahub. The commands in parentheses read only the
destination token from `.env`. These environment settings apply only
inside the parentheses.

```sh
(
  export INFRAHUB_ADDRESS="https://infrahub.example.invalid"
  export INFRAHUB_API_TOKEN="$(sed -n 's/^INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN=//p' .env)"
  .schema-tools/bin/infrahubctl branch list
)
```

Choose a branch from the list and replace `BRANCH_NAME` in every remaining
command with its name. If you need a new branch, run
`.schema-tools/bin/infrahubctl branch create BRANCH_NAME` inside the same scoped
environment block before loading the schema.

```sh
(
  export INFRAHUB_ADDRESS="https://infrahub.example.invalid"
  export INFRAHUB_API_TOKEN="$(sed -n 's/^INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN=//p' .env)"
  .schema-tools/bin/infrahubctl schema load schema.yml --branch BRANCH_NAME
)
```

Continue only after the schema load succeeds. In Infrahub, select that branch and inspect
its schema: `TestingSite` and `TestingDevice` must exist, with
`TestingDevice.site` referencing `TestingSite`. Resolve schema errors before
continuing. Registering a Sync package does not load this schema.

## Create and edit package.yml

Nautobot uses locations and different relationship fields from the NetBox
tutorial's example, so create `package.yml` in the deployment directory with this
complete Nautobot mapping:

```yaml
---
# Map Nautobot locations and devices to TestingSite and TestingDevice in Infrahub.
# Replace both URLs and provide the matching destination schema before you load this package.
# Set INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN and INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN
# in the deployment's .env file.
format_version: 1
configuration:
  name: my-nautobot-evaluation
  source:
    name: nautobot
    settings:
      url: https://nautobot.example.invalid
      token: {$credential: nautobot-token}
      depth: 1
  destination:
    name: infrahub
    settings:
      url: https://infrahub.example.invalid
      token: {$credential: infrahub-token}
  schema_mapping:
    - name: TestingSite
      mapping: dcim.locations
      identifiers: [name]
      fields:
        - name: name
          mapping: name
    - name: TestingDevice
      mapping: dcim.devices
      identifiers: [name]
      fields:
        - name: name
          mapping: name
        - name: model
          mapping: device_type.model
        - name: serial
          mapping: serial
        - name: site
          mapping: location
          reference: TestingSite
credentials:
  nautobot-token: {provider: env, identifier: INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN}
  infrahub-token: {provider: env, identifier: INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN}
```

This mapping sends every Nautobot location to `TestingSite`, whatever its `location_type`.
To import only one type, add a `filters` entry on the `TestingSite` mapping — see the
[Schema mapping reference](../reference/schema-mapping.mdx). If you do, every location that a
mapped device points to through `location` must still pass that same filter: `TestingDevice`
resolves `site` from `TestingSite`, so a device whose location is filtered out has no site to
resolve against, and planning fails.

Before you load `package.yml` into Infrahub:

- Replace both URLs with addresses the **worker container** can reach.
  `localhost` and `127.0.0.1` inside the worker refer to that container.
  The destination must be the same Infrahub instance where you loaded the
  schema, even if the host uses a different address to reach it.
- Keep the `{$credential: ...}` references in YAML; token values belong in
  `.env`.
- Keep the mapping's destination kinds and fields consistent with `schema.yml`.
- Keep `depth: 1` so the source response includes nested values such as
  `device_type.model`.

The mapping includes locations and devices only. It does not import IP addressing
or interfaces. Source devices need the mapped name, model, serial, and
location relationship; review source data before expecting a complete preview.

## Reload credentials and create the configuration

Recreate services whose environment changed, then check readiness:

```sh
docker compose up -d --wait
curl -s http://127.0.0.1:8000/status
```

Continue only when the `/status` response shows `worker.state` as `ready`.
`up -d --wait` recreates the services whose environment changed;
`docker compose restart` keeps the environment from when the containers were created.

Sync reads configurations from Infrahub. Wrap `package.yml` in an Infrahub object
file that creates a `SyncConfiguration` named `nautobot-first-preview`, with the package as its
`document`:

```sh
{
  printf '%s\n' '---' 'apiVersion: infrahub.app/v1' 'kind: Object' 'spec:' \
    '  kind: SyncConfiguration' '  data:' '    - name: nautobot-first-preview' '      document: |'
  sed 's/^/        /' package.yml
} > sync-configuration.yml
```

Load it with the same scoped environment you used for the schema. The token needs
`create` on `SyncConfiguration` in Infrahub:

```sh
(
  export INFRAHUB_ADDRESS="https://infrahub.example.invalid"
  export INFRAHUB_API_TOKEN="$(sed -n 's/^INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN=//p' .env)"
  .schema-tools/bin/infrahubctl object load sync-configuration.yml
)
```

Runs read the configuration on Infrahub's default branch, whatever `BRANCH_NAME` you
write to. The configuration's name, `nautobot-first-preview`, is its `CONFIG_ID` from here on.

## Validate the configuration

```sh
docker compose run --rm --no-deps -T cli configs validate nautobot-first-preview
```

Read `total_findings` and every `finding` line. If `next_offset` is not `<none>`,
repeat with `--offset` set to that value to read the remaining findings. Resolve
findings with `severity=error` before planning; a zero command exit alone does
not mean the report contains no errors.

This checks the configuration's declared content on Infrahub's default branch. It does not test source
credentials, connectivity, or the live destination schema. The preview below
performs the reads against both servers.

If you edit `package.yml` later, write `sync-configuration.yml` and load it again, or edit
the configuration's `document` in Infrahub, then validate it again. The next run records
the new content as the next version.

## Preview and review the changes

Use the same `BRANCH_NAME` where you loaded the schema:

```sh
docker compose run --rm --no-deps -T cli diff --config-id nautobot-first-preview \
  --branch BRANCH_NAME --reason 'preview Nautobot locations and devices'
```

The worker reads Nautobot and Infrahub and saves a plan. The CLI waits by default,
then prints `run_id`, `plan_checksum`, `checksum_ok`, and operation counts.
Record the run ID and inspect the complete plan:

```sh
docker compose run --rm --no-deps -T cli runs plan RUN_ID --detail
```

Expect `checksum_ok: true` and operations for `TestingSite` and `TestingDevice`.
On a destination with no objects of those kinds, expect creates for the mapped
source records. Counts depend on your source data. Check device names,
model and serial values, and each device's site relationship. An empty plan
can mean the source is empty or the destination already matches it; confirm
which case applies.

The preview does not create, update, or delete inventory objects in Infrahub.
Against an existing destination, the plan can include updates and recorded
deletes as well as creates; review every unexpected operation before proceeding.

If the run fails, the CLI's own error output includes `run_id`; use that value
to inspect the run's record:

```sh
docker compose run --rm --no-deps -T cli runs show RUN_ID
docker compose run --rm --no-deps -T cli runs results RUN_ID
```

`runs show` reports the run's status and Prefect execution ID (`flow_run_id`).
`runs results` prints saved failure evidence, including the stage and error types.
The saved evidence omits exception messages. For more detail, inspect the
[worker logs](../compose-deployment#logs):

```sh
docker compose logs --no-color --tail 200 sync-worker
```

Find the `flow_run_id` from `runs show` in the logs to identify the Prefect
flow-run name. Read the messages for that name. If they report a source connection
failure, check the source URL and reachability from the worker container. Correct the cause before creating another preview. After credential
edits, run `docker compose up -d --wait` again; after package edits, load and validate the configuration again.

## Continue

You now have a configuration in Infrahub and a saved preview to review. For
later approved writes and deployment maintenance, see the
[Compose operator sequence](../compose-deployment#the-operator-sequence) and
[Operate a Compose deployment](../operations/day-2-operations.mdx).

The following notes concern larger mappings beyond this first preview.

## Nautobot-specific schema notes

- Nautobot 2.x has no `Site` model. Its equivalent is `dcim.locations`, where
  each Location has a `location_type` such as `Site`.
- A device's source relationship is `location`, not `site`; the mapping writes
  it into the destination's `TestingDevice.site` field.
- Every Nautobot Location and Device needs a `status`, and every Device needs a
  `role`, even though this destination schema does not map them. That is a
  Nautobot data requirement, not a `package.yml` field.

## If you map Nautobot IP addressing

Nautobot 2.0 and later has a native IPAM namespace object
(`ipam.namespaces`). Map it directly into the prefix identity and into an
address identity through its prefix: `InfraPrefix` is identified by
`["prefix", "ip_namespace"]`, while `InfraIPAddress` is identified by
`["address", "ip_prefix"]`. Do not derive a Nautobot namespace from a VRF
name: native namespaces already separate data, and VRF-name keys can merge two
namespaces whose VRFs share a name.

See the [schema mapping reference](../reference/schema-mapping.mdx),
[migration guidance](../migrating-from-netbox-or-nautobot.mdx), and the [full
Nautobot v2 example](https://github.com/opsmill/infrahub-sync/blob/feature/v3-develop/examples/nautobot-v2_to_infrahub/config.yml).

## Recorded deletes when mapping namespaces

In the measured run, the source supplied `Global` and `a4-ns-blue` while the
destination also contained its built-in `default`. The first plan recorded 17
creates and one delete of `default`. Apply created the intended objects and left
the built-in namespace unchanged in identifier, name, and description. The second plan contained
zero creates, zero updates, and the same single recorded delete.

This follows the saved-plan contract: destination-only objects are recorded as
deletes, but apply never executes them. Review each identity and verify the
destination; do not treat an unexpected delete or a remaining create/update as
acceptable merely because this example includes one recorded delete.
