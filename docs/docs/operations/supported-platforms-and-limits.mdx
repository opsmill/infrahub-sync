There are [two ways to run V3](../installation.mdx#two-ways-to-run-v3). Both run the
same Sync service. A source build has passed the pull request checks, but not the
release checks that each published image passes.

## Release image platforms

Each release publishes the Sync image for Linux `amd64` and Linux `arm64`, as one
multi-platform tag. Docker pulls the platform that matches the host. Both platforms
pass the same smoke test before the release pushes either one; see
[Container image](../container-image.mdx#supported-platforms).

The [Compose deployment](../compose-deployment.mdx) needs Docker Compose 2.24 or
later on that host, because its `docker-compose.yml` carries the database bootstrap
script as a top-level `configs` entry with inline `content`. An older Compose cannot
parse the file.

## Object stores

The Compose deployment keeps plans and run files in an S3-compatible store: the
bundled MinIO by default, or a team's own store. OpsMill tests the deployment
with the bundled MinIO build, and with a MinIO instance from the same image that
runs outside the deployment, over HTTPS with a private CA, with both the `path`
and the `virtual` addressing style. No other store is named as supported.

A team's own store must support these S3 operations and behaviours:

- `PutObject` as a single request with the whole body, and with the default
  request checksums of botocore 1.43.83
- `PutObject` with `If-None-Match: *`, refused with 412 `PreconditionFailed`
  when the key exists
- `GetObject` and `HeadObject`, with status 404 for a missing key
- `CopyObject` within the bucket, and `DeleteObject` of one key
- `HeadBucket`, with 2xx for an existing bucket, 404 for an absent one and 403
  for a refused credential, and `CreateBucket` when the bucket is absent
- Signature Version 4 authentication with an access key and a secret key

Sync does not list objects, use multipart uploads, presign URLs, or rely on
versioning or object lock. The full table and the settings are in
[S3 operations and behaviours Sync relies on](../compose-deployment.mdx#s3-operations-sync-relies-on).

## Other platforms, including Apple Silicon

Docker Desktop on macOS runs the Linux `arm64` image, but a desktop host is not a
platform the release tests. To try the latest changes on any platform Docker supports,
[run from source](../development-stack.mdx#run-from-source). The image is built from
your checkout for your host's own architecture.

## Measured versions

The measured destination is Infrahub 1.10.6. The measured sources are NetBox
4.6.10, and Nautobot 2.4.41 with the adapter setting `depth: 1` (see the
[Nautobot adapter](../adapters/nautobot.mdx#configuration-parameters)). These
version numbers come from working through the
[NetBox](../tutorials/netbox-to-existing-infrahub.mdx) and
[Nautobot](../tutorials/nautobot-to-existing-infrahub.mdx) tutorials against
those source versions and this destination version. They are not an automated
compatibility matrix. Other Infrahub, NetBox, or Nautobot versions are not
measured, and they are not excluded.

### Infrahub 1.11 or later for testing

Test this release against Infrahub 1.11 or later. When Infrahub rejects a write, the
cause that Sync records for the run takes Infrahub's error code from the error, and the
node kind and attribute from the data of that code. An older Infrahub returns no error
code, so the cause of a rejected write holds no error code, node kind, or attribute. The
measured version above, 1.10.6, is older than 1.11.

## Product limits

- The deployment runs on one host, with no clustering, no public ingress, and no TLS.
- The testing release supports one worker per deployment. `configs validate --branch`
  compares a package's credential variables with the names that the most recent live
  worker published. A worker counts as live for 90 seconds after it last published
  them, when it starts and on each poll. With two workers that hold different
  credentials, the check reads only one of them.
- Deletes are recorded in plans but are not executed.
- A sync cannot remove an optional single-object relationship from a destination
  object, for example the rack of a device. When the source value is empty, apply
  leaves the destination value in place and the worker logs a warning. Remove the
  relationship in Infrahub directly.
- There is no verified in-place upgrade, migration, rollback, backup, or restore
  procedure.
- There is no built-in schedule. Start each run with the CLI or the Sync API, for
  example from cron or a CI job.

For the operating procedure of a release, including replacement with a fresh
deployment, use the [Compose deployment guide](../compose-deployment).
