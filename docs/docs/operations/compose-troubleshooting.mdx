title: Compose operator troubleshooting
---

Diagnose a Compose deployment on one Docker host. For the local stacks that run from
source, see [Local development stack](../development-stack.mdx). For the NetBox demo
tutorial, see its [Troubleshooting](../tutorials/netbox-demo-to-infrahub#troubleshooting)
section.

## Start with the deployment state

Run the [status procedure](../compose-deployment#status) first: `docker compose ps`,
then the worker state from `/status`.

Use the [log procedure](../compose-deployment#logs) to read service output. Credentials
are removed from run failures before they are printed.

If a configuration validation reports a finding, use its stable code to find the
meaning in the [finding-code reference](../reference/durable-product-records#finding-codes).
The message wording can change; the code stays the same.

## Failures before the start

| Symptom | Cause and action |
| --- | --- |
| Compose fails to parse `configs.db-bootstrap-script.content` | Compose is older than 2.24. Upgrade it; check with `docker compose version --short`. |
| `<NAME> is required` | A required credential is missing from `.env`. Compose prints this before any container starts, from `docker compose config --quiet` or `up`. Add the named variable. |
| A pull error naming `registry.opsmill.io/opsmill/infrahub-sync:<version>` | The image cannot be pulled. Check `docker login registry.opsmill.io`, which is needed until 3.0.0, then `VERSION` and `INFRAHUB_SYNC_DOCKER_IMAGE`. See [Choose an image](../compose-deployment#choose-an-image). |
| `up` fails on a port publication | Another process holds the Sync API port. Set `INFRAHUB_SYNC_API_PORT` in `.env`. When you named `prefect-ui.yml` to open the Prefect UI, the port can also be the Prefect port: set `INFRAHUB_SYNC_PREFECT_PORT` in `.env`. |
| The services run an unexpected image | A `VERSION` or `INFRAHUB_SYNC_DOCKER_IMAGE` exported in your shell overrides `.env`. Unset it, then run `docker compose up -d --wait`. |
| `docker compose logs sync-bootstrap` shows `refused: bundled-object-store-not-left-out` | `INFRAHUB_SYNC_S3_ENDPOINT_URL` names your own store, but the bundled MinIO still runs. Add `INFRAHUB_SYNC_BUNDLED_OBJECT_STORE=0` to `.env`, then run `docker compose up -d --wait`. See [Use your own S3-compatible store](../compose-deployment#use-your-own-s3-compatible-store). |
| `docker compose logs sync-bootstrap` shows `refused: object-store-setting-invalid: <setting> must be ...` | `sync-bootstrap` refused the value of the named store setting before it sent any request. The message names the setting and never prints its value. `INFRAHUB_SYNC_S3_ENDPOINT_URL` must be an absolute `http` or `https` URL with no user name or password in it; put the credential in `INFRAHUB_SYNC_S3_ACCESS_KEY` and `INFRAHUB_SYNC_S3_SECRET_KEY` instead. `INFRAHUB_SYNC_S3_ADDRESSING_STYLE` must be `path` or `virtual`. `INFRAHUB_SYNC_S3_REGION` must not be blank when it is set. Correct the named setting in `.env`, then run `docker compose up -d --wait`. See [Store settings](../compose-deployment#store-settings). |
| `docker compose logs sync-bootstrap` shows `refused: object-store-unavailable` | `sync-bootstrap` could not complete a request to the store. The log does not say which cause, because the store's own error text carries the endpoint. Check each cause in turn: <ul><li>The host name in `INFRAHUB_SYNC_S3_ENDPOINT_URL` does not resolve from the deployment's containers. With `INFRAHUB_SYNC_S3_ADDRESSING_STYLE=virtual`, `<bucket>.<host>` must resolve too.</li><li>The store's TLS certificate is not trusted: it comes from a private CA that is not in the directory named by `INFRAHUB_SYNC_CA_CERTIFICATES`, or it does not cover the host name. See [Use custom CA certificates](../custom-certificates).</li><li>The bucket is in another region than `INFRAHUB_SYNC_S3_REGION`, and the store answers the bucket check with 301. Set the bucket's region.</li><li>The store is not reachable on the network: a wrong port, a firewall, or a store that is stopped or answers with a server error.</li></ul>Correct `.env` or the store, then run `docker compose up -d --wait`. |
| `docker compose logs sync-bootstrap` shows `refused: object-store-access-refused` | The store answered 403 when `sync-bootstrap` checked the bucket, created it, or wrote or deleted its check key. The credential in `INFRAHUB_SYNC_S3_ACCESS_KEY` and `INFRAHUB_SYNC_S3_SECRET_KEY` has no access to the bucket in `INFRAHUB_SYNC_S3_BUCKET`, or the bucket belongs to another account. Grant the credential object operations on the bucket and permission to check that it exists, or create the bucket yourself when the credential may not create one, or correct the bucket or the credential in `.env`. Then run `docker compose up -d --wait`. |
| `docker compose logs sync-bootstrap` shows `refused: object-store-unsupported` | The store accepted a second write of the same key with `If-None-Match: *`, or answered 501 or `NotImplemented` to one of the requests `sync-bootstrap` sends. Sync relies on that refusal so that no write replaces a stored artifact. Enable conditional writes on the store, or use a store that supports them. See [S3 operations and behaviours Sync relies on](../compose-deployment#s3-operations-sync-relies-on). |
| `docker compose logs sync-bootstrap` shows `CA certificate file <file> cannot be loaded: <error class>` | A `.pem` or `.crt` file in the directory named by `INFRAHUB_SYNC_CA_CERTIFICATES` is not a PEM certificate that Python's `ssl` module can load. `sync-bootstrap`, `sync-api` and `sync-worker` stop before they connect to anything. Replace the named file with the PEM CA certificate, or remove it, then run `docker compose up -d --wait`. See [Use custom CA certificates](../custom-certificates). |
| `docker compose logs sync-bootstrap` shows `CA certificate directory cannot be read` or `CA certificate file <file> cannot be read` | The services run as user ID 10001, and that user cannot list the directory named by `INFRAHUB_SYNC_CA_CERTIFICATES` or read the named file. `sync-bootstrap`, `sync-api` and `sync-worker` stop before they connect to anything. Make the directory listable and the files readable by user ID 10001, for example with `chmod 0755` on the directory and `chmod 0644` on the files, then run `docker compose up -d --wait`. See [Use custom CA certificates](../custom-certificates). |
| `docker compose logs sync-bootstrap` shows `CA certificate file <file> holds a private key` | The named file in the directory named by `INFRAHUB_SYNC_CA_CERTIFICATES` holds a private key. `sync-bootstrap`, `sync-api` and `sync-worker` stop, and no log line holds the file's content. Move the file out of the directory, because only CA certificates belong there, then run `docker compose up -d --wait`. |

## Failures after the start

| Symptom | Action |
| --- | --- |
| No container is running | Run `docker compose up -d --wait`. |
| `worker.state` is `no-live-worker` | Read the worker logs, then run `docker compose restart sync-api sync-worker`. It keeps the durable records. A paused or hung worker still looks `running` to Docker; only the worker state shows it, after three missed heartbeats or 30 seconds. |
| A changed `.env` value has no effect | A container reads its environment once, when it is created. Run `docker compose up -d --wait`, not `restart`. |
| You want to delete all data and begin again | Follow the [replacement procedure](../compose-deployment#resetting-this-alpha-to-a-fresh-deployment). `docker compose down --volumes` cannot be undone. |

The [stop, restart, and reset procedure](../compose-deployment#stop-restart-and-reset)
describes each action. A reset followed by a fresh deployment is not an upgrade: the new
deployment starts empty.

## Command-line client failures

`docker compose run --rm --no-deps -T cli ...` calls the Sync API with
`INFRAHUB_SYNC_API_TOKEN`.

- **Every call fails to authenticate.** `INFRAHUB_SYNC_API_TOKEN` is empty, or differs
  from the principal's token in `INFRAHUB_SYNC_SERVICE_BEARER_TOKENS`. An `operator.env`
  carried over from an earlier alpha may lack the `INFRAHUB_SYNC_API_TOKEN` line entirely.
  Add it to `.env`, with the token already inside `INFRAHUB_SYNC_SERVICE_BEARER_TOKENS`.
- **The CLI cannot read a mounted package.** The image runs as UID 10001, so the file
  must be readable by other users. Run `chmod 0644` on it, and mount it read-only as in
  [Registering a package](../compose-deployment#registering-a-package).

## Reconcile before retrying writes

When a write might have reached the destination, do not repeat it. Follow the
[uncertain-write reconciliation procedure](../compose-deployment#when-the-outcome-of-a-write-is-uncertain):
read the run record, inspect the destination, and create a fresh plan.
