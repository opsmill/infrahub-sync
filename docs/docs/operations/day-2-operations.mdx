---
title: Operate a Compose deployment
---

Check the health of a running Compose deployment, stop or restart it, change its
credentials, and recover from a write with an unknown outcome. Run every command from
the directory that holds `docker-compose.yml` and `.env`. Each section links the full
procedure in the [Compose deployment guide](../compose-deployment).

## Check health and status

Run `docker compose ps` to see each container and the health of PostgreSQL, the object
store, and Prefect. Then ask the Sync API whether a worker is live:

```sh
curl -s http://127.0.0.1:8001/status
```

The response's `worker.state` is one of three values:

| `worker.state` | Meaning | Next action |
| --- | --- | --- |
| `ready` | A registered worker sends heartbeats and can take a run. | None. A live worker does not check a registered source or destination. |
| `busy` | A registered worker sends heartbeats and is running work. | None. |
| `no-live-worker` | No worker has sent a heartbeat recently. A stopped, paused, or hung worker causes this state. | Read the worker logs, then run `docker compose restart sync-api sync-worker`. |

If no container is running at all, run `docker compose up -d --wait`. See the
[status procedure](../compose-deployment#status) for the details of each state.

`docker compose logs --no-color --tail 200` prints the last 200 lines of each service.
Credentials are removed from run failures before they are printed. See the
[log procedure](../compose-deployment#logs).

## Stop, restart, or reset

The [stop, restart, and reset procedure](../compose-deployment#stop-restart-and-reset)
describes each action:

- `docker compose stop` stops all services and keeps their containers and volumes. Run
  `docker compose up -d --wait` to resume the deployment, including its dependencies.
- `docker compose restart sync-api sync-worker` replaces only the API and worker
  processes and keeps the durable records. The dependencies must already be running.
- `docker compose down --volumes --remove-orphans` deletes this deployment's
  containers, network, and volumes, with every registered configuration, run, and
  artifact. Nothing asks for confirmation, and you cannot undo it.

Before planned maintenance, ask everyone who submits runs to this deployment to stop
submitting new runs. Then check each run you know of with
`infrahub-sync runs show RUN_ID`, and wait until its
`execution_state` is `completed`, `failed`, `cancelled`, `abandoned`, or `interrupted`.
A `ready` worker says nothing about runs still executing. If you cannot account for
every submitted run, postpone the maintenance.

After you resume the deployment,
[verify a retained configuration version](../compose-deployment#verify-a-retained-configuration)
to check that your registered packages are still available.

## Change the image

Set `VERSION`, and optionally `INFRAHUB_SYNC_DOCKER_IMAGE`, in `.env`, then run
`docker compose up -d --wait`. Compose recreates only the services whose image changed.
See [Choose an image](../compose-deployment#choose-an-image). This release has no
in-place state migration, so a release that needs a new state requires a fresh
deployment.

### Changes when you move to the release that reports plan problems

The release that checks each plan for problems and leaves out the records that have one
changes these steps of an image change:

- Saved plans: a plan saved in format 2 or 3 by an earlier release can still be reviewed,
  but its apply is refused with `PlanFormatApplyUnsupportedError` before any write, because it
  was never checked for problems. Create a new plan for each reviewed plan that you have not
  applied yet, review it, and apply that one.
- The worker's Prefect deployment: an apply of a plan that leaves out records sends the
  parameter `confirm_left_out` to the worker. The Prefect deployment must be applied again with
  the new release before the Sync API of the new release accepts requests, so that the
  deployment accepts that parameter. In this Compose deployment, `docker compose up -d --wait`
  runs the `sync-bootstrap` job again when its image changes, and that job applies the
  deployment before `sync-api` starts. A deployment that is not run through this Compose file
  applies it with `python -m infrahub_sync.service.deploy`; see
  [Deploy the service flow](../reference/sync-http-api.mdx#deploy-the-service-flow).
- The CLI: upgrade the CLI together with the Sync API. An earlier CLI cannot read the new
  response of `configs register` and `configs version`: the command stores the version and then
  fails. The registration is kept; read it with `configs show CONFIG_ID --version VERSION`.
- The `worker_environments` table: each worker writes the names of its credential variables
  to this new table, never their values. Each worker restart adds a row under a new worker name,
  and the rows of earlier worker processes stay in the table. If you return to an earlier
  image, the table stays in the database and the earlier release does not read it.
- Warm incremental reads: no adapter bundled with Sync reads only the records changed since
  the last run, and the Sync API and the Prefect flow always read every record. A custom
  source adapter that defines `safe_cursor_before_load` reads this way only when it also
  implements `list_changed_records`; it then checks the changed records for problems as a
  full read does. Without `list_changed_records`, it reads every record. A source snapshot
  saved by an earlier release has no source record IDs, so the first run after the upgrade
  reads each kind in full once.

No in-place upgrade or return to an earlier release is verified; see
[Supported platforms and limits](./supported-platforms-and-limits.mdx).

## Replace a deployment with a fresh one

Delete the volumes only when you intend to delete the deployment's data. V3 releases
are test versions, and they have no in-place migration, backup, or restore procedure.
To replace a deployment, follow the
[replacement procedure](../compose-deployment#resetting-this-alpha-to-a-fresh-deployment):
run `docker compose down --volumes --remove-orphans`, then `docker compose up -d --wait`.
The new deployment starts with an empty registry, so register your packages again.

The volumes are named after the Compose project, which defaults to the directory name.
Moving or renaming the directory starts a different, empty deployment. Set
`COMPOSE_PROJECT_NAME` in `.env` if the directory may change.

## Change credentials

Source and destination tokens belong in `.env`. Packages contain references to them,
not their values. To add or change a token, edit its line in `.env` as
[The `.env` file](../compose-deployment#configuration-prerequisites) describes, then
run `docker compose up -d --wait`, which recreates the services whose environment
changed. `docker compose restart` keeps the environment the containers already had.

This release has no tested procedure for rotating credentials. The Sync API token that
the CLI presents, `INFRAHUB_SYNC_API_TOKEN`, must equal the principal's token in
`INFRAHUB_SYNC_SERVICE_BEARER_TOKENS`; change both together. The `cli` service reads
`INFRAHUB_SYNC_API_TOKEN` from `.env`. See [Use it](../compose-deployment#use-it).

Never `source` `.env` or put a credential on a command line. Keep values out of logs,
shell history, and configuration packages.

## Recover from a write with an unknown outcome

A write has an unknown outcome when the run ended without a record of what reached the
destination. `infrahub-sync runs show RUN_ID` then reports
`reconciliation_required: true`, or an apply ends with phase `apply-failed` and
`summary.may_have_partially_written` set.

Do not retry that write. Follow the
[reconciliation procedure](../compose-deployment#when-the-outcome-of-a-write-is-uncertain):
read the run record, which no longer changes once the run has ended, inspect the
destination, and then create a fresh plan. The fresh plan reads the destination as it is
now, so it holds only the changes that are still outstanding.
