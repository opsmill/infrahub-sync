## Use this adapter

In a [configuration package](../configuration-package.mdx), name `netbox` as the source. Then register the package, create and review a plan, and apply the plan, as described in [Run a sync](../running-a-sync.mdx).

The example package is [`examples/netbox_to_infrahub/package.yml`](https://github.com/opsmill/infrahub-sync/blob/feature/v3-develop/examples/netbox_to_infrahub/package.yml), and the [NetBox demo tutorial](../tutorials/netbox-demo-to-infrahub.mdx) uses it.

<!-- vale off -->
## What is NetBox?
<!-- vale on -->

NetBox is an open-source infrastructure resource management tool that centralizes and documents your network's devices, IP addresses, circuits, and connections using pre-configured models and automation for streamlined operations.

## Requirements

This adapter uses the [NetBox SDK](https://pypi.org/project/pynetbox), `pynetbox`. The Sync image and the `service` extra install it.

## Sync directions supported

- NetBox → Infrahub

NetBox is a source only. Infrahub Sync does not write to NetBox.

## Schema

The example package maps NetBox data into the `infrahub/traditional-infrastructure-sot` schema collection from the [Infrahub Marketplace](https://marketplace.infrahub.app/collections/infrahub/traditional-infrastructure-sot). This schema does not copy the NetBox data model one-to-one. The [NetBox demo tutorial](../tutorials/netbox-demo-to-infrahub.mdx) shows how to download the collection and load it into Infrahub.

## Configuration

Set `source.name` to `netbox`. In a registered package, the token is a `$credential` reference:

```yaml
format_version: 1
configuration:
  name: from-netbox
  source:
    name: netbox
    settings:
      url: "https://netbox.example.com"
      token:
        $credential: netbox-token
      verify_ssl: true # Default value
  destination:
    name: infrahub
    settings:
      url: "https://infrahub.example.com"
      token:
        $credential: infrahub-token
credentials:
  netbox-token:
    provider: env
    identifier: INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN
  infrahub-token:
    provider: env
    identifier: INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN
```

| Setting | Required | Description |
| --- | --- | --- |
| `url` | Yes | NetBox URL, as the Sync worker reaches it |
| `token` | Yes | `$credential` reference to the NetBox API token |
| `verify_ssl` | No | Verify TLS certificates. Defaults to `true`. |

The worker uses the declared `url`. `NETBOX_ADDRESS` and `NETBOX_URL` in the worker environment do not replace it. The worker reads the token from the environment variable that the credential names. For direct adapter use without a registered package, `NETBOX_ADDRESS`, `NETBOX_URL`, and `NETBOX_TOKEN` take precedence over the declared settings.

### Schema mapping

The mapping connects NetBox API paths to Infrahub kinds. This excerpt from the example package maps NetBox tags and sites:

```yaml
  schema_mapping:
    - name: BuiltinTag
      mapping: extras.tags
      identifiers: ["name"]
      fields:
        - name: name
          mapping: name
        - name: description
          mapping: description

    - name: LocationSite
      mapping: dcim.sites
      identifiers: ["name"]
      fields:
        - name: name
          mapping: slug
        - name: description
          mapping: name
        - name: status
          mapping: status.value
        - name: tags
          mapping: tags
          reference: BuiltinTag
```

The NetBox API paths are listed at `/api/schema/swagger-ui/` on your NetBox instance.

When a mapped NetBox record is excluded by a declared `filters` rule, the source omits references to it from optional relationships and logs a warning with the owning kind, record ID, field, peer kind, and excluded peer IDs. A relationship with several peers keeps the peers that passed the filter. Its plan can remove destination links to excluded peers. A full plan can also list a delete for a filtered record that exists at the destination, but apply skips every planned delete, so that record stays. For a relationship with one peer, an omitted reference becomes an absent value in the plan; an existing destination link can remain unchanged. Review these effects before applying the plan.

If a required relationship has no remaining peer, the run stops with an error that identifies the owning record, field, peer kind, and filter exclusion. A reference to a record that does not exist in NetBox remains an error. When an owner is loaded before its filtered peer kind, the first excluded-peer lookup reads the entire peer endpoint to distinguish filtering from absence; the later peer load can read it again. Direct incremental adapter calls also make this full read on their first lookup.
