## Use this adapter

In a [configuration package](../configuration-package.mdx), name `nautobot` as the source. Then register the package, create and review a plan, and apply the plan, as described in [Run a sync](../running-a-sync.mdx).

The [Nautobot tutorial](../tutorials/nautobot-to-existing-infrahub.mdx) contains a complete package.

<!-- vale off -->
## What is Nautobot?
<!-- vale on -->

Nautobot is an open-source network source of truth and automation platform, offering extended customization, plugin support, and enhanced functionality to simplify network documentation and operations.

## Requirements

This adapter uses the [Nautobot SDK](https://pypi.org/project/pynautobot), `pynautobot`. The Sync image and the `service` extra install it.

## Sync directions supported

- Nautobot → Infrahub

Nautobot is a source only. Infrahub Sync does not write to Nautobot.

## Schema

Our `infrahub` repository contains an **example schema** that serves as a starting point for syncing Nautobot data into Infrahub.
This schema follows best practices for Infrahub, **but it does not map the Nautobot data model one-to-one** since Infrahub may have additional use cases.

To reflect the breaking changes introduced in Nautobot v2, there is not one but two schemas. You can explore them to see the difference.

## Configuration

The [Nautobot tutorial](../tutorials/nautobot-to-existing-infrahub.mdx) contains a complete package for a small schema. The repository also contains two larger mapping examples that match the example schemas above:

- [`examples/nautobot-v1_to_infrahub/config.yml`](https://github.com/opsmill/infrahub-sync/blob/feature/v3-develop/examples/nautobot-v1_to_infrahub/config.yml) for Nautobot 1.x
- [`examples/nautobot-v2_to_infrahub/config.yml`](https://github.com/opsmill/infrahub-sync/blob/feature/v3-develop/examples/nautobot-v2_to_infrahub/config.yml) for Nautobot 2.x

These files are `config.yml` files, not packages. Registration refuses them as they are. To use one, convert it as described in [Convert a config.yml file](../configuration-package.mdx#convert-a-configyml-file).

### Configuration parameters

Set `source.name` to `nautobot`. In a registered package, the token is a `$credential` reference:

```yaml
format_version: 1
configuration:
  name: from-nautobot
  source:
    name: nautobot
    settings:
      url: "https://nautobot.example.com"
      token:
        $credential: nautobot-token
      verify_ssl: true # Default value
      depth: 1 # Optional. Omit to send no depth parameter.
  destination:
    name: infrahub
    settings:
      url: "https://infrahub.example.com"
      token:
        $credential: infrahub-token
credentials:
  nautobot-token:
    provider: env
    identifier: INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN
  infrahub-token:
    provider: env
    identifier: INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN
```

The worker uses the declared `url`. `NAUTOBOT_ADDRESS` and `NAUTOBOT_URL` in the worker environment do not replace it. The worker reads the token from the environment variable that the credential names. For direct adapter use without a registered package, `NAUTOBOT_ADDRESS`, `NAUTOBOT_URL`, and `NAUTOBOT_TOKEN` take precedence over the declared settings.

`depth` is passed straight through to Nautobot as a query parameter on every list
request the adapter makes. It is an integer between 0 and 10; any other value is
refused before the first request, and omitting the setting sends no depth
parameter at all. Raise it only as far as the mappings in use require: a non-zero
depth expands nested relations on every record of every page, so payload size and
latency grow with it — materially so on large tables such as `dcim.interfaces`.

### Schema mapping

The configuration file allows mapping Nautobot data to the Infrahub schema, which has been designed to loosely align with the Nautobot data model.
Below is an example showing how to:

- Set the destination Infrahub model (`OrganizationGeneric` and `InfraPlatform`)
- Map source data from Nautobot (`dcim.manufacturers`, and `dcim.platforms`)
- Specify field mappings between Nautobot and Infrahub models

As you can see in this example, we map different Nautobot paths to different Infrahub models, and reference one mapped model (`OrganizationGeneric`) from another (`InfraPlatform`).

```yaml
  - name: OrganizationGeneric
    mapping: dcim.manufacturers
    identifiers: ["name"]
    fields:
      - name: name
        mapping: name
      - name: description
        mapping: description
      - name: type
        static: "Manufacturer"

  - name: InfraPlatform
    mapping: dcim.platforms
    identifiers: ["name", "manufacturer"]
    fields:
      - name: name
        mapping: name
      - name: description
        mapping: description
      - name: napalm_driver
        mapping: napalm_driver
      - name: manufacturer
        mapping: manufacturer
        reference: OrganizationGeneric
```

The Nautobot API paths are listed at `/api/docs/` on your Nautobot instance.
