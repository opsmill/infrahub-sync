title: Generic REST API adapter
---

Use the Generic REST API adapter to read data from a system with a REST/JSON API when no dedicated adapter exists. You configure the base URL, the authentication method, and the location of the records in each response.

## Use this adapter

In a [configuration package](../configuration-package.mdx), name `genericrestapi` as the source. Then register the package, create and review a plan, and apply the plan, as described in [Run a sync](../running-a-sync.mdx).

On a Compose deployment, from source or from a release package, the worker receives only the Infrahub, NetBox, and Nautobot tokens, so a source that needs authentication cannot receive its credentials in this release; a source with `auth_method: none` is not affected. See [Credentials on a Compose deployment](./choosing-an-adapter.mdx#credentials-on-a-compose-deployment).

## Sync directions supported

- REST API source → Infrahub

The Generic REST API adapter is a source only. It does not write to the source system.

## How the adapter reads data

For each `schema_mapping` entry, the adapter sends one `GET` request to `<url>/<api_endpoint>/<mapping>` and reads the records from that one response. It does not follow pagination links. If the API returns records in pages, only the first page is read.

In a registered package, each `mapping` must be a relative path without a query string or fragment, for example `devices` or `api/devices`. Registration refuses a full URL or a path with query parameters.

## Configuration

Set `source.name` to `genericrestapi`. In a registered package, `token`, `username`, and `password` are `$credential` references:

```yaml
format_version: 1
configuration:
  name: rest-api-example
  source:
    name: genericrestapi
    settings:
      url: "https://api.example.com"
      api_endpoint: "api/v1"
      auth_method: "token"
      token:
        $credential: rest-api-token
  destination:
    name: infrahub
    settings:
      url: "https://infrahub.example.com"
      token:
        $credential: infrahub-token
  schema_mapping:
    - name: InfraDevice
      mapping: devices
      identifiers: ["name"]
      fields:
        - name: name
          mapping: hostname
        - name: serial_number
          mapping: serial
        - name: type
          static: "Network Device"
credentials:
  rest-api-token:
    provider: env
    identifier: REST_API_TOKEN
  infrahub-token:
    provider: env
    identifier: INFRAHUB_API_TOKEN
```

### Configuration parameters

| Parameter | Description | Default | Required |
|-----------|-------------|---------|----------|
| `url` | Base URL of the API | None | Yes |
| `api_endpoint` | Path between the base URL and each mapping path | `/api/v0` | No |
| `auth_method` | Authentication method: `token`, `x-auth-token`, `api-key`, `key`, `basic`, or `none` | `token` | No |
| `token` | API token, for the `token`, `x-auth-token`, `api-key`, and `key` methods | None | For those methods |
| `username` | Username for `basic` | None | For `basic` |
| `password` | Password for `basic` | None | For `basic` |
| `verify_ssl` | Verify TLS certificates | `true` | No |
| `timeout` | Request timeout in seconds | `30` | No |
| `response_key_pattern` | Key that holds the records in each response. See [Response handling](#response-handling). | None | No |

Registration refuses any other setting.

The authentication methods send these headers:

| `auth_method` | Request authentication |
| --- | --- |
| `token` | `Authorization: Token <token>` |
| `x-auth-token` | `X-Auth-Token: <token>` |
| `api-key` | `Authorization: Api-Key <token>` |
| `key` | `Authorization: Key <token>` |
| `basic` | HTTP basic authentication |
| `none` | No authentication |

### Direct adapter use

A registered package uses its declared settings and resolved credentials. For direct adapter use without a registered package, these environment variables take precedence over the declared settings:

| Setting | Environment variables |
|---------|----------------------|
| `url` | `GENERICRESTAPI_URL`, then `GENERICRESTAPI_ADDRESS` |
| `token` | `GENERICRESTAPI_TOKEN` |
| `username` | `GENERICRESTAPI_USERNAME` |
| `password` | `GENERICRESTAPI_PASSWORD` |

Bare `URL`, `ADDRESS`, `TOKEN`, `USERNAME`, and `PASSWORD` variables are not read.

### Response handling

By default, the adapter reads the records from the response key that matches the last part of the mapping path. For example, the records for `api/devices` are read from the `devices` key. If that key is missing, it tries the full mapping path as the key. The records can be a list or an object whose values are records.

If your API uses another key, set `response_key_pattern`:

```yaml
source:
  name: genericrestapi
  settings:
    # ...other settings...
    response_key_pattern: "data"
```

The pattern can contain two placeholders:

- `{resource}`: the mapping path
- `{default}`: the last part of the mapping path

## Schema mapping

The schema mapping connects API paths to Infrahub kinds. A field can map a response field, set a static value, or reference another mapped kind:

```yaml
schema_mapping:
  - name: InfraDevice      # Infrahub kind
    mapping: devices       # API path
    identifiers: ["name"]
    filters:
      - field: hostname
        operation: contains
        value: "router"
    fields:
      - name: name         # Infrahub field
        mapping: hostname  # Response field
      - name: type
        static: "Network Device"
      - name: site         # Reference to another mapped kind
        mapping: location
        reference: LocationSite
```

Filters remove records before mapping. For the filter operations, such as `==`, `!=`, `contains`, and `regex`, see [Available filter operations](../reference/schema-mapping.mdx#available-filter-operations).

The [LibreNMS](./librenms.mdx), [Observium](./observium.mdx), [Device42](./device42.mdx), and [PeeringDB](./peeringdb.mdx) pages link complete mapping examples for this adapter.

## Common issues

### Authentication failures

1. Check that the worker environment sets the variable that each credential names.
2. Check that `auth_method` matches what your API expects.
3. Check that `url` and `api_endpoint` together form the correct API path.

### Response parsing errors

1. Check the response format in the API documentation.
2. Set `response_key_pattern` to the key that holds the records.
3. If the API needs logic that configuration cannot express, the system needs a dedicated adapter. See [Choose an adapter](./choosing-an-adapter.mdx#when-to-build-a-custom-adapter).

### Timeouts and large responses

1. Increase `timeout`.
2. Use filters to reduce the records that are mapped. Filters run after the response is read, so they do not reduce the response size.
