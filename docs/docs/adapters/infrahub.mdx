## Use this adapter

Name `infrahub` as the destination, or as the source, in a [configuration package](../configuration-package.mdx). Then register the package, create and review a plan, and apply the plan, as described in [Run a sync](../running-a-sync.mdx).

<!-- vale off -->
## What is Infrahub?
<!-- vale on -->

Infrahub is an open-source infrastructure management platform that combines a version-controlled database with a schema-driven data model. It serves as the central hub for network automation, providing a single source of truth for infrastructure data.

## Requirements

This adapter uses the [Infrahub SDK](https://pypi.org/project/infrahub-sdk), which is included as a dependency of infrahub-sync.

## Sync directions supported

- Destination: every registered package writes to Infrahub. The Sync worker reads the destination schema before it plans, and Infrahub is the only adapter that supports that read. The worker refuses any other destination before it reads a schema.
- Source: Infrahub can also be the source. The destination is then another Infrahub branch or instance.

A single package moves data one way, from its source to its destination.

### Settings reference

| Setting | Type | Required | Default | Description |
|---------|------|----------|---------|-------------|
| `url` | string | Yes | - | Infrahub server URL, as the Sync worker reaches it |
| `token` | `$credential` reference | Yes | - | API token for authentication |
| `branch` | string | No | See below | Branch to read or write |
| `verify_ssl` | boolean | No | true | Verify TLS certificates |
| `source` | string | No | - | CoreAccountGroup name to use as lineage source |
| `owner` | string | No | - | CoreAccountGroup name to use as lineage owner |

For the destination, a declared `branch` takes precedence over the `--branch` option of `diff`, `sync`, and `apply`. The option is used only when the package declares no branch, and `main` is used when neither is set.

### Connection settings in a registered package

A registered package declares its own connection settings:

- The worker connects to the `url` declared in the package, for data and for the destination schema read. `INFRAHUB_ADDRESS` and `INFRAHUB_URL` in the worker environment do not replace it.
- The worker reads the token from the environment variable that the package's `credentials` entry names, for example `INFRAHUB_API_TOKEN`. Set that variable in the worker environment. On a Compose deployment, set it in `operator.env`.
- To change a URL or a branch, edit the package and register it as a new version with `configs version`. Then plan with the new version.

### Direct adapter use

The direct [Prefect remote run](../reference/prefect-remote-run.mdx) and Python callers that run a `config.yml` directory do not use a registered package. In that case the adapter reads these environment variables before the declared settings:

| Variable | Replaces |
|----------|----------|
| `INFRAHUB_ADDRESS` or `INFRAHUB_URL` | `settings.url` |
| `INFRAHUB_API_TOKEN` | `settings.token` |

## Schema mapping

When Infrahub is used as a destination, the schema mapping defines how source data maps to Infrahub node types. The `name` field in schema_mapping corresponds to the Infrahub schema kind.

### Basic example

```yaml
schema_mapping:
  - name: InfraDevice
    mapping: dcim.devices
    identifiers: ["name"]
    fields:
      - name: name
        mapping: name
      - name: description
        mapping: description
      - name: status
        mapping: status.value

  - name: InfraInterface
    mapping: dcim.interfaces
    identifiers: ["device", "name"]
    fields:
      - name: name
        mapping: name
      - name: device
        mapping: device.name
        reference: InfraDevice
```

### Relationship handling

The Infrahub adapter automatically resolves relationships based on the schema:

- **One-to-one relationships**: Resolved using the unique identifier of the related node
- **One-to-many relationships**: Resolved as a list of unique identifiers

```yaml
fields:
  # One-to-one relationship
  - name: site
    mapping: site.name
    reference: LocationSite

  # One-to-many relationship
  - name: tags
    mapping: tags
    reference: BuiltinTag
```

### Destination identity for writes

Infrahub must be able to find each planned object by a key: the kind's human-friendly ID or one of its uniqueness constraints. List every field of one such key in `identifiers` and map it in `fields`. The key cannot contain a value that Infrahub allocates or computes. Sync checks this against the destination schema before it extracts data, and refuses a kind without such a key. See [Destination key for Infrahub writes](../reference/schema-mapping.mdx#destination-key-for-infrahub-writes) for the rules and an example.

## Lineage tracking

When syncing data into Infrahub, the adapter tracks the source and owner of each record using Infrahub's lineage system. This enables:

- Tracking which system created each record
- Protecting source-managed attributes from manual edits
- Assigning ownership to teams or groups

Source and owner lineage is applied to newly created relationship edges and to relationship peers newly linked by an update. Rerunning a sync does not backfill lineage onto unchanged, pre-existing relationship edges.
Resource-pool allocations are an exception: their relationship mutation does not include source or owner lineage.

### Default behavior

By default, the adapter looks for a `CoreAccount` with a name matching the source adapter name. This account is used as both the source and owner for all synced attributes.

### Using account groups

You can override the default behavior by specifying `source` and/or `owner` in the destination settings. When specified, these values are used to look up a `CoreAccountGroup` by name:

```yaml
destination:
  name: infrahub
  settings:
    url: "https://infrahub.example.com"
    token:
      $credential: infrahub-token
    source: "data-sync"      # Uses CoreAccountGroup "data-sync" as source
    owner: "network-team"    # Uses CoreAccountGroup "network-team" as owner
```

This allows you to:

- Use different groups for source and owner
- Override only one while keeping the default account for the other
- Assign ownership to a team rather than an individual account

| Configuration | Source | Owner |
|--------------|--------|-------|
| Neither specified | CoreAccount (source name) | CoreAccount (source name) |
| Only `source` specified | CoreAccountGroup | CoreAccount (source name) |
| Only `owner` specified | CoreAccount (source name) | CoreAccountGroup |
| Both specified | CoreAccountGroup | CoreAccountGroup |

## Common issues and troubleshooting

### Authentication errors

- Check that the worker environment sets the variable that the package's token credential names, for example `INFRAHUB_API_TOKEN`. On a Compose deployment, run `./infrahub-sync-compose start` after you change `operator.env`.
- Check that the token has permission to read and write the target branch.
- Check the `url` in the registered package with `configs show <config-id> --version <version>`. The worker does not read `INFRAHUB_ADDRESS`.

### Schema mismatch errors

- Check that every kind in `schema_mapping` exists in the destination schema, on the branch the plan uses.
- Load or update the schema with `infrahubctl schema load`. See [Load an example schema into Infrahub](./choosing-an-adapter.mdx#load-an-example-schema-into-infrahub).
- Check that field names match the Infrahub schema attribute and relationship names.

### No writable destination identity

- An error containing `no complete writable destination convergence identity` names the unusable key fields. See [Destination key for Infrahub writes](../reference/schema-mapping.mdx#destination-key-for-infrahub-writes).
- After an upgrade, create and review a new plan before you apply. A plan saved by an earlier release can have a different schema fingerprint, and apply refuses it.

### Relationship resolution failures

- Check that each referenced kind has its own `schema_mapping` entry. Sync writes referenced kinds first unless an `order` list in the package overrides that order.
- Verify the unique identifier used in references matches the target object's identifier
- Check logs for "Unable to find ... in the Store" messages

### Branch operations

- Check that the target branch exists in Infrahub. List branches with `infrahubctl branch list`.
- Create a branch with `infrahubctl branch create <name>`.

### SSL certificate issues
<!-- vale Infrahub.sentence-case = YES -->

- `verify_ssl: false` turns off certificate verification. Use it only for development.
- To trust an internal certificate authority, see [Use custom CA certificates](../custom-certificates.mdx). That page also describes the current limit of the Compose deployment.
