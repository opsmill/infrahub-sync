## Use this adapter

Name `infrahub` as the destination, or as the source, in a [configuration package](../configuration-package.mdx). Then register the package, create and review a plan, and apply the plan, as described in [Run a sync](../running-a-sync.mdx).

<!-- vale off -->
## What is Infrahub?
<!-- vale on -->

Infrahub is an open-source infrastructure management platform that combines a version-controlled database with a schema-driven data model. It serves as the central hub for network automation, providing a single source of truth for infrastructure data.

## Requirements

This adapter uses the [Infrahub SDK](https://pypi.org/project/infrahub-sdk), which is included as a dependency of infrahub-sync.

## Sync directions supported

- Destination: Infrahub is currently the only destination for a registered run that can plan or apply. The Sync worker reads the destination schema before it plans, and Infrahub is the only adapter that supports that read. The worker refuses any other destination before it reads a schema.
- Source: Infrahub can also be the source. The destination is then another Infrahub branch or instance.

A single package moves data one way, from its source to its destination.

### Settings reference

| Setting | Type | Required | Default | Description |
|---------|------|----------|---------|-------------|
| `url` | string | Yes | - | Infrahub server URL, as the Sync worker reaches it |
| `token` | `$credential` reference | Yes | - | API token for authentication |
| `branch` | string | No | See below | Branch to read or write |
| `verify_ssl` | boolean | No | true | Verify TLS certificates |
| `source` | `{kind, name}` mapping | No | The import account | Node recorded as the source of every value the import writes. See [Lineage tracking](#lineage-tracking) |
| `owner` | `{kind, name}` mapping | No | No owner | Node set as the owner of the values the import creates. See [Lineage tracking](#lineage-tracking) |
| `protect` | boolean | No | false | Mark the values the import creates or changes as protected |

For the destination, a declared `branch` takes precedence over the `--branch` option of `diff`, `sync`, and `apply`. The option is used only when the package declares no branch, and `main` is used when neither is set. `INFRAHUB_DEFAULT_BRANCH` and `INFRAHUB_DEFAULT_BRANCH_FROM_GIT` do not change this choice. The completed `diff`, `sync`, and `apply` commands print `destination_branch`; `runs plan` also shows the branch saved with a plan.

The SDK still reads other `INFRAHUB_` settings for connection behavior. These include `ECHO_GRAPHQL_QUERIES`, `IDENTIFIER`, `INSERT_TRACKER`, `MAX_CONCURRENT_EXECUTION`, `MODE`, `PAGINATION_SIZE`, `PRIORITY`, `RETRY_*`, `RATE_LIMIT_*`, `MAX_RETRY_DURATION`, `SCHEMA_CONVERGE_TIMEOUT`, `TRANSPORT`, `RECORDER`, `PROXY`, `PROXY_MOUNTS`, `MARKETPLACE_URL`, `UPDATE_GROUP_CONTEXT`, and `TLS_CA_FILE`. They remain available. The adapter supplies a 60-second timeout, so `INFRAHUB_TIMEOUT` does not replace it. For a registered package, the declared `verify_ssl` setting alone controls TLS verification, and verification is on when it is not declared. The adapter and the destination schema read pass the declared URL and token directly to the SDK, so `INFRAHUB_ADDRESS`, `INFRAHUB_API_TOKEN`, `INFRAHUB_USERNAME`, `INFRAHUB_PASSWORD`, and `INFRAHUB_TLS_INSECURE` cannot replace or add to them. For direct adapter use, `INFRAHUB_TLS_INSECURE` controls TLS verification when `verify_ssl` is not declared.

For a registered package, the SDK validates the declared destination URL. An invalid `INFRAHUB_ADDRESS` does not reject that URL during schema discovery or adapter construction.

### Connection settings in a registered package

A registered package declares its own connection settings:

- The worker connects to the `url` declared in the package, for data and for the destination schema read. `INFRAHUB_ADDRESS` and `INFRAHUB_URL` in the worker environment do not replace it.
- The worker reads the token from the environment variable that the package's `credentials` entry names, for example `INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN`. Set that variable in the worker environment. On a Compose deployment, set it in `.env`.
- To change a URL or a branch, edit the package and register it as a new version with `configs version`. Then plan with the new version.

### Direct adapter use

The direct [Prefect remote run](../reference/prefect-remote-run.mdx) and Python callers that run a `config.yml` directory do not use a registered package. In that case the adapter reads these environment variables before the declared settings:

| Variable | Replaces |
|----------|----------|
| `INFRAHUB_ADDRESS` or `INFRAHUB_URL` | `settings.url` |
| `INFRAHUB_API_TOKEN` | `settings.token` |

## Schema mapping

When Infrahub is used as a destination, the schema mapping defines how source data maps to Infrahub node types. The `name` field in schema_mapping corresponds to the Infrahub schema kind.

### Basic example

```yaml
schema_mapping:
  - name: InfraDevice
    mapping: dcim.devices
    identifiers: ["name"]
    fields:
      - name: name
        mapping: name
      - name: description
        mapping: description
      - name: status
        mapping: status.value

  - name: InfraInterface
    mapping: dcim.interfaces
    identifiers: ["device", "name"]
    fields:
      - name: name
        mapping: name
      - name: device
        mapping: device.name
        reference: InfraDevice
```

### Relationship handling

The Infrahub adapter automatically resolves relationships based on the schema:

- **One-to-one relationships**: Resolved using the unique identifier of the related node
- **One-to-many relationships**: Resolved as a list of unique identifiers

```yaml
fields:
  # One-to-one relationship
  - name: site
    mapping: site.name
    reference: LocationSite

  # One-to-many relationship
  - name: tags
    mapping: tags
    reference: BuiltinTag
```

### Destination identity for writes

Infrahub must be able to find each planned object by a key: the kind's human-friendly ID or one of its uniqueness constraints. List every field of one such key in `identifiers` and map it in `fields`. The key cannot contain a value that Infrahub allocates or computes. Sync checks this against the destination schema before it extracts data, and refuses a kind without such a key. See [Destination key for Infrahub writes](../reference/schema-mapping.mdx#destination-key-for-infrahub-writes) for the rules and an example.

## Lineage tracking

Infrahub records three properties on each attribute and each relationship edge: a source, an owner, and a protection flag. An import sets them from the `source`, `owner`, and `protect` settings of the Infrahub destination. Infrahub also records which account last changed each value, and when. A plan shows that record for each value it updates.

### The import account

The import account is the Infrahub account that owns the API token the worker uses. The import reads it at the start of each plan and each apply.

- When the package names no `source`, the import records the import account as the source of every attribute and relationship edge it writes.
- Infrahub records the import account as the account that created and last changed each value the import writes.
- A plan records its import account. Apply refuses a saved plan when its own import account is different, and the error names both accounts. Apply also refuses a saved plan made by an earlier release, because that plan records no import account. Create a new plan in that case.

Create one Infrahub account for each import, for example `netbox`, and give its token only to that import:

- With an administrator token, the administrator account becomes the source of every value the import writes.
- Two imports that share one token write with the same account, so `updated_by` cannot tell their changes apart.

### Name a source or an owner

`source` and `owner` each name one node by kind and name:

```yaml
destination:
  name: infrahub
  settings:
    url: "https://infrahub.example.com"
    token:
      $credential: infrahub-token
    source:
      kind: CoreAccountGroup
      name: data-sync
    owner:
      kind: CoreAccountGroup
      name: network-team
    protect: false
```

- The kind must be `CoreAccount`, `CoreAccountGroup`, `CoreRepository`, or `CoreReadOnlyRepository`.
- Registration refuses a `source` or an `owner` given as a bare name, such as `owner: network-team`, and a kind outside this list.
- At the start of a plan, before it reads the source system, the import looks up each named node. When the node does not exist, the plan stops and names the setting, the kind and the name, for example: "The setting `owner` names `CoreAccountGroup` `network-team`, which does not exist." The import does not fall back to another node. Apply makes the same lookup before its first write.
- The import looks up a named node on the destination branch the run uses. On Infrahub 1.10.6 the schema marks all four kinds as branch-agnostic: each node of these kinds is the same node on every branch. So renaming or deleting the node on any branch, `main` included, also changes it on the branch the run uses, and the next plan or apply stops with the cause above.

A named `source` replaces the import account as the source of every value the import writes.

### Owner of the values an import writes

There is no default owner. Name the team responsible for the data as the `owner`.

- The owner goes on the attributes of each node the run creates, and on each relationship edge the run adds, including an edge added to a node that already exists.
- An update does not change the owner of a value that already exists, including a value with no owner.
- When the package names an owner, `runs plan` shows the notice "The owner setting applies only to values this run creates."

To set the owner of data that already exists in Infrahub, set it in Infrahub itself: an Infrahub update mutation that carries `owner` on an attribute or a relationship edge changes the owner of that value. Running a sync again does not change it.

### Protect the values an import writes

`protect` is off by default.

- With `protect` on, the import marks every attribute and relationship edge it creates or changes as protected.
- With `protect` off, the import sends no protection flag. A value that is already protected keeps its protection. This includes values that an earlier release protected, because earlier releases protected every value they wrote.
- On Infrahub 1.10.6, Infrahub stores the protection flag with or without an owner, and an import still changes a protected value.

What protection does in the web interface was not tested against a running Infrahub. The Infrahub 1.10.6 web interface code disables the edit field of a protected value for accounts other than its owner, and does not disable it when the value has no owner. So without an owner, the flag has no effect on who can edit the value.

### Values written before this release

The import does not rewrite the properties of values it wrote before this release.

- The next time an import writes a value again, the import records the import account, or the named `source`, as its source.
- The owner and the protection flag of that value stay as they are.

### Resource-pool allocations

A relationship edge that Infrahub allocates from a resource pool is the one exception. On such an edge the import sends no source, owner, or protection flag, so the pool stays the source that Infrahub records. No current import allocates from a resource pool.

### Who last changed a value

`runs plan --detail` shows, for each field that a proposed update changes, the account that last changed the value and when:

```text
  last change: description (attribute): updated_by=Alice, updated_at=2026-10-01T08:00:00+00:00
```

- A proposed create has no last-change line.
- For a cardinality-many relationship, the line shows the edge that changed most recently.
- When Infrahub holds no record for a field, the line shows `not recorded`, and the plan continues.
    - Infrahub records this metadata from version 1.7.0. On an earlier version, or when the plan cannot read the Infrahub version, the import does not read the metadata, and every field shows `not recorded`.
    - On Infrahub 1.10.6, only a relationship with no edge shows `not recorded`.
- The plan only displays this record. It does not stop a change.
- When the import reads this record, on Infrahub 1.7.0 or later, it reads the destination in full on every plan and does not use the incremental read.

### Permissions of the import account

The import account needs these Infrahub permissions. They were measured on Infrahub 1.10.6.

| Permission | Default branch | Any other branch | Used for |
|------------|----------------|------------------|----------|
| Global `edit_default_branch` | Required | Not required | Every create and update |
| Object `view` on each mapped destination kind, and on the peer kind of each mapped relationship | Required, decision `allow_default` | Required, decision `allow_other` | The plan's read of the destination, the lookup of each related node, and apply's read of a node's current relationship peers |
| Object `create` on each kind the import writes | Required, decision `allow_default` | Required, decision `allow_other` | Every create and update, because the import writes both as an upsert |
| Object `update` on each kind the import writes | Required, decision `allow_default` | Required, decision `allow_other` | Every create and update, for the same reason |
| Object `view` on the kind of a named `source` or `owner` | Required, decision `allow_default` | Required, decision `allow_other` | The lookup of the named node, only when the package names one |

The import reads only the name of a named node, so it needs `view` on that kind only:

- `CoreAccount`: needed only when `source` or `owner` names a `CoreAccount`.
- `CoreAccountGroup`: needed only when `source` or `owner` names a `CoreAccountGroup`.
- `CoreRepository` or `CoreReadOnlyRepository`: needed only when `source` or `owner` names a node of that kind.

The import account needs no permission for:

- reading its own account, the Infrahub version, and the schema;
- reading other accounts, unless the package names a `CoreAccount`;
- deleting, because apply does not delete;
- setting the source, the owner, or the protection flag;
- reading who last changed a value.

When Infrahub refuses a request with HTTP 403, the run reports a missing permission and quotes the permission Infrahub names. This applies to a plan and to an apply. A refused token is reported as a token problem. `diff`, `sync` and `apply` print the cause on a `cause:` line, and `runs results RUN_ID` shows it under `cause` and `infrahub_error`. If Infrahub refuses only the version query with HTTP 403, the plan continues and does not record who last changed each value.

## Common issues and troubleshooting

### Authentication errors

- Check that the worker environment sets the variable that the package's token credential names, for example `INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN`. On a Compose deployment, run `docker compose up -d --wait` after you change `.env`.
- Check that the token has permission to read and write the target branch.
- Check the `url` in the registered package with `configs show <config-id> --version <version>`. The worker does not read `INFRAHUB_ADDRESS`.

### Schema mismatch errors

- Check that every kind in `schema_mapping` exists in the destination schema, on the branch the plan uses.
- Load or update the schema with `infrahubctl schema load`. See [Load an example schema into Infrahub](./choosing-an-adapter.mdx#load-an-example-schema-into-infrahub).
- Check that field names match the Infrahub schema attribute and relationship names.

### No writable destination identity

- An error containing `no complete writable destination convergence identity` names the unusable key fields. See [Destination key for Infrahub writes](../reference/schema-mapping.mdx#destination-key-for-infrahub-writes).
- After an upgrade, create and review a new plan before you apply. A plan saved by an earlier release can have a different schema fingerprint, and apply refuses it.

### Relationship resolution failures

- Check that each referenced kind has its own `schema_mapping` entry. Sync writes referenced kinds first unless an `order` list in the package overrides that order.
- Verify the unique identifier used in references matches the target object's identifier
- Check logs for "Unable to find ... in the Store" messages

### Branch operations

- Check that the target branch exists in Infrahub. List branches with `infrahubctl branch list`.
- Create a branch with `infrahubctl branch create <name>`.

### SSL certificate issues
<!-- vale Infrahub.sentence-case = YES -->

- `verify_ssl: false` turns off certificate verification. Use it only for development.
- To trust an internal certificate authority, see [Use custom CA certificates](../custom-certificates.mdx). That page also describes the current limit of the Compose deployment.
