## What is Prometheus?
<!-- vale on -->

Prometheus is an open-source monitoring and alerting toolkit that collects and stores metrics as time series data. It is widely used for monitoring infrastructure, applications, and services through its pull-based model and powerful query language (PromQL).

## Requirements

<!-- vale Infrahub.branded-terms-case-swap = NO -->
This adapter uses the [prometheus-client](https://pypi.org/project/prometheus-client) library for parsing the Prometheus exposition format.
<!-- vale Infrahub.branded-terms-case-swap = YES -->

## Sync directions supported

- Prometheus → Infrahub

:::note
Currently, the Prometheus adapter supports only **one-way synchronization** from Prometheus to Infrahub. Writing data back to Prometheus is not supported as Prometheus is a read-only metrics store.
:::

## Operating modes

The Prometheus adapter supports two modes of operation:

### Scrape mode (default)

Directly scrapes a Prometheus text exposition endpoint (for example, from `node_exporter`, application metrics endpoints). Best for collecting metrics from individual exporters.

### API mode

Queries the Prometheus HTTP API using PromQL. Best for aggregating data from multiple targets or performing complex queries with joins.

## Configuration

### Scrape mode configuration

  <TabItem value="scrape" label="Scrape Mode" default>

  ```yaml
  ---
  name: from-node-exporter
  source:
    name: prometheus
    settings:
      mode: scrape
      url: "http://localhost:9100"
      endpoint: "/metrics"
      timeout: 10           # Optional, seconds
      verify_ssl: true      # Optional

  destination:
    name: infrahub
    settings:
      url: "http://localhost:8000"
  ```

  </TabItem>
  <TabItem value="api" label="API Mode">

  ```yaml
  ---
  name: from-prometheus-api
  source:
    name: prometheus
    settings:
      mode: api
      url: "http://prometheus:9090"
      endpoint: "/api/v1/query"
      promql:
        resources:
          node_uname_info: 'node_uname_info'
          node_memory_MemTotal_bytes: 'node_memory_MemTotal_bytes'
          node_cpu_idle_count: 'count(node_cpu_seconds_total{mode="idle"}) by (instance)'

  destination:
    name: infrahub
    settings:
      url: "http://localhost:8000"
  ```

  </TabItem>
</Tabs>

Each key under `promql.resources` is a resource name you choose; `schema_mapping.mapping` refers to
that resource name, not to the PromQL query. In API mode, naming the resource after the metric it
mostly resembles — as above — keeps `mapping:` consistent with the scrape-mode examples below. A
resource such as `node_cpu_idle_count`, built from an aggregating query with no single underlying
metric, needs its own distinct name.

### Environment variables

| Variable | Description |
|----------|-------------|
| `PROM_URL` or `PROM_ADDRESS` | Prometheus server URL for direct adapter use (takes precedence over `settings.url`); registered packages use their configured or resolved URL |
| `PROM_TOKEN` | Bearer token for authentication |
| `PROM_USERNAME` | Username for basic authentication |
| `PROM_PASSWORD` | Password for basic authentication |

### Settings reference

| Setting | Type | Required | Default | Description |
|---------|------|----------|---------|-------------|
| `mode` | string | No | `scrape` | Operating mode: `scrape` or `api` |
| `url` | string | Conditional | - | Prometheus server or exporter URL. Set it in a registered package. For direct adapter use, set it or `PROM_URL`/`PROM_ADDRESS`; an environment variable takes precedence. |
| `endpoint` | string | No | `/metrics` (scrape) or `/api/v1/query` (API) | Target endpoint |
| `timeout` | number | No | 10 | Request timeout in seconds |
| `verify_ssl` | boolean | No | true | Verify SSL certificates |
| `auth_method` | string | No | `none` | Authentication: `none`, `basic`, or `bearer` |
| `username` | string | No | - | Username for basic auth |
| `password` | string | No | - | Password for basic auth |
| `token` | string | No | - | Token for bearer auth |
| `headers` | object | No | - | Additional HTTP headers |
| `params` | object | No | - | Query parameters for scrape mode |
| `promql.resources` | object | No | - | PromQL queries for API mode (`resource_name`: `query`) |

## Schema mapping

The Prometheus adapter normalizes metrics into a consistent format for schema mapping:

```yaml
# Each metric sample contains:
# - __metric__: metric name
# - labels: { label_key: label_value, ... }
# - value: numeric value
# - timestamp: optional timestamp
# - help: metric help text
# - type: metric type (counter, gauge, etc.)
```

### Basic field mapping

Map fields using dot notation to access metric properties:

```yaml
schema_mapping:
  - name: VirtualizationVirtualMachine
    mapping: node_uname_info          # Metric name to load from
    identifiers: ["name"]
    fields:
      - name: name
        mapping: labels.nodename      # Access label value
      - name: os_name
        mapping: labels.sysname
      - name: os_kernel
        mapping: labels.release
```

### Using the lookup function

The `lookup()` function joins data from a different metric. It belongs in a schema_mapping
entry's `transforms` list, alongside `fields`:

```yaml
schema_mapping:
  - name: VirtualizationVMNetworkInterface
    mapping: node_network_mtu_bytes
    identifiers: ["virtual_machine", "name"]
    fields:
      - name: virtual_machine
        mapping: vm_name
      - name: name
        mapping: labels.device
      - name: mtu
        mapping: value
      - name: mac_address
        mapping: mac_addr_t

    transforms:
      # Syntax: lookup(metric_name, match_criteria, value_path [, default])

      # Join the MAC address from node_network_info by the interface's "device"
      # label. This example reads one target, so device identifies an interface.
      - field: vm_name
        expression: "{{ lookup('node_uname_info', {}, 'labels.nodename', 'unknown') }}"
      - field: mac_addr_t
        expression: "{{ lookup('node_network_info', 'labels.device', 'labels.address', '') }}"
```

Choose a `match_criteria` label that both metrics actually carry — check both in your scraped or
queried data first. `labels.device` works above because both metrics describe network interfaces.
It would not work to join, say, `node_uname_info` (labels: `nodename`, `sysname`, ...) with
`node_memory_MemTotal_bytes` (no labels at all in raw `node_exporter` output): neither metric has
`device`, and neither has any label the other one has. Without a fourth `lookup()` argument, a
missing value can leave a later transform field unset; pass a default for an optional metric. For
that pairing, see the empty-criteria
pattern under [Example: Node Exporter to Infrahub](#example-node-exporter-to-infrahub) below, which
is safe there only because scrape mode always covers exactly one target per run.

An empty `match_criteria` (`{}`, `''`, or `'*'`) does not match against the current record at
all — it returns the first sample of `metric_name` that has a value at `value_path`, out of every
record being processed. Use it only when the looked-up metric has a single, unambiguous sample
(guaranteed by the single-target nature of scrape mode) or you have separately guaranteed the pool
holds exactly one target's data; otherwise pass a dotted path shared by both metrics. The lookup
indexes one label and keeps the last sample for each value. A `device` label can repeat across
targets, while an `instance` label repeats across interfaces. For interfaces on multiple targets,
run this example once per target in scrape mode. An API-mode result that combines targets cannot
use this single-key lookup to join on both target and interface. In API mode, `labels.instance`
is usually available because Prometheus adds it during scraping. It is not guaranteed on every
query result. An aggregating PromQL expression (`sum by (...)`, `avg by (...)`, and similar)
drops any label, including `instance`, that its `by`/`without` clause does not keep. A scalar result
carries no labels at all. Check the actual response for your query before relying on
`labels.instance` as a join key, the same as for any other `match_criteria`.

### Lookup function parameters

| Parameter | Description |
|-----------|-------------|
| `metric_name` | Name of the metric to look up |
| `match_criteria` | Dotted path (for example `labels.nodename`) that must have the same value on the current record and the looked-up record. Leave empty to get the first sample of `metric_name` that has `value_path`, without matching against the current record. |
| `value_path` | Dot-notation path to extract (for example: `value`, `labels.hostname`) |
| `default` | Optional fourth argument returned if no matching sample or value exists. Use this argument for optional metrics; an `or` expression cannot prevent missing intermediate transform fields. |

## Example: Node Exporter to Infrahub

<ReferenceLink title="Node Exporter Example" url="https://github.com/opsmill/infrahub-sync/tree/main/examples/prometheus_to_infrahub%20(node_exporter)" openInNewTab />

This example syncs `node_exporter` metrics to create virtual machine records in Infrahub. It uses
`mode: scrape` against a single exporter URL (`examples/prometheus_to_infrahub (node_exporter)/package.yml`),
so every metric pool below holds samples from exactly one target. That single-target guarantee —
not the label content of any metric — is what makes the empty `{}` lookup calls below correct: each one
returns the pool's only sample of that metric, and there is never a second target's sample to
mix in. `node_memory_MemTotal_bytes`, `node_netstat_Ip_Forwarding`, `node_nf_conntrack_entries_limit`,
and `node_time_seconds` also have no labels of their own in raw `node_exporter` output, so a
label-based `match_criteria` is not available here even if you wanted one.

:::warning
Do not copy these `{}` lookup calls into a configuration that aggregates more than one target — for example an
API-mode `schema_mapping` reusing these same metric names against `promql.resources` results for
several instances. There, `{}` returns the first target's sample for every record, silently
attaching one host's data to another. Run one scrape-mode configuration per target for interface
lookup calls; `labels.instance` alone does not identify an interface. See
[Using the lookup function](#using-the-lookup-function) above.
:::

```yaml
schema_mapping:
  - name: VirtualizationVirtualMachine
    mapping: node_uname_info
    identifiers: ["name"]
    fields:
      - name: name
        mapping: labels.nodename
      - name: os_name
        mapping: labels.sysname
      - name: mem_total_bytes
        mapping: mem_total_t
      - name: status
        mapping: status_t

    transforms:
      # Safe with {} only because scrape mode covers exactly one target per run — see the warning above
      - field: mem_total_t
        expression: "{{ lookup('node_memory_MemTotal_bytes', {}, 'value') or 0 }}"

      # Derive status from exporter availability — also single-target-safe
      - field: status_t
        expression: "{{ 'active' if ((lookup('node_time_seconds', {}, 'value') | float) > 0) else 'unknown' }}"

  - name: VirtualizationVMNetworkInterface
    mapping: node_network_mtu_bytes
    identifiers: ["virtual_machine", "name"]
    fields:
      - name: virtual_machine
        mapping: vm_name
      - name: name
        mapping: labels.device
      - name: mtu
        mapping: value

    transforms:
      # Link to the parent VM — single-target-safe for the same reason
      - field: vm_name
        expression: "{{ lookup('node_uname_info', {}, 'labels.nodename') or 'unknown' }}"
```

## Common issues and troubleshooting

### Connection errors

- Verify the exporter or Prometheus server is running and accessible
- Check firewall rules allow connections to the metrics endpoint
- For scrape mode, ensure the endpoint returns Prometheus text format

### Empty results

- In scrape mode, verify the `/metrics` endpoint returns data
- In API mode, test your PromQL queries directly in Prometheus UI first
- Check that `schema_mapping.mapping` matches actual metric names

### Lookup failures

- Ensure the metric being looked up exists in the scraped data
- Verify label names match exactly (case-sensitive)
- Pass a dotted `match_criteria` path (for example `labels.nodename`) to join on a shared label; an empty one returns the first sample instead, which is rarely what a per-record join needs
- Provide default values for optional lookup operations

### Authentication issues

- For basic auth, set both `username` and `password`
- For bearer auth, set `auth_method: bearer` and provide `token`
- Use environment variables (`PROM_USERNAME`, `PROM_PASSWORD`, `PROM_TOKEN`) for credentials

### API mode specific

- Ensure `promql.resources` is a dict mapping resource names to PromQL queries
- Verify queries return vector or scalar results (other types not supported)
- Test queries in Prometheus UI before using in configuration
