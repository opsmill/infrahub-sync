## Use this adapter

In a [configuration package](../configuration-package.mdx), name `slurpitsync` as the source. Then register the package, create and review a plan, and apply the plan, as described in [Run a sync](../running-a-sync.mdx).

On a Compose deployment, from source or from a release package, the worker receives only the Infrahub, NetBox, and Nautobot tokens, so this adapter's credentials cannot reach it in this release. See [Credentials on a Compose deployment](./choosing-an-adapter.mdx#credentials-on-a-compose-deployment).

The example package is [`examples/slurpit_to_infrahub/package.yml`](https://github.com/opsmill/infrahub-sync/blob/feature/v3-develop/examples/slurpit_to_infrahub/package.yml).

<!-- vale off -->
## What is Slurp’it?
<!-- vale on -->

Slurp’it retrieves and stores network data — devices, sites, interfaces, and planning results — in a structured database, discovered by scanning a network with its installation wizard.

## Requirements

This Adapter uses the [Slurp’it SDK](https://pypi.org/project/slurpit-sdk), distributed as `slurpit-sdk` on PyPI.
It is available through the optional `slurpit` extra (`slurpit-sdk>=0.9.52,<0.10`), which uv marks
as conflicting with the `service` extra the default Sync image and the standard development setup
both use — `uv sync --extra service --extra slurpit` fails. The `prefect` and `slurpit` extras
alone do not install the service dependencies needed by a Sync worker. To use the SDK
with a Sync worker, build a custom service image: copy the repository Dockerfile
and add this command in the build stage after the final `uv sync` command:

```dockerfile
RUN uv pip install --python /opt/infrahub-sync/venv/bin/python \
    'ariadne-codegen==0.15.3' 'slurpit-sdk>=0.9.52,<0.10' \
    && uv pip check --python /opt/infrahub-sync/venv/bin/python
```

The current SDK requires `httpx>=0.27,<0.28`. The custom image also uses `ariadne-codegen==0.15.3` because the default service image's 0.18 release requires httpx 0.28. The default service image keeps httpx 0.28 and real urllib3.
The `service` and `slurpit` extras are marked as conflicting in uv because `uv sync --extra service --extra slurpit` cannot preserve the default service resolution.

## Sync directions supported

- Slurp’it → Infrahub

Slurp’it is a source only. Infrahub Sync does not write to Slurp’it.

## Schema

Our `infrahub` repository contains an **example schema** that serves as a starting point for syncing Slurp’it data into Infrahub.
This schema follows best practices for Infrahub, **but it does not map the Slurp’it data model one-to-one** since Infrahub may have additional use cases and Slurp’it can be customizable.

### Installing the example schema

Download the schema, then load it into the destination Infrahub as described in [Load an example schema into Infrahub](./choosing-an-adapter.mdx#load-an-example-schema-into-infrahub):

```bash
curl -o schema.yml https://raw.githubusercontent.com/opsmill/infrahub/refs/heads/stable/models/examples/slurpit/slurpit.yml
```

## Configuration

`infrahub-sync` allows defining what gets synchronized from a source to a destination. Register
`examples/slurpit_to_infrahub/package.yml` — a complete [configuration package](../configuration-package.mdx) —
directly. Its `configuration:` body matches `config.yml`, kept alongside it for reference only:
`config.yml`'s `$credential` references resolve only through registration, not through the legacy
config.yml discovery path.

<ReferenceLink title="package.yml" url="https://github.com/opsmill/infrahub-sync/blob/feature/v3-develop/examples/slurpit_to_infrahub/package.yml" openInNewTab />

### Configuration parameters

The `source.name` is set to `slurpitsync`, instructing `infrahub-sync` to use the Slurp’it adapter.

The settings dictionary is passed directly to the Slurp’it Python SDK for authentication and connection details.
Some of these parameters may be found in the [Slurp’it SDK Repository](https://gitlab.com/slurpit.io/slurpit_sdk).

Below is a snippet from the example `package.yml` file. Both credentials are declared in a
top-level `credentials` block and resolved by the service worker from its own environment — no
credential value is ever written into the registered package:

```yaml
---
format_version: 1
configuration:
  name: from-slurpit
  source:
    name: slurpitsync
    settings:
      url: "https://<SLURPIT-ENDPOINT>"
      api_key:
        $credential: slurpit-api-key

  destination:
    name: infrahub
    settings:
      url: "http://localhost:8000"
      token:
        $credential: infrahub-token
  # ... schema_mapping omitted, see the full file

credentials:
  slurpit-api-key:
    provider: env
    identifier: INFRAHUB_SYNC_CREDENTIAL_SLURPIT_API_KEY
  infrahub-token:
    provider: env
    identifier: INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN
```

The worker resolves these references from its own environment. Give both
`INFRAHUB_SYNC_CREDENTIAL_SLURPIT_API_KEY` and `INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN` to the custom service
worker.

The bundled [Compose deployment](../compose-deployment.mdx) cannot run this Slurp’it package.
Its worker uses the bundle's bound image, which does not include the Slurp’it SDK, and the
worker does not receive `INFRAHUB_SYNC_CREDENTIAL_SLURPIT_API_KEY`. Registering the package does not install the SDK
or pass the key to that worker. To run it with a service worker, deploy a worker image that
includes the SDK and give `INFRAHUB_SYNC_CREDENTIAL_SLURPIT_API_KEY` to that worker's environment.

See [Configuration package](../configuration-package.mdx) for the full envelope reference.

### Schema mapping

The configuration file allows mapping Slurp’it data to the Infrahub schema, which has been designed to loosely align with the Slurp’it data model.
Below is an example showing how to:

- Set the destination Infrahub model (`OrganizationGeneric`)
- Map source data from Slurp’it and run a custom function `unique_vendors`
- Specify field mappings between Slurp’it and Infrahub models

```yaml
schema_mapping:
  - name: OrganizationGeneric
    mapping: unique_vendors
    fields:
      - name: name
        mapping: brand
      - name: type
        static: "Vendor"
```

Schema mapping connects Slurp’it fields to Infrahub's Node attributes and relationships.

Each field can either map directly to a Slurp’it field or be statically defined.
This table highlights the available `mappings` the adapter has to gather and normalize data from Slurp’it

| Name | Description |
| --- | --- |
| `unique_vendors` | Retrieves devices through the async SDK and returns each distinct brand. |
| `unique_device_type` | Retrieves devices through the async SDK and returns each distinct brand, device type, and operating system combination. |
| `device.get_devices` or `site.get_sites` | Retrieves devices or sites through the SDK. Other dotted SDK methods are rejected so a data load cannot call an SDK write method. |
| `planning_results`.`<planning_name>` | Retrieves results for the planning whose SDK `slug` matches the suffix. For example, `planning_results.routing-table` uses the planning slug `routing-table`. |
| `filter_networks` | The `filter_networks` function processes a list of network entries, normalizing the network and mask fields, and filters out unwanted networks based on predefined "ignore" prefixes (such as 0.0.0.0/0 and 127.0.0.0/8). It returns a list of filtered, normalized networks, excluding those with prefixes deemed unnecessary or invalid. `normalized_prefix` holds the network address and CIDR prefix length, so a prefix that Slurp’it reports with host bits (for example `10.0.0.5/24`) becomes `10.0.0.0/24`. A `Network` and `Mask` pair, including a mask written in dotted IPv4 form, gives the same value as the equivalent CIDR text. |
| `filter_interfaces` | Normalizes interface IP addresses and matches them against previously loaded network prefixes. The `prefix` it sets uses the same network-address/CIDR form as `normalized_prefix`, so an address is related to its prefix whether or not Slurp’it reported the prefix with host bits. |

The current SDK has a `site.get_sites` API, which the example maps to locations.
