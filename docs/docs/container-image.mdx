title: Container image
---

Infrahub Sync ships as one container image. It carries the Sync API, the service
worker, the deployment bootstrap, and one-off CLI or Python commands, so a deployment
runs one artifact instead of four.

## Where the image lives

Every release publishes the image to the OpsMill registry:

```text
registry.opsmill.io/opsmill/infrahub-sync
```

The release workflow builds the image from the release commit, smoke-tests every
platform, and only then pushes, tags, signs, and attaches the bills of materials.

## Tags

| Tag | Applied to | Moves? |
| --- | --- | --- |
| `<version>`, for example `3.0.0` | Every release, stable or pre-release | No. It names one release. |
| `latest` | Stable releases only | Yes. It follows the newest stable release. |

Tags carry the bare version, with no `v` prefix, the same string as the Git tag and
the PyPI version. A pre-release never moves `latest`. Neither does a stable patch for
an older line: `latest` only moves when the release is also the latest release on
GitHub.

Pin a version tag in anything you deploy. `latest` is a convenience for trying the
image, not a deployment target.

## Supported platforms

Each tag is a multi-platform manifest list:

- `linux/amd64`
- `linux/arm64`

Docker pulls the platform that matches the host. Both platforms pass the same smoke
test before the release pushes either one.

## Pull the image

Until the 3.0.0 release, the registry project is private and open to invited testers
only. Sign in with the account you were given before you pull:

```bash
docker login registry.opsmill.io
```

Then pull a version:

```bash
docker pull registry.opsmill.io/opsmill/infrahub-sync:<version>
```

From 3.0.0, the project is public and the `docker login` step is no longer needed.

## Command forms

The image defaults to the Sync API. Every other form is an explicit override, because
the module and console entry points already name the commands. Replace `IMAGE` with
the reference you pulled, such as `registry.opsmill.io/opsmill/infrahub-sync:<version>`.

| Purpose | Command |
| --- | --- |
| Sync API | `docker run IMAGE` |
| Service worker | `docker run IMAGE python -m infrahub_sync.service.worker --pool POOL` |
| Deployment bootstrap | `docker run IMAGE python -m infrahub_sync.service.deploy` |
| CLI | `docker run IMAGE infrahub-sync --help` |
| Python | `docker run IMAGE python -c "import infrahub_sync"` |

To run the whole service, with its database, Prefect, and object storage, use the
[Compose deployment](./compose-deployment.mdx).

## Writable paths

The image runs as the numeric user `10001:10001`. The interpreter, the installed
distribution, and the recorded lock stay owned by root and are not writable, so the root
filesystem can be mounted read-only with writable mounts at exactly three paths.

| Path | Holds |
| --- | --- |
| `/var/lib/infrahub-sync` | `HOME` |
| `/var/lib/infrahub-sync/prefect` | `PREFECT_HOME` |
| `/tmp/infrahub-sync` | `TMPDIR` |

Hand each mount to the runtime user. A mount takes its own ownership, so a bare
`--tmpfs` arrives owned by root and the container cannot write to it however the image
created the directory underneath:

```bash
docker run --rm --read-only \
  --tmpfs /var/lib/infrahub-sync:uid=10001,gid=10001,mode=0700 \
  --tmpfs /var/lib/infrahub-sync/prefect:uid=10001,gid=10001,mode=0700 \
  --tmpfs /tmp/infrahub-sync:uid=10001,gid=10001,mode=0700 \
  IMAGE infrahub-sync --help
```

A named volume or host bind takes the same treatment: the mounted directory has to be
owned by `10001:10001` before the container starts.

## Image labels

Each published image carries the standard OCI labels that trace it back to its
release:

| Label | Value |
| --- | --- |
| `org.opencontainers.image.source` | `https://github.com/opsmill/infrahub-sync` |
| `org.opencontainers.image.version` | The release version |
| `org.opencontainers.image.revision` | The full commit SHA the image was built from |

Read them with `docker image inspect`:

```bash
docker image inspect --format '{{json .Config.Labels}}' \
  registry.opsmill.io/opsmill/infrahub-sync:<version>
```

## Verify the signature and the bills of materials

The release workflow signs each image with [cosign](https://docs.sigstore.dev/). The
signature uses no long-lived key: it is bound to this repository's GitHub Actions
identity. The workflow also attaches an
SPDX JSON and a CycloneDX JSON bill of materials as signed attestations.

Check the signature:

```bash
cosign verify registry.opsmill.io/opsmill/infrahub-sync:<version> \
  --certificate-identity-regexp 'https://github.com/opsmill/infrahub-sync/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Check both bills of materials, with the same identity flags:

```bash
cosign verify-attestation --type spdxjson \
  --certificate-identity-regexp 'https://github.com/opsmill/infrahub-sync/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  registry.opsmill.io/opsmill/infrahub-sync:<version>

cosign verify-attestation --type cyclonedx \
  --certificate-identity-regexp 'https://github.com/opsmill/infrahub-sync/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  registry.opsmill.io/opsmill/infrahub-sync:<version>
```

Each command exits non-zero when the signature or attestation is missing or was not
issued to this repository's workflows. Until 3.0.0, run `docker login
registry.opsmill.io` first, because cosign reads the same private registry.

## Build the image locally

To build from a checkout instead of pulling, run from the repository root:

```bash
docker build -t infrahub-sync:local .
```

A local build is unsigned and carries no release labels. Use it for development and
testing. Deploy from a published version tag.
