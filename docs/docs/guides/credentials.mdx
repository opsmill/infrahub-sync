---
title: Manage stored credentials
---

A sync needs a token or a password to read its source and to write to its destination. An
administrator stores each one in the Sync API as a stored credential, under a name. A
configuration package names the credential in its source block and in its destination block. The
package never holds the value.

The Sync API encrypts each value. When a worker runs a stage of a run, it asks the Sync API for
the values that the run's package names, and uses them for that stage only. A worker needs no
credential variable in its own environment, so every worker can run every package.

The commands on this page need a CLI connected to the Sync API, as
[Connect the CLI to the Sync API](../running-a-sync.mdx#connect-the-cli-to-the-sync-api)
describes. From a repository checkout, run each command as `uv run infrahub-sync <command>`.

This page covers the CLI. A page for stored credentials in the web interface is not part of this
build.

## Who can do what

| Action | Command | Who |
| --- | --- | --- |
| List credentials | `credentials list` | every signed-in account |
| View one credential | `credentials show NAME` | every signed-in account |
| Create a credential | `credentials create NAME` | administrator |
| Replace the value | `credentials set NAME` | administrator |
| Change the description | `credentials describe NAME TEXT` | administrator |

No command and no route for accounts returns a value, including the answer to a creation. The
list and the view show which fields a credential holds, never what they hold.

A credential cannot be renamed. This build has no command that deletes a credential.

## The fields of a credential

A credential holds one of three sets of fields:

- `token`
- `username` and `password`
- `username` and `token`

Every other set is refused, including all three fields together. Each value is 1 to 4,096
characters with no control character.

The fields a block needs depend on its adapter and its authentication method:

| Adapter | Fields the block needs |
| --- | --- |
| `infrahub`, `netbox`, `nautobot`, `ipfabricsync`, `slurpitsync` | `token` |
| `aci` | `username` and `password` |
| `genericrestapi`, `peeringmanager` | By `auth_method`: `token`, `x-auth-token`, `api-key` and `key` need `token`; `basic` needs `username` and `password`; `none` needs no credential. The default method is `token`. |
| `prometheus` | By `auth_method`: `bearer` needs `token`; `basic` needs `username` and `password`; `none` needs no credential. The default method is `none`. |

A block whose method needs no credential must not name one. Validation reports
`credential-not-used` for it.

## Create a credential

The name is what a package writes after `credential:`. It starts with a lowercase letter and
holds 1 to 63 lowercase letters, digits and hyphens, for example `netbox-token`.

The command never takes a value as an argument. Without `--username`, it asks for a token and
does not echo it:

```bash
infrahub-sync credentials create netbox-token --description "NetBox lab, read-only token"
```

From a script, send the token on standard input:

```bash
printf '%s' "$NETBOX_TOKEN" | infrahub-sync credentials create netbox-token --token-stdin
```

For a username and a password, give `--username`. The command then asks for the password, or
reads it with `--password-stdin`:

```bash
infrahub-sync credentials create apic-account --username sync-reader
```

For a username and a token, give `--username` and `--token-stdin`.

The command prints the credential without its value: its name, its description, the names of its
fields, its revision, and the account and time of its creation. A new credential has revision 1.

Create each credential before you register a package that names it. Registration refuses a
package that names a credential that does not exist, or one that lacks a field the block needs.

## Name a credential in a package

Each adapter block takes one `credential` key, next to the adapter name and `settings`:

```yaml
configuration:
  source:
    name: netbox
    credential: netbox-token
    settings:
      url: https://netbox.example.com
  destination:
    name: infrahub
    credential: infrahub-token
    settings:
      url: http://infrahub-server:8000
```

The worker fills the block's credential settings from the stored fields. Do not write `token`,
`username` or `password` in `settings`; a package that holds one is refused.

Two blocks can name the same credential, and several packages can name it too.

To point a block to another credential, edit the package and register it as a new version with
`configs version`. A change of the value needs no new version.

## Change a value

```bash
infrahub-sync credentials set netbox-token
```

The command reads the new value in the same way as `create`, and prints the new revision. The
new value replaces every field, so give `--username` again for a credential that has one.

Every run that starts a stage afterwards uses the new value. No package is registered again and
no worker is restarted. When a value changes between a plan and its apply, the apply uses the
new value and is not refused.

`credentials describe NAME TEXT` changes the description only. The revision stays.

## When a run cannot get its values

The Sync API checks the credentials of a version before it starts a run, and refuses the request
with HTTP 422 when a credential is missing or lacks a field:

| Code | Meaning | What to do |
| --- | --- | --- |
| `credential-not-found` | A block names a credential that does not exist. | An administrator runs `infrahub-sync credentials create <name>`. |
| `credential-field-missing` | The credential lacks a field that the block needs. The message names the fields. | An administrator runs `infrahub-sync credentials set <name>` with those fields. |
| `credential-method-unknown` | The block's `auth_method` is not one that its adapter accepts. | Register a new version with an accepted method. |
| `credential-format-removed` | The version uses the removed `credentials` block or `$credential` references. | Register the package again with `credential: <name>` in each block. See [Versions registered with the earlier format](#versions-registered-with-the-earlier-format). |

`configs validate` reports the first three as findings of a registered version.

A stage can still fail to get its values after the run started. The run then fails before it
reads the source, and its failure cause names the reason and the next action:

- The worker could not reach the Sync API. Check `INFRAHUB_SYNC_API_URL` on the worker.
- The Sync API refused the worker token. Set `INFRAHUB_SYNC_WORKER_TOKEN` to the same value on
  `sync-api` and on every worker.
- The credential was removed or lost a field after the run was accepted.
- The Sync API cannot decrypt the value with its current key. See [The encryption key](#the-encryption-key).

No refusal and no failure cause holds a value.

## The `worker` account

The workers call the Sync API as one account named `worker`. The deployment's environment
defines it, in the way it defines `admin`:

- `INFRAHUB_SYNC_WORKER_TOKEN` is its token. Set the same value on `sync-api` and on every
  `sync-worker`. It follows the rules of `INFRAHUB_SYNC_ADMIN_ACCOUNT_TOKEN`: at least 16
  printable ASCII characters, with no `ifs_pat_` or `ifs_ses_` prefix. It must not equal the
  `admin` token; `sync-api` refuses to start when it does.
- `INFRAHUB_SYNC_API_URL` on each worker is the address of the Sync API, for example
  `http://sync-api:8000`.

`sync-api` refuses to start when `INFRAHUB_SYNC_WORKER_TOKEN` is not set, is empty or breaks one
of these rules. The message names the variable and never its value. The Compose deployment also
requires the variable: Compose stops before any container starts when it is missing.

A worker starts without `INFRAHUB_SYNC_WORKER_TOKEN` or `INFRAHUB_SYNC_API_URL`. Each run that
names a stored credential then fails on that worker before it reads the source, and the cause
names the two variables.

`sync-api` applies the account and its token at each start. The account has no password and
cannot sign in. It is not an administrator. The Sync API refuses to change it, and no person can
create an account named `worker`.

The `worker` account can call two routes only. Every other route answers `403 forbidden` to it,
and both routes refuse every other account, including an administrator:

- `POST /api/worker/runs/{run_id}/credentials` returns the values that one stage of a run in
  progress needs. The Sync API refuses the request when the stage is not claimed by a worker or
  is finished. An apply, a verify and a resume get the destination credential only.
- `POST /api/worker/schedules/{schedule_id}/proposed-change-states` returns the states of the
  earlier proposed changes of a schedule with branch review. The Sync API reads Infrahub itself
  with the destination credential and returns the states only, with no value.

All workers share the token. To change it, edit the variable, then recreate `sync-api` and every
worker. One worker cannot be revoked alone.

## The encryption key

`INFRAHUB_SYNC_ENCRYPTION_KEY` is the key that the Sync API encrypts every value with. It is 32
bytes, base64-encoded, and only `sync-api` receives it.

- `sync-api` refuses to start when the variable is not set or is empty, and names the variable.
- `sync-api` refuses to start with a value that is not base64 or does not decode to 32 bytes,
  and names the variable. No message holds the value.
- The Compose deployment also requires the variable: Compose stops before any container starts
  when it is missing.

Generate one:

```bash
head -c 32 /dev/urandom | base64
```

Keep a copy of the key outside the deployment. A copy of the database without the key reveals no
value, and a restored database is of no use without the key it was written with.

Changing the key is not supported in this version.

### When the key is lost or replaced

The Sync API starts with a new key, but it cannot decrypt the values stored under the earlier
one. `credentials list` and `credentials show` still work, because they read no value. A run
that needs a value fails before it reads the source, with the cause that the stored value cannot
be decrypted with the current key (`credential-undecryptable`).

To recover, an administrator enters every credential again:

```bash
infrahub-sync credentials list
infrahub-sync credentials set <name>
```

Run `credentials set` for each name of the list. Each one gets a new revision under the current
key. No package is registered again.

## Versions registered with the earlier format

An earlier build named secrets with a `credentials` block and `$credential` references, and the
worker read each value from an `INFRAHUB_SYNC_CREDENTIAL_*` variable. That format is removed:

- Registration refuses a package that holds a `credentials` key or a `$credential` reference.
- A registered version that used a `$credential` reference is refused with
  `422 credential-format-removed` when you start a plan, a sync, a verify, an apply, an approval
  or a resume of it, and when you create or change a schedule that names it. A schedule that
  already names it fails at each start. You can still view the version, its runs, their results,
  artifacts and logs.
- A registered version that used no secret holds an empty `credentials` block. It is read as
  before and keeps its checksum, so its saved plans can still be approved and applied.

For each configuration that used a secret:

1. Create the stored credentials, as described in [Create a credential](#create-a-credential).
2. Replace the `credentials` block and the references in the package with `credential: <name>`
   in each block.
3. Add the package as a new version with `infrahub-sync configs version <config-id> package.yml`.
4. Point each schedule of the configuration to the new version with
   `infrahub-sync schedules change <schedule> --version <version>`.
5. Plan again from the new version. The saved plans of the refused version cannot be approved
   or applied.
