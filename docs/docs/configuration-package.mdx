---
title: Configuration package
---

A configuration package is the YAML or JSON file that describes one sync: its source, its
destination, and how source records map to destination kinds. You register the package with
the Sync API. Every later run uses the registered copy, not the file.

For the fields inside `configuration`, see [Sync instance configuration](./reference/config.mdx)
and the [Schema mapping reference](./reference/schema-mapping.mdx). To write a first package
step by step, see [Create a sync project](./creating-a-sync-project.mdx).

## Package shape

A package has three top-level keys:

| Key | Required | Content |
| --- | --- | --- |
| `format_version` | No | The package format. Only `1` is accepted, and it is the default. |
| `configuration` | Yes | The source, the destination, and the mappings. See [Sync instance configuration](./reference/config.mdx). |
| `credentials` | No | The credential references that the configuration uses. See [Credentials](#credentials). |

This outline shows only the structure. It is not a complete package; the `...` parts are
placeholders:

```yaml
format_version: 1
configuration:
  name: from-netbox
  source: ...          # adapter name and settings
  destination: ...     # adapter name and settings
  schema_mapping: ...  # list of mappings
credentials: ...       # credential references
```

For complete packages, see
[`examples/netbox_to_infrahub/package.yml`](https://github.com/opsmill/infrahub-sync/blob/feature/v3-develop/examples/netbox_to_infrahub/package.yml)
and the package in [Create a sync project](./creating-a-sync-project.mdx).

## Credentials

A credential-bearing setting, such as a token or a password, never contains the value. It
contains a `$credential` reference to an entry in the top-level `credentials` block:

```yaml
configuration:
  source:
    settings:
      token:
        $credential: netbox-token

credentials:
  netbox-token:
    provider: env
    identifier: INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN
```

Each entry declares a `provider` and an `identifier`. `env` is the only provider in this
release, and the identifier is the name of the environment variable that the Sync worker
reads when a run starts. The identifier must start with `INFRAHUB_SYNC_CREDENTIAL_`;
validation refuses any other identifier. Set that variable where the worker runs. On a Compose deployment,
set it in `.env` and run `docker compose up -d --wait`; see
[Reading from NetBox or Nautobot](./compose-deployment.mdx#reading-from-netbox-or-nautobot).
Registration refuses a package that contains a literal credential value.

The API checks every `env` declaration in previously registered versions, including
unused declarations. An invalid identifier returns HTTP 422 with error code
`malformed-credential-reference` before a new run is created or worker execution is
submitted. This check also applies to verification and apply of existing runs, even when
only the source credential is invalid and apply would not read it. Retrying a request whose
worker submission was not recorded as accepted also checks the version. Retrying an already
accepted request with the same idempotency key returns its stored response.

Register a new version with identifiers that start with `INFRAHUB_SYNC_CREDENTIAL_`
followed by a nonempty name made only of ASCII letters, digits, and underscores. Recreate affected saved plans by planning from the new version
before you verify or apply them. Existing versions and their saved plans are not rewritten.
The API checks declarations without resolving credential values.

## Connection settings

The worker connects to the URLs declared in the registered package. Environment variables
such as `NETBOX_URL` or `INFRAHUB_ADDRESS` do not replace them. Only the credential values
come from the worker environment. To change a URL, a branch, or any other setting, edit the
file and register it as a new version with `configs version`.

Declare URLs that the worker can reach. On a Compose deployment, `localhost` in a package
refers to the worker container.

## Registration and versions

Register a new package, or a new version of a registered one:

```bash
infrahub-sync configs register package.yml --reason "register NetBox import"
infrahub-sync configs version <config-id> package.yml --reason "update the device mapping"
```

[Run a sync](./running-a-sync.mdx) shows the same commands for a Compose deployment.

- `configs register` always creates a new configuration with a new `config_id`, at version 1.
- The configuration takes its name from `configuration.name` in the newest version. A name
  belongs to one configuration only. `configs register` refuses a package whose name another
  configuration already has, so registering the same named file again is refused. The refusal names
  that configuration and prints the `configs version` command that adds the package to it as a
  new version.
- `configs version` adds the next version to an existing configuration. A new version can keep
  the configuration's name or rename it. It cannot take the name of another configuration.
- A package with an empty name is not checked. Several configurations can have no name.
- Registered versions are immutable. A new version never changes an earlier one.
- Each run names one registered version by `config_id` and version number. No run command
  takes a file path.

Both commands print the version's `config_id`, `registry_version`, `package_checksum`,
`created_at` and `registered_without_validation`; see
[Versions registered without validation](#versions-registered-without-validation). They do not
print the package content in the registration response. Read it with
`configs show CONFIG_ID --version VERSION`. `configs version` also prints `created`. It is `false`
when the submitted content matches an existing version of that configuration. In that case
the command prints the existing version and stores nothing.

### When registration fails

If another configuration already has the name of the package, the command reports
`code: configuration-name-in-use` and stores nothing. The message names that configuration:

```text
error: api
status: 409
code: configuration-name-in-use
run_id: <none>
mutation_id: <none>
message: A configuration named 'from-netbox' already exists (20261120T1249-9d57f620). Did you mean to add a new version of it? Register the package as a new version of that configuration.
hint: infrahub-sync configs version 20261120T1249-9d57f620 package.yml
```

Run the `hint` command to add the package as a new version of that configuration. To keep
two configurations, change `configuration.name` in the package and register it again.
`configs version` reports the same code when the new version takes the name of another
configuration.

Registration also checks the package before it stores anything. If the check fails, the command
reports `code: configs-validation` and stores nothing. The response does not name the
defect, and `configs validate` cannot check a package that was not stored.
[`configs check`](#check-a-package-before-registering-it) gives the same refusal for the same
file, so it does not name the defect either. Compare the file
with [Sync instance configuration](./reference/config.mdx) and the adapter page. Check
these causes first:

- An adapter name that is not bundled. See [Choose an adapter](./adapters/choosing-an-adapter.mdx).
- A setting that the adapter does not accept.
- A literal credential value instead of a `$credential` reference.
- A URL setting that is not an absolute URL.

## Check a package before registering it

`configs check` runs the checks of `configs validate` on a package file that is not
registered. The Sync API stores nothing and records nothing in the audit history for a check
that it accepts.

```bash
infrahub-sync configs check package.yml
infrahub-sync configs check package.yml --branch main
```

- The command needs an administrator token, as `configs register` does. The Sync API refuses
  any other token with HTTP 403 and records the refused attempt in the audit history. With
  `--branch`, the Sync API connects to the destination URL that the file declares and sends
  the destination token that the service holds, so only an administrator can choose that URL.
- The file is a YAML or JSON package. The CLI reads it and sends its content to the Sync API.
- Without `--branch`, the command checks the declared content against the adapter
  declarations of the Sync release that runs now. With `--branch`, it also checks the mapping,
  the import account's permissions and the workers' credential variables against that
  Infrahub branch, as `configs validate --branch` does.
- For the same file, branch and destination state, the findings are the findings that
  `configs validate` reports for the version that registering the file creates.
- A file that registration refuses gets the same refusal, for example
  `code: configs-validation`. A v2 `config.yml` is refused with a message that names
  `infrahub-sync configs convert`; see [Convert a config.yml file](#convert-a-configyml-file).

The command prints `package_checksum`, `destination_read`, `destination_schema_fingerprint`,
the page fields `offset`, `limit`, `total_findings` and `next_offset`, and one `finding:` line
for each finding on the page. Findings have the format described in
[Validate a version](#validate-a-version).

`destination_read` states whether the Sync API read the schema of the branch:

| Value | Meaning |
| --- | --- |
| `not_requested` | The command ran without `--branch`. |
| `read` | The Sync API read the schema of the branch. |
| `not_read` | The destination adapter is unknown or does not read a destination schema, so the Sync API read nothing. With the current adapters, the command does not print this value: the Sync API refuses such a package before it checks it, with the refusal that registration gives. |
| `timeout`, `unreachable` | The Sync API could not reach the destination. |
| `unauthorized`, `forbidden` | The destination refused the destination token. |
| `nobranch` | The branch does not exist in the destination. |
| `rejected` | The destination answered but rejected the schema read, or returned a schema response that the Sync API cannot use. |
| `unconfigured` | The package declares no destination URL. |
| `credentials` | The destination token reference does not resolve in the service environment. |

For every value other than `not_requested`, `read` and `not_read`, the findings also include a
`destination-schema-read-failed` finding.

The command exits 1 when any page of findings has an error finding, with or without `--branch`.
When the printed page has no error finding, the command reads the following pages to find one, and
names the `--offset` of the page where it is.
A warning does not change the exit code. `configs validate` exits 1 only for an error finding,
and only with `--branch`. The output is paged as the output of `configs validate` is; read every page with
`--offset` to view all findings.

## Register a package from the web interface

The web interface checks a package file as `configs check --branch` does, shows the result,
and registers the package only when you select **Register**. See
[Open the web interface](./compose-deployment.mdx#open-the-web-interface) to sign in.

- To register a new configuration, drop the package file on the area **Register a
  configuration** of the Configurations page.
- To add a version to a configuration, drop the file on the area **Add a version** of that
  configuration's page.

Both areas also have a **choose a file** button, which opens the browser's file dialog. With a
token that is not an administrator token, both areas are disabled and show "Registering needs
an administrator token".

The web interface refuses some files before it opens the review step:

- More than one file: "Drop one package file."
- An empty file, or a file that is not YAML or JSON: "This file is not a YAML or JSON
  configuration package."
- A v2 `config.yml`: a message that names `infrahub-sync configs convert`. Convert the file,
  then drop the package; see [Convert a config.yml file](#convert-a-configyml-file).
- A file that a proxy in front of the Sync API refuses as too large: "The file is larger than
  the Sync API accepts."

The review step then shows:

- the configuration name, the source adapter and the destination adapter;
- for a new version, the changes to the mappings compared with the newest version, and a
  message when the version renames the configuration;
- "A configuration named N already exists." when another configuration has the name of the
  package, for a new configuration or for a version that renames its configuration.
  Configuration names are unique, so **Register** stays disabled. Select **Add as a new
  version** to review the same file as a new version of configuration N;
- the names of the environment variables that the credential references point to, without
  their values;
- the validation result against the branch in the **Validation branch** field. The field
  defaults to the destination's `branch` setting in the package, or to `main`. Change it to
  validate again against another branch;
- an optional reason, which the Sync API records with the version.

**Register** is enabled only when the result is "Valid against branch B". Warnings are listed
under that result and do not disable **Register**: for example, the Sync API reports a warning
when no worker has published which credential variables it holds. When an error finding is
listed, fix the package and drop it again. When the Sync API cannot
reach the destination, the review step shows "Could not validate: the destination cannot be
reached" and the button becomes **Register without validation**. When the check itself does not
complete, the review step shows "Validation did not complete." and a **Validate again** button.

After a registration, the web interface opens the configuration's page at the new version.
When the package is the same as a version already stored for the configuration, not only the
newest one, the review step shows "This package is the same as version N. No new version was
registered." When the request does not complete, select
**Retry**. The retry sends the same request with the same retry key, so the Sync API stores the
version at most once; see [Retry keys](#retry-keys). The reason cannot be changed after the
first attempt, because the Sync API refuses a retry key reused with a different request.

### Versions registered without validation

A version registered with **Register without validation** carries a mark:

- In the web interface, the version bar of the configuration's page shows "Registered without
  validation", and the list of versions shows "registered without validation" next to the
  version number.
- `configs show CONFIG_ID --version VERSION`, `configs versions CONFIG_ID`, `configs register`
  and `configs version` print `registered_without_validation: true`. For every other version
  they print `registered_without_validation: false`.

The CLI never sets the mark. Run `configs validate CONFIG_ID VERSION --branch BRANCH` on a
marked version once the destination can be reached.

A version without the mark is not known to be validated. `configs register` and
`configs version` do not check a package against the destination before they register it,
and versions registered before the mark existed have no mark. Run `configs validate` with
`--branch` to check any version.

## Validate a version

`configs validate` checks a registered version again, against the adapter declarations of
the Sync release that runs now. A version that registered without findings can report
findings after an upgrade.

```bash
infrahub-sync configs validate <config-id> <version>
```

Without `--branch`, the check reads only the declared content. It does not connect to the
source or the destination, so it does not test URLs, tokens, or the destination schema.

Each finding has a `code`, a `severity` of `error` or `warning`, a `location` in the package
as a JSON Pointer, and a message. The codes are listed in
[Finding codes](./reference/durable-product-records.mdx#finding-codes).

The output is paged. The default page holds 256 findings. The output reports
`total_findings` and `next_offset`; to read the next page, pass `--offset <next_offset>`.
`--limit` sets the page size.

## Retry keys

`configs register` and `configs version` accept `--idempotency-key`. If you omit it, the CLI
generates a key and prints it before it sends the request.

If the connection fails, you cannot tell whether the service stored the version. Run the
same command again with the printed key. For `configs version`, name the configuration by the
`config_id` that the first attempt printed, not by its name: the name follows the newest
version, so a stored version with a new name renames the configuration. If the service
already accepted the first request,
it returns the original response and stores nothing new. A retry with the same key but a
different request is refused with `idempotency-conflict`.

## Convert a config.yml file

Several examples in the repository are `config.yml` files, not packages. Registration
refuses them as they are.

`infrahub-sync configs convert config.yml` converts a v1 or v2 `config.yml` into a package. It
prints each change it makes, asks before it writes `package.yml`, and needs no Sync API. See
[Move a V2 configuration to V3](./v2-to-v3.mdx#move-a-v2-configuration-to-v3) for the report,
the keys it drops, and the configurations it refuses.

To convert a file by hand instead:

1. Add `format_version: 1`, and indent the whole file under a `configuration:` key.
2. Replace each literal credential value with a `$credential` reference, and declare the
   reference in a top-level `credentials` block.
3. Add a token credential to the Infrahub destination. Most `config.yml` examples omit it.
4. Replace example URLs with addresses that the Sync worker can reach.
5. Remove settings that the adapter does not accept in a registered package. The adapter
   pages list the accepted settings.
6. Write a destination `source` or `owner` group name as
   `{kind: CoreAccountGroup, name: <name>}`. A registered package refuses a bare name.

A `config.yml` file is used directly only by the
[Prefect remote run](./reference/prefect-remote-run.mdx). In that use, adapters read environment variables such as
`NETBOX_URL` before the declared settings.
