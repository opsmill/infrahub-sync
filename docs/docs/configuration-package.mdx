---
title: Configuration package
---

A configuration package is the YAML or JSON file that describes one sync: its source, its
destination, and how source records map to destination kinds. You register the package with
the Sync API. Every later run uses the registered copy, not the file.

For the fields inside `configuration`, see [Sync instance configuration](./reference/config.mdx)
and the [Schema mapping reference](./reference/schema-mapping.mdx). To write a first package
step by step, see [Create a sync project](./creating-a-sync-project.mdx).

## Package shape

A package has two top-level keys:

| Key | Required | Content |
| --- | --- | --- |
| `format_version` | No | The package format. Only `1` is accepted, and it is the default. |
| `configuration` | Yes | The source, the destination, and the mappings. See [Sync instance configuration](./reference/config.mdx). |

A top-level `credentials` key is refused. See [Credentials](#credentials).

This outline shows only the structure. It is not a complete package; the `...` parts are
placeholders:

```yaml
format_version: 1
configuration:
  name: from-netbox
  source: ...          # adapter name, stored credential name and settings
  destination: ...     # adapter name, stored credential name and settings
  schema_mapping: ...  # list of mappings
```

For complete packages, see
[`examples/netbox_to_infrahub/package.yml`](https://github.com/opsmill/infrahub-sync/blob/feature/v3-develop/examples/netbox_to_infrahub/package.yml)
and the package in [Create a sync project](./creating-a-sync-project.mdx).

## Credentials

A package never contains a token or a password. Each adapter block names a stored credential
with `credential: <name>`, next to the adapter name and `settings`:

```yaml
configuration:
  source:
    name: netbox
    credential: netbox-token
    settings:
      url: https://netbox.example.com
  destination:
    name: infrahub
    credential: infrahub-token
    settings:
      url: http://infrahub-server:8000
```

An administrator creates each credential in the Sync API before the package is registered, for
example with `infrahub-sync credentials create netbox-token`. The Sync API stores the value
encrypted. When a worker runs a stage, it gets the values of that run from the Sync API and
fills the credential settings of each block from them. [Manage stored
credentials](./guides/credentials.mdx) describes the commands, the fields that each adapter
needs, and the refusals.

These rules apply:

- A block names at most one credential. The name starts with a lowercase letter and holds 1 to 63
  lowercase letters, digits and hyphens.
- A block does not write its credential settings, such as `token`, `username` or `password`, in
  `settings`. Registration refuses a package that contains a literal credential value.
- A block whose authentication method needs no credential, for example `auth_method: none`, must
  not name one.
- Registration refuses a package that names a credential that does not exist, or one that lacks
  a field the block needs.
- The checksum of a version covers the credential name. To point a block to another credential,
  register a new version. A change of the stored value needs no new version.

### The earlier credential format is removed

An earlier build declared a top-level `credentials` block with the `env` provider, and wrote a
`$credential` reference in each credential setting. Both are removed:

- Registration refuses a package that holds a `credentials` key, empty or not, or a
  `$credential` reference. The message names `credential: <name>`.
- A version that was registered with a `$credential` reference is refused with HTTP 422 and the
  code `credential-format-removed` when a plan, a sync, a verify, an apply, an approval or a
  resume of it starts, and when a schedule that names it is created or changed. Its read
  commands, such as `configs show` and `runs show`, still work.
- A version that was registered with no secret holds an empty `credentials` block. It is read as
  before and keeps its checksum.

To use such a configuration again, follow
[Versions registered with the earlier format](./guides/credentials.mdx#versions-registered-with-the-earlier-format).

## Connection settings

The worker connects to the URLs declared in the registered package. Environment variables
such as `NETBOX_URL` or `INFRAHUB_ADDRESS` do not replace them, and the worker reads no token
or password from its environment for a registered package. To change a URL, a branch, or any
other setting, edit the file and register it as a new version with `configs version`.

Declare URLs that the worker can reach. On a Compose deployment, `localhost` in a package
refers to the worker container.

## Registration and versions

Register a new package, or a new version of a registered one:

```bash
infrahub-sync configs register package.yml --reason "register NetBox import"
infrahub-sync configs version <config-id> package.yml --reason "update the device mapping"
```

[Run a sync](./running-a-sync.mdx) shows the same commands for a Compose deployment.

- `configs register` always creates a new configuration with a new `config_id`, at version 1.
  Registering the same file again creates another configuration. It does not add a version.
- `configs version` adds the next version to an existing configuration.
- Registered versions are immutable. A new version never changes an earlier one.
- Each run names one registered version by `config_id` and version number. No run command
  takes a file path.

Both commands print the version's `config_id`, `registry_version`, `package_checksum` and
`created_at`. They do not print the package content in the registration response. Read it with
`configs show CONFIG_ID --version VERSION`. `configs version` also prints `created`. It is `false`
when the submitted content matches an existing version of that configuration. In that case
the command prints the existing version and stores nothing.

### When registration fails

Registration checks the package before it stores anything. If the check fails, the command
reports `code: configs-validation` and stores nothing. The response does not name the
defect, and `configs validate` cannot check a package that was not stored. Compare the file
with [Sync instance configuration](./reference/config.mdx) and the adapter page. Check
these causes first:

- An adapter name that is not bundled. See [Choose an adapter](./adapters/choosing-an-adapter.mdx).
- A setting that the adapter does not accept.
- A literal credential value in `settings`, instead of `credential: <name>` in the block.
- A `credentials` block or a `$credential` reference, which are removed.
- A stored credential that does not exist, or that lacks a field the block needs.
- A URL setting that is not an absolute URL.

## Validate a version

`configs validate` checks a registered version again, against the adapter declarations of
the Sync release that runs now. A version that registered without findings can report
findings after an upgrade.

```bash
infrahub-sync configs validate <config-id> <version>
```

The check reads the declared content, and whether each stored credential that a block names
exists and holds the fields the block needs. It does not connect to the source or the
destination, so it does not test URLs, tokens, or the destination schema.

Each finding has a `code`, a `severity` of `error` or `warning`, a `location` in the package
as a JSON Pointer, and a message. The codes are listed in
[Finding codes](./reference/durable-product-records.mdx#finding-codes).

The output is paged. The default page holds 256 findings. The output reports
`total_findings` and `next_offset`; to read the next page, pass `--offset <next_offset>`.
`--limit` sets the page size.

## Retry keys

`configs register` and `configs version` accept `--idempotency-key`. If you omit it, the CLI
generates a key and prints it before it sends the request.

If the connection fails, you cannot tell whether the service stored the version. Run the
same command again with the printed key. For `configs version`, name the configuration by the
`config_id` that the first attempt printed, not by its name: the name follows the newest
version, so a stored version with a new name renames the configuration. If the service
already accepted the first request,
it returns the original response and stores nothing new. A retry with the same key but a
different request is refused with `idempotency-conflict`.

## Convert a config.yml file

Several examples in the repository are `config.yml` files, not packages. Registration
refuses them as they are.

`infrahub-sync configs convert config.yml` converts a v1 or v2 `config.yml` into a package. It
prints each change it makes, asks before it writes `package.yml`, and needs no Sync API. See
[Move a V2 configuration to V3](./v2-to-v3.mdx#move-a-v2-configuration-to-v3) for the report,
the keys it drops, and the configurations it refuses.

To convert a file by hand instead:

1. Add `format_version: 1`, and indent the whole file under a `configuration:` key.
2. Remove each credential setting, such as `token`, from `settings`, and name a stored credential
   in the block with `credential: <name>`.
3. Name a stored credential in the Infrahub destination block too. Most `config.yml` examples
   omit its token.
4. Replace example URLs with addresses that the Sync worker can reach.
5. Remove settings that the adapter does not accept in a registered package. The adapter
   pages list the accepted settings.
6. Write a destination `source` or `owner` group name as
   `{kind: CoreAccountGroup, name: <name>}`. A registered package refuses a bare name.

A `config.yml` file is used directly only by the
[Prefect remote run](./reference/prefect-remote-run.mdx). In that use, the adapters read
environment variables of the serving process, such as `NETBOX_URL` and `NETBOX_TOKEN`, before
the declared settings, and no stored credential is used. The Sync API and its worker read no
such variable for a registered package.
