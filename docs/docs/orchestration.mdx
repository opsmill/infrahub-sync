---
title: Schedule sync runs
---

The V3 CLI submits a run to a deployed Sync service and waits for its result. This release has no built-in scheduler, so schedule that CLI command with cron, CI, or a workflow tool.

## Common orchestration options

Any tool that can run a CLI command on a schedule and capture its output works. Pick whichever fits your existing operational model.

### Cron

The most direct option. A cron entry submits `infrahub-sync sync --config-id <id>
--version <version> --reason "scheduled sync"` on a defined schedule. Output and exit
codes are captured by your normal cron logging.

**When this works well:**

- You already operate a cron host for scheduled jobs.
- The sync is straightforward — one project, one schedule, no dependencies on other jobs.
- Failure handling can be reactive (logs are reviewed when something looks off).

**Trade-offs:** No native retry on failure, no visibility beyond logs, no built-in alerting. For mission-critical syncs, wrap the cron entry in a script that handles retries and alerts.

### CI jobs (GitHub Actions, GitLab CI, etc.)

Define the sync as a scheduled workflow in your CI system. CI provides run history, log retention, secret management, and notification on failure.

**When this works well:**

- You treat infrastructure data movement as part of your software delivery pipeline.
- You want run history and structured failure notifications from tooling you already operate.
- Sync project configurations live in a git repository alongside other infrastructure code.

**Trade-offs:** CI systems are designed for short-lived jobs. For very large or long-running syncs, watch out for job timeout limits.

### Prefect

Prefect runs underneath both packaged execution surfaces — the Sync API and worker that the
Compose deployment runs, and the direct deployment below — rather than being something you
choose instead of Compose:

- Install the `prefect` extra to serve one direct deployment that accepts read-only plan
  requests through Prefect's API, without the rest of the Sync service; it refuses
  `operation="sync"`. Use the Sync API for confirmed sync or reviewed-plan apply. Sync output
  is forwarded into the flow-run log. This is a lighter-weight alternative to a full Compose
  deployment when you only need to trigger plan requests through Prefect. See the
  [Prefect remote run reference](./reference/prefect-remote-run.mdx) and
  `examples/prefect_remote_run/README.md` in the repository.
- Install the `service` extra to run the Sync-owned authenticated HTTP API, durable records
  and artifacts, reviewed-plan apply, idempotency, cancellation, and worker execution — the
  same surface the [Compose deployment](./compose-deployment.mdx) runs its `sync-api` and
  `sync-worker` services from. See the
  [Sync HTTP API reference](./reference/sync-http-api.mdx).

**When this works well:**

- You already use Prefect for other infrastructure or data workflows.
- A sync needs to be triggered on demand from another system, over an API rather than a shell.
- You want centralized observability across many sync projects.

**Trade-offs:** Prefect itself has to be operated. If you do not already run it, this adds
operational surface area. The direct deployment runs and observes one plan; it does not add
scheduling, retry, queue, or overlap policy.

Use the Sync API for the supported worker-backed run lifecycle. For schedules, retry
policies, triggers, or composing several syncs into a larger workflow, configure Prefect
around either packaged surface or wrap the CLI in a flow you own.

#### What a service flow run shows in Prefect

Each stage of a Sync run (`plan`, `verify`, `apply` or `sync`) runs as one Prefect flow run.
Each line that Sync writes to the flow run's log starts with the name of the Sync logger that
wrote it, then ` | `, for example `infrahub_sync.service.flow | `. Lines that Prefect writes,
such as `Finished in state Completed()`, have no such prefix.

You do not need access to Prefect to read these lines. `infrahub-sync runs logs <run_id>` and
`GET /runs/{run_id}/logs` read them through the Sync API and leave out Prefect's own lines;
`--follow` prints new lines until the run ends. See
[Read a run's log](./reference/sync-http-api.mdx#read-a-runs-log).

When a stage fails with an error that Sync knows, such as a destination branch that does not
exist, the worker writes one ERROR line with the cause and the next step, without a Python
traceback, and the flow run ends `Failed` with the same text as its state message.

When the stage ends, the worker writes its last INFO line to the flow run's log. Prefect then
adds its own line with the flow run's final state.

```text
infrahub_sync.service.flow | service run <run_id> stage=<stage> outcome=<outcome>; next step: <action>
```

The next step is the next action that the run recorded for its failure, when there is one.
Otherwise it is `` `infrahub-sync runs show <run_id>` ``. A stage that fails without a recorded
outcome reports `outcome=failed`.

After that line, the worker publishes a markdown artifact on the flow run, in the flow run's
Artifacts tab. Its key is `sync-run-<run_id>-<stage>`, in lowercase, for example
`sync-run-20261105t1514-f62dfb83-plan`. A later flow run of the same stage adds a version to the
same key. The artifact holds:

- the Sync run ID, the stage and the outcome;
- the configuration and its version, and the destination branch, when the run has them;
- the operation counts by action and by kind, when the run has them;
- for a `plan` or `sync` stage, the number of records the plan left out, with how many have a
  problem and how many depend on one, and the number of problems, when the run records them;
- the next steps: `infrahub-sync runs show <run_id>`, then `infrahub-sync runs plan <run_id> --detail`
  when the run saved a plan review, then `infrahub-sync runs plan <run_id> --problems` and
  `--left-out` when the plan left out records, then the run's recorded next action, when there is one.

A `sync` whose plan leaves out records stops after the plan, before any write. Its last log line
reads `stage=sync outcome=left-out-review-required`, and its next step names the review commands
and `infrahub-sync apply <run_id> --expected-checksum <checksum> --confirm-left-out`.

The artifact is built from the run record's named fields and fixed text only, and the stage's
secrets are removed from it. It never holds an error message. If the artifact cannot be
published, the worker logs one WARNING line, `run summary artifact for run <run_id> stage <stage>
could not be published (<ErrorType>)`, and the run's outcome does not change.

A Sync run is not replayed from Prefect. The worker refuses a flow run that the Sync API did not
submit and is not waiting for: a Prefect Retry, a run started by hand from the deployment, or an
execution whose admission expired. The refused flow run reads and writes nothing, logs one ERROR
line without a Python traceback, then ends `Failed` with the same text as its state message. The line
reads, on one line in the log:

```text
service worker execution claim was refused: this Prefect flow run is not an execution the Sync API submitted
for run <run_id> and is waiting for. A Prefect Retry, a run started by hand from the deployment, and an
execution whose admission expired are refused. Nothing was read or written. A Sync run is not replayed from
Prefect: check it with `infrahub-sync runs show <run_id>`, then start a new run with `infrahub-sync plan` or
`infrahub-sync sync`, or apply a reviewed plan with
`infrahub-sync apply <run_id> --expected-checksum <checksum>`.
```

A refused flow run gets no artifact and no `service run ... next step:` line.

### Dagster, Airflow, and other workflow engines

Any workflow engine that can run a CLI command works the same way as Prefect. Pick based on what you already use and what other workloads share the orchestration platform.

### Event-driven execution

Some sync use cases are better started by an event than by a schedule. For example: "when a device is created in Infrahub, sync its details from the inventory system." An event handler that you run, such as a service that receives an Infrahub webhook, can start the run with the CLI or the [Sync HTTP API](./reference/sync-http-api.mdx).

Event-driven sync is the exception, not the rule. Most data movement is well-served by a recurring schedule. Use event-driven patterns when the data volume is small, the freshness requirement is high, or the source system is itself event-driven.

## Choosing a cadence

Match the cadence to the rate at which source data changes and your tolerance for staleness:

- **Every few minutes** — for high-change-rate sources that need near-real-time freshness. Verify the sync run completes faster than the cadence to avoid overlap.
- **Hourly** — a common default for active infrastructure data.
- **Daily** — appropriate for slower-moving data or for syncs where the next run can absorb a missed one.
- **On demand** — for migrations, audits, or one-off seeding rather than steady-state operation.

Each run reads the source and the destination in full, then writes only the differences. A shorter cadence repeats that read more often, so check that each run finishes before the next one starts.

## Observability and failure handling

Whatever scheduling tool you use, plan for these operational concerns:

- **Logging.** Adapter and lifecycle logs come from the Sync worker that runs the request
  (`docker compose logs sync-worker` on a Compose deployment); the CLI itself reports
  the run ID, the final state, and the exit code. `infrahub-sync runs logs <run_id>` prints one
  run's lines and `infrahub-sync events --run-id <run_id>` prints what happened to it, both
  through the Sync API. Forward the worker's logs to the logging system used by the scheduler.
- **Failure detection.** The CLI returns a non-zero exit code on failure. Wire the scheduling tool to catch this and alert the appropriate channel.
- **Failure recovery.** Inspect the run record and destination after a failed write, then
  calculate a fresh plan. A failed operation can have written part of its change, unless the
  run records that it wrote nothing; follow
  [When the outcome of a write is uncertain](./compose-deployment.mdx#when-the-outcome-of-a-write-is-uncertain).
- **Run isolation.** Avoid overlapping runs of the same sync project. Set the cadence longer than the run time, or have the scheduler skip a run if the previous one is still active.
- **Sync project versioning.** Keep the configuration package files in version control and register each change as a new version.

## Running Infrahub Sync in a container

To run the CLI from an orchestrator in a container, use the Infrahub Sync image (or the
Compose deployment's `cli` service) with `INFRAHUB_SYNC_API_URL` and
`INFRAHUB_SYNC_API_TOKEN` set. Register the configuration package with the service, and put
source and destination credentials in the deployment's `.env`, where the worker
resolves them — see [Container image](./container-image.mdx) and
[Compose deployment](./compose-deployment.mdx). The Compose deployment gives the source
credentials (for example `INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN`, `INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN`)
only to the `sync-worker` service. `INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN` goes to
`sync-worker` and `sync-api`, which reads the destination schema when it validates a
package. `cli` receives only the Sync API URL and token.

## What this release does not include

- **Built-in scheduler.** This release has no scheduler. Use one of the options above.
- **Sync history dashboard.** The scheduling tool typically provides this — CI run history, Prefect UI, or aggregated logs.
- **Built-in retry policies.** Configure retries in the scheduling tool. Treat write
  retries according to the [documented recovery and convergence boundaries](./running-a-sync.mdx).
- **Alerting on failure.** Configure alerts in the scheduling tool or log aggregator.
