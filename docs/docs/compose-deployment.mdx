Each release deploys Infrahub Sync on one host from a single file,
`docker-compose.yml`, and a `.env` file that you write beside it. The deployment
runs the Sync API, the Sync worker, a Prefect server, PostgreSQL, and
S3-compatible object storage. The Prefect server runs from the Sync image, so
the deployment pulls no Prefect image. Docker pulls the Sync image from the
OpsMill registry like every other service image. A host needs Docker with Docker Compose
2.24 or later, and nothing else: no product checkout, no Python, no `uv`.

For the shortest path to a running deployment, follow the
[Compose quickstart](quickstart-compose). This page is the reference for that
flow, and for the configuration and reviewed-run procedure that follows it.

## Prerequisites

- Docker Engine with Docker Compose 2.24 or later. The file carries the database
  bootstrap script as a top-level `configs` entry with inline `content`, which
  older Compose versions cannot parse. Check the version with:

  ```bash
  docker compose version --short
  ```

- A Linux host on `amd64` or `arm64`. The image is published for both platforms,
  and Docker pulls the one that matches the host.
- A registry login. Until the 3.0.0 release, the registry project is open to
  invited testers only, so run `docker login registry.opsmill.io` before the
  first start. See [Install Infrahub Sync](./installation.mdx#run-the-container-image).
- Port 8001 free on `127.0.0.1`, or another port set in `.env`. The Sync API is
  the only port the deployment publishes. Its default leaves port 8000 to
  Infrahub, so both can run on one machine.

## Get the file

Fetch `docker-compose.yml` from the release tag you want to run. Tags carry the
bare version, for example `3.0.0`:

```bash
mkdir infrahub-sync && cd infrahub-sync
curl -fsSLO https://raw.githubusercontent.com/opsmill/infrahub-sync/<version>/docker-compose.yml
```

The file pins the Sync image of the release it was taken from. Every other image
carries its digest, so a re-pointed tag cannot change what the file runs.

| Service | What it does |
| --- | --- |
| `postgres` | PostgreSQL. Holds the product database and the Prefect database. |
| `db-bootstrap` | A short-lived job that creates both databases and their owner roles. |
| `object-store-init`, `object-store` | S3-compatible object storage for plans and artifacts, on the Silo image, and a short-lived job that prepares its volume. |
| `prefect-server` | The Prefect API, from the Sync image. It publishes no port and serves no UI. |
| `sync-bootstrap` | A short-lived job that creates the product schema, the bucket, the work pool, and the Prefect deployment. |
| `sync-api` | The Sync API. |
| `sync-worker` | The Sync worker that runs plans and applies. |
| `cli` | The Sync CLI, in profile `cli`. It runs only when you call it. |

The API and the worker share no mount, no volume, and no scratch directory. Run
state travels between them through PostgreSQL and the object store, which is
why the worker needs no configuration mount and why replacing it loses nothing.
PostgreSQL and the object store hold the only volumes that survive a restart.

### The object store image and its licence

The object store runs
`pgsty/silo:RELEASE.2026-10-18T00-00-00Z`, pinned by digest in the file. Silo
is a maintained build of the MinIO server. It is licensed under the AGPLv3, and
its source is at [github.com/pgsty/silo](https://github.com/pgsty/silo). The
deployment does not publish the object store port and does not start its
browser console. The Sync services use it over the deployment's own network,
and its port is not published on the host. A team that already runs an
S3-compatible store can use it instead and leave this one out; see
[Use your own S3-compatible store](#use-your-own-s3-compatible-store).

Run every `docker compose` command on this page from the directory that holds
`docker-compose.yml` and `.env`. Compose finds both files there without `-f` or
`--env-file`.

## The `.env` file {#configuration-prerequisites}

Compose reads `.env` from the directory of `docker-compose.yml`. Nothing in the
file defaults a credential: each required variable is guarded, and a missing one
stops Compose before any container starts, with a message naming it:

```text
required variable INFRAHUB_SYNC_PRODUCT_PASSWORD is missing a value: INFRAHUB_SYNC_PRODUCT_PASSWORD is required
```

### Required credentials

| Variable | Used by |
| --- | --- |
| `INFRAHUB_SYNC_POSTGRES_ADMIN_PASSWORD` | `postgres`, `db-bootstrap` |
| `INFRAHUB_SYNC_PRODUCT_PASSWORD` | `db-bootstrap` and the Sync services: the product database role |
| `INFRAHUB_SYNC_PREFECT_PASSWORD` | `db-bootstrap`, `prefect-server`: the Prefect database role |
| `INFRAHUB_SYNC_PREFECT_AUTH_STRING` | `prefect-server` and the Sync services: the Prefect API credential. See [Prefect API authentication](#prefect-api-authentication). |
| `INFRAHUB_SYNC_S3_ACCESS_KEY` | `object-store` and the Sync services |
| `INFRAHUB_SYNC_S3_SECRET_KEY` | `object-store` and the Sync services |
| `INFRAHUB_SYNC_SERVICE_BEARER_TOKENS` | `sync-api`: a JSON object of API principals |

`INFRAHUB_SYNC_SERVICE_BEARER_TOKENS` maps each principal name to its token, for
example `{"operator": {"token": "<random>", "administrator": true}}`. The API
refuses a token shorter than 16 characters.

The database connection strings are composed inside the file from the role,
database, and password settings. A password used in them must be URL-safe:
hexadecimal output is. To use another password, set the whole connection string
in `INFRAHUB_SYNC_DATABASE_URL` or `INFRAHUB_SYNC_PREFECT_DATABASE_URL` instead.

### Optional settings

| Variable | Default | Meaning |
| --- | --- | --- |
| `INFRAHUB_SYNC_API_TOKEN` | empty | The token the `cli` service presents. It must equal a principal's `token` in `INFRAHUB_SYNC_SERVICE_BEARER_TOKENS`. Empty, every `cli` call is refused. |
| `INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN` | empty | The destination Infrahub token, for a package that references it. |
| `INFRAHUB_SYNC_CREDENTIAL_*` | empty | Source credentials, for a package that references them. Only the worker receives them. The full list is in [Credential variables the worker receives](#credential-variables-the-worker-receives). |
| `VERSION` | the release the file was taken from | The tag of the Sync image. See [Choose an image](#choose-an-image). |
| `INFRAHUB_SYNC_DOCKER_IMAGE` | `registry.opsmill.io/opsmill/infrahub-sync` | The repository of the Sync image. |
| `INFRAHUB_SYNC_DATABASE_URL` | composed | The product database connection string, as a whole. |
| `INFRAHUB_SYNC_PREFECT_DATABASE_URL` | composed | The Prefect database connection string, as a whole. |
| `INFRAHUB_SYNC_BIND_ADDRESS` | `127.0.0.1` | The address the published Sync API port binds to. |
| `INFRAHUB_SYNC_API_PORT` | `8001` | The published Sync API port. |
| `INFRAHUB_SYNC_PREFECT_PORT` | `4200` | The host port of the Prefect UI. The file does not publish the Prefect port, so this setting has no effect without the override snippet in [Open the Prefect UI](#open-the-prefect-ui). |
| `INFRAHUB_SYNC_POSTGRES_ADMIN_ROLE` | `postgres` | The PostgreSQL administrator role. |
| `INFRAHUB_SYNC_PRODUCT_DATABASE`, `INFRAHUB_SYNC_PRODUCT_ROLE` | `infrahub_sync` | The product database and its owner role. |
| `INFRAHUB_SYNC_PREFECT_DATABASE`, `INFRAHUB_SYNC_PREFECT_ROLE` | `prefect` | The Prefect database and its owner role. |
| `INFRAHUB_SYNC_S3_BUCKET`, `INFRAHUB_SYNC_S3_PREFIX` | `infrahub-sync` | The artifact bucket and key prefix. |
| `INFRAHUB_SYNC_S3_REGION` | `us-east-1` | The object store region. |
| `INFRAHUB_SYNC_S3_ENDPOINT_URL` | `http://object-store:9000` | The object store address. Set it, with `INFRAHUB_SYNC_BUNDLED_OBJECT_STORE=0`, to use your own store; see [Use your own S3-compatible store](#use-your-own-s3-compatible-store). |
| `INFRAHUB_SYNC_S3_ADDRESSING_STYLE` | `path` | `path` puts the bucket in the request path, `virtual` in the host name. Any other value stops the Sync services and `sync-bootstrap`. |
| `INFRAHUB_SYNC_BUNDLED_OBJECT_STORE` | `1` | `0` leaves the bundled store out: Compose creates no `object-store-init` or `object-store` container. |
| `INFRAHUB_SYNC_WORK_POOL` | `infrahub-sync` | The Prefect work pool. |
| `INFRAHUB_SYNC_RUN_ADMISSION_TTL_SECONDS` | `300` | How long a run admission stays valid. |
| `INFRAHUB_SYNC_REQUIRE_APPROVAL` | `false` | Set on `sync-api`. When `true`, `apply` refuses a plan that has no approval matching the checksum it names, and `sync` is refused; operators run `plan`, `approve` and `apply` instead. Accepted values are `true`, `1`, `yes`, `on`, `false`, `0`, `no` and `off`, in any case. Any other value, including an empty one, stops `sync-api` at startup. The service reads it for each `apply` or `sync` request, so restart `sync-api` to change it; stored runs and approvals are not changed. `infrahub-sync whoami` prints the value as `approval_required`. See [Require an approved plan](./running-a-sync.mdx#require-an-approved-plan). |
| `PREFECT_WORKER_QUERY_SECONDS`, `PREFECT_WORKER_HEARTBEAT_SECONDS` | `10` | The worker's polling and heartbeat intervals. |
| `INFRAHUB_SYNC_PREFECT_UI_URL` | empty | The address you open the Prefect UI at, for example `http://127.0.0.1:4200`. Run responses and `infrahub-sync runs show` then link each flow run to its Prefect UI page. Empty turns the link off. The Sync API refuses to start when the value is not an absolute `http` or `https` URL, or when it carries credentials, a query or a fragment; see [Valid values of `INFRAHUB_SYNC_PREFECT_UI_URL`](#valid-values-of-infrahub_sync_prefect_ui_url). |

### An example `.env`

Every value below is a placeholder. Replace each one with a random value of
your own:

```dotenv
# Required credentials
INFRAHUB_SYNC_POSTGRES_ADMIN_PASSWORD=<random hex>
INFRAHUB_SYNC_PRODUCT_PASSWORD=<random hex>
INFRAHUB_SYNC_PREFECT_PASSWORD=<random hex>
INFRAHUB_SYNC_PREFECT_AUTH_STRING=<random hex>
INFRAHUB_SYNC_S3_ACCESS_KEY=<random hex>
INFRAHUB_SYNC_S3_SECRET_KEY=<random hex>
INFRAHUB_SYNC_SERVICE_BEARER_TOKENS={"operator": {"token": "<principal token>", "administrator": true}}

# The token the cli service presents: the same value as the principal's token
INFRAHUB_SYNC_API_TOKEN=<principal token>

# Only for a registered package that references them
# INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN=<your Infrahub token>
# INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN=<your NetBox token>
# INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN=<your Nautobot token>

# Optional: another release, or a mirror of the image
# VERSION=<version>
# INFRAHUB_SYNC_DOCKER_IMAGE=registry.opsmill.io/opsmill/infrahub-sync
```

To generate the credentials instead, run this once, in the directory of
`docker-compose.yml`. It reads `/dev/urandom` and needs no Python:

```bash
rand() { od -An -tx1 -N"$1" /dev/urandom | tr -d ' \n'; }
principal=$(rand 24)
# mktemp creates the file readable by you alone, whatever an existing .env allowed.
env_file=$(mktemp .env.XXXXXX)
cat > "$env_file" <<EOF
INFRAHUB_SYNC_POSTGRES_ADMIN_PASSWORD=$(rand 24)
INFRAHUB_SYNC_PRODUCT_PASSWORD=$(rand 24)
INFRAHUB_SYNC_PREFECT_PASSWORD=$(rand 24)
INFRAHUB_SYNC_PREFECT_AUTH_STRING=$(rand 24)
INFRAHUB_SYNC_S3_ACCESS_KEY=$(rand 12)
INFRAHUB_SYNC_S3_SECRET_KEY=$(rand 24)
INFRAHUB_SYNC_SERVICE_BEARER_TOKENS={"operator": {"token": "$principal", "administrator": true}}
INFRAHUB_SYNC_API_TOKEN=$principal
EOF
mv -f "$env_file" .env
```

`INFRAHUB_SYNC_SERVICE_BEARER_TOKENS` and `INFRAHUB_SYNC_API_TOKEN` hold one
credential. If you change the principal's token, change both to the same value.

Handle `.env` as the secret it is:

- Keep it at mode 0600 and out of version control.
- Never `source` it: it holds every credential of the deployment.
- Nothing in the deployment prints a credential value. A refusal names the
  variable, never its value.

:::warning
A variable exported in your shell overrides the same name in `.env`. An exported
`VERSION`, a common name, silently changes the Sync image. Check `env` before you
start, or unset it.
:::

### Credentials in a package

A configuration package holds credential references, never values. The value
goes in `.env`:

```yaml
token:
  $credential: infrahub-token
credentials:
  infrahub-token:
    provider: env
    identifier: INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN
```

An `env` identifier must start with `INFRAHUB_SYNC_CREDENTIAL_`; validation refuses any
other identifier, so a package cannot name the deployment's own storage, database, or
Prefect settings.

If you upgrade from an earlier alpha, move to the prefixed names:

1. In `.env`, rename `INFRAHUB_API_TOKEN`, `NETBOX_TOKEN`, and `NAUTOBOT_TOKEN` to
   `INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN`, `INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN`,
   and `INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN`.
2. Change the `identifier` of each `env` credential in your packages to the new name.
3. Register a new version of each package with `configs version`. A version registered
   before the upgrade keeps its old identifiers, and its runs fail in the worker.
4. Run `docker compose up -d --wait`, so the services receive the renamed variables.

:::note
A container reads its environment once, when it is created. After changing a
value in `.env`, run `docker compose up -d --wait` again, which recreates the
services whose environment changed. `docker compose restart` keeps the
environment the containers were created with.
:::

### Reading from NetBox or Nautobot

The image installs the bundled NetBox and Nautobot source adapters, so a package
may declare either as its source. Set only the token your package names:

```dotenv
INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN=<your NetBox token>
# INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN=<your Nautobot token>
```

```yaml
configuration:
  source:
    name: netbox
    settings:
      url: "http://netbox.example.net:8080"
      token:
        $credential: netbox-token
credentials:
  netbox-token:
    provider: env
    identifier: INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN
```

Nautobot uses the same shape with `nautobot`, `nautobot-token` and
`INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN`.

- **Name a URL a container can reach.** The worker resolves it from inside the
  Compose network, where `localhost` is the worker itself. If NetBox, Nautobot, or
  Infrahub runs in containers on the same host and publishes only on `127.0.0.1`, the
  worker cannot reach it: publish it on an address containers can reach and use
  `http://<host-IP>:<port>`.
- **The declared `url` is the one used.** `NETBOX_ADDRESS`, `NETBOX_URL`,
  `NAUTOBOT_ADDRESS` and `NAUTOBOT_URL` exported in your shell are ignored: a
  registered run reads what its package declares.
- **Both tokens are optional.** A deployment that reads from neither source
  starts normally, and a package naming one source does not need the other's
  token. When a package does select a source, a missing or empty token fails
  that run and the message names the environment variable, never its value.
- **Start again after changing either value.** `docker compose up -d --wait`
  recreates the worker with the new value; `restart` keeps the old one.

Only `sync-worker` receives these tokens. Registration and the default
validation judge declared content without resolving a source secret, so the API
and the bootstrap job never hold one.

### Credential variables the worker receives

Compose can pass only variables the file names, so `sync-worker` receives a fixed list of
credential variables: a name for each credential setting of each bundled adapter, and every
name the shipped examples and adapter pages use. A package for this deployment uses these names
as its `env` identifiers. A name that is not on the list does not reach the worker, and a run
that selects it fails naming the variable. Each one is optional: set only the ones your packages
reference.

| Adapter | Variables |
| --- | --- |
| `aci` | `INFRAHUB_SYNC_CREDENTIAL_CISCO_APIC_USERNAME`, `INFRAHUB_SYNC_CREDENTIAL_CISCO_APIC_PASSWORD` |
| `genericrestapi` | `INFRAHUB_SYNC_CREDENTIAL_REST_API_TOKEN`, `INFRAHUB_SYNC_CREDENTIAL_REST_API_USERNAME`, `INFRAHUB_SYNC_CREDENTIAL_REST_API_PASSWORD`, and for the [Device42](./adapters/device42.mdx), [LibreNMS](./adapters/librenms.mdx), [Observium](./adapters/observium.mdx) and [PeeringDB](./adapters/peeringdb.mdx) pages `INFRAHUB_SYNC_CREDENTIAL_DEVICE42_USERNAME`, `INFRAHUB_SYNC_CREDENTIAL_DEVICE42_PASSWORD`, `INFRAHUB_SYNC_CREDENTIAL_LIBRENMS_TOKEN`, `INFRAHUB_SYNC_CREDENTIAL_OBSERVIUM_USERNAME`, `INFRAHUB_SYNC_CREDENTIAL_OBSERVIUM_PASSWORD`, `INFRAHUB_SYNC_CREDENTIAL_PEERINGDB_API_KEY` |
| `infrahub` | `INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN` (the destination; `sync-api` receives it too), `INFRAHUB_SYNC_CREDENTIAL_SOURCE_INFRAHUB_TOKEN` (Infrahub as a source) |
| `ipfabricsync` | `INFRAHUB_SYNC_CREDENTIAL_IPF_TOKEN` |
| `nautobot` | `INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN` |
| `netbox` | `INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN` |
| `peeringmanager` | `INFRAHUB_SYNC_CREDENTIAL_PEERING_MANAGER_TOKEN`, `INFRAHUB_SYNC_CREDENTIAL_PEERING_MANAGER_USERNAME`, `INFRAHUB_SYNC_CREDENTIAL_PEERING_MANAGER_PASSWORD` |
| `prometheus` | `INFRAHUB_SYNC_CREDENTIAL_PROMETHEUS_TOKEN`, `INFRAHUB_SYNC_CREDENTIAL_PROMETHEUS_USERNAME`, `INFRAHUB_SYNC_CREDENTIAL_PROMETHEUS_PASSWORD` |
| `slurpitsync` | `INFRAHUB_SYNC_CREDENTIAL_SLURPIT_API_KEY`, `INFRAHUB_SYNC_CREDENTIAL_SLURPIT_TOKEN` |

Which service receives which credential:

- `sync-worker` receives every variable above.
- `sync-api` receives only `INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN`, for the destination
  schema reads it serves.
- `sync-bootstrap`, `prefect-server` and `cli` receive no adapter credential.

The configuration check of `configs validate` reports a `$credential` reference that no live
worker holds, by name and without its value, once that check is available in your release.

:::note
That both adapters install and import is a packaging property of this release.
It is not a statement that any particular NetBox or Nautobot server version has
been qualified against it.
:::

## Use your own S3-compatible store

A team that already runs an S3-compatible store can keep plans and run files there. Create a
bucket and a credential for Sync in that store, then set these values in `.env` together:

```bash
INFRAHUB_SYNC_S3_ENDPOINT_URL=https://s3.example.com
INFRAHUB_SYNC_S3_BUCKET=<bucket>
INFRAHUB_SYNC_S3_PREFIX=infrahub-sync
INFRAHUB_SYNC_S3_REGION=<region>
INFRAHUB_SYNC_S3_ACCESS_KEY=<access key for that bucket>
INFRAHUB_SYNC_S3_SECRET_KEY=<secret key for that bucket>
INFRAHUB_SYNC_S3_ADDRESSING_STYLE=path
INFRAHUB_SYNC_BUNDLED_OBJECT_STORE=0
```

With `INFRAHUB_SYNC_BUNDLED_OBJECT_STORE=0`, Compose creates no `object-store-init` or
`object-store` container, so the bundled store never receives the credential of your store.
`sync-bootstrap` refuses to start when the two settings disagree:

- `refused: bundled-object-store-not-left-out`: the endpoint names your store while the bundled
  store runs. The bundled store takes `INFRAHUB_SYNC_S3_ACCESS_KEY` and
  `INFRAHUB_SYNC_S3_SECRET_KEY` as its own root credential, so it has received yours. Set
  `INFRAHUB_SYNC_BUNDLED_OBJECT_STORE=0`, then run `docker compose up -d --wait --remove-orphans`.
- `refused: object-store-endpoint-not-set`: the bundled store is left out but the endpoint still
  names it.

Use `https` for your store. Request signing never sends the secret key, but over `http` object
content crosses the network unencrypted. An endpoint that carries a user name or a password is
refused with `refused: object-store-endpoint-invalid`.

### What Sync needs from the store

`sync-bootstrap` checks for the bucket with `HeadBucket` and creates it only when the store
answers that it is absent, so a credential that may not create buckets works with a bucket you
created. A `HeadBucket` refusal stops it with `refused: object-store-access-refused`. It then
writes one empty check object under `<prefix>/.infrahub-sync/bootstrap-check/` twice with
`If-None-Match: *`, and deletes it. A store that accepts the second write stops it with
`refused: object-store-unsupported`, because Sync relies on that refusal to never replace a
stored artifact.

The S3 operations Sync uses:

| Operation | What Sync relies on |
| --- | --- |
| `PutObject` | A single request with the whole body |
| `PutObject` with `If-None-Match: *` | A second write of an existing key is refused with `412 PreconditionFailed` |
| `GetObject`, `HeadObject` | A missing key answers `404`, not `403` |
| `CopyObject`, `DeleteObject` | One key at a time, within the bucket |
| `HeadBucket`, `CreateBucket` | `sync-bootstrap` only |

A missing key must answer `404`. On stores with S3-style access policies that usually means the
credential may list the bucket.

OpsMill tests this setup with a Silo instance outside the deployment. No other product is
named as supported.

Moving from the bundled store to your own does not copy earlier plans and run files. They stay in
the `object-store-data` volume, and `runs plan` and `runs artifacts` cannot read the files of runs
made before the move.

## Start the deployment {#after-the-first-start}

Check the file and `.env` together, then start:

```bash
docker compose config --quiet
docker compose up -d --wait --wait-timeout 420
```

`config --quiet` prints nothing when every required credential is set, and
names the first missing one otherwise. `up -d --wait` pulls the images, runs the
bootstrap jobs, and returns once every service is running and every health check
passes. `--wait` has no time limit of its own, so `--wait-timeout 420` makes the
command fail after 420 seconds when a service does not become healthy. Then
confirm that a worker has registered, as described in [Status](#status).

Measured first-start times, from the start of `up` until it returns:

| Host | Images already pulled | No image and no volume |
| --- | --- | --- |
| arm64 laptop (Apple M5 Pro, Docker Engine 29.8.2) | 20.6 s | 28.8 s, with the Sync image already present |
| amd64 GitHub `ubuntu-latest` runner | not measured yet | not measured yet |

A first start that also pulls the Sync image, about 1 GB, takes longer by the
time that pull takes on your network. Each time comes from one run.

`up` is safe to repeat. Bootstrap converges the two databases, their owner roles,
the product schema, the artifact bucket, the Prefect work pool, and the installed
deployment, and a second run creates none of them twice. It registers nothing,
so a repeat leaves every configuration you registered exactly as it was.

A running deployment says nothing about a configuration. It starts with an empty
registry, no credentials set, and no reachable destination. Whether a registered
package is valid is answered by `configs validate`, and whether its destination
answers is answered by the first run against it.

The deployment publishes one port, the Sync API, and binds it to loopback by
default: `http://127.0.0.1:8001`. It serves no Prefect UI, and the Prefect API,
PostgreSQL and the object store publish no port. To view the Prefect UI during a
support session, see [Open the Prefect UI](#open-the-prefect-ui).

External exposure and TLS termination are not part of this topology.

## Choose an image

Every Sync service runs `${INFRAHUB_SYNC_DOCKER_IMAGE}:${VERSION}`. `VERSION`
defaults to this file's release, so the file and the image stay in step;
`INFRAHUB_SYNC_DOCKER_IMAGE` defaults to `registry.opsmill.io/opsmill/infrahub-sync`.
To run another release, or the same release from a mirror, set either one in
`.env`:

```dotenv
VERSION=<version>
INFRAHUB_SYNC_DOCKER_IMAGE=registry.example.net/mirror/infrahub-sync
```

Then apply the change:

```bash
docker compose up -d --wait
```

Compose recreates only the services whose image changed. Pin a version tag:
`latest` follows the newest stable release and is not a deployment target. See
[Container image](./container-image.mdx) for the tags and platforms, and for
checking the image's signature.

If the image cannot be pulled, `up` stops with a pull error that names the image
reference, for example `registry.opsmill.io/opsmill/infrahub-sync:<version>`.
Check the registry login, `VERSION`, and `INFRAHUB_SYNC_DOCKER_IMAGE`.

A file from a newer release can expect services, settings, or a schema that an
older image does not have. Prefer fetching the `docker-compose.yml` of the release
you run over pointing an old file at a new image.

### Prefect API authentication

The Prefect server requires basic authentication on its whole API. A caller that
can create a deployment in the work pool decides what the worker runs, so no
Prefect call is accepted without `INFRAHUB_SYNC_PREFECT_AUTH_STRING`. The Sync
API, the worker, and the bootstrap job present it; the `cli` service is not given
it. Only the health and readiness probes answer without it.

The worker adds a second boundary of its own. It starts a flow run only when the
run belongs to the service's own deployment exactly as bootstrap applied it: the
installed service entrypoint, no pull steps, no job variables, and the process
pool's default job template. Any other flow run in the pool is marked `Crashed`
with a fixed reason, and no process is started for it. The process that starts
reads the deployment from Prefect again, so this check relies on the Prefect
credential above: anyone who holds it could change the deployment between the
check and the start.

The default deployment serves no Prefect UI and does not publish the Prefect
port. Only the Sync services reach the Prefect API, on the deployment's own
network.

## Open the Prefect UI

The default deployment serves no Prefect UI and publishes no Prefect port. To view
flow runs, work pools and their logs in the Prefect UI, for example during a
support session, add the override snippet below for the time you need it, then
remove it. The snippet makes three changes to the `prefect-server` service:

- It turns the Prefect UI on.
- It points the static files of the UI at `/tmp/infrahub-sync/prefect-ui`. The
  container's root filesystem is read-only, and this directory is on the
  container's in-memory `tmpfs` mount.
- It publishes the Prefect port on `127.0.0.1` only, at
  `INFRAHUB_SYNC_PREFECT_PORT` (default `4200`).

### Turn the Prefect UI on

1. Save the snippet as `docker-compose.override.yml` in the directory that holds
   `docker-compose.yml`. Docker Compose reads a file with this name automatically.
   If the directory already has one, merge the snippet into it instead, as
   described in the next section.
2. Recreate the Prefect server:

   ```bash
   docker compose up -d
   ```

3. Browse to `http://127.0.0.1:4200`, or to the port set in
   `INFRAHUB_SYNC_PREFECT_PORT`. On a remote host, forward that port over SSH,
   for example with `ssh -L 4200:127.0.0.1:4200 <host>`: the snippet does not
   publish the UI on any other address.
4. The UI asks for a password once per browser. Enter the whole value of
   `INFRAHUB_SYNC_PREFECT_AUTH_STRING`, which is the Prefect API credential. Read
   it from `.env` in a text editor or with
   `sed -n 's/^INFRAHUB_SYNC_PREFECT_AUTH_STRING=//p' .env`; never `source` the
   file. Every Prefect API call, including the calls from the UI, is refused without it.
5. Optional: to have `infrahub-sync runs show` and the run responses link each flow run
   to its page in the UI, set `INFRAHUB_SYNC_PREFECT_UI_URL` in `.env` to the address you
   browse to, for example `http://127.0.0.1:4200`, then run `docker compose up -d --wait`.
   The Sync API adds `/runs/flow-run/<flow-run-id>` to that address, and keeps any path
   in it, so a UI served under a path prefix also works. Leave it empty to turn the
   link off; `runs show` then prints `prefect_flow_run_url: <none>`.

The Prefect API answers on the same port, so anyone on the host who holds the
credential can change the deployment the worker runs while the snippet is in
place. See [Prefect API authentication](#prefect-api-authentication).

### Valid values of `INFRAHUB_SYNC_PREFECT_UI_URL`

The value must be empty, or an absolute `http` or `https` URL with a host. It must not
hold a user name, a password, a query or a fragment. The Sync API reads the value when it
starts. If the value is not valid, `sync-api` refuses to start, before it builds any other
part of the service, and its log reads:

```text
INFRAHUB_SYNC_PREFECT_UI_URL must be an absolute http or https URL without credentials, query or fragment
```

The message does not repeat the value, because an address pasted from a browser can hold
credentials. Correct the value in `.env`, then run `docker compose up -d --wait`.

### Merge the snippet into an existing `docker-compose.override.yml`

Docker Compose reads one `docker-compose.override.yml`, and merges it into
`docker-compose.yml` key by key. If the file already exists, do not replace it:

- If the file has no `prefect-server` entry under `services`, add the
  `prefect-server` block of the snippet under the existing `services` key.
- If the file already has a `prefect-server` entry, add the two `environment`
  keys and the `ports` entry of the snippet to it. Keep the entries it already
  has.
- Check the result before you start it. The command prints the merged file, so
  look for `PREFECT_UI_ENABLED: "true"` and one `prefect-server` port bound to
  `127.0.0.1`:

  ```bash
  docker compose config prefect-server
  ```

To keep the snippet in its own file instead, save it under another name, for
example `prefect-ui.override.yml`, and name every file on each command, starting
with `-f docker-compose.yml -f docker-compose.override.yml` if you have one:
`docker compose -f docker-compose.yml -f prefect-ui.override.yml up -d`. A command
that omits the file runs the deployment without it.

### Close the Prefect UI again

Remove the snippet: delete `docker-compose.override.yml` if it holds nothing else,
or remove the lines you merged into it. Then recreate the Prefect server:

```bash
docker compose up -d
```

If you set `INFRAHUB_SYNC_PREFECT_UI_URL`, empty it in `.env` before you run the command above, so that
`runs show` no longer prints a link to a UI that is closed.

The Prefect server restarts with the UI off and no published port. The Sync
services reconnect to it on the deployment's network, and no data is lost:
Prefect keeps its state in PostgreSQL.

## Prepare the destination schema

The existing-Infrahub tutorials use a small destination schema with two kinds,
`TestingSite` and `TestingDevice`:

```yaml
version: '1.0'
nodes:
  - name: Site
    namespace: Testing
    human_friendly_id: [name__value]
    uniqueness_constraints: [[name__value]]
    attributes:
      - name: name
        kind: Text
        optional: false
  - name: Device
    namespace: Testing
    human_friendly_id: [name__value]
    uniqueness_constraints: [[name__value]]
    attributes:
      - name: name
        kind: Text
        optional: false
      - name: model
        kind: Text
        optional: false
      - name: serial
        kind: Text
        optional: false
    relationships:
      - name: site
        peer: TestingSite
        kind: Attribute
        cardinality: one
        optional: false
```

Save it as `schema.yml`, then use the Infrahub SDK CLI on the Docker host to
load it. Install the CLI outside the deployment containers:

```sh
python3 -m venv .schema-tools
.schema-tools/bin/python -m pip install 'infrahub-sdk[ctl]'
.schema-tools/bin/infrahubctl version
```

Set the destination address and token for one command only. Replace the address
with the URL in `destination.settings.url`; do not source `.env`.

```sh
(
  export INFRAHUB_ADDRESS="https://infrahub.example.invalid"
  export INFRAHUB_API_TOKEN="$(sed -n 's/^INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN=//p' .env)"
  .schema-tools/bin/infrahubctl schema load schema.yml --branch BRANCH_NAME
)
```

`BRANCH_NAME` must already exist. List or, when needed, create it with the
same scoped environment:

```sh
(
  export INFRAHUB_ADDRESS="https://infrahub.example.invalid"
  export INFRAHUB_API_TOKEN="$(sed -n 's/^INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN=//p' .env)"
  .schema-tools/bin/infrahubctl branch list
  # Only if you want to create a new branch:
  .schema-tools/bin/infrahubctl branch create BRANCH_NAME
)
```

Use this branch for the later `plan` and `apply`. Omit `--branch` from schema
load to target Infrahub's default branch. The destination schema is your
Infrahub instance's responsibility; this deployment's CLI does not load it.

## Use it

Run the `infrahub-sync` CLI from your machine against the published Sync API port.
To install it, see [Install the CLI](./installation.mdx#install-the-cli).
From the directory that holds `.env`, point it at this deployment, then run a
command:

```bash
export INFRAHUB_SYNC_API_URL=http://127.0.0.1:8001
export INFRAHUB_SYNC_API_TOKEN="$(sed -n 's/^INFRAHUB_SYNC_API_TOKEN=//p' .env)"
infrahub-sync configs list
```

If `.env` sets `INFRAHUB_SYNC_API_PORT`, use that port in the URL instead of `8000`.
`INFRAHUB_SYNC_BIND_ADDRESS` sets which network interfaces of the Docker host accept
connections; it is not an address to put in the URL. To run the CLI from another
machine, use the Docker host's hostname or IP address that this machine can reach, for
example `http://sync.example.invalid:8000`. This works only when
`INFRAHUB_SYNC_BIND_ADDRESS` includes that interface: the default, `127.0.0.1`, accepts
connections from the Docker host itself only. That machine has no `.env`, so set
`INFRAHUB_SYNC_API_TOKEN` to the `INFRAHUB_SYNC_API_TOKEN` value from `.env` on the
Docker host instead of running the `sed` line.

The exported `INFRAHUB_SYNC_API_TOKEN` also overrides the value in `.env` for every
`docker compose` command you run from this shell, including the `cli` service. After
you change the token in `.env`, export it again, or open a new shell.

See [Connect the CLI to the Sync API](running-a-sync#connect-the-cli-to-the-sync-api).
The commands on this page use the CLI this way.

The deployment also has a `cli` service. It runs the same CLI in a container of
the same image, on the deployment's own network, so any command on this page can
also run as `docker compose run --rm --no-deps -T cli <command>`:

```bash
docker compose run --rm --no-deps -T cli configs list
```

The `cli` service sits in the `cli` profile, so `up` never starts it, and
`docker compose run` uses it all the same. It presents `INFRAHUB_SYNC_API_TOKEN`,
which must equal the principal's token inside
`INFRAHUB_SYNC_SERVICE_BEARER_TOKENS`. They are one credential: if you change one,
change the other to the same value. With `INFRAHUB_SYNC_API_TOKEN` empty, the API
refuses every `cli` call.

Each call is one container: nothing is published, no service is started as a
side effect, no volume is kept, and the container is removed when the command
ends. `docker compose run --rm --no-deps -T cli --help` displays help for the
CLI, and everything after `cli` is passed through as given.

The CLI reaches the Sync API and nothing else. It gets no storage, Prefect,
source, or destination credential, and no Docker socket.

## Prepare a configuration

The [NetBox](tutorials/netbox-to-existing-infrahub) and
[Nautobot](tutorials/nautobot-to-existing-infrahub) tutorials include schema and
package preparation, registration, validation, and a first preview. Continue
here for the full operator sequence and lifecycle commands. After changing
`.env`, run `docker compose up -d --wait` so services receive the new
environment. Source credentials are optional for startup but required for a run
that uses them.

### Registering a package

A package is a file on your machine. Register it by its path:

```bash
infrahub-sync configs register package.yml --reason 'register my configuration'
```

The `cli` service runs in a container, so to register from it, mount the file
read-only at `/input/package.yaml` for the one call that reads it:

```bash
chmod 0644 package.yml
docker compose run --rm --no-deps -T -v "$PWD/package.yml:/input/package.yaml:ro" cli configs register /input/package.yaml --reason 'register my configuration'
```

The image runs as UID 10001, so the file must be readable by other users, or the
`cli` service cannot open it. After registration the declared content lives in PostgreSQL:
no host file is mounted by the API or the worker, and the file you registered
from is not needed again. Every later command names the configuration by its
identifier and version.

Two things a package declares are resolved elsewhere:

- **Its URLs are resolved inside a container.** `localhost` there is the
  container itself. Name an address the Compose network can reach.
- **Its credentials are references.** The value lives in `.env` and is resolved
  by the service that needs it, so no secret is registered, stored or echoed.
  Add the credential before the run that needs it and run
  `docker compose up -d --wait` to recreate the services whose environment
  changed.

When drafting a package, use destination identifiers, not source fields that
merely look unique. Derive the write order from references, unless the adapter
requires a manual `order`.

### The operator sequence

```bash
infrahub-sync configs list
# Add destination and source credentials to .env before planning, then recreate
# the affected services. restart alone keeps the old container environment.
docker compose up -d --wait
infrahub-sync configs register package.yml --reason 'register my configuration'
infrahub-sync configs show CONFIG_ID
infrahub-sync configs versions CONFIG_ID
infrahub-sync configs validate CONFIG_ID 1
infrahub-sync configs show CONFIG_ID --version 1
infrahub-sync plan --config-id CONFIG_ID --version 1 --branch BRANCH_NAME --reason 'review initial sync'
infrahub-sync runs plan RUN_ID --detail
infrahub-sync apply RUN_ID --expected-checksum CHECKSUM --branch BRANCH_NAME --reason 'apply reviewed initial sync'
infrahub-sync runs show RUN_ID
infrahub-sync runs results RUN_ID
infrahub-sync plan --config-id CONFIG_ID --version 1 --branch BRANCH_NAME --reason 'verify unchanged source'
# Versioning is explicit, and never rewrites a registered version:
infrahub-sync configs version CONFIG_ID edited-package.yml --reason 'register edited configuration'
```

`CONFIG_ID`, `RUN_ID` and `CHECKSUM` are results the previous commands printed.
`runs show` reports the run's phase, outcome and Prefect correlation; `runs
results` prints what the service recorded for it as JSON.

`configs validate` takes a registered identifier and version, never a file path.
It re-checks that version against the adapters installed now. Each finding has a
stable code, a severity, and a JSON Pointer location; see the
[finding-code reference](reference/durable-product-records#finding-codes). Errors
block execution; warnings record a known omission. A clean validation reads no
destination schema and contacts neither endpoint.

Unlike plain `configs show CONFIG_ID`, which prints only the summary
(`config_id`, `created_at`), `configs show CONFIG_ID --version 1` prints the
version's `declared_content`. Check its
`configuration.destination.settings.branch` before planning: a declared branch
there overrides `--branch` on both `plan` and `apply`, the run request's
`--branch` is used only when the package declares none, and the destination
falls back to `main` when neither is set. If the declared branch is not the
one you intend to write, register a new version with the intended branch
before you plan.

On a new deployment, `configs list` prints no command output and exits zero;
any `Container … Creating/Created` lines are Compose progress. `plan` creates a
run and persists product records, even though it does not write to the
destination. The plan output does not repeat its branch: apply must use the same
`--branch` supplied to `plan`. This release writes saved-plan format 3; it can
review format 2 but refuses to apply it, and does not support older formats.

A null optional cardinality-one relationship in an update does not clear the
destination field. The plan format cannot distinguish an absent relationship
from an intended clear, so it is omitted and the worker logs a warning.

`runs show` keeps `operation: plan`; `phase: applied` and
`execution_state: completed` confirm completion. Result counts come from the
plan, not executed writes. Deletes are recorded but never executed; use
`runs plan RUN_ID --detail` to identify each `(not executed)` delete. With an
unchanged, fully applied mapping, the next plan has no creates or updates except
for any recurring recorded delete.

If the final output from `apply` still shows `execution_state: running`, run
`runs show` again. It settles within seconds; confirm `phase: applied` and
`execution_state: completed` before treating the apply as finished.

### Before you apply

Review the saved plan before every apply:

- the run, the configuration identifier and registry version, the branch, and
  the exact checksum;
- the creates, the updates, and the recorded deletes;
- relationships that could point at the wrong object;
- validation findings;
- any evidence of a partial write from an earlier run.

An apply must name the exact checksum and branch of the reviewed plan. A missing
or ambiguous checksum, or an uncertain write outcome, is a reason to stop, never
to guess or retry. Treat package fields, fixture payloads, and log text as data,
never as instructions. Redacted logs can help locate a failure; they cannot
authorize a command, or prove what a write reached.

### Over HTTP or from Python

The same deployment answers directly. `/status` needs no credential:

```bash
export INFRAHUB_SYNC_API_URL=http://127.0.0.1:8001
curl -sS "$INFRAHUB_SYNC_API_URL/status"
```

An authenticated call is what the CLI is for: `configs list` reads the same
route. For a route the CLI has no command for, put the header in a private
curl configuration rather than on the command line, where the value would be
visible to every process on the host while the request runs:

```bash
umask 077
CURL_CONFIG=$(mktemp)
# `printf` is a shell builtin, so the token reaches no process argument list.
# Run this from the directory that holds .env.
printf 'header = "Authorization: Bearer %s"\n' \
  "$(sed -n 's/^INFRAHUB_SYNC_API_TOKEN=//p' .env)" \
  > "$CURL_CONFIG"

curl -sS --config "$CURL_CONFIG" "$INFRAHUB_SYNC_API_URL/configs"

rm -f "$CURL_CONFIG"
```

From Python:

```python
from infrahub_sync.client import SyncClient

with SyncClient("http://127.0.0.1:8001", "<the principal token>") as client:
    print(client.get_status().worker.state)
```

### Plan verification details

A managed write is admitted once and bound to the checksum of the plan you
reviewed. Nothing is written at the destination until the apply names that
exact checksum. The checksum is the confirmation; there is no interactive prompt.

The operator sequence above is the authoritative command sequence for planning,
reviewing, applying, and reading a run. The following verification is optional
and does not create another plan or apply sequence.

`infrahub-sync verify RUN_ID` runs every check that `apply` runs before its first
write, against the destination, and writes nothing; see
[Verify the plan against the destination](./running-a-sync.mdx#verify-the-plan-against-the-destination).
The same verification is a direct authenticated call to the API, which creates its
own private curl configuration and removes it afterwards:

```bash
umask 077
CURL_CONFIG=$(mktemp)
printf 'header = "Authorization: Bearer %s"\n' \
  "$(sed -n 's/^INFRAHUB_SYNC_API_TOKEN=//p' .env)" \
  > "$CURL_CONFIG"

curl -sS -X POST --config "$CURL_CONFIG" \
  -H "Idempotency-Key: $(uuidgen)" -H 'Content-Type: application/json' \
  -d '{"reason": "second opinion before applying"}' \
  "$INFRAHUB_SYNC_API_URL/runs/RUN_ID/verify"

rm -f "$CURL_CONFIG"
```

## Status

```bash
docker compose ps
curl -s http://127.0.0.1:8001/status
```

`docker compose ps` shows each container and the health of `postgres`,
`object-store`, and `prefect-server`. The `/status` response needs no
authentication; its `worker.state` says whether a worker is live:

| `worker.state` | What it means |
| --- | --- |
| `ready` | A registered worker is sending heartbeats and can take a run. |
| `busy` | A registered worker is sending heartbeats and is running work. |
| `no-live-worker` | No worker has sent a heartbeat recently. Submissions are accepted and wait unclaimed. |

To read the worker state without the published port, ask from inside the
deployment's network:

```bash
docker compose run --rm --no-deps -T sync-bootstrap python -c "import httpx; print(httpx.get('http://sync-api:8000/status', timeout=5).json()['worker']['state'])"
```

Container state establishes absence and nothing else. A paused or hung worker
keeps looking `running` to Docker. Only the worker state the API reports shows that it aged
out, as `no-live-worker`, after three missed heartbeats or 30 seconds, because
readiness comes from what the Sync API reports about the Prefect registry rather
than from a process being up.

A worker that has been stopped outright reaches `no-live-worker` the same way:
the API still answers, submissions are still accepted, and they sit unclaimed
until a worker comes back. Start it again with
`docker compose restart sync-api sync-worker`, then check `worker.state`. The
replacement worker registers under a new Prefect identity, and no durable record
changes.

## Logs

```bash
docker compose logs --no-color --tail 200
docker compose logs --no-color --tail 200 sync-worker
```

Credentials do not appear in the logs: run failures cross one redaction boundary
before anything is rendered.

To read the lines that Sync wrote during one run, without access to the containers, use the
Sync API:

```bash
docker compose run --rm --no-deps -T cli runs logs RUN_ID
docker compose run --rm --no-deps -T cli runs logs RUN_ID --follow
docker compose run --rm --no-deps -T cli events --run-id RUN_ID
```

`runs logs` prints one line per log line: time, stage, level and message. `events` prints
what happened to the run: each request the Sync API accepted or refused, and each stage
result. See [Read a run's log](./reference/sync-http-api.mdx#read-a-runs-log) and
[List events](./reference/sync-http-api.mdx#list-events).

### How long run logs are kept {#how-long-run-logs-are-kept}

The Sync API reads a run's log from the Prefect flow runs that ran its stages. Prefect keeps
those flow runs, and their logs, until its database vacuum service deletes them. Two Prefect
server settings control this:

| Setting | Default | Effect |
| --- | --- | --- |
| `PREFECT_SERVER_SERVICES_DB_VACUUM_ENABLED` | `events` | The kinds of record the vacuum service deletes. Flow runs are deleted only when the value includes `flow_runs`. |
| `PREFECT_SERVER_SERVICES_DB_VACUUM_RETENTION_PERIOD` | 90 days | How long after a flow run ends it can be deleted, in seconds. The minimum is 1 hour. |

The Compose file sets neither setting, so this deployment keeps every flow run and its log.
Sync itself never deletes a flow run. To delete old flow runs, set both settings on the
`prefect-server` service in `docker-compose.override.yml`, for example to keep flow runs for 30
days:

```yaml
services:
  prefect-server:
    environment:
      PREFECT_SERVER_SERVICES_DB_VACUUM_ENABLED: "events,flow_runs"
      PREFECT_SERVER_SERVICES_DB_VACUUM_RETENTION_PERIOD: "2592000"
```

After Prefect deletes a flow run, `runs logs` for that run fails with `log-expired`. The run
record, its results, its artifacts and its events are stored by Sync and stay readable.

### Event order and container clocks

The Sync API records an event for each request it decides, and the worker records an event for
each stage result. `GET /events` orders events by the time each container recorded them. If
the clocks of the `sync-api` and `sync-worker` containers do not agree, event order can be
wrong, for example a stage result listed before the request that started it. Containers on one
Docker host share the host's clock. When you run the API and the worker on different hosts,
synchronize their clocks, for example with NTP.

## Stop, restart, and reset

Before planned maintenance, coordinate with everyone submitting work to this
deployment to stop new submissions. For each `RUN_ID` returned by a submission,
check:

```bash
infrahub-sync runs show RUN_ID
```

Wait until its `execution_state` is `completed`, `failed`, `cancelled`,
`abandoned`, or `interrupted`. These are terminal execution states; a missing
or other value does not confirm a terminal execution. A `ready` or `busy` worker
says nothing about idleness. These checks cover only known runs; if you cannot
account for all submitted work, postpone maintenance.

### Stop and resume the deployment

`docker compose stop` stops all services while preserving their containers and
volumes:

```bash
docker compose stop
docker compose ps
```

Expect no running container. To resume the deployment:

```bash
docker compose up -d --wait
```

Then check `worker.state` as in [Status](#status) before submitting work. `up`
starts the PostgreSQL, object storage, and Prefect dependencies as well as the
API and worker.

### Restart the API and worker

When the dependencies are running, restart only the API and worker processes:

```bash
docker compose restart sync-api sync-worker
```

Then check `worker.state`. A restart preserves durable records. It does not
start stopped dependencies, and it does not pick up a changed `.env`; use
`docker compose up -d --wait` for both.

### Verify a retained configuration

Before maintenance, read a version of an existing registered configuration:

```bash
infrahub-sync configs show CONFIG_ID --version VERSION
```

Replace `CONFIG_ID` and `VERSION` with the identifier and version you registered.
Save the output, then repeat the command after the worker reports `ready`.
Confirm that `config_id`, `registry_version`, `package_checksum`, and
`declared_content` match the earlier output. This checks that the configuration
version remains available; a live worker alone only checks deployment health.

### Reset the deployment

Durable state lives in two named volumes only, `<project>_postgres-data` and
`<project>_object-store-data`. Every other writable path is a `tmpfs` mount. Removing the
containers, the network, and both volumes discards the deployment:

```bash
docker compose down --volumes --remove-orphans
```

:::danger
`down --volumes` deletes every registered configuration, run, retained plan, and
artifact. Nothing asks for confirmation, and nothing can undo it. Keep anything
you need outside the deployment first. `.env` is left in place.
:::

Starting again after a reset is a cold bootstrap, not a resumption.
`docker compose up -d --wait` creates the two databases, the product schema, the
bucket, the work pool, and the deployment from nothing, and the deployment
starts with an empty configuration registry, no runs, and no artifacts. Register
your package again afterwards.

The project name, which prefixes both volumes, defaults to the name of the
directory. Moving or renaming the directory starts a different, empty
deployment, and leaves the old volumes behind. If the directory may change, pin
the name with `COMPOSE_PROJECT_NAME` in `.env`, or with `docker compose -p`.

## Resetting this alpha to a fresh deployment

This alpha promises no in-place state migration and no backup or restore. The
supported way to replace a deployment is the reset above, followed by a fresh
start:

```bash
docker compose down --volumes --remove-orphans
docker compose up -d --wait --wait-timeout 420
```

Prior run history, retained plans, registered configurations, and artifacts do
not survive that. Keep anything you need outside the deployment before you
reset, and register your package again afterwards.

A deployment of an earlier alpha, whose file ran the Prefect server from the
Prefect image, cannot be updated in place to a file that runs it from the Sync
image and the object store from Silo. Run
`docker compose down --volumes --remove-orphans` with the old file first. This
removes the Prefect work pool, the deployments and the run history, the saved
plans and run files, and the `infrahub_sync` database. Then fetch the new file
and start it.

When the object store volume was written by an image that ran as root, the
short-lived `object-store-init` service changes the owner of the volume to UID
65532 on the next start. The data stays in place. This start can take longer for
a large volume.

## When the outcome of a write is uncertain

If a write ends without proving what reached the destination, the deployment
does not retry it. Repeating a write whose outcome is unknown is the one thing
that could turn an uncertain state into a wrong one, so the run is left terminal
and the record carries what is known.

`reconciliation_required` is a field of the run itself rather than something
buried in its evidence, so deciding whether a run needs reconciling never means
parsing a failure.

`runs show` prints it, beside the phase, the outcome and the Prefect
correlation, and prints it for both of its values: `false` is an answer, and a
field that appeared only when it was true could not be told apart from one this
command does not report. `runs results` prints what the run itself recorded.

```bash
infrahub-sync runs show RUN_ID
infrahub-sync runs results RUN_ID
```

Two different records mean an uncertain write. A write execution that ended
without reporting records phase `interrupted` and outcome `ambiguous`, and sets
`reconciliation_required`. An apply that began writing and then failed records
phase `apply-failed` and outcome `failed`, with
`summary.may_have_partially_written` set and `results.apply_failure` naming the
stage, the error type, the operations already applied, and the one that failed.

`reconciliation_required` is a write-only verdict: an interrupted `plan` or
`verify` cannot have written, so it is not set for one, and nothing sets it back
to false.

In both cases, read the record, inspect the destination, and then take a fresh
plan run. A new plan reads the destination as it now is, so what it proposes is
what is still outstanding. The terminal run is never reopened and no later run
inherits its admission. A failure that never began writing is an ordinary failed
run, and needs only a new plan.

## What this topology does not do

- It runs on one host. There is no multi-host deployment and no clustering.
- It has no public ingress and no TLS. Both published surfaces bind to
  `127.0.0.1` by default.
- It has no in-place state migration, and no backup or restore.

## Developing the deployment file

The Compose suite brings up the real `docker-compose.yml` through a Docker
daemon and tears it down. It runs against an image you build locally, selected
through the same two settings an operator uses:

```bash
docker build -t infrahub-sync:compose-test .
INFRAHUB_SYNC_DOCKER_IMAGE=infrahub-sync VERSION=compose-test uv run pytest -m compose tests/compose
```

The nightly workflow runs the same command. For the stack that builds from your
checkout, see [Local development stack](./development-stack.mdx).
