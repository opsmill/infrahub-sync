title: Compose deployment
---

Each release deploys Infrahub Sync next to an Infrahub deployment from a single
file, `docker-compose.yml`, and a `.env` file that you write beside it. The
deployment runs the Sync API, the Sync worker, and S3-compatible object storage.
It runs its work on Infrahub's task manager, which is Infrahub's Prefect server,
and keeps its records in its own database on the task manager's PostgreSQL
server. Your configurations live in Infrahub itself, and callers sign in with their own
Infrahub API tokens. Docker pulls the Sync image from the OpsMill
registry like every other service image. A host needs Docker with Docker Compose
2.24 or later, and nothing else: no product checkout, no Python, no `uv`.

For the shortest path to a running deployment, follow the
[Compose quickstart](quickstart-compose). This page is the reference for that
flow, and for the configuration and reviewed-run procedure that follows it.

## Prerequisites

- Docker Engine with Docker Compose 2.24 or later. The file carries the database
  bootstrap script as a top-level `configs` entry with inline `content`, which
  older Compose versions cannot parse. Check the version with:

  ```bash
  docker compose version --short
  ```

- A Linux host on `amd64` or `arm64`. The image is published for both platforms,
  and Docker pulls the one that matches the host.
- A registry login. Until the 3.0.0 release, the registry project is open to
  invited testers only, so run `docker login registry.opsmill.io` before the
  first start. See [Install Infrahub Sync](./installation.mdx#run-the-container-image).
- An Infrahub release that ships the Prefect version this Sync release requires,
  started with Docker Compose on the same host. Infrahub 1.11.3 and 1.11.4 ship
  Prefect 3.8.6. Sync refuses to start against another Prefect version, naming
  both versions.
- The Sync schema extension loaded into that Infrahub, and an Infrahub account for
  Sync with an API token. See [Load the Sync schema](#load-the-sync-schema).
- Port 8000 free on `127.0.0.1`, or another port set in `.env`.

## Get the file

Fetch `docker-compose.yml` from the release tag you want to run. Tags carry the
bare version, for example `3.0.0`:

```bash
mkdir infrahub-sync && cd infrahub-sync
curl -fsSLO https://raw.githubusercontent.com/opsmill/infrahub-sync/<version>/docker-compose.yml
```

The file pins the Sync image of the release it was taken from. Every other image
carries its digest, so a re-pointed tag cannot change what the file runs.

| Service | What it does |
| --- | --- |
| `db-bootstrap` | A short-lived job that creates Sync's product database and its owner role on the task manager's PostgreSQL server. |
| `object-store-init`, `object-store` | S3-compatible object storage for plans and artifacts, and a short-lived job that prepares its volume. |
| `sync-bootstrap` | A short-lived job that creates the product schema, the bucket, the work pool, and the Prefect deployment. |
| `sync-api` | The Sync API. |
| `sync-worker` | The Sync worker that runs plans and applies. |
| `cli` | The Sync CLI, in profile `cli`. It runs only when you call it. |

The API and the worker share no mount, no volume, and no scratch directory. Run
state travels between them through PostgreSQL and the object store, which is
why the worker needs no configuration mount and why replacing it loses nothing.
The product database lives on the task manager's PostgreSQL server, so the
object store holds the only volume that survives a restart.

### Infrahub's task manager

The file joins Infrahub's Compose network, `infrahub_default` unless you set
`INFRAHUB_NETWORK`, and reaches two Infrahub services on it by name:
`task-manager`, Infrahub's Prefect server, and `task-manager-db`, its PostgreSQL
server. Sync creates its own `infrahub_sync` database there and never touches
Infrahub's `prefect` database. Its runs appear in Infrahub's task list, tagged
with their branch and their stage, and in the **Tasks** tab of the run's `SyncRun`
and `SyncConfiguration` nodes.

One Infrahub holds one Sync deployment. Sync registers a fixed Prefect deployment,
`infrahub-sync-service/run`, on the task manager, so a second Sync deployment
started against the same Infrahub would take over the first one's runs. Run a
second Sync deployment against its own Infrahub.

Infrahub removes the task records of a deleted branch, Sync runs included, and
`infrahub tasks flush flow-runs` removes old ones. That removes the run's Prefect
state and logs only: Sync's own run records stay, and the API reports such a run's
execution as unavailable.

Run every `docker compose` command on this page from the directory that holds
`docker-compose.yml` and `.env`. Compose finds both files there without `-f` or
`--env-file`.

## Load the Sync schema

Sync keeps configurations, their versions, and a copy of each run in Infrahub, in four
kinds that the schema extension `schema/sync.yml` adds: `SyncConfiguration`,
`SyncConfigurationVersion`, `SyncRun`, and `SyncApproval`. Load it once per installation,
and again on each Sync upgrade that changes it. Sync never loads a schema itself: the API
and the worker check the kinds at startup and refuse to start when one is missing.

Fetch the file from the same release tag as `docker-compose.yml`, and load it through a
branch, as for any schema change. Run `infrahubctl` with an Infrahub administrator's token,
as in [Prepare the destination schema](#prepare-the-destination-schema):

```sh
curl -fsSLO https://raw.githubusercontent.com/opsmill/infrahub-sync/<version>/schema/sync.yml
infrahubctl branch create sync-schema
infrahubctl schema load sync.yml --branch sync-schema
infrahubctl branch merge sync-schema
```

### The Sync service account

Sync reads configurations and writes versions, run copies, and approvals with its own
Infrahub account. Create an account for it, give it a role with these object permissions,
and create an API token for the account. The token is `INFRAHUB_SYNC_INFRAHUB_TOKEN` in
`.env`.

| Namespace | Name | Action | Decision |
| --- | --- | --- | --- |
| `Sync` | `Configuration` | `view` | `allow_all` (Sync reads a configuration on another branch when a caller validates it there) |
| `Sync` | `ConfigurationVersion`, `Run`, `Approval` | `view` | `allow_default` |
| `Sync` | `ConfigurationVersion`, `Run`, `Approval` | `create` | `allow_default` |
| `Sync` | `Run` | `update` | `allow_default` |
| global | `edit_default_branch` | — | `allow_all` (Infrahub requires it for any write on the default branch, where every Sync record lives) |

### Caller permissions

Everyone who calls Sync, through the `cli` service, HTTP, or Python, uses their own Infrahub
API token. Sync asks Infrahub who the caller is and checks these permissions on the default
branch:

| To | Grant |
| --- | --- |
| Read configurations and versions, validate a configuration | `view` on `SyncConfiguration` |
| Read runs, plans, results, and artifacts | `view` on `SyncRun` |
| Plan with `diff`, or verify a plan | `create` on `SyncRun` |
| Apply a reviewed plan | `create` on `SyncApproval` |
| Run `sync` | `create` on `SyncRun` and on `SyncApproval` |
| Cancel a run | `update` on `SyncRun` |

Granting `create` on `SyncRun` without `create` on `SyncApproval` lets an account plan but
not write. The permission alone decides: an account with `create` on `SyncApproval` can
apply a plan that another account created. See
[Permissions](./reference/sync-http-api.mdx#permissions).

## The `.env` file {#configuration-prerequisites}

Compose reads `.env` from the directory of `docker-compose.yml`. Nothing in the
file defaults a credential: each required variable is guarded, and a missing one
stops Compose before any container starts, with a message naming it:

```text
required variable INFRAHUB_SYNC_PRODUCT_PASSWORD is missing a value: INFRAHUB_SYNC_PRODUCT_PASSWORD is required
```

### Required credentials

| Variable | Used by |
| --- | --- |
| `INFRAHUB_TASKMANAGER_DB_PASSWORD` | `db-bootstrap`: the administrator password of Infrahub's task-manager PostgreSQL server, the same value Infrahub's own Compose file uses |
| `INFRAHUB_SYNC_PRODUCT_PASSWORD` | `db-bootstrap` and the Sync services: the product database role |
| `INFRAHUB_SYNC_S3_ACCESS_KEY` | `object-store` and the Sync services |
| `INFRAHUB_SYNC_S3_SECRET_KEY` | `object-store` and the Sync services |
| `INFRAHUB_SYNC_INFRAHUB_TOKEN` | `sync-api` and `sync-worker`: the API token of [the Sync service account](#the-sync-service-account). It is never a caller's token, and Sync never logs it. |

The database connection strings are composed inside the file from the role,
database, and password settings. A password used in them must be URL-safe:
hexadecimal output is. To use another password, set the whole connection string
in `INFRAHUB_SYNC_DATABASE_URL` instead.

### Optional settings

| Variable | Default | Meaning |
| --- | --- | --- |
| `INFRAHUB_SYNC_TOKEN` | empty | Your own Infrahub API token, which the `cli` service presents. Set it in your shell rather than in `.env` when several people use the host. Empty, every `cli` call stops before it reaches the API, with `error: client-input` and `argument: token`. |
| `INFRAHUB_SYNC_INFRAHUB_ADDRESS` | `http://infrahub-server:8000` | The Infrahub that holds the configurations, as `sync-api` and `sync-worker` reach it on Infrahub's Compose network. |
| `INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN` | empty | The destination Infrahub token, for a package that references it. |
| `INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN`, `INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN` | empty | Source tokens, for a package that references them. Only the worker receives them. |
| `VERSION` | the release the file was taken from | The tag of the Sync image. See [Choose an image](#choose-an-image). |
| `INFRAHUB_SYNC_DOCKER_IMAGE` | `registry.opsmill.io/opsmill/infrahub-sync` | The repository of the Sync image. |
| `INFRAHUB_SYNC_DATABASE_URL` | composed | The product database connection string, as a whole. |
| `INFRAHUB_SYNC_PREFECT_AUTH_STRING` | empty | A Prefect API credential, when the task manager is put behind one. See [Prefect API authentication](#prefect-api-authentication). |
| `INFRAHUB_NETWORK` | `infrahub_default` | Infrahub's Compose network. |
| `INFRAHUB_WORKFLOW_ADDRESS`, `INFRAHUB_WORKFLOW_PORT` | `task-manager`, `4200` | Infrahub's task manager, as Infrahub's own Compose file names it. |
| `INFRAHUB_TASKMANAGER_DB_HOST` | `task-manager-db` | The task manager's PostgreSQL server. |
| `INFRAHUB_TASKMANAGER_DB_USER` | `postgres` | Its administrator role. |
| `INFRAHUB_SYNC_BIND_ADDRESS` | `127.0.0.1` | The address the published API port binds to. |
| `INFRAHUB_SYNC_API_PORT` | `8000` | The published Sync API port. |
| `INFRAHUB_SYNC_PRODUCT_DATABASE`, `INFRAHUB_SYNC_PRODUCT_ROLE` | `infrahub_sync` | The product database and its owner role. |
| `INFRAHUB_SYNC_S3_BUCKET`, `INFRAHUB_SYNC_S3_PREFIX` | `infrahub-sync` | The artifact bucket and key prefix. |
| `INFRAHUB_SYNC_S3_REGION` | `us-east-1` | The object store region. |
| `INFRAHUB_SYNC_WORK_POOL` | `infrahub-sync` | The Prefect work pool. |
| `INFRAHUB_SYNC_RUN_ADMISSION_TTL_SECONDS` | `300` | How long a run admission stays valid. |
| `PREFECT_WORKER_QUERY_SECONDS`, `PREFECT_WORKER_HEARTBEAT_SECONDS` | `10` | The worker's polling and heartbeat intervals. |

### An example `.env`

Every value below is a placeholder. Replace each one with a random value of
your own:

```dotenv
# Required credentials
INFRAHUB_TASKMANAGER_DB_PASSWORD=<Infrahub's task-manager database password>
INFRAHUB_SYNC_PRODUCT_PASSWORD=<random hex>
INFRAHUB_SYNC_S3_ACCESS_KEY=<random hex>
INFRAHUB_SYNC_S3_SECRET_KEY=<random hex>
INFRAHUB_SYNC_INFRAHUB_TOKEN=<the Sync service account's Infrahub API token>

# Only for a package that references them
# INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN=<your Infrahub token>
# INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN=<your NetBox token>
# INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN=<your Nautobot token>

# Optional: another release, or a mirror of the image
# VERSION=<version>
# INFRAHUB_SYNC_DOCKER_IMAGE=registry.opsmill.io/opsmill/infrahub-sync
```

To generate the credentials instead, run this once, in the directory of
`docker-compose.yml`. It reads `/dev/urandom` and needs no Python. It asks for the
Sync service account's token first; `read -s` keeps it off the screen and out of
your shell history:

```bash
rand() { od -An -tx1 -N"$1" /dev/urandom | tr -d ' \n'; }
read -rs -p 'Sync service account token: ' sync_service_token; echo
# mktemp creates the file readable by you alone, whatever an existing .env allowed.
env_file=$(mktemp .env.XXXXXX)
cat > "$env_file" <<EOF
INFRAHUB_TASKMANAGER_DB_PASSWORD=${INFRAHUB_TASKMANAGER_DB_PASSWORD:-postgres}
INFRAHUB_SYNC_PRODUCT_PASSWORD=$(rand 24)
INFRAHUB_SYNC_S3_ACCESS_KEY=$(rand 12)
INFRAHUB_SYNC_S3_SECRET_KEY=$(rand 24)
INFRAHUB_SYNC_INFRAHUB_TOKEN=$sync_service_token
EOF
mv -f "$env_file" .env
unset sync_service_token
```

The `cli` service presents `INFRAHUB_SYNC_TOKEN`, your own Infrahub API token. Export it
in your shell before you call the CLI; Compose passes it to the `cli` service.

Handle `.env` as the secret it is:

- Keep it at mode 0600 and out of version control.
- Never `source` it: it holds every credential of the deployment.
- Nothing in the deployment prints a credential value. A refusal names the
  variable, never its value.

:::warning
A variable exported in your shell overrides the same name in `.env`. An exported
`VERSION`, a common name, silently changes the Sync image. Check `env` before you
start, or unset it.
:::

### Credentials in a package

A configuration package holds credential references, never values. The value
goes in `.env`:

```yaml
token:
  $credential: infrahub-token
credentials:
  infrahub-token:
    provider: env
    identifier: INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN
```

An `env` identifier must start with `INFRAHUB_SYNC_CREDENTIAL_`; validation refuses any
other identifier, so a package cannot name the deployment's own storage, database, or
Prefect settings.

If you upgrade from an earlier alpha, move to the prefixed names:

1. In `.env`, rename `INFRAHUB_API_TOKEN`, `NETBOX_TOKEN`, and `NAUTOBOT_TOKEN` to
   `INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN`, `INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN`,
   and `INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN`.
2. Change the `identifier` of each `env` credential in your packages to the new name.
3. Update the document of each configuration in Infrahub. The next run records it as a
   new version. A version recorded before the upgrade keeps its old identifiers, and its
   runs fail in the worker.
4. Run `docker compose up -d --wait`, so the services receive the renamed variables.

:::note
A container reads its environment once, when it is created. After changing a
value in `.env`, run `docker compose up -d --wait` again, which recreates the
services whose environment changed. `docker compose restart` keeps the
environment the containers were created with.
:::

### Reading from NetBox or Nautobot

The image installs the bundled NetBox and Nautobot source adapters, so a package
may declare either as its source. Set only the token your package names:

```dotenv
INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN=<your NetBox token>
# INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN=<your Nautobot token>
```

```yaml
configuration:
  source:
    name: netbox
    settings:
      url: "http://netbox.example.net:8080"
      token:
        $credential: netbox-token
credentials:
  netbox-token:
    provider: env
    identifier: INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN
```

Nautobot uses the same shape with `nautobot`, `nautobot-token` and
`INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN`.

- **Name a URL a container can reach.** The worker resolves it from inside the
  Compose network, where `localhost` is the worker itself. If NetBox, Nautobot, or
  Infrahub runs in containers on the same host and publishes only on `127.0.0.1`, the
  worker cannot reach it: publish it on an address containers can reach and use
  `http://<host-IP>:<port>`.
- **The declared `url` is the one used.** `NETBOX_ADDRESS`, `NETBOX_URL`,
  `NAUTOBOT_ADDRESS` and `NAUTOBOT_URL` exported in your shell are ignored: a
  run reads what its package declares.
- **Both tokens are optional.** A deployment that reads from neither source
  starts normally, and a package naming one source does not need the other's
  token. When a package does select a source, a missing or empty token fails
  that run and the message names the environment variable, never its value.
- **Start again after changing either value.** `docker compose up -d --wait`
  recreates the worker with the new value; `restart` keeps the old one.

Only `sync-worker` receives these tokens. Validation judges declared content
without resolving a source secret, so the API and the bootstrap job never hold one.

:::note
That both adapters install and import is a packaging property of this release.
It is not a statement that any particular NetBox or Nautobot server version has
been qualified against it.
:::

## Start the deployment {#after-the-first-start}

Check the file and `.env` together, then start:

```bash
docker compose config --quiet
docker compose up -d --wait
```

`config --quiet` prints nothing when every required credential is set, and
names the first missing one otherwise. `up -d --wait` pulls the images, runs the
bootstrap jobs, and returns once every service is running and every health check
passes. Then confirm that a worker has registered, as described in
[Status](#status).

`up` is safe to repeat. Bootstrap converges the product database, its owner role,
the product schema, the artifact bucket, the Prefect work pool on Infrahub's task
manager, and the installed deployment, and a second run creates none of them twice. It
writes nothing to Infrahub, so a repeat leaves every configuration exactly as it was.

The API and the worker check at startup that the Sync schema is loaded, and refuse to
start when a kind or field is missing. If Infrahub cannot be reached at that moment, they
start with a warning.

A running deployment says nothing about a configuration. Whether a configuration
is valid is answered by `configs validate`, and whether its destination answers
is answered by the first run against it.

The published API binds to loopback by default:

| Surface | Address |
| --- | --- |
| Sync API | `http://127.0.0.1:8000` |
| Runs and their logs | Infrahub's task list, and the Prefect UI Infrahub publishes |

External exposure and TLS termination are not part of this topology.

## Choose an image

Every Sync service runs `${INFRAHUB_SYNC_DOCKER_IMAGE}:${VERSION}`. `VERSION`
defaults to this file's release, so the file and the image stay in step;
`INFRAHUB_SYNC_DOCKER_IMAGE` defaults to `registry.opsmill.io/opsmill/infrahub-sync`.
To run another release, or the same release from a mirror, set either one in
`.env`:

```dotenv
VERSION=<version>
INFRAHUB_SYNC_DOCKER_IMAGE=registry.example.net/mirror/infrahub-sync
```

Then apply the change:

```bash
docker compose up -d --wait
```

Compose recreates only the services whose image changed. Pin a version tag:
`latest` follows the newest stable release and is not a deployment target. See
[Container image](./container-image.mdx) for the tags and platforms, and for
checking the image's signature.

If the image cannot be pulled, `up` stops with a pull error that names the image
reference, for example `registry.opsmill.io/opsmill/infrahub-sync:<version>`.
Check the registry login, `VERSION`, and `INFRAHUB_SYNC_DOCKER_IMAGE`.

A file from a newer release can expect services, settings, or a schema that an
older image does not have. Prefer fetching the `docker-compose.yml` of the release
you run over pointing an old file at a new image.

### Prefect API authentication

Infrahub's task manager offers no API credential setting, so by default anything
that can reach it on Infrahub's network can read and change its deployments and
flow runs. That includes Infrahub's own task workers, which run the Python code of
the repositories added to Infrahub. A credential does not change this much: if the
task manager is put behind a proxy that checks one, Infrahub's task workers need
it too, and so does the code they run. Keep Infrahub's network private to Infrahub
and Sync either way.

Sync therefore does not rely on the credential. If you set one in
`INFRAHUB_SYNC_PREFECT_AUTH_STRING`, the Sync API, the worker, and the bootstrap
job present it; the `cli` service is not given it. At startup the API and the
worker log `prefect_auth=credential` or `prefect_auth=network-isolation`; the
first only says a credential is sent, not that the task manager checks it. A task
manager that refuses the credential stops the API at startup.

The boundary Sync relies on is the worker's. It starts a flow run only when the
run belongs to the service's own deployment exactly as bootstrap applied it: the
installed service entrypoint, no pull steps, no job variables, and the process
pool's default job template. Any other flow run in the pool is marked `Crashed`
with a fixed reason, and no process is started for it. After that check nothing
reads the deployment again: the child process runs the installed service flow
directly, and the worker's crash and cancellation hooks load the same installed
flow. A deployment changed after admission therefore cannot change what runs.

Both the API and the worker refuse to start when the task manager runs another
Prefect version than the one this Sync release requires, and name both versions.
The check runs at startup only: when Infrahub upgrades its Prefect version,
upgrade Sync with it, or the next restart of Sync refuses to start.

## Wrapper equivalents

Earlier alphas shipped an `infrahub-sync-compose` wrapper script. It is gone: each
of its commands has a plain `docker compose` equivalent.

| Wrapper command | `docker compose` equivalent |
| --- | --- |
| `init` | Write `.env` by hand, or generate it as shown in [An example `.env`](#an-example-env). There is no instance identity: the Compose project name, which defaults to the directory name, plays that role. |
| `preflight` | `docker compose version --short`, expecting 2.24 or later, then `docker compose config --quiet`, which names the first missing credential. `up` reports a pull failure or a port in use. |
| `start` | `docker compose up -d --wait`, then check the worker as in [Status](#status). |
| `status` | `docker compose ps`, then `curl -s http://127.0.0.1:8000/status` and read `worker.state`. |
| `logs` | `docker compose logs --no-color --tail 200 [service]` |
| `stop` | `docker compose stop` |
| `restart` | `docker compose restart sync-api sync-worker`, then check the worker. It does not pick up a changed `.env`. |
| `reset` | `docker compose down --volumes --remove-orphans`, then drop Sync's database. **This deletes every run, retained plan, and artifact**; configurations, versions, and run copies stay in Infrahub, and nothing asks for confirmation. See [Reset the deployment](#reset-the-deployment). |
| `cli` | `docker compose run --rm --no-deps -T cli ARGS`. Export `INFRAHUB_SYNC_TOKEN` first. |

The image binding file, the `.instance` file, `operator.env`, and the
`secrets/` directory have no successor. The administrator password that lived in
`secrets/` has no successor either: Sync now uses Infrahub's task-manager database
server, whose administrator password is `INFRAHUB_TASKMANAGER_DB_PASSWORD`.

## Prepare the destination schema

The existing-Infrahub tutorials use a small destination schema with two kinds,
`TestingSite` and `TestingDevice`:

```yaml
version: '1.0'
nodes:
  - name: Site
    namespace: Testing
    human_friendly_id: [name__value]
    uniqueness_constraints: [[name__value]]
    attributes:
      - name: name
        kind: Text
        optional: false
  - name: Device
    namespace: Testing
    human_friendly_id: [name__value]
    uniqueness_constraints: [[name__value]]
    attributes:
      - name: name
        kind: Text
        optional: false
      - name: model
        kind: Text
        optional: false
      - name: serial
        kind: Text
        optional: false
    relationships:
      - name: site
        peer: TestingSite
        kind: Attribute
        cardinality: one
        optional: false
```

Save it as `schema.yml`, then use the Infrahub SDK CLI on the Docker host to
load it. Install the CLI outside the deployment containers:

```sh
python3 -m venv .schema-tools
.schema-tools/bin/python -m pip install 'infrahub-sdk[ctl]'
.schema-tools/bin/infrahubctl version
```

Set the destination address and token for one command only. Replace the address
with the URL in `destination.settings.url`; do not source `.env`.

```sh
(
  export INFRAHUB_ADDRESS="https://infrahub.example.invalid"
  export INFRAHUB_API_TOKEN="$(sed -n 's/^INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN=//p' .env)"
  .schema-tools/bin/infrahubctl schema load schema.yml --branch BRANCH_NAME
)
```

`BRANCH_NAME` must already exist. List or, when needed, create it with the
same scoped environment:

```sh
(
  export INFRAHUB_ADDRESS="https://infrahub.example.invalid"
  export INFRAHUB_API_TOKEN="$(sed -n 's/^INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN=//p' .env)"
  .schema-tools/bin/infrahubctl branch list
  # Only if you want to create a new branch:
  .schema-tools/bin/infrahubctl branch create BRANCH_NAME
)
```

Use this branch for the later `diff` and `apply`. Omit `--branch` from schema
load to target Infrahub's default branch. The destination schema is your
Infrahub instance's responsibility; this deployment's CLI does not load it.

## Use it

The `cli` service runs the shipped CLI against this deployment, in a container of
the same image, on the deployment's own network:

```bash
docker compose run --rm --no-deps -T cli configs list
```

The `cli` service sits in the `cli` profile, so `up` never starts it, and
`docker compose run` uses it all the same. Its environment holds two settings:
`INFRAHUB_SYNC_API_URL`, set to `http://sync-api:8000` on the deployment's network,
and `INFRAHUB_SYNC_TOKEN`. It presents `INFRAHUB_SYNC_TOKEN`, your
own Infrahub API token, from your shell or `.env`. Sync checks your Infrahub
permissions on each call; see [Caller permissions](#caller-permissions). With
`INFRAHUB_SYNC_TOKEN` empty, the client refuses every `cli` call before it reaches the
API, printing `error: client-input` and `argument: token`. A token that Infrahub refuses
gets `401` from the API.

Each call is one container: nothing is published, no service is started as a
side effect, no volume is kept, and the container is removed when the command
ends. `docker compose run --rm --no-deps -T cli --help` displays help for the
CLI, and everything after `cli` is passed through as given.

The CLI reaches the Sync API and nothing else. It gets no storage, Prefect,
source, or destination credential, and no Docker socket.

## Prepare a configuration

The [NetBox](tutorials/netbox-to-existing-infrahub) and
[Nautobot](tutorials/nautobot-to-existing-infrahub) tutorials include schema and
package preparation, validation, and a first preview. Continue here for the full
operator sequence and lifecycle commands. After changing `.env`, run
`docker compose up -d --wait` so services receive the new environment. Source
credentials are optional for startup but required for a run that uses them.

### Create the configuration in Infrahub

A configuration is a `SyncConfiguration` node in Infrahub: a `name`, which Sync calls
`CONFIG_ID`, an optional `description`, and a `document` that holds the whole
[configuration package](configuration-package) as YAML or JSON. Create it in the Infrahub
web interface, or load an object file with `infrahubctl`:

```sh
infrahubctl object load sync-configuration.yml
```

[`examples/netbox_to_infrahub/sync-configuration.yml`](https://github.com/opsmill/infrahub-sync/blob/feature/v3-develop/examples/netbox_to_infrahub/sync-configuration.yml)
is a complete object file. Make the change on an Infrahub branch to review it in a
proposed change; runs read the configuration on the default branch once it is merged.
The API and the worker mount no host file.

Two things a package declares are resolved elsewhere:

- **Its URLs are resolved inside a container.** `localhost` there is the
  container itself. Name an address the Compose network can reach.
- **Its credentials are references.** The value lives in `.env` and is resolved
  by the service that needs it, so no secret is stored in Infrahub or echoed.
  Add the credential before the run that needs it and run
  `docker compose up -d --wait` to recreate the services whose environment
  changed.

When drafting a package, use destination identifiers, not source fields that
merely look unique. Derive the write order from references, unless the adapter
requires a manual `order`.

### The operator sequence

```bash
export INFRAHUB_SYNC_TOKEN=<your Infrahub API token>
docker compose run --rm --no-deps -T cli configs list
# Add destination and source credentials to .env before planning, then recreate
# the affected services. restart alone keeps the old container environment.
docker compose up -d --wait
docker compose run --rm --no-deps -T cli configs show CONFIG_ID
docker compose run --rm --no-deps -T cli configs validate CONFIG_ID
docker compose run --rm --no-deps -T cli diff --config-id CONFIG_ID --branch BRANCH_NAME --reason 'review initial sync'
docker compose run --rm --no-deps -T cli runs plan RUN_ID --detail
docker compose run --rm --no-deps -T cli apply RUN_ID --expected-checksum CHECKSUM --branch BRANCH_NAME --reason 'apply reviewed initial sync'
docker compose run --rm --no-deps -T cli runs show RUN_ID
docker compose run --rm --no-deps -T cli runs results RUN_ID
docker compose run --rm --no-deps -T cli diff --config-id CONFIG_ID --branch BRANCH_NAME --reason 'verify unchanged source'
docker compose run --rm --no-deps -T cli configs versions CONFIG_ID
# Check an edit on an Infrahub branch before you merge it; this records nothing:
docker compose run --rm --no-deps -T cli configs validate CONFIG_ID --branch CHANGE_BRANCH
```

`CONFIG_ID` is the configuration's `name` in Infrahub. `RUN_ID` and `CHECKSUM` are
results the previous commands printed. `runs show` reports the run's phase, outcome
and Prefect correlation; `runs results` prints what the service recorded for it as
JSON.

`configs validate CONFIG_ID` checks the configuration's document on the Infrahub
default branch, or on the branch `--branch` names, and records nothing.
`configs validate CONFIG_ID --version N` re-checks a recorded version against the
adapters installed now. Each finding has a stable code, a severity, and a JSON
Pointer location; see the
[finding-code reference](reference/durable-product-records#finding-codes). Errors
block execution; warnings record a known omission. A clean validation reads no
destination schema and contacts neither endpoint.

`diff` without `--version` plans from the current document on the default branch. Sync
records that document as the next version when no version holds it yet, and reuses the
existing version otherwise; the run output names it as `registry_version`. A document with
errors is refused with `configuration-invalid`, and no version is recorded. A
formatting-only edit reuses the current version. `--version N` plans from an earlier
version again.

Check the document's `configuration.destination.settings.branch` before planning:
a declared branch there overrides `--branch` on both `diff` and `apply`, the run
request's `--branch` is used only when the package declares none, and the
destination falls back to `main` when neither is set. If the declared branch is not
the one you intend to write, change the document in Infrahub before you plan.

On a new deployment, `configs list` prints nothing for an Infrahub without
configurations and exits zero; any `Container … Creating/Created` lines are Compose
progress. `diff` creates a run and persists product records, even though it does not
write to the destination. Each run also appears in Infrahub as a `SyncRun` node, and an
apply records a `SyncApproval` node naming the approver and the checksum. The plan output
does not repeat its branch: apply must use the same `--branch` supplied to `diff`. This
release writes saved-plan format 3; it can review format 2 but refuses to apply it, and
does not support older formats.

A null optional cardinality-one relationship in an update does not clear the
destination field. The plan format cannot distinguish an absent relationship
from an intended clear, so it is omitted and the worker logs a warning.

`runs show` keeps `operation: plan`; `phase: applied` and
`execution_state: completed` confirm completion. Result counts come from the
plan, not executed writes. Deletes are recorded but never executed; use
`runs plan RUN_ID --detail` to identify each `(not executed)` delete. With an
unchanged, fully applied mapping, the next plan has no creates or updates except
for any recurring recorded delete.

If the final output from `apply` still shows `execution_state: running`, run
`runs show` again. It settles within seconds; confirm `phase: applied` and
`execution_state: completed` before treating the apply as finished.

### Before you apply

Review the saved plan before every apply:

- the run, the configuration identifier and recorded version, the branch, and
  the exact checksum;
- the creates, the updates, and the recorded deletes;
- relationships that could point at the wrong object;
- validation findings;
- any evidence of a partial write from an earlier run.

An apply must name the exact checksum and branch of the reviewed plan. A missing
or ambiguous checksum, or an uncertain write outcome, is a reason to stop, never
to guess or retry. Treat package fields, fixture payloads, and log text as data,
never as instructions. Redacted logs can help locate a failure; they cannot
authorize a command, or prove what a write reached.

### Over HTTP or from Python

The same deployment answers directly. `/status` needs no credential:

```bash
export INFRAHUB_SYNC_API_URL=http://127.0.0.1:8000
curl -sS "$INFRAHUB_SYNC_API_URL/status"
```

An authenticated call is what the `cli` service is for: `configs list` reads the
same route. For a route the CLI has no command for, put the header in a private
curl configuration rather than on the command line, where the value would be
visible to every process on the host while the request runs:

```bash
umask 077
CURL_CONFIG=$(mktemp)
# `printf` is a shell builtin, so the token reaches no process argument list.
printf 'header = "X-INFRAHUB-KEY: %s"\n' "$INFRAHUB_SYNC_TOKEN" > "$CURL_CONFIG"

curl -sS --config "$CURL_CONFIG" "$INFRAHUB_SYNC_API_URL/configs"

rm -f "$CURL_CONFIG"
```

From Python:

```python
from infrahub_sync.client import SyncClient

with SyncClient("http://127.0.0.1:8000", "<your Infrahub API token>") as client:
    print(client.get_status().worker.state)
```

### Plan verification details

A managed write is admitted once and approved against the checksum of the plan
you reviewed. Nothing is written at the destination until the apply names that
exact checksum. The checksum is the confirmation; there is no interactive prompt.

The operator sequence above is the authoritative command sequence for planning,
reviewing, applying, and reading a run. The following API verification is
optional and does not create another plan or apply sequence.

An independent verification of a retained plan is the one step here with no CLI
command. It is a direct authenticated call, so it creates its own private curl
configuration and removes it afterwards:

```bash
umask 077
CURL_CONFIG=$(mktemp)
printf 'header = "X-INFRAHUB-KEY: %s"\n' "$INFRAHUB_SYNC_TOKEN" > "$CURL_CONFIG"

curl -sS -X POST --config "$CURL_CONFIG" \
  -H "Idempotency-Key: $(uuidgen)" -H 'Content-Type: application/json' \
  -d '{"reason": "second opinion before applying"}' \
  "$INFRAHUB_SYNC_API_URL/runs/RUN_ID/verify"

rm -f "$CURL_CONFIG"
```

## Status

```bash
docker compose ps
curl -s http://127.0.0.1:8000/status
```

`docker compose ps` shows each container and the health of `object-store`.
Infrahub's own Compose project reports the task manager and its database. The
`/status` response needs no authentication; its `worker.state` says whether a
worker is live:

| `worker.state` | What it means |
| --- | --- |
| `ready` | A registered worker is sending heartbeats and can take a run. |
| `busy` | A registered worker is sending heartbeats and is running work. |
| `no-live-worker` | No worker has sent a heartbeat recently. Submissions are accepted and wait unclaimed. |

To read the worker state without the published port, ask from inside the
deployment's network:

```bash
docker compose run --rm --no-deps -T sync-bootstrap python -c "import httpx; print(httpx.get('http://sync-api:8000/status', timeout=5).json()['worker']['state'])"
```

Container state establishes absence and nothing else. A paused or hung worker
keeps looking `running` to Docker. Only the worker state the API reports shows that it aged
out, as `no-live-worker`, after three missed heartbeats or 30 seconds, because
readiness comes from what the Sync API reports about the Prefect registry rather
than from a process being up.

A worker that has been stopped outright reaches `no-live-worker` the same way:
the API still answers, submissions are still accepted, and they sit unclaimed
until a worker comes back. Start it again with
`docker compose restart sync-api sync-worker`, then check `worker.state`. The
replacement worker registers under a new Prefect identity, and no durable record
changes.

## Stop, restart, and reset

Before planned maintenance, coordinate with everyone submitting work to this
deployment to stop new submissions. For each `RUN_ID` returned by a submission,
check:

```bash
docker compose run --rm --no-deps -T cli runs show RUN_ID
```

Wait until its `execution_state` is `completed`, `failed`, `cancelled`,
`abandoned`, or `interrupted`. These are terminal execution states; a missing
or other value does not confirm a terminal execution. A `ready` or `busy` worker
says nothing about idleness. These checks cover only known runs; if you cannot
account for all submitted work, postpone maintenance.

### Stop and resume the deployment

`docker compose stop` stops all services while preserving their containers and
volumes:

```bash
docker compose stop
docker compose ps
```

Expect no running container. To resume the deployment:

```bash
docker compose up -d --wait
```

Then check `worker.state` as in [Status](#status) before submitting work. `up`
starts the object storage as well as the API and worker; Infrahub's task manager
and its database are started with Infrahub.

### Restart the API and worker

When the dependencies are running, restart only the API and worker processes:

```bash
docker compose restart sync-api sync-worker
```

Then check `worker.state`. A restart preserves durable records. It does not
start stopped dependencies, and it does not pick up a changed `.env`; use
`docker compose up -d --wait` for both.

### Verify a retained configuration

Before maintenance, read a recorded version of an existing configuration:

```bash
docker compose run --rm --no-deps -T cli configs show CONFIG_ID --version VERSION
```

Replace `CONFIG_ID` and `VERSION` with the configuration's name and a version a run recorded.
Save the output, then repeat the command after the worker reports `ready`.
Confirm that `config_id`, `registry_version`, `package_checksum`, and
`declared_content` match the earlier output. This checks that the configuration
version remains available; a live worker alone only checks deployment health.

### Reset the deployment

Durable state lives in three places: the `infrahub_sync` database and role on
Infrahub's task-manager PostgreSQL server, the named volume
`<project>_object-store-data`, and Sync's nodes in Infrahub itself. Every other
writable path is a `tmpfs` mount. Removing the containers, the network, the volume,
the database, and the role discards the deployment:

```bash
docker compose down --volumes --remove-orphans
docker compose -p infrahub exec task-manager-db dropdb -U postgres infrahub_sync
docker compose -p infrahub exec task-manager-db dropuser -U postgres infrahub_sync
docker compose -p infrahub exec task-worker prefect deployment delete infrahub-sync-service/run
docker compose -p infrahub exec task-worker prefect work-pool delete infrahub-sync
```

Run the last four commands against Infrahub's Compose project; `-p infrahub` and
the `postgres` role are Infrahub's defaults. `down` alone leaves the
database, and the next start resumes from it. The last two remove Sync's Prefect
deployment and work pool from Infrahub's task manager (run from `task-worker`, which
has `PREFECT_API_URL` set), so no scheduled run of the
old deployment is taken by the next start's worker against an empty database.
Bootstrap sets the role's password to `INFRAHUB_SYNC_PRODUCT_PASSWORD` on every
start, so a regenerated `.env` takes effect either way.

:::danger
`down --volumes` and dropping the database delete every run, retained plan, and
artifact. Nothing asks for confirmation, and nothing can undo it. Configurations,
their versions, the `SyncRun` copies, and approvals stay in Infrahub; delete those
nodes in Infrahub to remove them. Keep anything you need outside the deployment
first. `.env` is left in place.
:::

Starting again after a reset is a cold bootstrap, not a resumption.
`docker compose up -d --wait` creates the product database, the product schema,
the bucket, the work pool, and the deployment from nothing, and the deployment
starts with no runs and no artifacts. Your configurations in Infrahub are
unchanged.

The project name defaults to the name of the directory, and prefixes the
object-store volume. Moving or renaming the directory starts a second set of
containers beside the first that share Sync's database but not its object-store
volume. If the directory may change, pin the name with `COMPOSE_PROJECT_NAME` in
`.env`, or with `docker compose -p`.

## Resetting this alpha to a fresh deployment

This alpha promises no in-place state migration and no backup or restore. The
supported way to replace a deployment is the full reset above, every command of
it, followed by a fresh start with `docker compose up -d --wait`. `down`
alone is not a reset: the product database on Infrahub's server survives it.

Sync's records live on Infrahub's task-manager PostgreSQL server, so Infrahub's own
backup, restore, and reset of that server apply to them too. Prior run history,
retained plans, registered configurations, and artifacts do not survive the full
reset. Keep anything you need outside the deployment before you
reset, and register your package again afterwards.

The object store image is a temporary, pinned MinIO build, while a maintained
S3-compatible store is selected. On the first start after upgrading from the
former root-running image, the short-lived `object-store-init` service changes the
owner of the existing volume to UID 65532. The data stays in place. This first
start can take longer for a large volume.

## When the outcome of a write is uncertain

If a write ends without proving what reached the destination, the deployment
does not retry it. Repeating a write whose outcome is unknown is the one thing
that could turn an uncertain state into a wrong one, so the run is left terminal
and the record carries what is known.

`reconciliation_required` is a field of the run itself rather than something
buried in its evidence, so deciding whether a run needs reconciling never means
parsing a failure.

`runs show` prints it, beside the phase, the outcome and the Prefect
correlation, and prints it for both of its values: `false` is an answer, and a
field that appeared only when it was true could not be told apart from one this
command does not report. `runs results` prints what the run itself recorded.

```bash
docker compose run --rm --no-deps -T cli runs show RUN_ID
docker compose run --rm --no-deps -T cli runs results RUN_ID
```

Two different records mean an uncertain write. A write execution that ended
without reporting records phase `interrupted` and outcome `ambiguous`, and sets
`reconciliation_required`. An apply that began writing and then failed records
phase `apply-failed` and outcome `failed`, with
`summary.may_have_partially_written` set and `results.apply_failure` naming the
stage, the error type, the operations already applied, and the one that failed.

`reconciliation_required` is a write-only verdict: an interrupted `plan` or
`verify` cannot have written, so it is not set for one, and nothing sets it back
to false.

In both cases, read the record, inspect the destination, and then take a fresh
plan run. A new plan reads the destination as it now is, so what it proposes is
what is still outstanding. The terminal run is never reopened and no later run
inherits its admission. A failure that never began writing is an ordinary failed
run, and needs only a new plan.

## What this topology does not do

- It runs on one host. There is no multi-host deployment and no clustering.
- It has no public ingress and no TLS. The published API port binds to
  `127.0.0.1` by default.
- It has no in-place state migration, and no backup or restore.
