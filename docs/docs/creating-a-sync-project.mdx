---
title: Create a sync project
---

A sync project is one configuration package: a YAML or JSON file that tells the Sync
service where to read data, where to write it, and how source records map to destination
kinds. This guide explains each part of a package, using a Nautobot → Infrahub example.

Before you start:

- Have a running Sync deployment and a CLI that can reach it. See
  [Run a sync](./running-a-sync.mdx#connect-the-cli-to-the-sync-api).
- Have a destination Infrahub whose schema contains the kinds that the package maps.
  Registering a package does not load a schema.

## The complete package

This package maps Nautobot locations and devices to the `TestingSite` and `TestingDevice`
kinds. It is the package from the
[Nautobot tutorial](./tutorials/nautobot-to-existing-infrahub.mdx), which also provides the
matching Infrahub schema:

```yaml
format_version: 1
configuration:
  name: my-nautobot-evaluation
  source:
    name: nautobot
    settings:
      url: https://nautobot.example.invalid
      token:
        $credential: nautobot-token
      depth: 1
  destination:
    name: infrahub
    settings:
      url: https://infrahub.example.invalid
      token:
        $credential: infrahub-token
  schema_mapping:
    - name: TestingSite
      mapping: dcim.locations
      identifiers: [name]
      fields:
        - name: name
          mapping: name
    - name: TestingDevice
      mapping: dcim.devices
      identifiers: [name]
      fields:
        - name: name
          mapping: name
        - name: model
          mapping: device_type.model
        - name: serial
          mapping: serial
        - name: site
          mapping: location
          reference: TestingSite
credentials:
  nautobot-token:
    provider: env
    identifier: INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN
  infrahub-token:
    provider: env
    identifier: INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN
```

The sections below explain each part. For the package format itself, see
[Configuration package](./configuration-package.mdx).

## Source and destination

`source` and `destination` each name an adapter and its connection settings:

- `name` selects a bundled adapter. See [Choose an adapter](./adapters/choosing-an-adapter.mdx)
  for the adapters and their settings.
- `url` is the address that the Sync worker uses. The worker runs in a container on a Compose
  deployment and on the [local development stack](./development-stack.mdx), and there
  `localhost` refers to the worker container, so use an address that the container can reach.
  For a service published on the same machine, that is `http://host.docker.internal:<port>`,
  for example `http://host.docker.internal:8000` for a local Infrahub.
- A token or password is a `$credential` reference, never a literal value.

A registered run can write only to Infrahub, so `destination.name` is `infrahub`.

## Credentials

The `credentials` block declares each `$credential` reference. `identifier` is the name of
the environment variable that the Sync worker reads when a run starts. In this example, the
worker needs `INFRAHUB_SYNC_CREDENTIAL_NAUTOBOT_TOKEN` and `INFRAHUB_SYNC_CREDENTIAL_INFRAHUB_API_TOKEN`. On a Compose deployment, set them in
the deployment's `.env`, then run `docker compose up -d --wait`. On the local development
stack, export them in your shell, then run `uv run invoke start`. See
[Credentials](./configuration-package.mdx#credentials).

## Schema mapping

Each `schema_mapping` entry maps one source path to one destination kind:

- `name` is the Infrahub kind, for example `TestingDevice`.
- `mapping` is the source path, for example the Nautobot API path `dcim.devices`.
- `identifiers` lists the fields that identify one object. Infrahub must be able to find the
  object by these fields; see
  [Destination key for Infrahub writes](./reference/schema-mapping.mdx#destination-key-for-infrahub-writes).
- Each `fields` entry sets one destination field. `mapping` names the source field. A dotted
  path, such as `device_type.model`, reads a nested value. `static` sets a fixed value
  instead.
- `reference` makes the field a relationship to another mapped kind. In the example, the
  device's `site` points to the `TestingSite` object whose `name` matches the device's
  Nautobot location. A reference needs both `mapping` and `reference`; a field with only
  `reference` is skipped.

Two rules come from the destination schema rather than from the package, and a package that
breaks either one registers without an error:

- **Identifiers must stay unique under the kind's uniqueness constraint.** Two source records
  that produce the same values for the destination kind's uniqueness constraint are one object
  to Infrahub, and the plan refuses them. For example, the `DcimDevice` kind in the
  `infrahub/traditional-infrastructure-sot` schema is unique by name, so two NetBox devices
  with the same name in different sites stop the plan. Filter one of them out, or build a
  unique name with a transform.
- **A Dropdown attribute takes one of the schema's choices.** A source value outside them
  reaches the plan unchanged, and Infrahub rejects it during the apply. Translate source values
  to the schema's choices with a transform.

For all mapping options, including filters and transforms, see the
[Schema mapping reference](./reference/schema-mapping.mdx).

## Write order

Sync writes a referenced kind before the kinds that reference it. In the example,
`TestingSite` objects are written before `TestingDevice` objects, because `site` references
`TestingSite`. You do not need to declare this order.

If an adapter needs a different order, add an `order` list under `configuration`. It
replaces the computed order, and every kind in it needs a `schema_mapping` entry:

```yaml
  order:
    - "TestingSite"
    - "TestingDevice"
```

See [Automatic write order](./reference/config.mdx#automatic-write-order).

## Creates, updates, and deletes

A plan contains three kinds of operations:

- A **create** for a source object that the destination does not contain.
- An **update** for an object in both systems whose values differ.
- A **delete** for a destination object that the source does not contain.

Apply writes creates and updates. It never executes a delete: it records the delete in the
plan, skips it, and reports how many deletes it skipped. Deletes are recorded only when the
destination side was read in full. See
[Deletes in a plan](./reference/cache-layout#deletes-in-a-plan).

The optional `diffsync_flags` list under `configuration` changes which operations a plan
contains:

| Flag | Effect |
| --- | --- |
| `SKIP_UNMATCHED_SRC` | The plan contains no creates. Only objects that already exist in the destination are updated. |
| `SKIP_UNMATCHED_DST` | Always in effect. Listing it changes nothing. |

No flag makes apply execute a delete.

```yaml
  diffsync_flags:
    - "SKIP_UNMATCHED_SRC"
```

## Register the package

When the package is complete, register it, validate it, and create a plan. See
[Run a sync](./running-a-sync.mdx). For the other fields of `configuration`, see
[Sync instance configuration](./reference/config.mdx).
