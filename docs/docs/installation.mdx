title: Install Infrahub Sync
---

Infrahub Sync V3 runs as a service. The service includes the Sync API, a worker,
Prefect, PostgreSQL, and object storage. You use the `infrahub-sync`
command-line client to send requests to the Sync API.

**Moving from V2?** [Move from V2 to V3](./v2-to-v3.mdx) compares the two lines and states
what to prepare first. A switch starts a fresh deployment; there is no in-place state
migration. The public [PyPI package](https://pypi.org/project/infrahub-sync/) is V2.

## Two ways to run V3

- **Run from source** — to try the latest changes or use a Mac. Build and start the
  service from a checkout of `feature/v3-develop`, on any platform Docker supports,
  including Apple Silicon.
- **Run a release package** — to test a fixed version. A candidate is a prebuilt image
  and Docker Compose bundle for one fixed version, tested together on Linux amd64
  before it is published.

Both run the same Sync service. A source build has passed the pull request checks, but
not the full deployment tests that each release package passes.

| | Run from source | Run a release package |
| --- | --- | --- |
| You need | Docker, Git, [uv](https://docs.astral.sh/uv/), and Python 3.11 to 3.13 | A Linux amd64 host with Docker Compose, and access to the private release list |
| Start here | [Run from source](./development-stack.mdx#run-from-source) | [Get a release package](#get-the-private-candidate) below |
| Where it ends | A first sync from a local NetBox into a local Infrahub | A saved preview from your own NetBox or Nautobot, then a reviewed apply |

See [Supported platforms and limits](./operations/supported-platforms-and-limits.mdx)
for what the release qualification covers and for the current product limits.

## Get a release package {#get-the-private-candidate}

Candidates are available from the
[private release list](https://github.com/opsmill/infrahub-sync-lab/releases).
Sign in to GitHub with an account that has access to `opsmill/infrahub-sync-lab`.
If you cannot open a release or download its attachments, contact the person
who provided the candidate. The release page and the file names show the candidate's
version.

Download both release attachments:

- `private-candidate-<version>-<sha7>.tar.gz`
- `private-candidate-<version>-<sha7>.tar.gz.sha256`

Each candidate's release page links the documentation as of that candidate. This
site shows the latest documentation, which can describe changes that your candidate
does not include. When the two differ, follow the documentation that your release
page links.

Then follow the [Quick Start][candidate-quickstart]. It verifies both checksum
layers, loads the image, extracts the Compose bundle, and runs `init` and `start`.
Continue below only when `status` reports `READY`.

## Check the included CLI {#install-the-command-line-client}

The Compose bundle includes the Sync CLI. You do not need to install Infrahub Sync
on the host. From the extracted `infrahub-sync-compose-<version>/` directory on the
Docker host, run:

```bash
./infrahub-sync-compose cli configs list
```

The wrapper runs the CLI in the same image as the deployment, on its network,
with the API token generated by `init`. You do not need to export a token.

On a fresh deployment, the registry is empty: the command prints no configuration
output and exits zero. Docker Compose may print container progress messages.
This checks access to the Sync API, not a connection to your source or destination.
If it fails, run `./infrahub-sync-compose status` and follow the
[operator guide][candidate-operator] for diagnosis.

The extracted bundle also includes `OPERATING.md` with local operating instructions
for that bundle.
