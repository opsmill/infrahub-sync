Infrahub Sync synchronizes infrastructure data between Infrahub and other systems, such
as NetBox, Nautobot, IP Fabric, Slurp’it, Cisco ACI, Peering Manager, and systems with a
REST/JSON API. Describe the source, the destination, and the field mapping in one YAML or
JSON configuration package. Then use the `infrahub-sync` client to register the package,
plan the changes, review the plan, and apply it.

These pages describe V3, built from the `feature/v3-develop` branch. V2 is the version on
[PyPI](https://pypi.org/project/infrahub-sync/); select it from the version menu to read
its documentation. Each V3 candidate's release page links the documentation as of that
candidate.

## Get started

1. **Choose how to run V3.** [Install Infrahub Sync](./installation.mdx) describes the two
   ways: run from source, or run the container image.
2. **Run a first sync.** Run from source continues to a first sync from a local NetBox. The
   container image continues to a tutorial for your own
   [NetBox](./tutorials/netbox-to-existing-infrahub.mdx) or
   [Nautobot](./tutorials/nautobot-to-existing-infrahub.mdx).
3. **Write your own configuration.** Continue with
   [Create a sync project](./creating-a-sync-project.mdx) and
   [Run a sync](./running-a-sync.mdx).

## Use cases

- **Migrate from an existing system, one model at a time.** Move data from NetBox,
  Nautobot, or another source into Infrahub while that system keeps running.
- **Keep Infrahub in sync with another system.** Run the same configuration again. Each
  run plans the differences, and apply writes only those differences.
- **Build inventory from network discovery.** Read discovered state from IP Fabric or
  Slurp’it into Infrahub.
- **Translate between data models.** Map source fields to destination fields in YAML, with
  identifiers, references, static values, filters, and transforms.

## How it works

### Concepts

- **Configuration package** — a JSON or YAML file that defines one synchronization
  between two systems. When you register it, the Sync API assigns a configuration ID, a
  version, and a checksum.
- **Adapter** — the component that connects Infrahub Sync to one system. It handles the
  API calls and authentication, and converts the system's data for the sync engine.
- **Schema mapping** — the part of the package that maps source fields to destination
  fields, with identifiers, references between models, and static values.
- **Plan** — the list of creates, updates, and deletes that a run calculates. The Sync
  API saves it with a checksum, so you can review it before anything is written.

### Register, plan, review, apply

1. `infrahub-sync configs register <package>` registers the package. Later commands use
   the returned configuration ID and version.
2. `infrahub-sync diff --config-id <id> --version <version> --reason <reason>` asks the
   worker to read both systems and save a plan. The destination is not changed. The
   client waits for the plan by default and prints its summary and checksum.
3. `infrahub-sync runs plan <run-id> --detail` shows the saved plan again, for example
   after you started the run with `--no-wait`.
4. `infrahub-sync apply <run-id> --expected-checksum <checksum> --reason <reason>` writes
   exactly the reviewed plan.

`infrahub-sync sync --config-id <id> --version <version> --reason <reason>` calculates a
plan and writes it in one run, with no stop for review.

When `order` is omitted, the write order comes from the mapping's references. A plan
records destination objects that have no match in the source as deletes, and apply never
executes them.

After a failed write, inspect the run record and the destination before you create a
fresh plan. A failed operation can have written part of its change, unless the run
records that it wrote nothing. See [Run a sync](./running-a-sync.mdx) for recovery.

### Choose a client

| Client | Use it for | Runtime requirements |
|---|---|---|
| CLI | Configuration and run operations through the Sync API | Included in the Compose image; a source checkout also installs it |
| Python client | Typed access to every Sync API resource | A compatible V3 Python package and Sync API access |
| Direct Prefect deployment | Starting and observing one read-only plan through Prefect's API | `prefect` extra and a Prefect server |
| Sync HTTP API | Authenticated remote runs, durable records and artifacts, reviewed apply, idempotency, and cancellation | `service` extra, Prefect, a work pool, a worker, and shared durable storage |

Use the [Python API](./reference/python-api.mdx),
[Prefect remote run](./reference/prefect-remote-run.mdx), or
[Sync HTTP API](./reference/sync-http-api.mdx) reference for setup and contracts.

## What's included

- **Adapters** for Infrahub, NetBox, Nautobot, IP Fabric, Cisco ACI, Peering Manager,
  Prometheus, and Slurp’it, plus a Generic REST API adapter for systems with HTTP/JSON
  APIs. The examples include Generic REST API configurations for LibreNMS, Observium,
  Device42, and PeeringDB.
- **Declarative configuration** — one package per sync defines the source, destination,
  optional write order, and per-model schema mapping. Mappings support 14 filter
  operations (including `regex` and `is_ip_within`), per-field transforms, custom Jinja
  filters, and cross-reference resolution.
- **Sync service** — the Sync API registers packages, admits runs, and keeps run records,
  saved plans, and artifacts. A Prefect worker reads the source and destination and
  writes the reviewed plan.
- **Custom CA certificates** — trust an internal CA for the CLI's connection to the Sync API. A
  Compose worker cannot trust a custom CA yet; see [Use custom CA certificates](./custom-certificates.mdx).

A registered package must name an adapter bundled with Infrahub Sync. Running a custom
adapter from a registered package is not qualified in this release; see
[Local adapters](./adapters/local-adapters.mdx).

### Adapter reference

| Adapter | Direction supported |
|---|---|
| Infrahub | source or destination |
| NetBox | NetBox → Infrahub |
| Nautobot | Nautobot → Infrahub |
| IP Fabric | IP Fabric → Infrahub |
| Cisco ACI | Cisco ACI → Infrahub |
| Peering Manager | Peering Manager → Infrahub |
| Prometheus | Prometheus → Infrahub |
| Slurp’it | Slurp’it → Infrahub |

The IP Fabric and Slurp’it adapters need a worker image that installs their client libraries; see
[IP Fabric](./adapters/ipfabric.mdx) and [Slurp’it](./adapters/slurpit.mdx).

## Common questions

**Do I have to migrate everything at once?**
No. Map one model at a time and run each configuration when you choose. The existing
system keeps running.

**Does Infrahub Sync schedule runs?**
Not in V3 today: there is no built-in schedule. Start each `diff` or `sync` run with the
client, for example from cron, a CI job, or another scheduler you already use.

**What happens if a sync run fails partway through?**
Inspect the run record and the destination before you retry, and create a fresh plan after
a failed write. The [run recovery guidance](./running-a-sync.mdx) explains how to read
partial-write evidence.

**Can a sync overwrite changes in the destination?**
A sync never deletes a destination object that has no match in the source. For an object
that does match, an update writes the mapped fields. Decide which system owns each model
before you apply a plan, and review every update in the plan.

**What if my source system doesn't have a pre-built adapter?**
Many systems with a REST/JSON API can use the
[Generic REST API adapter](./adapters/genericrestapi.mdx).

**Can I run two sync projects at the same time?**
Yes. Each sync project is its own registered configuration, with its own package,
configuration ID, and runs.
