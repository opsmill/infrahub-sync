---
title: Run a sync
---

The Infrahub Sync CLI is a client of the Sync API. The Sync service stores your
configuration packages and plans. Its worker connects to the source and the destination.
The CLI does not load adapters and does not run a sync locally.

A reviewed sync has these steps:

1. Register the configuration package.
2. Validate the registered version.
3. Create a plan.
4. Review the plan.
5. Optional: verify the plan against the destination.
6. Optional, unless the Sync API requires it: approve the plan.
7. Apply the reviewed plan.

## Connect the CLI to the Sync API

The commands on this page are written as `infrahub-sync <command>`. To get the CLI, see
[Install the CLI](./installation.mdx#install-the-cli). From a repository checkout, run each command
as `uv run infrahub-sync <command>`.

The CLI reads the Sync API URL and the bearer token from two environment variables. Set
them before the first command. For the local development stack, these are:

```bash
export INFRAHUB_SYNC_API_URL=http://127.0.0.1:8001
export INFRAHUB_SYNC_API_TOKEN=infrahub-sync-dev-token
```

The token has no command-line option, so it does not appear in shell history or in
process arguments. `--api-url` overrides the URL for one command. For a
[Compose deployment](./compose-deployment.mdx) with the default port, the URL is
`http://127.0.0.1:8001`, and the token is the `INFRAHUB_SYNC_API_TOKEN` value in its `.env`.

The same commands also run from the `cli` service of a
[Compose deployment](./compose-deployment.mdx#use-it), as
`docker compose run --rm --no-deps -T cli <command>`. That service supplies the URL and the
token. A command that reads a package file then needs the file mounted into the container;
see [Registering a package](./compose-deployment.mdx#registering-a-package).

Before its first authenticated request, the CLI checks that the service is compatible. It
refuses an incompatible service before it sends the token.

To check the token before you start, run:

```bash
infrahub-sync whoami
```

It prints the `actor` that the token authenticates as and whether that actor is an
`administrator`. Only an administrator can register packages. A token the service does not
accept fails with an authentication error.

In the commands below, replace `CONFIG_ID`, `RUN_ID`, and `CHECKSUM` with the values that
the previous command printed, and `BRANCH` with the destination branch. Wherever a command
takes `CONFIG_ID`, you can give the configuration's name instead. The CLI tries the value as
an identifier first, then as a name. When several configurations share the name, the command
exits with status 2 and lists their identifiers; use one of them.

## Register the package

```bash
infrahub-sync configs register package.yml --reason "register inventory import"
```

The output includes the `config_id` and the `registry_version`, which is `1` for a new
registration. Every later command names the package by these two values. The file itself is
not read again. For what registration checks and returns, see
[Configuration package](./configuration-package.mdx#registration-and-versions).

## Validate the registered version

```bash
infrahub-sync configs validate CONFIG_ID 1
infrahub-sync configs show CONFIG_ID --version 1
```

`configs validate` reports findings in the declared content. It does not connect to the
source or the destination.

`configs show --version` prints the registered content. Check
`configuration.destination.settings.branch`:

- If the package declares a branch, every run writes to that branch, and `--branch` has no
  effect.
- If the package declares no branch, the run uses `--branch`. Without `--branch`, it uses
  `main`.

The worker ignores `INFRAHUB_DEFAULT_BRANCH` and `INFRAHUB_DEFAULT_BRANCH_FROM_GIT` for this choice. After a completed run, the CLI prints `destination_branch`; `runs plan RUN_ID` shows the branch recorded in its saved plan. If the CLI cannot read the saved plan after a successful `sync` or `apply`, it prints `destination_branch: <unavailable>` and still exits successfully. A plan without a destination binding reports `destination_branch: <none>`.

To inspect what is registered, use `configs list`, `configs show CONFIG_ID`, and
`configs versions CONFIG_ID`.

## Create a plan

```bash
infrahub-sync plan --config-id CONFIG_ID --version 1 \
  --branch BRANCH --reason "review inventory import"
```

`plan` asks the service to create a plan. The worker reads the source and the destination
and saves the plan. It writes nothing to the destination. By default, `plan` waits for the
plan, then prints the `run_id`, the `plan_checksum`, and the operation counts by action and
by kind.

### Follow the read of each side

To follow the reads while the plan runs, start it with `--no-wait`, then run `runs show`
again until the stage ends. `plan --no-wait` can return before the worker starts the stage,
and the read lines appear only once the worker has started it. This example repeats
`runs show` every 5 seconds; press Ctrl+C to stop it:

```bash
infrahub-sync plan --config-id CONFIG_ID --version 1 --no-wait
while true; do infrahub-sync runs show RUN_ID; sleep 5; done
```

`runs show` prints a `source_read` and a `destination_read` line after
`prefect_flow_run_url`. They show the read state of each side in the run's latest `plan` or
`sync` execution, even after `verify` or `apply` executions:

```text
source_read: state=succeeded mode=full started_at=2026-11-09T10:00:01+00:00 ended_at=2026-11-09T10:00:13+00:00 nodes=DcimDevice:3,LocationSite:2
destination_read: state=failed started_at=2026-11-09T10:00:01+00:00 ended_at=2026-11-09T10:00:04+00:00 error=ConnectionError
```

Each side starts as `state=waiting`, then shows `state=reading` with `started_at` while the
worker reads it. A read that ends shows `state=succeeded`, with the read `mode` (`full` or
`incremental`; `full` only when every top-level kind of the side was extracted in full) and
the number of `nodes` of each kind, or `state=failed`, with the class name
of the error. When the stage ends before a side's read ends, that side shows
`state=not_started` or `state=interrupted`, with no `ended_at`. A side whose read state the
worker could not store, whose end the service did not record, or whose stored state does not
parse, shows `<none>`. A key with no value is left out. Neither line is printed for a run
created before the service recorded the read state, while the worker has not started the
latest `plan` or `sync` execution, or when the worker could not store the read state of
either side. Only
`runs show` prints these lines; `plan`, `sync`, `verify`, `apply` and `runs cancel` do not. The
[Sync HTTP API reference](./reference/sync-http-api.mdx#read-state-of-each-side) describes each
state.

When a side's read ends, the run's log also holds one line for it, which
`infrahub-sync runs logs RUN_ID` prints. The example shows the message only; `runs logs` also
prints each line's timestamp, stage and level:

```text
Load: source read succeeded (full): 5 nodes; DcimDevice 3, LocationSite 2
Load: destination read failed (ConnectionError)
```

A `sync` run shows the same lines for its `sync` stage.

## Review the plan

```bash
infrahub-sync runs plan RUN_ID --detail
infrahub-sync runs plan RUN_ID --detail --kind <destination-kind>
```

`runs plan` prints the summary and the checksum. `--detail` also prints every operation, and
`--kind` limits the list to one destination kind. A kind that matches no operation is an
input error.

The review prints control characters and invisible characters in source values as visible
escapes, such as `\x1b` or `\u202e`, so a value cannot hide or rewrite a line. Only the
printed review changes: the saved plan and JSON output keep the real values. A value that
contains the literal text `\x1b` looks the same as an escaped character.

The plan can contain delete operations for destination objects that the source does not
contain. Apply never executes a delete. The detailed output marks each delete as
`(not executed)`, and the summary states how many deletes apply will skip. When the
destination side was not read in full, the plan contains no deletes and the review says so.
See [Deletes in a plan](./reference/cache-layout#deletes-in-a-plan).

After the review, three commands follow, each with one purpose:

1. `verify` checks that the saved plan would still apply now, without writing.
2. `approve` records that you accept the plan, without writing.
3. `apply` writes the plan to the destination.

`verify` and `approve` are optional unless the Sync API requires approval; see
[Require an approved plan](#require-an-approved-plan).

## Verify the plan against the destination

```bash
infrahub-sync verify RUN_ID --reason "check plan before apply"
```

`verify` runs every check that `apply` runs before its first write, and writes nothing. The
worker connects to the destination for this, with the same credentials and network access
that `apply` uses, so `verify` fails when it cannot reach the destination. The checks are:

- The saved plan files are unchanged: the plan belongs to this run, the plan checksum and the
  saved source snapshot are unchanged, and the configuration version and plan format are the
  ones the plan was created with.
- The current destination schema matches the schema the plan was made against.
- The destination URL and branch match the ones the plan recorded.
- The destination adapter can apply a saved plan, and every planned field still exists in the
  destination schema and can still be written.

On success, `verify` prints one `check: NAME passed` line for each check, in the order it ran
them, such as `check: destination_schema passed`. When a check fails, `verify` exits with a
non-zero status and the run's phase stays `planned`. Before the `error: run-terminal` line,
`verify` prints `verify failed: ERROR_TYPE`, one `failed_check: NAME` line for each check
that failed, such as `failed_check: destination_binding`, and, when the run recorded a next
action, a `hint:` line that says what to do. `runs results RUN_ID` shows the same failure under `verify_failure`: `failed_checks`
names the check, `error_type` names the refusal, and `next_action` says what to do. The
refusal is the same one that `apply` reports when it refuses on that check. A run with no registered configuration
binding cannot be applied by the service; `verify` checks only its saved files, and its
results report `destination_checked: false`.

`verify` describes the destination when it read it. It does not change the run's phase, does
not compute a new plan, and does not wait for an `apply` of the same configuration that is
writing. `apply` runs the same checks again before its first write.

### Is `verify` an approval?

No. `verify` records no decision, and a run that passed `verify` is not approved. To record
that you accept the plan, use `approve`.

## Approve the plan

```bash
infrahub-sync approve RUN_ID --expected-checksum CHECKSUM \
  --reason "reviewed by the network team"
```

`approve` records on the run who approved the plan, when, and which checksum they approved.
It writes nothing to the destination and starts no execution. `--reason` is optional. The
command prints the run, its approval, and the counts of the plan approved:
`approved_creates`, `approved_updates` and `approved_deletes_recorded`. `runs show RUN_ID`
then prints `approved_by`, `approved_at` and `approved_checksum`. The run stays in phase
`planned`.

The service refuses an approval in these cases, and records nothing:

- The checksum differs from the saved plan's checksum (`checksum-mismatch`).
- The saved plan's checksum could not be confirmed (`plan-checksum-unverified`).
- The run is not in phase `planned`, or a stage of the run is still running
  (`run-not-approvable`).
- The run was cancelled (`run-cancelled`).
- The run already has an approval (`already-approved`). The error shows the existing approval.

Only the actor who started the run, or an administrator, can approve it. Approval does not run
the destination checks: when the destination changes after the approval, `apply` still
refuses, and `verify` reports the failure beforehand.

## Apply the reviewed plan

Pass the checksum that the review printed, and the same `--branch` that you gave `plan`:

```bash
infrahub-sync apply RUN_ID --expected-checksum CHECKSUM \
  --branch BRANCH --reason "apply reviewed inventory import"
infrahub-sync runs show RUN_ID
```

The service compares the checksum with the saved plan and refuses a mismatch before it
writes. The CLI never reads or builds a local plan. When `runs show` reports
`phase: applied` and `execution_state: completed`, the apply is finished.

Before the first write, apply checks every planned field against the current destination
schema. It repeats the check for each operation before that operation's write. If a field is
no longer writable, or a planned value would be dropped, apply refuses the write and names
the kind and the field. Create and review a new plan in that case. Operations applied before
a refusal stay applied.

The check does not compare a value with the choices of a Dropdown attribute. A plan can
therefore hold a value the destination schema does not offer, such as a NetBox device status
`planned` for a `status` attribute whose choices are `active`, `provisioning`, `maintenance`,
`deprecated`, and `reserved`. Infrahub rejects that write during the apply, and the apply stops
there. Translate such values with a transform in the package; see the
[Schema mapping reference](./reference/schema-mapping.mdx).

The service refuses to apply a run in phase `cancelled` (`run-cancelled`). Create a new plan
run instead.

## Require an approved plan

A site can require an approval before every apply. The operator of the Sync API sets
`INFRAHUB_SYNC_REQUIRE_APPROVAL=true` on the service; see the
[Compose deployment](./compose-deployment.mdx). It is off by default. To find whether it is
on, run `infrahub-sync whoami`: it prints `approval_required: true` or
`approval_required: false`.

When the setting is on:

- `apply` refuses a run that has no approval (`approval-required`), and tells you to run
  `approve` first.
- `apply` refuses a run whose approval names a different checksum from the one you pass with
  `--expected-checksum` (`approval-checksum-mismatch`). The error shows both checksums.
- `sync` is refused before the run starts (`approval-required-for-sync`). Use `plan`,
  `approve` and `apply` instead.

The service reads the setting when each `apply` or `sync` request arrives. Approvals recorded
while the setting was off still count after it is turned on. When the setting is off,
approvals stay recorded and visible, and `apply` does not read them.

## Withdraw a plan

To withdraw a finished plan, approved or not, cancel its run:

```bash
infrahub-sync runs cancel RUN_ID --yes
```

The run's phase becomes `cancelled`. Its approval, if it has one, stays recorded and visible.
Nothing is written to the destination or sent to Prefect. After that, `approve` and `apply`
refuse the run (`run-cancelled`); to try again, create a new plan run. Cancelling a run that is
already cancelled is refused (`run-already-cancelled`), and cancelling an applied run, or a run
whose plan failed, is refused as before.

## Find runs

`runs list` prints one line per run, newest first: the `run_id`, the configuration and
version as `CONFIG_ID@VERSION`, the destination branch, the phase, the outcome, the actor, and
the start time. A run created before the service recorded its branch shows `-` for the
branch.

```bash
infrahub-sync runs list
infrahub-sync runs list --config CONFIG_ID --version 2
```

`--config` limits the list to one configuration, and `--version` to one of its versions.
`--version` requires `--config`. The CLI prints one page of up to 50 runs. When more runs
exist, it prints `more runs: rerun with --all, or --limit up to 200` on standard error.
`--limit` sets the page size, from 1 to 200, and `--all` reads every page. `configs list`
takes the same `--limit` and `--all` options. To list only the configurations with one exact
name, run `infrahub-sync configs list --name NAME`.

To find the latest run of each version of a configuration, run:

```bash
infrahub-sync configs versions CONFIG_ID
```

It prints one page of versions, newest first; `--limit` sets the page size, up to 200, and
`--all` reads every page. When more versions follow, it says so on standard error. For each
version on the page, it prints who registered the version and why
(`registered_by` and `registration_reason`), then the `latest_run` and the
`latest_applied_run`, each with its `run_id`, phase and outcome. `latest_run` is the run
created most recently, shown with its start time (`started_at`). `latest_applied_run` is the
run applied most recently, which can be an older plan that you applied after a newer one. It
is shown with the time its apply finished (`finished_at`).

`runs artifacts RUN_ID` lists the files that the service kept for a run.
`runs cancel RUN_ID` cancels a run's stage that is still running, or withdraws a finished
plan; see [Withdraw a plan](#withdraw-a-plan). It asks for confirmation, or refuses when it
cannot ask; `--yes` skips the question. Cancelling a run that is writing can leave an
`ambiguous` outcome, because the worker may already have changed the destination.

### Find a run's flow runs in Prefect

Each stage of a run (`plan`, `verify`, `apply`, or `sync`) runs as one Prefect flow run. The
service tags each flow run so you can filter them in the Prefect UI or API:

- `run:RUN_ID` selects every stage of one run.
- `config:CONFIG_ID` selects every run of one configuration.
- `config-version:CONFIG_ID@VERSION` selects every run of one configuration version.
- `stage:STAGE` selects one kind of stage, such as `stage:apply`.

The `config:` and `config-version:` tags are set only on runs of a registered configuration.

When the Sync API has a Prefect UI address (`INFRAHUB_SYNC_PREFECT_UI_URL`, see
[Compose deployment](./compose-deployment.mdx)), `runs show RUN_ID` prints a
`prefect_flow_run_url` line that opens the run's flow run in the Prefect UI. Without it, the
line reads `prefect_flow_run_url: <none>`.

In the Prefect UI, the worker's last line in each flow run's log names the stage, its outcome and the
next step, and the flow run's Artifacts tab holds a summary of the Sync run. See
[What a service flow run shows in Prefect](./orchestration.mdx#what-a-service-flow-run-shows-in-prefect).

## Find why a run failed

`plan`, `verify`, `sync`, and `apply` print the final phase and outcome of a failed run, such
as `phase: plan-failed`. When the run recorded the class of the error, the command also prints
`<stage> failed: <ErrorClass>`, for example `plan failed: ValueError`. When `verify` or `apply`
fails on a check that runs before the first write, the command then prints one
`failed_check: NAME` line for each check that failed, such as `failed_check: destination_schema`,
and `runs results RUN_ID` lists the same names under `failed_checks`. `verify` and `apply` name
the same check for the same problem.

For some failures the run also records a cause that you can act on, and the command prints it
on a `cause:` line:

- Infrahub refused a request with HTTP 403. The cause names the permission the import account
  needs.
- Infrahub refused the token with HTTP 401.
- The `source` or `owner` setting names a node that does not exist in the destination.
- The saved plan records no import account.
- The apply runs with a different import account than the plan. The cause names both accounts.

For the last three, a `hint:` line says what to do next. A `hint:` line also follows other
refusals that infrahub-sync writes a next action for, such as a destination schema that changed
since the plan was made, a saved plan whose format version is missing or not supported by this
release, or an operation that the destination rejected during an apply. When a saved plan fails
its checks before an apply, the hint names each failed check and what to do about it. These
refusals print no `cause:` line, unless Infrahub also refused a request with HTTP 401 or 403.
When the run was recorded by an earlier Sync API release that recorded no next action, the
command prints the fixed hint for a changed schema or a saved plan's format version, as earlier
releases did. `runs results RUN_ID`
prints the same fields, as `cause`, `next_action` and `infrahub_error`, under `plan_failure`,
`sync_failure` or `apply_failure`, and a failed `verify` under `verify_failure`.

When the destination branch does not exist, the `cause:` line names the branch, and the
`hint:` line says to create it or to start the run with `--branch <existing branch>`. A
failure to read the destination schema also prints a `cause:` and a `hint:` line.

`infrahub-sync runs logs RUN_ID` prints the lines that Sync wrote during the run, including
the ERROR line that holds the cause and the next step. It reads them through the Sync API.

For any other failure:

1. Run `infrahub-sync runs show RUN_ID`. When the run recorded the failure, the output
   ends with the failed stage's error type and, when they are known, a `cause:` and a
   `hint:` line.
2. Run `infrahub-sync runs logs RUN_ID`. The ERROR line names the error class of the failure.
3. When these do not explain the failure, read the error on the run's Prefect flow run. The
   `runs show` output includes `flow_run_id`, and `prefect_flow_run_url` when the Sync API has
   a Prefect UI address. You can also filter flow runs in the Prefect UI by the tag
   `run:RUN_ID`. Open `prefect_flow_run_url`, or `<prefect-ui>/runs/flow-run/FLOW_RUN_ID`, in a
   browser. The state message of the failed flow run contains the error. A Compose deployment serves no Prefect UI until you add the
   override snippet in [Open the Prefect UI](./compose-deployment.mdx#open-the-prefect-ui);
   with it, the UI is at `http://127.0.0.1:4200` with the default port. The
   [local development stack](./development-stack.mdx) serves it at `http://127.0.0.1:4230`.

The same error is in the worker's log: `docker compose logs sync-worker` from the deployment
directory, or `docker compose -f development/docker-compose.yml logs sync-worker` from a
checkout running the local development stack.

### Recover from an interrupted apply

An apply can stop after it has written earlier operations. Nothing is rolled back: those
writes stay written. How the run ends depends on what the service knows about the operation
that failed:

- If the failed operation is known not to have written, the run ends with
  `phase: apply-failed` and `outcome: failed`.
- If the service cannot tell whether it wrote, the run ends with `phase: apply-interrupted`
  and `outcome: ambiguous`, and the failed operation may have written part of its change.

Remove the cause first, in the source data or in the package. Then create a new plan for the
same branch with `plan`, review it, and apply it. The new plan compares the source with what
the destination now holds, so it contains only what is still missing or different.

## Change a registered package

A registered version never changes. To change a package, edit the file and register it as a
new version of the same configuration:

```bash
infrahub-sync configs version CONFIG_ID package.yml --reason "update inventory mapping"
```

Then validate the new version and create a plan with `--version` set to the new version
number. Do not use `configs register` for an edited package: it creates a separate
configuration with a new `config_id`.

## Run a sync without a review step

`sync` creates a plan and applies it in the same run, with no pause for review:

```bash
infrahub-sync sync --config-id CONFIG_ID --version 1 --branch BRANCH \
  --reason "scheduled synchronization"
```

The worker saves the plan before the first write, so you can read it afterwards with
`runs plan`. `sync` does not apply a plan that you reviewed earlier; it creates a new one. To
review the exact operations before they are written, use `plan`, `runs plan`, and `apply`.
When the Sync API requires approval, `sync` is refused; see
[Require an approved plan](#require-an-approved-plan).

## Reference

### Waiting for a run

`plan`, `verify`, `sync`, and `apply` wait for the run by default. They poll the service every
2 seconds for at most 30 minutes. `--poll-interval` and `--wait-timeout` change these
values, in seconds. A large apply needs a longer wait, and how long it takes depends on the
destination. For example, applies of the NetBox demo package took 11 minutes for about 1,700
operations on 2026-09-29, and 46 seconds for 1,609 operations on 2026-10-05, against different
local Infrahub instances.

`--no-wait` returns after the service accepts the request. The output includes the run ID
and the retry key. Check the run later with `runs show RUN_ID` or `runs plan RUN_ID`.

### Wait outcomes

- A run that succeeds prints its latest record.
- A run that fails, is cancelled, or ends in an unknown state exits with a nonzero status
  and prints the run ID and its final fields.
- A failed run also prints `<stage> failed: <ErrorClass>` when the service recorded the
  error, and `cause:` and `hint:` lines when it recorded them; see
  [Find why a run failed](#find-why-a-run-failed). For `PlanSchemaChangedError`, the destination schema changed after the plan was
  saved: create and review a new plan. A plan saved by a different release can need a new
  plan too, and the message says so.
- When the wait times out, the CLI exits with a nonzero status and prints the run ID and its
  last phase, outcome, and execution state. The run continues on the service.
- Ctrl-C stops the wait, prints the last record, and exits with status 130. It does not
  cancel the run.

### Audit reasons

`configs register`, `configs version`, `plan`, `verify`, `sync`, `apply`, and `runs cancel`
accept `--reason`. The
reason is optional. When you give one, the service records it in the audit history of the
request. When you omit it, the service records the request without a reason.

### Retry keys

`configs register`, `configs version`, `plan`, `verify`, `sync`, `apply`, and `runs cancel`
accept `--idempotency-key`. If you omit it, the CLI generates a key and prints it. If the connection
fails before you see a response, run the same command again with that key. The service then
returns the original response instead of starting a second operation. See
[Retry keys](./configuration-package.mdx#retry-keys).

### Output fields

- `configs validate` prints `offset`, `limit`, `total_findings`, and `next_offset`. Use
  `--offset` and `--limit` to read another page of findings.
- `runs show RUN_ID` prints the run's phase, outcome, execution state, and Prefect
  correlation.
- `runs results RUN_ID` prints the results that the service recorded for the run, as JSON.

For every command and option, see the [Sync CLI reference](./reference/cli.mdx).
