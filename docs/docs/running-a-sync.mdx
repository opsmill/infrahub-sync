The Infrahub Sync CLI is a client of the Sync API. The Sync service stores your
configuration packages and plans. Its worker connects to the source and the destination.
The CLI does not load adapters and does not run a sync locally.

A reviewed sync has five steps:

1. Register the configuration package.
2. Validate the registered version.
3. Create a plan.
4. Review the plan, including the source records it leaves out.
5. Apply the reviewed plan.

## Connect the CLI to the Sync API

The commands on this page are the same for both ways to run V3. Only the command prefix
differs:

<Tabs groupId="sync-client">
  <TabItem value="compose" label="Run the container image" default>

  Run each command as `docker compose run --rm --no-deps -T cli <command>` from the
  directory that holds `docker-compose.yml` and `.env`. The `cli` service supplies the Sync
  API URL and token.

  A command that reads a file from your machine needs that file mounted read-only at
  `/input/package.yaml`, with `-v "$PWD/package.yml:/input/package.yaml:ro"` before `cli`.
  The image runs as UID 10001, so the file must be readable by other users. See
  [Registering a package](./compose-deployment.mdx#registering-a-package).

  </TabItem>
  <TabItem value="source" label="Run from source">

  Run each command as `uv run infrahub-sync <command>` from the repository checkout. Set the
  Sync API URL and bearer token first. For the local development stack, these are:

  ```bash
  export INFRAHUB_SYNC_API_URL=http://127.0.0.1:8030
  export INFRAHUB_SYNC_API_TOKEN=infrahub-sync-dev-token
  ```

  The token has no command-line option, so it does not appear in shell history or in
  process arguments. `--api-url` overrides the URL for one command.

  </TabItem>
</Tabs>

Before its first authenticated request, the CLI checks that the service is compatible. It
refuses an incompatible service before it sends the token.

In the commands below, replace `CONFIG_ID`, `RUN_ID`, `CHECKSUM`, and `LEFT_OUT` with the
values that the previous command printed, and `BRANCH` with the destination branch.

## Register the package

<Tabs groupId="sync-client">
  <TabItem value="compose" label="Run the container image" default>

  ```bash
  docker compose run --rm --no-deps -T -v "$PWD/package.yml:/input/package.yaml:ro" \
    cli configs register /input/package.yaml --reason "register inventory import"
  ```

  </TabItem>
  <TabItem value="source" label="Run from source">

  ```bash
  uv run infrahub-sync configs register package.yml --reason "register inventory import"
  ```

  </TabItem>
</Tabs>

The output includes the `config_id` and the `registry_version`, which is `1` for a new
registration. Every later command names the package by these two values. The file itself is
not read again. For what registration checks and returns, see
[Configuration package](./configuration-package.mdx#registration-and-versions).

## Validate the registered version

<Tabs groupId="sync-client">
  <TabItem value="compose" label="Run the container image" default>

  ```bash
  docker compose run --rm --no-deps -T cli configs validate CONFIG_ID 1
  docker compose run --rm --no-deps -T cli configs show CONFIG_ID --version 1
  ```

  </TabItem>
  <TabItem value="source" label="Run from source">

  ```bash
  uv run infrahub-sync configs validate CONFIG_ID 1
  uv run infrahub-sync configs show CONFIG_ID --version 1
  ```

  </TabItem>
</Tabs>

`configs validate` reports findings in the declared content. It does not connect to the
source or the destination. Add `--branch <branch>` to also check the mapping against that
branch's destination schema and the credentials the worker holds; see
[Validate a version](./configuration-package.mdx#validate-a-version).

`configs show --version` prints the registered content. Check
`configuration.destination.settings.branch`:

- If the package declares a branch, every run writes to that branch, and `--branch` has no
  effect.
- If the package declares no branch, the run uses `--branch`. Without `--branch`, it uses
  `main`.

The worker ignores `INFRAHUB_DEFAULT_BRANCH` and `INFRAHUB_DEFAULT_BRANCH_FROM_GIT` for this choice. After a completed run, the CLI prints `destination_branch`; `runs plan RUN_ID` shows the branch recorded in its saved plan. If the CLI cannot read the saved plan after a successful `sync` or `apply`, it prints `destination_branch: <unavailable>` and still exits successfully. A plan without a destination binding reports `destination_branch: <none>`.

To inspect what is registered, use `configs list`, `configs show CONFIG_ID`, and
`configs versions CONFIG_ID`.

## Create a plan

<Tabs groupId="sync-client">
  <TabItem value="compose" label="Run the container image" default>

  ```bash
  docker compose run --rm --no-deps -T cli diff --config-id CONFIG_ID --version 1 \
    --branch BRANCH --reason "review inventory import"
  ```

  </TabItem>
  <TabItem value="source" label="Run from source">

  ```bash
  uv run infrahub-sync diff --config-id CONFIG_ID --version 1 \
    --branch BRANCH --reason "review inventory import"
  ```

  </TabItem>
</Tabs>

`diff` asks the service to create a plan. The worker reads the source and the destination
and saves the plan. It writes nothing to the destination. By default, `diff` waits for the
plan, then prints the `run_id`, the `plan_checksum`, and the operation counts by action and
by kind.

After the counts by action, `diff` prints three counts about the source data:

```text
left_out: 6 (with a problem: 1, depending on one: 5)
problems: 1
kept_without_relationship: 0
```

- `left_out` is the number of source records that the plan does not write. A record is left
  out when it has a problem, or when it depends on a left-out record through a required
  relationship or through a relationship that is one of the identifiers of its mapping.
- `problems` is the number of problems found in the source data, such as a value that is not
  one of the choices of a Dropdown attribute.
- `kept_without_relationship` is the number of records that the plan writes without one
  optional relationship, because the related record is left out or is not in the source.

When the plan has problems, `diff` also prints the first 20 of them and the `runs problems`
command that lists the rest.

## Review the plan

<Tabs groupId="sync-client">
  <TabItem value="compose" label="Run the container image" default>

  ```bash
  docker compose run --rm --no-deps -T cli runs plan RUN_ID --detail
  docker compose run --rm --no-deps -T cli runs plan RUN_ID --detail --kind <destination-kind>
  ```

  </TabItem>
  <TabItem value="source" label="Run from source">

  ```bash
  uv run infrahub-sync runs plan RUN_ID --detail
  uv run infrahub-sync runs plan RUN_ID --detail --kind <destination-kind>
  ```

  </TabItem>
</Tabs>

`runs plan` prints the summary and the checksum. `--detail` also prints every operation, and
`--kind` limits the list to one destination kind. A kind that matches no operation is an
input error.

The review prints control characters and invisible characters in source values as visible
escapes, such as `\x1b` or `\u202e`, so a value cannot hide or rewrite a line. Only the
printed review changes: the saved plan and JSON output keep the real values. A value that
contains the literal text `\x1b` looks the same as an escaped character.

The plan can contain delete operations for destination objects that the source does not
contain. Apply never executes a delete. The detailed output marks each delete as
`(not executed)`, and the summary states how many deletes apply will skip. When the
destination side was not read in full, the plan contains no deletes and the review says so.
When the plan leaves out a source record whose identity it cannot form, the plan contains no
delete of that record's kind, because that record can be any Infrahub node of the kind.
See [Deletes in a plan](./reference/cache-layout#deletes-in-a-plan).

### Review problems, left-out records and kept records

Three commands list the records behind the counts of the summary. Each one reads every page
from the Sync API and prints one line per entry. `--kind` limits a list to one destination
kind, and `runs problems --type` limits it to one problem type.

<Tabs groupId="sync-client">
  <TabItem value="compose" label="Run the container image" default>

  ```bash
  docker compose run --rm --no-deps -T cli runs problems RUN_ID
  docker compose run --rm --no-deps -T cli runs left-out RUN_ID
  docker compose run --rm --no-deps -T cli runs kept RUN_ID
  ```

  </TabItem>
  <TabItem value="source" label="Run from source">

  ```bash
  uv run infrahub-sync runs problems RUN_ID
  uv run infrahub-sync runs left-out RUN_ID
  uv run infrahub-sync runs kept RUN_ID
  ```

  </TabItem>
</Tabs>

`runs problems` prints the problem type, the destination kind, the identity of the source
record, and what is wrong:

```text
dropdown_value_not_in_choices  DcimDevice  location=dc1 name=rtr1  status='planned' is not one of: active, deprecated, maintenance, provisioning, reserved
peer_not_found_in_source  IpamIPAddress  address=10.0.0.1/32  vrf refers to IpamVRF source ID 17, which is not in the source
```

The problem types are:

- `dropdown_value_not_in_choices`: a value is not one of the choices of a Dropdown attribute.
- `duplicate_source_identity`: two or more source records of one kind have the same
  identity.
- `destination_identity_collision`: two or more creates would form the same Infrahub
  human-friendly ID.
- `wrong_value_type`: a value has the wrong type for its attribute, such as `2.5` for a
  Number.
- `required_peer_excluded_by_filter`: a required relationship points to a record that a
  filter of the package removes.
- `identities_merge_in_destination`: two or more source records with different identities
  would be stored as one Infrahub node.
- `peer_not_found_in_source`: a relationship points to a record that is not in the source.

`runs left-out` prints each left-out record and its cause: `has_problem` with the problem
types, or `depends_on_left_out` with the left-out record it depends on and the relationship:

```text
depends_on_left_out  InterfacePhysical  device=rtr1 name=eth0  depends on DcimDevice location=dc1 name=rtr1 through device
```

`runs kept` prints each record that the plan writes without one optional relationship, and
names the related record that is left out or not in the source.

Fix a problem in the source data or in the package, then create a new plan. To write the
other records now, apply the plan and confirm the records left out.

## Apply the reviewed plan

Pass the checksum that the review printed, and the same `--branch` that you gave `diff`. When
the plan leaves out records, also pass `--confirm-left-out` to confirm that you reviewed them:

<Tabs groupId="sync-client">
  <TabItem value="compose" label="Run the container image" default>

  ```bash
  docker compose run --rm --no-deps -T cli apply RUN_ID --expected-checksum CHECKSUM \
    --confirm-left-out --branch BRANCH --reason "apply reviewed inventory import"
  docker compose run --rm --no-deps -T cli runs show RUN_ID
  ```

  </TabItem>
  <TabItem value="source" label="Run from source">

  ```bash
  uv run infrahub-sync apply RUN_ID --expected-checksum CHECKSUM \
    --confirm-left-out --branch BRANCH --reason "apply reviewed inventory import"
  uv run infrahub-sync runs show RUN_ID
  ```

  </TabItem>
</Tabs>

The service compares the checksum with the saved plan and refuses a mismatch before it
writes. The CLI never reads or builds a local plan. When `runs show` reports
`phase: applied` and `execution_state: completed`, the apply is finished. `runs show` then
also prints `operations_written` and `left_out`.

When the plan leaves out records and `--confirm-left-out` is missing, the service refuses the
apply before any write. The command exits with code 1 and prints how many records the plan
leaves out:

```text
apply refused: this plan leaves out 12 records; confirm with --confirm-left-out
```

`--confirm-left-out` takes no count: the checksum already ties the apply to the plan you
reviewed. When the plan leaves out no records, you can omit `--confirm-left-out`; the service
ignores it. A plan saved by an
earlier release records no left-out count; the service refuses to apply it, and you create a
new plan.

Before the first write, apply checks every planned field against the current destination
schema. It repeats the check for each operation before that operation's write. If a field is
no longer writable, or a planned value would be dropped, apply refuses the write and names
the kind and the field. Create and review a new plan in that case. Operations applied before
a refusal stay applied.

The plan compares each value of a Dropdown attribute with the choices in the destination
schema it read. A record with a value the schema does not offer, such as a NetBox device
status `planned` for a `status` attribute whose choices are `active`, `provisioning`,
`maintenance`, `deprecated`, and `reserved`, has the problem `dropdown_value_not_in_choices`
and is left out of the plan. Translate such values with a transform in the package; see the
[Schema mapping reference](./reference/schema-mapping.mdx).

## Find why a run failed

`diff`, `sync`, `apply`, and `runs show` print the final phase and outcome of a failed run,
such as `phase: plan-failed`, and then the cause that the worker recorded for the run. The
first line names the stage, whether it failed or stopped, and a one-sentence summary. The
next lines give the fields that apply to the cause, and the last line gives the next step:

```text
apply stopped: the destination rejected a write to DcimDevice with error code ATTRIBUTE_CONSTRAINT_VIOLATION
  node kind: DcimDevice   attribute: status
  Infrahub message: planned is not a valid value for status
  written: 692 of 2291 operations
  failed operation: op_518aada155d790ad update DcimDevice name=rtr1 (may have written part of its change)
  next: Fix the cause, then create and review a new plan.
```

```text
plan failed: the destination system (infrahub) rejected the token
  next: Check the token that the worker uses for this system, then run the stage again.
```

The detail lines are:

- `node kind` and `attribute`: the destination kind and attribute that Infrahub named in its
  error.
- `record` and `field`: the source record and the field that could not be loaded or
  transformed.
- `Infrahub message`: the message of the error that Infrahub returned for a rejected write.
- `written` and `failed operation`: how far a stopped apply got, and the operation it stopped
  at.

The worker builds the cause only from named fields, such as Infrahub's error code and the
kind and attribute that Infrahub reports. It never copies the text of an error, an address,
or a header into the cause. The command exits with code 1 for a run that failed or stopped.
The API returns the same cause in the run's `failure` field; see
[Run failure cause](./reference/sync-http-api.mdx#run-failure-cause).

When the summary reports an internal error, or you need more detail, read the run's Prefect
flow run:

1. Run `runs show RUN_ID`. The output includes `flow_run_id`.
2. Open `<prefect-ui>/runs/flow-run/FLOW_RUN_ID` in a browser. The state message of the failed
   flow run contains the error. On a Compose deployment, the Prefect UI is not published by
   default; open it on `127.0.0.1` as described in
   [Open the Prefect UI](./compose-deployment.mdx#open-the-prefect-ui). It is at
   `http://127.0.0.1:4230` on the
   [local development stack](./development-stack.mdx).

The same error is in the worker's log: `docker compose logs sync-worker` from the deployment
directory, or `docker compose -f development/docker-compose.dev.yml logs sync-worker` from a
checkout running the local development stack.

### Recover from an interrupted apply

An apply can stop after it has written earlier operations. Nothing is rolled back: those
writes stay written. How the run ends depends on what the service knows about the operation
that failed:

- If the failed operation is known not to have written, the run ends with
  `phase: apply-failed` and `outcome: failed`.
- If the service cannot tell whether it wrote, the run ends with `phase: apply-interrupted`
  and `outcome: ambiguous`, and the failed operation may have written part of its change.

Remove the cause first, in the source data or in the package. Then create a new plan for the
same branch with `diff`, review it, and apply it. The new plan compares the source with what
the destination now holds, so it contains only what is still missing or different.

A run accepts one apply. A second `apply` of a run whose apply finished or stopped is refused
before any write, with code 1:

```text
apply refused: This plan was already applied or its apply stopped; create and review a new plan
```

## Change a registered package

A registered version never changes. To change a package, edit the file and register it as a
new version of the same configuration:

<Tabs groupId="sync-client">
  <TabItem value="compose" label="Run the container image" default>

  ```bash
  docker compose run --rm --no-deps -T -v "$PWD/package.yml:/input/package.yaml:ro" \
    cli configs version CONFIG_ID /input/package.yaml --reason "update inventory mapping"
  ```

  </TabItem>
  <TabItem value="source" label="Run from source">

  ```bash
  uv run infrahub-sync configs version CONFIG_ID package.yml --reason "update inventory mapping"
  ```

  </TabItem>
</Tabs>

Then validate the new version and create a plan with `--version` set to the new version
number. Do not use `configs register` for an edited package: it creates a separate
configuration with a new `config_id`.

## Run a sync without a review step

`sync` creates a plan and applies it in the same run, with no pause for review:

Run from source:

```bash
uv run infrahub-sync sync --config-id CONFIG_ID --version 1 --branch BRANCH \
  --reason "scheduled synchronization"
```

Run the container image:

```bash
docker compose run --rm --no-deps -T cli sync --config-id CONFIG_ID --version 1 --branch BRANCH \
  --reason "scheduled synchronization"
```

The worker saves the plan before the first write, so you can read it afterwards with
`runs plan`. `sync` does not apply a plan that you reviewed earlier; it creates a new one. To
approve the exact operations before they are written, use `diff`, `runs plan`, and `apply`.

When the plan of a `sync` leaves out records, the run stops after the plan and writes nothing.
The run ends with `phase: planned` and `outcome: left-out-review-required`, and the command
exits with code 1:

```text
sync stopped: the plan leaves out 12 records, so the sync stopped before writing
  next: Review the left-out records with `infrahub-sync runs left-out`, then apply the plan with `infrahub-sync apply --confirm-left-out`.
```

Review the plan with `runs plan`, `runs problems`, and `runs left-out`. Then apply the same
run with `apply RUN_ID --expected-checksum CHECKSUM --confirm-left-out`. No option of
`sync` skips this stop.

## Reference

### Waiting for a run

`diff`, `sync`, and `apply` wait for the run by default. They poll the service every
2 seconds for at most 30 minutes. `--poll-interval` and `--wait-timeout` change these
values, in seconds. A large apply needs a longer wait, and how long it takes depends on the
destination. For example, applies of the NetBox demo package took 11 minutes for about 1,700
operations on 2026-09-29, and 46 seconds for 1,609 operations on 2026-10-05, against different
local Infrahub instances.

`--no-wait` returns after the service accepts the request. The output includes the run ID
and the retry key. Check the run later with `runs show RUN_ID` or `runs plan RUN_ID`.

### Wait outcomes

- A run that succeeds prints its latest record.
- A run that fails, is cancelled, or ends in an unknown state exits with a nonzero status
  and prints the run ID and its final fields.
- A run that failed or stopped also prints its cause: a `<stage> failed: <summary>` or
  `<stage> stopped: <summary>` line, the detail lines, and the next step. See
  [Find why a run failed](#find-why-a-run-failed). When the destination schema changed after
  the plan was saved, the summary reads `the saved plan did not pass verification`: create and
  review a new plan.
- When the wait times out, the CLI exits with a nonzero status and prints the run ID and its
  last phase, outcome, and execution state. The run continues on the service.
- Ctrl-C stops the wait, prints the last record, and exits with status 130. It does not
  cancel the run.

### Retry keys

`configs register`, `configs version`, `diff`, `sync`, and `apply` accept
`--idempotency-key`. If you omit it, the CLI generates a key and prints it. If the connection
fails before you see a response, run the same command again with that key. The service then
returns the original response instead of starting a second operation. See
[Retry keys](./configuration-package.mdx#retry-keys).

### Output fields

- `configs validate` prints `offset`, `limit`, `total_findings`, and `next_offset`. Use
  `--offset` and `--limit` to read another page of findings.
- `runs show RUN_ID` prints the run's phase, outcome, execution state, and Prefect
  correlation. After an apply or a `sync`, it also prints `operations_written` and
  `left_out`, and for a run that failed or stopped, its cause.
- `runs results RUN_ID` prints the results that the service recorded for the run, as JSON.

For every command and option, see the [Sync CLI reference](./reference/cli.mdx).
