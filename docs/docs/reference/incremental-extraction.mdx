---
title: Incremental extraction
---

Incremental extraction lets a run read only what changed since a previous run, instead of
re-reading every source record. Today, whether a run extracts incrementally or in full is
decided by the worker that runs it, not by the CLI: the CLI submits only a registered
configuration version and does not select local extraction or cache controls.

A configuration package can declare the optional incremental capability. During
validation, `optional-feature-unqualified` warns when the selected source adapter does not
qualify that feature.

## The supported service

The managed `plan` and `sync` stages begin in a private empty directory they create for
themselves and release when the stage ends. They inherit no side snapshot and no cursor from
an earlier run, so each is an explicit cold start and extracts in full. The `verify` and
`apply` stages do not extract: `verify` reads the saved plan back, and `apply` opens and
applies it.

`incremental.full_resync_every` remains schema-valid, and a package declaring it is still
accepted, but it governs nothing on this path: with no earlier run's state to carry forward
(no **predecessor state**) there is nothing for a cadence to count. Carrying that state
across workers (**predecessor hydration**) and the cadence that would pace it are later
work; until they exist, every managed extraction (`plan` and `sync`) is full.

## Direct execution

Direct non-service execution keeps the engine's own cache layout, where **cursors**
(per-adapter bookmarks of what was already read), **side snapshots** (a saved copy of the
prior extraction used to detect changes), and the **schema sub-hash** (a digest of the
mapped schema, used to invalidate a cursor when the mapping changes) live under the run's
cache root. The incremental path and the adapter cursor contract are implemented there.
Every managed stage that extracts (`plan` and `sync`) requests a full extraction (`full_extract=True`), so incremental
extraction is not reachable through the managed path. A direct caller of `execute_run` may
instead set `full_extract=False` and reuse a persistent cache root across runs; that call
reaches the per-resource incremental branch when a prior successful run exists there with a
matching schema sub-hash. No product code writes the cursor sidecar there either, though, so
every resource still falls back to a full extraction on that path too, one resource at a
time, instead of reading only what changed.

## What a saved plan records about deletes

Timestamp-based incremental extraction can miss deleted source rows, so a plan records
whether its deletes were derived from a fully enumerated destination. When the destination
side did not run a full extract, the saved plan reports `delete_operations_computed:
false`, and `runs plan` discloses that the review may omit destination deletes. A run that
extracted the destination in full records `true`.

Current timestamp-capable adapters include NetBox, Nautobot, and Infrahub. Other adapters
use full extraction unless their capability contract says otherwise.
