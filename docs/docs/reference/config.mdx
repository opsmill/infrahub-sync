The `configuration` object of a [configuration package](../configuration-package.mdx)
defines the source, the destination, and the mappings of one sync. A package also has an
optional `format_version` (only `1`, the default) and an optional `credentials` block. For
a complete package, see `examples/netbox_to_infrahub/package.yml`.

Write the package as YAML or JSON and register it with `infrahub-sync configs register`.
Run commands then select it by its configuration ID and registry version. The service
worker resolves the registered configuration and loads installed or pre-rendered adapter
classes. It reads the registered content, not the file.

## Configuration fields

Describes the overall synchronization configuration.

| Property | Type | Description | Mandatory |
| -------- | ---- | ----------- | --------- |
| `name` | string | Unique identifier for the sync instance. | Yes |
| `store` | `SyncStore` | Configuration for the optional storage mechanism. | No |
| `source` | `SyncAdapter` | Configuration for the source adapter. | Yes |
| `destination` | `SyncAdapter` | Configuration for the destination adapter. | Yes |
| `order` | List of strings | Order in which objects should be synchronized. Optional — when omitted, infrahub-sync auto-computes tiers from schema_mapping. | No |
| `schema_mapping` | List of `SchemaMappingModel` | Defines how data is mapped from source to destination. | No; a package without mappings registers but synchronizes nothing. |
| `diffsync_flags` | List of DiffSync flag names | Changes which operations a plan contains. `SKIP_UNMATCHED_SRC` removes creates. `SKIP_UNMATCHED_DST` is always in effect. No flag makes apply execute a delete. See [Creates, updates, and deletes](../creating-a-sync-project.mdx#creates-updates-and-deletes). | No |

### Automatic write order

`order:` is optional. Omit it and infrahub-sync computes a write order for
you from the `reference:` entries in `schema_mapping`, so a kind is normally
written after the kinds it references. A self-reference (a kind referencing
itself) adds no ordering edge, and a reference outside the kind's
`identifiers` is optional. When cycles prevent ordering, infrahub-sync discovers
cycles by visiting kinds in `schema_mapping` order and sorting only each kind's
references, then drops all optional edges in those discovered cycles in one pass.
It repeats this until
ordering succeeds or only identity-reference cycles remain, which cause an error.
Each dropped edge is logged at WARNING level, and its kind may be written before
the referenced kind. For every adapter, this stabilizes tiers for cyclic
configurations that previously varied between runs. Keep `order:` only to override
the computed order for an adapter quirk.

For an Infrahub destination, a `reference:` to a generic kind waits for every
mapped concrete kind in that generic's live schema `used_by` list. The generic
itself is not added as work when it has no mapping. If neither the generic nor
any of its concrete peer kinds is mapped, the run reports a configuration error
before loading records. Map the generic or concrete peer kinds, or provide an
explicit `order:` list.
Expansion can expose an identity-reference cycle that previously went unnoticed;
resolve the cycle in your mapping or provide an explicit `order:`. Saved plans that
reference an Infrahub generic must be created and reviewed again after upgrading,
because the plan's schema fingerprint now includes its mapped concrete peers.

For every adapter, a dependency required by an identity field stays required even
when an optional field references the same peer. This applies to concrete references
and expanded generic references. Cycle breaking preserves that dependency and
refuses cycles made entirely of identity dependencies.

Internally, infrahub-sync derives a write-order graph from the `reference:`
entries in each `schema_mapping` field and groups kinds into **tiers**:

- Tier 0: kinds with no outgoing references.
- Tier N: kinds whose references all live in tiers `0..N-1`.

The flattened tier order replaces the manual `order:` list, and every planned operation
records the tier its kind belongs to. A plan stores its operations ordered by
`(tier, operation_id)` and an apply executes them in exactly that order, so a kind is
written after the kinds it references — except an optional reference dropped to
break a cycle, as described above.

If you must override the computed order because it does not match an adapter quirk, keep
the `order:` list. It always wins: no tiers are computed, and each operation's recorded
tier is the kind's position in the list you gave. The ordering is the same either way —
the reviewed operation sequence is what an apply consumes, and there is no separate
serial or parallel execution mode to choose.

### Source and Destination

<!-- vale on -->
Configuration for source and destination adapters.

| Property | Type | Description | Mandatory |
| -------- | ---- | ----------- | --------- |
| name | string | Name of a bundled adapter. See [Choose an adapter](../adapters/choosing-an-adapter.mdx). | Yes |
| settings | Dictionary | Adapter-specific settings such as `url` and `token`. A credential-bearing setting holds a `$credential` reference to the package's `credentials` block, never a literal value; see [Credentials](../configuration-package.mdx#credentials). | No |

#### Settings in a registered package

A registered run uses the settings declared in the package:

- The worker connects to the declared `url` of each adapter. Environment URL variables such
  as `NETBOX_URL` or `INFRAHUB_ADDRESS` do not replace it. The destination schema read uses
  the same declared URL.
- Each `$credential` reference resolves when a run starts, from the environment variable that
  its `credentials` entry names in the worker environment.
- To change a URL or another setting, edit the package and register a new version with
  `configs version`. Then run the new version.

IP Fabric also reads `IPF_URL` and `IPF_TOKEN` from the worker environment in a registered
run when `base_url` or `auth` is not declared.

Direct adapter use without a registered package is different. The
[Prefect remote run](./prefect-remote-run.mdx) and Python callers that load a `config.yml`
directory let each adapter read its environment variables, such as `NETBOX_URL`, before the
declared settings. Each adapter page lists its variables.

### Schema Mapping

<!-- vale on -->
Defines the mappings from source to destination schemas. The tables below are the structural field reference. For the mapping syntax in depth — direct mappings, references, identifiers, filters, transforms, and worked NetBox and Nautobot examples — see [Schema mapping reference](./schema-mapping.mdx).

#### Mapping models

| Property | Type | Description | Mandatory |
| -------- | ---- | ----------- | --------- |
| name | string | Infrahub model name to be mapped. | Yes |
| mapping | string | The source's schema mapping (API) path. | Yes |
| identifiers | List of strings | Fields used to uniquely identify an object. | Yes |
| fields | List of SchemaMappingField | Describes individual field mappings or transformations. | Yes |
| filters | List of SchemaMappingFilter | Filters you want to apply during the sync. | No |
| transforms | List of SchemaMappingTransform | Transforms you want to apply during the sync. | No |

##### Mapping field

| Property | Type | Description | Mandatory |
| -------- | ---- | ----------- | --------- |
| name | string | Name of the field. | Yes |
| mapping | string | How the field is mapped from source to destination. | No |
| static | Any | A static value to assign to the field. Any declared value is assigned, including `false`, `0`, `""` and `[]`; omit it or set it to `null` for no static value. Takes precedence over `mapping` when both are declared. See [Static values](./schema-mapping.mdx#static-values) for the adapters that do not assign these values yet. | No |
| reference | string | Reference to another object in the configuration, used if direct mapping is not applicable. | No |

##### Mapping filters

| Property | Type | Description | Mandatory |
| -------- | ---- | ----------- | --------- |
| field | string | Name of the source field to filter on. | Yes |
| operation | string | Which filters will be applied on the field. Available operations are described below. | No |
| value | string | The expected value linked to the operation. | Yes except for both is_empty and is_not_empty operation |

For the full list of filter operations (`==`, `!=`, `>`, `<`, `>=`, `<=`, `in`, `not in`, `contains`, `not contains`, `is_empty`, `is_not_empty`, `regex`, `is_ip_within`) with examples, see [Available filter operations](./schema-mapping.mdx#available-filter-operations).

##### Mapping transforms

| Property | Type | Description | Mandatory |
| -------- | ---- | ----------- | --------- |
| field | string | Name of the target field. | Yes |
| expression | string | A Jinja filter compatible expression. | Yes |
