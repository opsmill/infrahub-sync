# `infrahub-sync`

Synchronize registered configurations through the Sync API.

Sign in with `infrahub-sync login`, which saves a session for the address in
`INFRAHUB_SYNC_API_URL`, or, for a script, set `INFRAHUB_SYNC_API_TOKEN` to an API token
of an account. When `INFRAHUB_SYNC_API_TOKEN` is set and not empty, every command other than
`login` and `logout` presents it and not the saved session. The CLI reads the token from the
environment and never accepts it as a flag.
See [Manage accounts](../guides/accounts.mdx) for accounts and tokens, and
[Sync HTTP API — Accounts and API tokens](./sync-http-api.mdx#accounts-and-api-tokens).

When the Sync API address is missing or invalid, or the token is missing, a command prints
`error: client-input` and `argument: service_url` or `argument: token` on standard error,
then a `hint:` line. An address is invalid when it does not use `http` or `https`, has no
host, or carries a user name, a password, a query string or a fragment. For the address,
set `INFRAHUB_SYNC_API_URL` or pass `--api-url` with the address of the Sync service, for
example `http://127.0.0.1:8001`; the client adds `/api`. For the token, run
`infrahub-sync login` or set `INFRAHUB_SYNC_API_TOKEN`. Other `client-input` errors print no
`hint:` line.

**Usage**:

```console
$ infrahub-sync [OPTIONS] COMMAND [ARGS]...
```

**Options**:

* `--api-url <str>`: Address of the Sync service, for example http://127.0.0.1:8001. The client adds /api. Defaults to INFRAHUB_SYNC_API_URL.  [env var: INFRAHUB_SYNC_API_URL]
* `--verbosity <quiet|default|verbose>`: Log verbosity level.  [default: default]

## `infrahub-sync login`

Sign in with an account name and its password, and save the session for this Sync API address.

The password is asked for without echo. With --password-stdin it is read from standard input,
and --name is required. The session is saved in sessions.json in the application directory of
infrahub-sync, with mode 0600 so that only you can read it; on Windows, access to the file
follows the permissions of that directory. While INFRAHUB_SYNC_API_TOKEN is set and not empty,
every command other than login and logout uses that variable and not the saved session.

**Usage**:

```console
$ infrahub-sync login [OPTIONS]
```

**Options**:

* `--name <str>`: Account name. Asked for when not given.
* `--password-stdin`: Read the password from standard input instead of a prompt.
* `--help`: Show this message and exit.

### `infrahub-sync configs convert`

Convert a v1 or v2 config.yml into a V3 configuration package. Needs no Sync API.


The command never prints or reads a credential value. It opens no network
connection unless --live-schema is given; then it reads the Infrahub schema
without a token and maps each IP namespace that a uniqueness constraint
needs and config.yml does not map to the &#x27;default&#x27; namespace, where v2
wrote it. It prints a report, asks before it writes, and writes nothing
without a terminal unless --yes is given.


The report names each credential setting that v2 used with the
environment variable the Sync worker reads in V3, each address with its origin (a flag, a v2
variable, or config.yml), each dropped key with its reason, and notes.
It warns when config.yml still holds a literal credential, when the
shipped Compose file does not pass a credential variable to the Sync
worker, when an address is localhost or 127.0.0.1, and when an address
came from a generic variable name.


Exit status 1, nothing written, when the configuration has any of:
- a source or destination name that is not a bundled adapter
- a custom adapter (INFP-654, planned for 3.0)
- a destination other than Infrahub
- a setting the bundled adapter does not accept
- an `auth_method` value v2 did not accept
- a placeholder v2 did not read
- an address with a user name or password
- an address with no value in config.yml, a v2 variable or a flag
- a placeholder in a setting v2 read from a variable, when no such variable is set


Exit status 1 also when:
- the package fails a registration check
- the output file exists and --force is not given
- --output names the input file, even with --force
- there is no terminal and --yes is not given
- the package cannot be written


Exit status 2 when:
- PATH cannot be read
- PATH is not valid YAML
- PATH is not a v1 or v2 configuration
- the directory of the output file does not exist

**Usage**:

```console
$ infrahub-sync configs convert [OPTIONS] {path}
```

**Arguments**:

* `path`: The v1 or v2 config.yml to read.  [required]

**Options**:

* `--output <path>`: Where to write the package. Defaults to package.yml next to PATH.
* `--force`: Replace an existing output file.
* `--yes`: Write without asking.
* `--source-url <str>`: The source address. Overrides the file and the v2 variables.
* `--destination-url <str>`: The Infrahub address. Overrides the file and the v2 variables.
* `--live-schema`: Read the Infrahub schema, without a token, and map an unmapped IP namespace to &#x27;default&#x27;.
* `--help`: Show this message and exit.

### `infrahub-sync runs show`

Show one run&#x27;s service record and its selected execution.

`prefect_flow_run_url` links the flow run in the Prefect UI; it reads &lt;none&gt; when the Sync API has no UI address.
For a run with a `plan` or `sync` stage, `source_read` and `destination_read` show the read state of each side
in that stage&#x27;s latest execution: `state`, `mode`, `started_at`, `ended_at`, `nodes` and `error`, without the
keys that have no value. A side with no read state to return reads &lt;none&gt;. Neither line is printed when that
execution has no read state: a run recorded before the read state, a stage the worker has not started, or a
stage whose read state the worker could not store.
After them, one `plan_&lt;part&gt;` line per part of that execution&#x27;s plan step that started: `plan_waiting`,
`plan_preparing`, `plan_comparing`, `plan_checking` and `plan_saving`. A part that ended shows its duration in
seconds, the part that runs shows `running`, and a part that was running when the stage failed, was cancelled or
was interrupted shows `stopped after &lt;seconds&gt;s`, or `stopped` when no stop time exists. No plan line is printed
for a run recorded before these timings. The plan step lines are subject to change in a later release.
A failed stage adds its error type and, when the run recorded them, a `cause:` and a `hint:` line.
A `sync` that stopped after a plan that leaves out records adds a `sync stopped:` and a `hint:` line.
A run with a write adds a `progress:` line, a `resumable:` line, one `kind` line per kind with its committed,
uncertain and not reached operations, and one `resume` line per resume of the run. The counts are over the
plan&#x27;s positions, recorded deletes included. The uncertain operations follow the saved position: through the
failed operation when the worker recorded it, and every remaining operation when the worker was killed or its
last save is not known to have succeeded. While a resume runs, they are the next 500 creates and updates
and the recorded deletes between them; while a first apply or `sync` runs, none are uncertain. A `resume`
line counts the creates and updates that resume wrote; the `written:` line of a failed write counts those of
every execution of the run.
Then `trigger_type` is `manual` for a run a person started and `scheduled` for a run a schedule started; a
scheduled run also shows its `schedule_id` and `scheduled_start_at`, the start time of the cadence.

**Usage**:

```console
$ infrahub-sync runs show [OPTIONS] {run_id}
```

**Arguments**:

* `run_id`: Service-issued run ID.  [required]

**Options**:

* `--help`: Show this message and exit.

### `infrahub-sync schedules create`

Create a schedule that starts a `sync` run of one configuration version on a cron cadence.

By default each run writes to a new branch and opens a proposed change for review in Infrahub.
With `--write-to-default-branch`, each run writes to the branch that a `sync` run of the
configuration writes to; a Sync API that requires an approved plan refuses it. The Sync API
validates the cron expression and the time zone. The output shows the schedule with `next_start_at`.

**Usage**:

```console
$ infrahub-sync schedules create [OPTIONS]
```

**Options**:

* `--name <str>`: Schedule name, unique among the schedules that are not deleted.  [required]
* `--config <str>`: Configuration ID or name. The ID is tried first, then the name.  [required]
* `--version <int range>`: The configuration version each run synchronizes.  [x&gt;=1; required]
* `--cron <str>`: Cron expression with five fields, such as &quot;0 2 * * *&quot;.  [required]
* `--timezone <str>`: Time zone of the cron expression, such as Europe/Paris.  [default: UTC]
* `--write-to-default-branch`: Write each run to the branch that a sync run of the configuration writes to, with no proposed change. Without this option each run writes to a new branch and opens a proposed change for review. A Sync API that requires an approved plan refuses it.
* `--write-when-left-out / --no-write-when-left-out`: Turn on or off the left-out setting: when on, a run whose plan leaves out records writes the other records instead of stopping after the plan. Applies only to a schedule that writes to the default branch; the Sync API refuses it for branch review.
* `--overlap-policy <reject|queue>`: What a start does while a run of the configuration is in progress: reject skips the start, queue makes one start wait and run when the run in progress ends.
* `--start-late-by-at-most <str>`: How late the most recent start may begin after a time when the Sync service was not running, such as 30m or 2h (from 1m to 7d). The Sync API uses 1h when the option is not given.
* `--reason <str>`: Optional audit reason.
* `--idempotency-key <str>`: Retry key.
* `--help`: Show this message and exit.
