The Sync HTTP API accepts authenticated run requests, records a stable Sync run
identity, and delegates execution to a separate Prefect deployment. Sync owns the HTTP,
authorization, plan, result, artifact, audit, and idempotency contracts. Prefect owns live
execution state, workers, retries, logs, and cancellation.

The [direct Prefect remote run](./prefect-remote-run.mdx) remains a
separate four-parameter deployment. Use the Sync API when a trusted automation client
needs reviewed-plan apply, durable results, artifact retrieval, or actor-scoped mutation
control.

## Terms

- **Configuration**: a registered sync definition, identified by `config_id`. Its `name` is
  readable but not unique.
- **Configuration version**: one immutable registered revision of a configuration,
  identified by `config_id` and `registry_version`.
- **Run**: one attempt to synchronize one configuration version to one branch, identified by
  `run_id`. A run creates exactly one plan and applies that plan at most once.
- **Plan**: the creates, updates and recorded deletes that a run computes before it writes,
  with their checksum. Verify and apply act on the plan of the run they name: they do not
  compute a new plan.
- **Stage**: one execution step of a run: `plan`, `verify`, `apply` or `sync`. Each stage runs
  as one Prefect flow run.

## Install the service profile

The service profile requires Python 3.11 or later. Install it from a repository checkout on
the API host and on every worker that can run its deployment:

```bash
uv sync --extra dev --extra prefect --extra service
```

The profile directly installs FastAPI, HTTPX, Uvicorn, Prefect 3.8.6, Psycopg, and Boto3. It also installs
the client libraries of the bundled NetBox and Nautobot adapters, `prometheus-client`, and `infrahubctl`. The OpsMill
Prefect Extras integration ships with the package itself as a vendored copy of upstream
commit `97465e75137f6121d0377cd637383cfb3530d734`. The base installation does not import
any of these modules. Ordinary CLI and Python API imports remain Prefect-free.

You also need:

- a Prefect API and an existing process work pool;
- a worker with access to the allowed Sync configuration directory, needed only for
  legacy unregistered runs;
- PostgreSQL for product records; and
- an S3-compatible bucket for immutable artifacts.

The API and worker each create a process-local client from the same PostgreSQL/S3 settings.
They share durable records and artifacts through those services, not through a product filesystem.
S3 credentials use Boto3's standard credential-provider chain.

## Configure principals

`INFRAHUB_SYNC_SERVICE_BEARER_TOKENS` contains a non-empty JSON object keyed by actor. Each
entry has a bearer token of at least 16 characters and an optional administrator flag:

```bash
export INFRAHUB_SYNC_SERVICE_BEARER_TOKENS='{
  "automation@example.com": {
    "token": "replace-with-a-secret-token",
    "administrator": false
  },
  "sync-admin@example.com": {
    "token": "replace-with-another-secret-token",
    "administrator": true
  }
}'
```

Inject this value through your deployment's secret mechanism. Do not put a real token in a
shell history, Sync configuration, request body, idempotency key, or Prefect parameter.
Tokens must be unique. The resolver compares them with a timing-safe operation and never
persists, returns, or submits them to Prefect.

Any authenticated principal can create and inspect a run. Only the initiating actor or an
administrator can verify, apply, or cancel it. Every accepted mutation and authorization
refusal records secret-safe actor, reason, and outcome evidence.

## Deploy the service flow

Set the work pool name, then apply the service deployment:

```bash
export PREFECT_API_URL="http://127.0.0.1:4200/api"
export INFRAHUB_SYNC_SERVICE_WORK_POOL="sync-process-pool"
python -m infrahub_sync.service.deploy
```

The command validates and applies `infrahub-sync-service/run` through OpsMill Prefect
Extras, then drives the deployment's pull steps to empty. It does not create a work pool
or start a worker.

The deployment's entrypoint is the installed module path
`infrahub_sync.service.flow.service_sync_run`. A worker resolves it by importing the
installed `infrahub-sync` distribution, so it needs no repository checkout, no declared
working directory, and no source-pull step. Applying the deployment removes any pull step
an earlier release installed; without that, workers would keep entering a source tree
that need not exist on their host. Install the same `infrahub-sync` version on every
worker.

## Start service workers

Start each worker through the service entry point. The work pool must already exist:

```bash
python -m infrahub_sync.service.worker \
  --pool "$INFRAHUB_SYNC_SERVICE_WORK_POOL"
```

Each invocation generates a new UUID-suffixed worker name. After its Prefect heartbeat,
the worker reads the exact Worker record for that name and work pool and records the
server-issued UUID as its Prefect backend identity. Prefect 3.8.6 passes that identity
to each `ProcessJobConfiguration` and injects `PREFECT__WORKER_ID` into that worker's
flow-run child. The deployment stores no worker identity.

A restarted process generates a new name and resolves its current server Worker UUID.
It does not reuse an identity from the previous process.

Plan, verify, apply, and sync share no Sync filesystem. Each stage creates its own
private scratch directory, hands the next stage what it needs through internal artifacts
in the product store, and releases the directory when it ends. An apply therefore runs on
any worker, including one that never saw the plan: it resolves the plan from the run's
internal checkpoint and refuses if that checkpoint is missing, oversized, corrupt,
digest-mismatched, or another run's.

Use this entry point for every worker eligible to run the service deployment; manually
named or standard Prefect process workers are outside the supported topology.

The worker does not poll for runs until its heartbeat is complete and the pool returns
exactly one online record with its name, work pool, and a standard UUID string. An
absent, malformed, offline, wrong-pool, or ambiguous record keeps polling disabled and
fails with fixed, value-free text.

Configure the worker environment before it starts:

| Variable | Requirement |
| --- | --- |
| `PREFECT_API_URL` | Prefect API used by the deployment and worker. |
| `INFRAHUB_SYNC_CONFIG_DIRECTORY` | Legacy runs only. A registered run reads its declared configuration from PostgreSQL and resolves both adapters from installed code, so a worker serving registered runs needs no directory and no configuration mount. Set it only where unregistered runs — which resolve a `SyncConfig` file by name — still have to be served; those runs refuse when it is unset or names no directory. |
| `INFRAHUB_SYNC_DATABASE_URL` | Non-empty PostgreSQL connection string accepted by Psycopg for product records. |
| `INFRAHUB_SYNC_S3_BUCKET` | Non-empty bucket for immutable product artifacts. |
| `INFRAHUB_SYNC_S3_PREFIX` | Optional object-key prefix; defaults to `infrahub-sync`. |
| `INFRAHUB_SYNC_S3_ENDPOINT_URL` | Optional absolute `http` or `https` URL with no userinfo. The value reaches Boto3 unchanged; Boto3 owns any narrower SDK compatibility. |
| `INFRAHUB_SYNC_S3_REGION` | Optional region passed to Boto3. |
| `INFRAHUB_SYNC_SERVICE_WORK_POOL` | Name of the existing Prefect pool used by the deployment, worker, and API reconciliation. It is never returned by the API. |
| `INFRAHUB_SYNC_RUN_ADMISSION_TTL_SECONDS` | Optional decimal integer from 1 through 86400; defaults to 300. An unclaimed execution becomes abandoned at this inclusive deadline. |
| `PREFECT_WORKER_QUERY_SECONDS` | Prefect worker polling interval. It must be a finite positive decimal no greater than 3600; the API derives its liveness thresholds from the same value. |
| Adapter credential variables | The environment variables that the `credentials` entries of a registered package name, for example `INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN`. A registered run reads only these credential values from the worker environment; adapter URL variables such as `NETBOX_URL` do not replace the declared URLs. |

The service flow accepts exactly eight bounded parameters:

| Parameter | Type | Purpose |
| --- | --- | --- |
| `run_id` | `str` | API-created Sync run identity. |
| `stage` | `plan`, `verify`, `apply`, or `sync` | Execution stage accepted by the API. |
| `config_id` | `str` or `null` | Registered configuration identity. |
| `registry_version` | `int` or `null` | Immutable version of the registered configuration. |
| `package_checksum` | `str` or `null` | Checksum bound to the registered configuration package. |
| `branch` | `str` or `null` | Optional Infrahub branch. |
| `expected_checksum` | SHA-256 string or `null` | Reviewed checksum required by `apply`. |
| `confirm_writes` | `bool` | Required for `apply` and composed `sync`. |

`config_id`, `registry_version`, and `package_checksum` must be all present for a
registered execution or all `null` for a legacy execution.

The API rejects configured secret values in flow-bound request fields. Credentials,
endpoints, adapter instances, and filesystem paths are never flow parameters.

## Start the API

Set the same durable-store contract used by the worker and start Uvicorn through the packaged
entry point:

```bash
export PREFECT_API_URL="http://127.0.0.1:4200/api"
export INFRAHUB_SYNC_DATABASE_URL="postgresql://sync:replace-me@postgres/infrahub_sync"
export INFRAHUB_SYNC_S3_BUCKET="infrahub-sync-artifacts"
export INFRAHUB_SYNC_S3_PREFIX="infrahub-sync"
export INFRAHUB_SYNC_SERVICE_HOST="127.0.0.1"
python -m infrahub_sync.service.serve
```

:::warning First startup after upgrading a legacy product store

A validated single legacy startup migrates `mutation_receipts.run_id` and
`mutation_receipts.prefect_key` from `is_nullable=NO/NO` to nullable. Two simultaneous
first startups while the PostgreSQL catalog is still legacy can deadlock one startup.
The failed startup fails closed before worker claim or admission, writes no Sync data,
and the catalog converges through the successful startup.

Restart the failed process after the first migration converges. Repeated or concurrent
startups against an already-migrated nullable catalog are supported. The failed startup
does not retry automatically.

:::

The server listens on port `8000`. Its host defaults to `127.0.0.1`. Put TLS and any
network access controls at your ingress boundary. The bearer-token provider is the MVP
application authentication boundary, not a replacement for transport security.

Open `http://127.0.0.1:8000/docs`, select **Authorize**, and enter the configured token
without the `Bearer` prefix; Swagger UI adds the complete `Authorization` header.

## Discovery and liveness

`GET /status` and `GET /version` are the two unauthenticated lifecycle and
server-discovery routes. They intentionally disclose neither a configured work-pool
name, worker or run identity, credential, nor Prefect endpoint. All run and
configuration routes remain bearer-authenticated.

`GET /version` returns the installed server version and the currently supported
unstable API identifier:

```json
{"server_version":"<installed version>","api_versions":["v3-unstable"],"stability":"unstable"}
```

It is a discovery resource only. This server does not yet reject clients based on a
claimed compatibility range.

`GET /status` describes the configured work pool without exposing its identity:

```json
{
  "service": "ready",
  "worker": {
    "state": "ready",
    "detail_available": true,
    "live_workers": 1,
    "queue_depth": 0,
    "observed_at": "2026-08-29T12:00:00+00:00"
  }
}
```

The worker state is `ready` when at least one fresh ONLINE worker has no queued
runs, `busy` when one is fresh and the queue is non-empty, and `no-live-worker`
when pool detail was read but no worker is fresh. A fresh worker has a heartbeat no
older than `max(3 × heartbeat interval, 30 seconds)`. If Prefect cannot provide a
usable pool result, the state is `unavailable`, `detail_available` is `false`, and
`live_workers`, `queue_depth`, and `observed_at` are all `null`. This value-free
response does not expose provider errors or values.

Each submitted Prefect execution is claimed by its worker before it resolves a
configuration or builds adapters. The API derives the stall threshold as
`max(3 × PREFECT_WORKER_QUERY_SECONDS, 30 seconds)`, and reconciles no less often
than that threshold permits (at most five seconds, with a 0.25-second lower bound).
An unclaimed execution is marked stalled at that threshold and becomes abandoned at
the admission TTL. A claimed execution whose exact owner is no longer fresh becomes
`interrupted` with an `ambiguous` outcome; it is not retried automatically.

Cancellation is also bounded. Sync persists cancellation intent before contacting
Prefect. A successful Prefect acknowledgement is recorded separately. Until the
same liveness threshold expires, that intent fences claim, abandonment, and orphan
adjudication. At the inclusive deadline, an unconfirmed cancellation settles as
unavailable and the execution becomes abandoned or interrupted/ambiguous according
to whether it was claimed. An acknowledged request retains its accepted response,
but still reaches that terminal verdict unless Prefect is durably observed as
terminally cancelled first.

A terminal execution is immutable, so its summary is served from the retained record
and carries no live provider detail: `detail_available` is `false` and
`unavailable_reason` is `live-detail-not-requested`. Once an execution has a recorded
`terminal_state`, its `state` is that terminal state, in every response, even when a live
or retained Prefect observation reports an earlier state such as `running`.
`terminal_state` and `terminal_outcome` are the authoritative fields for how an
execution ended. Only the response that records an execution's terminal
verdict still carries that execution's live detail.

Each orchestration entry also carries `prefect_flow_run_url`: the address of the flow
run's page in the Prefect UI, `<INFRAHUB_SYNC_PREFECT_UI_URL>/runs/flow-run/<flow_run_id>`.
It is `null` when `INFRAHUB_SYNC_PREFECT_UI_URL` is unset or empty. The Sync API reads that
setting at start-up and refuses to start when it is not an absolute `http` or `https` URL
with a host, or when it holds credentials, a query or a fragment. The refusal message names
the setting and does not repeat its value. A client from an earlier release accepts a
response that holds the field.

### Read state of each side

Each orchestration entry also carries `reads`: the state of the source read and the
destination read of a `plan` or `sync` execution. Read the run while the stage runs to follow
each side, and after it ends to find which side failed or did not start. Every route whose
response holds orchestration entries returns it: `POST /runs`, `GET /runs/{run_id}`,
`POST /runs/{run_id}/verify`, `POST /runs/{run_id}/apply` and `POST /runs/{run_id}/cancel`.
`GET /runs` does not return it, because its items hold no orchestration entries.

```json
"reads": {
  "source": {
    "state": "succeeded",
    "started_at": "2026-11-09T10:00:01Z",
    "ended_at": "2026-11-09T10:00:13Z",
    "read_mode": "full",
    "nodes_by_kind": {"DcimDevice": 3, "LocationSite": 2},
    "error_class": null
  },
  "destination": {
    "state": "reading",
    "started_at": "2026-11-09T10:00:01Z",
    "ended_at": null,
    "read_mode": null,
    "nodes_by_kind": {},
    "error_class": null
  }
}
```

`reads` is `null` in four cases:

- For a `verify` or `apply` execution, which reads neither side.
- For an execution recorded before the Sync API stored the read state.
- For a `plan` or `sync` execution that the worker has not started yet.
- For a `plan` or `sync` execution in which the worker could not store the read state of
  either side. The worker logs a warning when a write fails and continues the stage, so
  `reads` can stay `null` after the stage has started.

When the worker starts a `plan` or `sync` stage, it records both sides as `waiting` before
it reads the destination schema and, for a `sync`, before it waits for the configuration's
write guard. When that write succeeds, `source` and `destination` are both present from that
moment, so a stage that fails before either read returns both sides as `not_started`. When
`reads` is not `null`, `source` or `destination` is `null` when the worker could not store
that side's read state, and in the cases that the list after the table describes.

| `state` | Meaning |
| --- | --- |
| `waiting` | The worker started the stage and has not started reading this side. |
| `reading` | The read of this side has started and has not ended. `started_at` is set. |
| `succeeded` | The read ended without an error. `ended_at`, `read_mode` and `nodes_by_kind` are set. |
| `failed` | The read ended with an error. `ended_at` and `error_class` are set. |
| `not_started` | The execution ended without completing before this side's read started. |
| `interrupted` | The execution ended without completing while this side was being read. |

The Sync API stores only `waiting`, `reading`, `succeeded` and `failed`. It derives the
returned state from the stored state, the execution's `terminal_state`, and the flow run
state it last observed in Prefect:

- When `terminal_state` is set to anything other than `completed`, a side stored as `waiting`
  is returned as `not_started`, and a side stored as `reading` is returned as `interrupted`.
  `ended_at` is `null` for both.
- When `terminal_state` is not set yet, but Prefect reports the flow run as `failed`,
  `crashed` or `cancelled`, the Sync API returns the sides the same way. This covers a worker
  that stopped before the service recorded its execution's verdict.
- When `terminal_state` is `completed`, a side still stored as `waiting` or `reading` is
  returned as `null`, because the end of its read was not recorded. The Sync API logs a
  warning.
- A stored state that does not parse, or that holds a state or read mode the Sync API does
  not store, is returned as `null`, and the Sync API logs a warning.

`state` and `read_mode` are strings in the client model, so a client from this release
reads a run response that holds a state or a read mode added by a later release.

`read_mode` is `full` when the worker extracted every top-level kind of the side in full,
and `incremental` otherwise, including for a side that mixes kinds extracted in full and
kinds read incrementally. `nodes_by_kind` counts the nodes read for each
top-level kind of the side and each other kind the side holds, sorted by kind name; a
top-level kind with no node counts `0`. It is `{}` for every state other than `succeeded`,
and for a succeeded read whose nodes could not be counted, in which case the worker logs a
warning. `error_class` is the class name of the error that
ended the read, such as `ConnectionError`, and is `null` for every state other than `failed`.
No field holds an exception message, an address, a secret or configuration content.

A run can hold `plan`, `verify` and `apply` entries in order. To show one read state for a
run, use the latest entry whose `purpose` is `plan` or `sync`. The change is additive:
existing fields keep their meaning and order.

## Routes

Every route below requires `Authorization: Bearer <token>`. Every `POST` route that writes or
requests a change also requires a non-empty `Idempotency-Key` header and a JSON body;
`POST /configs/{config_id}/versions/{registry_version}/validate` is the one exception, since it
only re-checks an already-registered version and takes no body. The body's `reason` is
optional. When present, it must be non-empty, and the service records it in the audit history.
When it is absent or `null`, the service records the request without a reason. For idempotency,
an absent reason and a `null` reason are the same value, and both differ from any text.

| Route | Behavior |
| --- | --- |
| `POST /configs` | Register a new configuration package as version 1. Administrator only. |
| `POST /configs/{config_id}/versions` | Register a new version of an existing configuration. Administrator only. |
| `GET /me` | Return the actor that the bearer token authenticates as and its administrator flag. |
| `GET /configs` | List registered configurations, newest first, one page at a time. Filter by exact `name`. |
| `GET /configs/{config_id}` | Return one registered configuration's summary, with its `name` and `latest_version`. |
| `GET /configs/{config_id}/versions` | List a configuration's version summaries, newest first, one page at a time. |
| `GET /configs/{config_id}/versions/{registry_version}` | Return one registered version, with its package content. |
| `POST /configs/{config_id}/versions/{registry_version}/validate` | Re-check a registered version against the adapter declarations installed now. |
| `GET /runs` | List runs, newest first, one page at a time. Filter by `config_id` and `registry_version`. |
| `POST /runs` | Create one Sync run and accept `plan` or confirmed composed `sync`. |
| `GET /runs/{run_id}` | Return the durable product record, with current linked Prefect detail for non-terminal executions. |
| `GET /runs/{run_id}/plan` | Return retained saved-plan review data. |
| `GET /runs/{run_id}/results` | Return retained results independently of Prefect result retention. |
| `GET /runs/{run_id}/artifacts` | List immutable run-owned artifact references. |
| `GET /runs/{run_id}/artifacts/{artifact_id}` | Return verified artifact bytes with their media type and `Digest` header. |
| `GET /runs/{run_id}/logs` | Return the log lines that Sync wrote during the run's stages, oldest first, one page at a time. |
| `GET /events` | List typed events about runs and configurations, oldest first, one page at a time. |
| `POST /runs/{run_id}/verify` | Accept read-only saved-plan verification without changing product lifecycle state. |
| `POST /runs/{run_id}/apply` | Accept a confirmed apply for the exact retained reviewed checksum. |
| `POST /runs/{run_id}/cancel` | Ask Prefect to cancel only the latest active linked execution. |

### CLI commands and the API actions they call

A configuration value in the CLI can be a `config_id` or a configuration name. The CLI reads
`GET /configs/{config_id}` first and, when no configuration has that identifier, looks the
value up as a name. When several configurations share the name, the CLI exits with status 2 and
lists their identifiers.

| CLI command | API action |
| --- | --- |
| `infrahub-sync configs register PACKAGE` | `POST /configs` |
| `infrahub-sync configs version CONFIG PACKAGE` | `POST /configs/{config_id}/versions` |
| `infrahub-sync configs list` | `GET /configs` |
| `infrahub-sync configs show CONFIG` | `GET /configs/{config_id}` |
| `infrahub-sync configs show CONFIG --version VERSION` | `GET /configs/{config_id}/versions/{registry_version}` |
| `infrahub-sync configs versions CONFIG` | `GET /configs/{config_id}/versions` |
| `infrahub-sync configs validate CONFIG VERSION` | `POST /configs/{config_id}/versions/{registry_version}/validate` |
| `infrahub-sync plan` | `POST /runs` with `operation: plan` |
| `infrahub-sync sync` | `POST /runs` with `operation: sync` |
| `infrahub-sync verify RUN_ID` | `POST /runs/{run_id}/verify` |
| `infrahub-sync apply RUN_ID` | `POST /runs/{run_id}/apply` |
| `infrahub-sync runs list` | `GET /runs` |
| `infrahub-sync runs show RUN_ID` | `GET /runs/{run_id}` |
| `infrahub-sync runs plan RUN_ID` | `GET /runs/{run_id}/plan` |
| `infrahub-sync runs results RUN_ID` | `GET /runs/{run_id}/results` |
| `infrahub-sync runs artifacts RUN_ID` | `GET /runs/{run_id}/artifacts` |
| `infrahub-sync runs logs RUN_ID` | `GET /runs/{run_id}/logs` |
| `infrahub-sync events` | `GET /events` |
| `infrahub-sync runs cancel RUN_ID` | `POST /runs/{run_id}/cancel` |
| `infrahub-sync whoami` | `GET /me` |

The `diff` command is a hidden, deprecated alias of `plan`. It calls the same action and
prints a deprecation warning to standard error.

### List runs and configurations

`GET /runs`, `GET /configs` and `GET /configs/{config_id}/versions` return one page at a time
in the same envelope:

```json
{"items": [], "next_cursor": null}
```

| Query parameter | Applies to | Rule |
| --- | --- | --- |
| `limit` | all three lists | Items per page, from 1 to 200. Defaults to 50. A value outside that range returns `422 request-invalid`. |
| `cursor` | all three lists | The `next_cursor` of the previous page, sent with the same filters. A cursor that does not decode, or that was issued for another list or for other filters, returns `422 invalid-cursor`. |
| `config_id` | `GET /runs` | Only runs of this configuration. A malformed configuration ID returns `422 request-invalid`; an unknown configuration returns `404 configuration-not-found`. |
| `registry_version` | `GET /runs` | Only runs of this configuration version. Requires `config_id`, otherwise `422 request-invalid`. An unknown version returns `404 configuration-version-not-found`. |
| `name` | `GET /configs` | Only configurations with exactly this name. |

`next_cursor` is `null` on the last page. The lists return no total count.

- `GET /runs` orders runs by `started_at`, newest first. A list item has the same fields as the
  `run` object that `GET /runs/{run_id}` returns, except that `artifact_refs` and
  `prefect_executions` are always empty. The list has no `orchestration` field. Read the run
  itself for those values. `destination_branch` is the branch the run writes to. It is
  `null` for runs created before the field existed. Without filters, the list also includes
  legacy runs that have no `config_id`.
- `GET /configs` orders configurations by `created_at`, newest first. Each item carries
  `config_id`, `name`, `latest_version` and `created_at`.
- `GET /configs/{config_id}/versions` orders versions by `registry_version`, newest first. Each
  item carries `config_id`, `registry_version`, `package_checksum`, `created_at`,
  `registered_by`, `registration_reason`, `latest_run` and `latest_applied_run`, and no
  package content. `latest_run` is the version's newest run by `started_at`.
  `latest_applied_run` is the most recently applied run, ordered by the time its apply
  finished. An apply updates the plan run, so its `started_at` is the time the plan was
  created and its `finished_at` is the time the apply finished. Each run reference carries
  `run_id`, `phase`, `outcome`, `started_at` and `finished_at`; `finished_at` is `null` for a
  run that has not finished. `registered_by` and `registration_reason` are `null` for versions
  registered before they were recorded. Read
  `GET /configs/{config_id}/versions/{registry_version}` for the package content.

Both configuration lists previously returned a bare array and accepted `offset`. They now
return the envelope above. `offset` is removed: the service ignores it, so a client that
pages with `offset` reads the first page again.

`GET /me` returns the actor that the token authenticates as:

```json
{"actor": "automation@example.com", "administrator": false}
```

It performs no other action. Use it to check a token before you submit a run.

### Find a run's flow runs in Prefect

Each flow run that Sync submits to Prefect carries tags that identify its run, its stage and,
for a registered run, its configuration version. Sync creates the flow run with these tags,
and Prefect adds the deployment's tags, including any tag you added to the deployment:

| Tag | Example |
| --- | --- |
| `run:<run_id>` | `run:20260810T1500-0123abcd` |
| `stage:<stage>` | `stage:apply` |
| `config:<config_id>` | `config:cfg-netbox` |
| `config-version:<config_id>@<registry_version>` | `config-version:cfg-netbox@2` |

Filter flow runs by one of these tags in the Prefect UI or API to list every stage of one run,
or every run of one configuration version.

### Read a run's log

`GET /runs/{run_id}/logs` returns the lines that Sync wrote while it ran the run's stages. The
Sync API reads them from every flow run that the run record names, one or more per stage. It
returns only the lines that Sync's own code wrote, and leaves out the lines that the engine
and the worker of the orchestrator wrote, such as the flow run's final state.

| Query parameter | Rule |
| --- | --- |
| `stage` | Only the lines of this stage: `plan`, `verify`, `apply` or `sync`. |
| `limit` | Lines per page, from 1 to 1000. Defaults to 200. |
| `offset` | The number of lines to skip. Defaults to 0. |

A value outside these rules returns `422 request-invalid`.

```json
{
  "run_id": "20261106T1015-0123abcd",
  "items": [
    {
      "stage": "plan",
      "attempt": 1,
      "timestamp": "2026-11-06T10:15:01Z",
      "level": "ERROR",
      "source": "infrahub_sync.service.flow",
      "message": "Branch `demo-test` does not exist in Infrahub. Next step: Create it, or start the run with `--branch <existing branch>`."
    }
  ],
  "limit": 200,
  "offset": 0,
  "has_more": false,
  "run_phase": "plan-failed"
}
```

- `stage` and `attempt` name the flow run that wrote the line. `source` is the name of the
  Sync logger that wrote it.
- `level` is `DEBUG`, `INFO`, `WARNING`, `ERROR` or `CRITICAL`.
- Lines are ordered by flow run, in the order the run record lists them, then by time.
- Control characters other than line breaks and tabs are removed from `message`, and a message
  is cut at 4,096 characters.
- `run_phase` is the run's phase when the page was read.
- A run that has no flow run yet returns an empty `items` list.

To read new lines while a run is in progress, send `offset` equal to the number of lines
already read: the response holds only the newer lines. `run_phase` alone does not show that
a stage ended: a verify or an apply of a planned run keeps the phase `planned` while it runs,
and a verify does not change the phase when it ends. Read `GET /runs/{run_id}` and check the
`terminal_state` of the latest `orchestration` entry instead. The orchestrator stores the
last lines of a flow run a moment after it ends, so read again for a few seconds after that
before you stop. `infrahub-sync runs logs RUN_ID --follow` reads every 2 seconds this way and
exits after three reads in a row return no new line once the run has ended.

The orchestrator keeps the log of a flow run for as long as it keeps the flow run. When it no
longer holds a flow run that the run record names, the route returns `410 log-expired`. When
it cannot be reached, the route returns `503 log-unavailable`; `GET /runs/{run_id}`,
`GET /runs/{run_id}/results` and `GET /events` keep answering. The deployment page explains
[how long Prefect keeps flow runs](../compose-deployment.mdx#how-long-run-logs-are-kept).

### List events

`GET /events` lists what happened to runs and configurations: each decision the Sync API made
on a request, and each stage result the worker recorded. An event is saved in the same
database transaction as the decision or result it records, so neither is saved without the
other. An event that records a refusal is saved on its own.

| Query parameter | Rule |
| --- | --- |
| `run_id` | Only events about this run. |
| `config_id` | Only events about this configuration, or that name it as a related resource. |
| `event_type` | Only events of this type. Repeat it for several types. |
| `related` | Only events with this related resource, written `<kind>:<id>`, for example `account:alice` or `branch:main`. Repeat it for several. |
| `since` | Only events at or after this time. A date and time with a time zone. |
| `until` | Only events before this time. A date and time with a time zone. |
| `limit` | Events per page, from 1 to 200. Defaults to 50. |
| `offset` | The number of matching events to skip. Defaults to 0. |

A value outside these rules returns `422 request-invalid`. Events are ordered by
`occurred_at`, then `event_id`, oldest first. To read new events, send `offset` equal to the
number of events already read; `infrahub-sync events --follow` reads every 2 seconds this way
until you stop it. An event saved late with an earlier `occurred_at` than events already read
takes a position among them and moves the later events down by one, so a reader that pages
this way can skip one event or read one event twice.

```json
{
  "items": [
    {
      "event_id": "a-3f0c9d2e5b7a4c1e8f6d0b2a4c6e8f01",
      "event_type": "infrahub_sync.run.planned",
      "occurred_at": "2026-11-06T10:15:02Z",
      "actor": "alice",
      "operation": "plan",
      "outcome": "succeeded",
      "reason": null,
      "primary_resource": {"kind": "run", "id": "20261106T1015-0123abcd"},
      "related": [
        {"kind": "account", "id": "alice"},
        {"kind": "config", "id": "cfg-netbox"},
        {"kind": "config_version", "id": "cfg-netbox@3"},
        {"kind": "branch", "id": "main"}
      ]
    }
  ],
  "limit": 50,
  "offset": 0,
  "has_more": false
}
```

`primary_resource` is the run or the configuration that the event is about. It is `null`
when the event names neither a run nor a configuration. `related` holds
the actor's account and, when they are known, the configuration, its version and the
destination branch. The event types are:

| Event type | Recorded when |
| --- | --- |
| `infrahub_sync.run.accepted` | The Sync API accepted a plan, sync, verify or apply request, or a cancel request. For a cancel request, `operation` is `cancel`. |
| `infrahub_sync.run.replayed` | A retry with the same idempotency key received the stored answer. |
| `infrahub_sync.run.refused` | The Sync API refused a run request. `outcome` names the reason, for example `refused-checksum`. |
| `infrahub_sync.run.unavailable` | The orchestrator could not confirm a submission or a cancellation request. |
| `infrahub_sync.run.planned` | A plan stage succeeded. |
| `infrahub_sync.run.verified` | A verify stage succeeded. |
| `infrahub_sync.run.applied` | An apply stage succeeded. |
| `infrahub_sync.run.synced` | A sync stage succeeded. |
| `infrahub_sync.run.failed` | A stage failed, or was interrupted. `outcome` is `failed`, or `ambiguous` when the stage may have written to the destination. The Sync API records this event, with `outcome` `ambiguous`, when it ends an execution whose worker stopped without recording a result. |
| `infrahub_sync.run.cancelled` | An execution that a cancel request stopped ended cancelled. `actor` and `reason` come from the cancel request. |
| `infrahub_sync.config.registered` | A configuration was registered as version 1. |
| `infrahub_sync.config.version_registered` | A new version of a configuration was registered. |
| `infrahub_sync.config.refused`, `.replayed`, `.unavailable` | The same decisions as for a run, on a configuration request. |

A request refused for a missing or invalid token is not an event, and `GET /events` never
returns it. Events recorded before this release get a type when the Sync API first starts on
this release, from their operation and outcome. They name the account of their actor, but no
configuration, version or branch, because the earlier record did not hold them. A request
refused for a missing or invalid token that an earlier release recorded gets no type and is
not listed.

### Read why a stage failed

When a stage fails with an error that Sync knows, the run records a `cause` and a
`next_action` under `plan_failure`, `verify_failure`, `apply_failure` or `sync_failure` in
`GET /runs/{run_id}/results`. The worker writes one `ERROR` line to the run's log,
`<cause> Next step: <next_action>`, without a Python traceback, and the stage ends failed. For
example, when the destination branch does not exist:

```text
Branch `demo-test` does not exist in Infrahub. Next step: Create it, or start the run with `--branch <existing branch>`.
```

A failure to read the destination schema also records a cause and a next action, for example a
refused token or a missing permission. An error that Sync does not know records its class name
only.

### Create a plan

Address the exact registered configuration revision by its `config_id` and
`registry_version`:

```bash
curl --request POST http://127.0.0.1:8000/runs \
  --header "Authorization: Bearer $SYNC_API_TOKEN" \
  --header "Idempotency-Key: plan-inventory-2026-08-10" \
  --header "Content-Type: application/json" \
  --data '{
    "operation": "plan",
    "config_id": "<config_id>",
    "registry_version": 1,
    "reason": "review inventory changes"
  }'
```

`branch` and `confirm_writes` are also accepted. `POST /runs` accepts only this registered
form — `config_id`, `registry_version`, `branch`, `confirm_writes`, and `reason` — and
forbids extra fields; it does not accept a `sync_name` or `configuration_reference` form.
A legacy, directory-resolved configuration runs through the
[direct Prefect deployment](./prefect-remote-run.mdx) instead.

Acceptance returns `202` with the durable `ProductRun` and its first orchestration link.
The `run_id` in that response is the identity for every later stage, result, artifact, and
Prefect execution link.

Read the plan after the worker publishes it:

```bash
curl --header "Authorization: Bearer $SYNC_API_TOKEN" \
  http://127.0.0.1:8000/runs/20260810T1500-0123abcd/plan
```

The plan response includes its checksum, checksum verification state, summary, verification
notes, per-object operations, and `schema_fingerprint`. For a registered plan,
`schema_fingerprint` is the 64-character SHA-256 digest of the destination-schema
semantics consumed by that configuration. It is `null` only for a legacy unregistered
plan.

### Verify and apply the reviewed plan

Verification is read-only and retains verification evidence without finishing or otherwise
advancing the product run:

```bash
curl --request POST \
  http://127.0.0.1:8000/runs/20260810T1500-0123abcd/verify \
  --header "Authorization: Bearer $SYNC_API_TOKEN" \
  --header "Idempotency-Key: verify-20260810T1500-0123abcd" \
  --header "Content-Type: application/json" \
  --data '{"reason":"verify the reviewed plan"}'
```

Apply requires the exact retained checksum and explicit write confirmation:

```bash
curl --request POST \
  http://127.0.0.1:8000/runs/20260810T1500-0123abcd/apply \
  --header "Authorization: Bearer $SYNC_API_TOKEN" \
  --header "Idempotency-Key: apply-20260810T1500-0123abcd" \
  --header "Content-Type: application/json" \
  --data '{
    "expected_checksum": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
    "confirm_writes": true,
    "reason": "change approved"
  }'
```

The worker verifies the saved plan again before its first destination write. Destination
deletes remain disabled.

`PlanSchemaChangedError` means the live destination-schema semantics no longer match the
reviewed plan's `schema_fingerprint`. The worker refuses the retained plan before any
destination write. Create a new plan against the current schema, review its
`schema_fingerprint`, operations, and checksum, then apply that new plan. There is no
schema-drift override.

## Idempotency and retries

An exact retry by the same actor with the same `Idempotency-Key`, target, and JSON body
returns the stored status and body. A different request using that actor and key returns
`409 idempotency-conflict`.

Sync stores a SHA-256 digest of the client key, never the raw key. Before dispatch, it
atomically reserves a durable mutation receipt; run creation reserves the receipt and
product run in one transaction. The receipt owns a separate opaque key passed to Prefect's
native idempotency field. If an HTTP or Prefect response is lost after submission, retry the
exact request. The retry reuses the receipt, opaque Prefect key, Sync run ID, and Prefect
flow-run ID.

Do not change the request body, including `reason`, while retrying. Use a new idempotency key
for a new intent.

The first confirmed composed `sync` or reviewed `apply` permanently consumes that run's
single write admission, including when the execution later fails, crashes, or is cancelled.
Retry an uncertain request with its original idempotency key. To make another write attempt
after a terminal failure or cancellation, create and review a new plan run.

A run admits its one write only while nothing else is in flight on it: no other write
admission, no other unresolved plan, verify, apply, or sync submission, and no unfinished
execution. Whichever request wins is decided before either competitor is submitted to
Prefect, so the loser never starts work. It is answered with `409 run-execution-conflict`
stored on its own receipt, and replaying that idempotency key replays the refusal. Once a
run has admitted its write, every later plan, verify, apply, and sync submission on that run
gets the same refusal — including after the write becomes terminal, because terminal write
evidence is not reopened.

A submission stays unresolved until it has a stored response, a stored refusal included. If
a client abandons one — the process dies before it reads the reply, and the key is never
replayed — that run cannot admit another stage. There is no receipt-expiry mechanism; create
a new plan or sync run instead.

## Write safety and reconciliation

A managed apply or sync holds one PostgreSQL advisory guard for the registered configuration
it writes, so two workers cannot write the same configuration at once. The guard is held
across the destination-sensitive checks and the whole write loop, and its release is
confirmed before any success is published.

Public run resources carry `reconciliation_required`. It is `false` on every new run and
becomes `true` only when a write execution ends without proving what reached the
destination. Nothing sets it back to `false`.

| What happened | Durable outcome | Your next step |
| --- | --- | --- |
| Another writer held the guard for the whole deadline | `failed`; no destination was contacted and nothing was written | Create a new plan: the other writer may have changed the destination |
| A destination-sensitive check failed under the guard | The existing specific refusal; nothing was written | Fix the cause and create a new plan |
| The adapter failed after the first operation was dispatched | `interrupted` / `ambiguous`, `reconciliation_required: true`, with the partial `ApplyRecord` in the retained results | Inspect the destination, then create a new plan |
| You cancelled a run whose worker already held the write | `interrupted` / `ambiguous`, `reconciliation_required: true`; the cancel request answers `409 cancellation-ambiguous` | Inspect the destination, then create a new plan |
| The worker or its guard session was lost | `interrupted` / `ambiguous`, `reconciliation_required: true` | Inspect the destination, then create a new plan |
| The run completed normally | The existing succeeded result | Nothing; this run accepts no further write |

Cancellation is not a clean-stop guarantee for a write. A worker that has already begun
dispatching may have changed the destination before the cancellation reached it, so Sync
records the conservative answer rather than a cancelled one — unless the normal completion
path won first.

### Reconcile an uncertain write

Sync never calls an adapter or infers success after an uncertain result, and there is no
endpoint that clears `reconciliation_required`. Reconcile by planning again:

1. create a new plan run on the same registered configuration;
2. read its summary. A plan with no operations means the destination currently matches the desired
   state; it does not prove which run made the changes; and
3. otherwise review the remaining operations and apply that new plan.

## Errors and retained state

Every error uses the same envelope:

```json
{
  "error": {
    "code": "checksum-conflict",
    "message": "expected_checksum does not match the retained reviewed plan",
    "status": 409,
    "run_id": "20260810T1500-0123abcd",
    "mutation_id": null
  }
}
```

| Status | Meaning |
| --- | --- |
| `401` | Missing or invalid authentication. |
| `403` | The actor does not own the mutation and is not an administrator. |
| `404` | The Sync run or run-owned artifact does not exist, or a list filter names an unknown configuration (`configuration-not-found`) or configuration version (`configuration-version-not-found`). |
| `409` | Idempotency conflict, missing confirmation, stale checksum, non-cancellable execution, a run that cannot admit another stage (`run-execution-conflict`), or a cancelled write whose outcome is uncertain (`cancellation-ambiguous`). |
| `410` | The retained plan or artifact has expired, or the orchestrator no longer holds a flow run whose log `GET /runs/{run_id}/logs` reads (`log-expired`). |
| `422` | Invalid request schema or query parameter (`request-invalid`), a list cursor that does not decode or was issued for another list or other filters (`invalid-cursor`), missing idempotency key, or a secret-bearing flow parameter. |
| `503` | Submission, live orchestration detail, or retained data cannot be confirmed or retrieved, or the orchestrator cannot be reached to read a run's log (`log-unavailable`). |

Error messages name "the orchestrator", not Prefect, and never hold its address.

Prefect detail can expire or become unavailable while the durable Sync record, results,
and published artifacts remain readable. Cancellation never deletes the product record or
its execution history. The API does not add a Sync-owned queue, retry policy, scheduler,
recovery state machine, or overlap policy.
