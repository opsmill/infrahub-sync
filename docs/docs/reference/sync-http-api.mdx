The Sync HTTP API accepts authenticated run requests, records a stable Sync run
identity, and delegates execution to a separate Prefect deployment. Sync owns the HTTP,
authorization, plan, result, artifact, audit, and idempotency contracts. Prefect owns live
execution state, workers, retries, logs, and cancellation.

The [direct Prefect remote run](./prefect-remote-run.mdx) remains a
separate four-parameter deployment. Use the Sync API when a trusted automation client
needs reviewed-plan apply, durable results, artifact retrieval, or actor-scoped mutation
control.

Every route in this document is relative to `/api` on the address of the Sync service. For
example, `GET /runs` is `http://127.0.0.1:8000/api/runs`, the interactive documentation is at
`/api/docs` and the OpenAPI document is at `/api/openapi.json`. The root of the address serves the
web interface. A script that calls the Sync API directly adds `/api` to the address of the Sync
service. The `infrahub-sync` CLI adds it itself, so `INFRAHUB_SYNC_API_URL` holds the address
without `/api`.

## Terms

- **Configuration**: a registered sync definition, identified by `config_id`. Its `name` is the
  name in its newest version, and no other configuration has it. A configuration without a name
  has `name: null`.
- **Configuration version**: one immutable registered revision of a configuration,
  identified by `config_id` and `registry_version`.
- **Run**: one attempt to synchronize one configuration version to one branch, identified by
  `run_id`. A run creates exactly one plan and applies that plan at most once. A resume does not
  apply the plan again: it continues the interrupted apply from the operation after its last saved
  position.
- **Plan**: the creates, updates and recorded deletes that a run computes before it writes,
  with their checksum. Verify and apply act on the plan of the run they name: they do not
  compute a new plan.
- **Stage**: one execution step of a run: `plan`, `verify`, `apply` or `sync`. Each stage runs
  as one Prefect flow run.

## Install the service profile

The service profile requires Python 3.11 or later. Install it from a repository checkout on
the API host and on every worker that can run its deployment:

```bash
uv sync --extra dev --extra prefect --extra service
```

The profile directly installs FastAPI, HTTPX, Uvicorn, Prefect 3.8.6, Psycopg, and Boto3. It also installs
the client libraries of the bundled NetBox and Nautobot adapters, `prometheus-client`, and `infrahubctl`. The OpsMill
Prefect Extras integration ships with the package itself as a vendored copy of upstream
commit `97465e75137f6121d0377cd637383cfb3530d734`. The base installation does not import
any of these modules. Ordinary CLI and Python API imports remain Prefect-free.

You also need:

- a Prefect API and an existing process work pool;
- a Sync worker that takes runs from that work pool;
- PostgreSQL for product records; and
- an S3-compatible bucket for immutable artifacts.

The API and worker each create a process-local client from the same PostgreSQL/S3 settings.
They share durable records and artifacts through those services, not through a product filesystem.
S3 credentials use Boto3's standard credential-provider chain.

## Accounts and API tokens

Every caller of the Sync API acts as an account stored in the product database. A request
presents an API token or a session token in `Authorization: Bearer <token>`, except to
`POST /auth/sign-in`, `GET /health` and `GET /version`, which take no token. A person gets a
session token by signing in with the account name and password. A script uses an API token
that an account created.

The `admin` account always exists and is an administrator. Three variables of the API process
define it and the sessions:

| Variable | Required | Rule |
| --- | --- | --- |
| `INFRAHUB_SYNC_ADMIN_ACCOUNT_PASSWORD` | yes | The password of `admin`. 12 to 1,024 characters of valid UTF-8 text. No default value. |
| `INFRAHUB_SYNC_ADMIN_ACCOUNT_TOKEN` | no | One API token of `admin`. At least 16 printable ASCII characters with no space at either end, and it must not start with `ifs_pat_` or `ifs_ses_`. Empty or unset: `admin` has no API token. |
| `INFRAHUB_SYNC_SESSION_IDLE_SECONDS` | no | The number of seconds without a request after which a session ends. Default `28800` (8 hours). A whole number from 60 to 999999999999. Empty means the default. |

The API applies the first two at each start, then removes the password from its own process
environment. A value that breaks a rule stops the start with a message that names the variable
and never shows the value. The API and the CLI refuse every change to the password, the tokens,
the level or the state of `admin`, and its deletion: its password and its token change only
through these variables and a restart of the API. An administrator can end a refusal after
repeated failed sign-ins for any account, `admin` included, with `POST /accounts/{name}/unlock`;
a restart of the API also ends it for `admin`.

`INFRAHUB_SYNC_SERVICE_BEARER_TOKENS`, which defined the callers in earlier releases, is no
longer read. A process that still has it starts and ignores it.

Inject these values through your deployment's secret mechanism. Do not put a real password or
token in a shell history, Sync configuration, idempotency key, or Prefect parameter, or in a
request body other than the password fields of the sign-in and password routes below. The API returns a token value only once, in the answer that creates it.

Any account can create and inspect a run. Only the account that created a run, or an
administrator, can verify, approve, apply, or cancel it. Every accepted mutation and
authorization refusal records secret-safe actor, reason, and outcome evidence. The `actor` of a
run is the name of the account.

### Sign-in, sign-out and account routes

These routes take no `Idempotency-Key`. Each mutation except sign-in and sign-out accepts an
optional `reason` of at most 512 characters. A mutation that changes something records it in
the audit history; a `PATCH` that changes nothing records nothing. The `DELETE` routes take it as a query
parameter; the other routes take it in the JSON body.

| Route | Who | Behavior |
| --- | --- | --- |
| `POST /auth/sign-in` | anyone, without a token | Takes `{"name", "password"}` and returns a session token. |
| `POST /auth/sign-out` | a session | Ends the session. With an API token, it answers `422`, code `not-a-session`. |
| `PUT /me/password` | any account | Takes `{"current_password", "new_password"}`. The other sessions of the account end. Its API tokens keep working. |
| `GET /me/tokens` | any account | Lists the API tokens of the account, without their values. |
| `POST /me/tokens` | any account | Takes `{"name", "expires_at"?}` and returns the new token value once. |
| `DELETE /me/tokens/{token_id}` | any account | Deletes one API token of the account. |
| `GET /accounts` | administrator | Lists accounts. Query `state=active`, `disabled` or `all` (the default). |
| `POST /accounts` | administrator | Takes `{"name", "password", "administrator"?}` and creates an account. |
| `GET /accounts/{name}` | administrator | Returns one account. |
| `PATCH /accounts/{name}` | administrator | Takes `{"disabled"?, "administrator"?}`, at least one of the two. `disabled`: `true` disables the account, `false` enables it; disabling deletes the API tokens of the account and ends its sessions. `administrator` sets the level, which applies from the next request of the account. A value the account already has changes nothing and writes no audit event. |
| `PUT /accounts/{name}/password` | administrator | Takes `{"new_password"}`. Every session of the account ends. |
| `POST /accounts/{name}/unlock` | administrator | Ends a refusal after repeated failed sign-ins. Accepted for `admin` too. |
| `DELETE /accounts/{name}` | administrator | Deletes the account and returns `{"placeholder": "Deleted account <short identifier>"}`. Cannot be reversed. See [Deleting an account](#deleting-an-account). |
| `GET /accounts/{name}/tokens` | administrator | Lists the API tokens of the account, without their values. |
| `DELETE /accounts/{name}/tokens/{token_id}` | administrator | Deletes one API token of the account. |

The refusals of these routes:

- A wrong name, a wrong password, a disabled account and a name refused after repeated failures
  all answer `401`, code `sign-in-refused`, with one message that does not say whether the
  account exists. Each writes an authentication refusal record without the name, except a
  sign-in whose name or password no account can have (empty, a name longer than 64 characters,
  a password longer than 1,024 characters, or a character that UTF-8 cannot encode): it is
  refused before any password check and writes no record.
- After 5 failed sign-ins for one name in 15 minutes, the API refuses that name for 15 minutes.
  An attempt during the refusal does not extend it. API tokens of the account keep working.
- A wrong `current_password` answers `403`, code `current-password-refused`, and counts as a
  failed sign-in. While the name is refused, the route answers the same code without checking
  the password.
- A request answers `503`, code `sign-in-busy`, and is not counted, when it waits more than
  5 seconds:
    - for one of the two places of the API process that check or hash a password, which a
      sign-in, `PUT /me/password`, `POST /accounts` and `PUT /accounts/{name}/password` take;
    - or, for a sign-in or `PUT /me/password`, for the end of another password check of the
      same account name in the API process.
- A new password shorter than 12 characters answers `422`, code `password-too-short`. One
  longer than 1,024 characters answers `422`, code `password-too-long`. One that holds a
  character that UTF-8 cannot encode, such as a lone surrogate, answers `422`, code
  `password-invalid`.
- An account name outside the rule of names, a reserved name (`admin`, `unknown`,
  `unauthenticated`, in any letter case), a name that starts with `acct_` in any letter case, or
  a name that holds `ifs_pat_` or `ifs_ses_` answers `422`, code `account-name-invalid`. A name that an account already has, in any letter case, answers `409`,
  code `account-name-taken`.
- A token name that the account already uses answers `409`, code `token-name-taken`. An
  `expires_at` that is not in the future answers `422`, code `expiry-in-the-past`.
- A caller that is not an administrator receives `403`, code `forbidden`, on the `/accounts`
  routes. So an account cannot raise its own level. A body that is not valid JSON is read before
  the token and the level are checked: it answers `422`, code `request-invalid`, whatever the
  caller.
- An unknown or deleted account name answers `404`, code `account-not-found`.
- A `PATCH /accounts/{name}` body with neither `disabled` nor `administrator` answers `422`,
  code `request-invalid`.
- A token ID that the account does not have answers `404`, code `token-not-found`.
- A change to `admin` answers `409`, code `environment-managed-account`, except
  `POST /accounts/admin/unlock`, which is accepted:
    - a change of its password, with `PUT /accounts/admin/password` or `PUT /me/password`: the
      message names `INFRAHUB_SYNC_ADMIN_ACCOUNT_PASSWORD`;
    - the deletion of its token, or a `/me/tokens` mutation called by `admin`: the message names
      `INFRAHUB_SYNC_ADMIN_ACCOUNT_TOKEN`;
    - a change of its state or its level, or its deletion: the message says that `admin` is
      always an active administrator that the environment defines.
- A `reason`, or a token name, that contains a secret value of the process or the prefix
  `ifs_pat_` or `ifs_ses_` answers `422`, code `secret-parameter-refused`.

A request with no token, an unknown or deleted token, or a token of a disabled account answers
`401`, code `unauthenticated`, unless its body is not valid JSON: that answer is `422`, code
`request-invalid`. An API token used after its expiry date answers `401`, code
`token-expired`. A session idle for longer than `INFRAHUB_SYNC_SESSION_IDLE_SECONDS` answers
`401`, code `unauthenticated`.

### Deleting an account

`DELETE /accounts/{name}` empties the name, the password and the lower-case name of the account
row, deletes its API tokens, its sessions and its record of failed sign-ins, and writes the
audit event `infrahub_sync.account.deleted`, in one database transaction. The row keeps the
account identifier and an 8-character short identifier. No run, approval, mutation receipt,
audit event or configuration version changes:

- Every answer shows `Deleted account <short identifier>` in the `actor`, `approved_by` and
  `registered_by` fields, and in each related resource of kind `account`, that refer to the
  deleted account. Answers replayed from a mutation receipt show it too.
- An approval of the deleted account stays valid. A run of the account that is in progress
  continues. An administrator can act on both.
- A `reason` that a person typed keeps the name if it holds it. Log lines are not rewritten.
- The name is free again. A new account with that name has a new identifier and no right over
  the runs of the deleted account.

An administrator can delete their own account; the next request of that account is refused.
Deleting an account that is already deleted answers `404`, code `account-not-found`.

For the CLI commands that call these routes, see [Manage accounts](../guides/accounts.mdx).

## Deploy the service flow

Set the work pool name, then apply the service deployment:

```bash
export PREFECT_API_URL="http://127.0.0.1:4200/api"
export INFRAHUB_SYNC_SERVICE_WORK_POOL="sync-process-pool"
python -m infrahub_sync.service.deploy
```

The command validates and applies `infrahub-sync-service/run` through OpsMill Prefect
Extras, then drives the deployment's pull steps to empty. It does not create a work pool
or start a worker.

Apply the deployment again each time you install a new release, before you start that
release's Sync API. The deployment records the parameters the service flow accepts, and a
newer Sync API can send a parameter that is missing from an older deployment's list, such as
`confirm_left_out`.

The Sync API and the worker also read a bootstrap record when they start, and refuse to start
until it names their Sync version and work pool. `python -m infrahub_sync.service.deploy` does
not write that record. To write it, run `python -m infrahub_sync.service.bootstrap` with the
same database, object store and Prefect settings as the Sync API. It creates the bucket and the
work pool when they are missing, applies this deployment, initializes the product schema, and
writes the record as its last step. Run it again each time you install a new release or change
the work pool.

The deployment's entrypoint is the installed module path
`infrahub_sync.service.flow.service_sync_run`. A worker resolves it by importing the
installed `infrahub-sync` distribution, so it needs no repository checkout, no declared
working directory, and no source-pull step. Applying the deployment removes any pull step
an earlier release installed; without that, workers would keep entering a source tree
that need not exist on their host. Install the same `infrahub-sync` version on every
worker.

## Start service workers

Start each worker through the service entry point. The work pool must already exist, and the
bootstrap of this release must have written its record for this work pool:

```bash
python -m infrahub_sync.service.worker \
  --pool "$INFRAHUB_SYNC_SERVICE_WORK_POOL"
```

Each invocation generates a new UUID-suffixed worker name. After its Prefect heartbeat,
the worker reads the exact Worker record for that name and work pool and records the
server-issued UUID as its Prefect backend identity. Prefect 3.8.6 passes that identity
to each `ProcessJobConfiguration` and injects `PREFECT__WORKER_ID` into that worker's
flow-run child. The deployment stores no worker identity.

A restarted process generates a new name and resolves its current server Worker UUID.
It does not reuse an identity from the previous process.

Plan, verify, apply, and sync share no Sync filesystem. Each stage creates its own
private scratch directory, hands the next stage what it needs through internal artifacts
in the product store, and releases the directory when it ends. An apply therefore runs on
any worker, including one that never saw the plan: it resolves the plan from the run's
internal checkpoint and refuses if that checkpoint is missing, oversized, corrupt,
digest-mismatched, or another run's.

Use this entry point for every worker eligible to run the service deployment; manually
named or standard Prefect process workers are outside the supported topology.

The worker does not poll for runs until its heartbeat is complete and the pool returns
exactly one online record with its name, work pool, and a standard UUID string. An
absent, malformed, offline, wrong-pool, or ambiguous record keeps polling disabled and
fails with fixed, value-free text.

Configure the worker environment before it starts:

| Variable | Requirement |
| --- | --- |
| `PREFECT_API_URL` | Prefect API used by the deployment and worker. |
| `INFRAHUB_SYNC_DATABASE_URL` | Non-empty PostgreSQL connection string accepted by Psycopg for product records. |
| `INFRAHUB_SYNC_S3_BUCKET` | Non-empty bucket for immutable product artifacts. |
| `INFRAHUB_SYNC_S3_PREFIX` | Optional object-key prefix; defaults to `infrahub-sync`. |
| `INFRAHUB_SYNC_S3_ENDPOINT_URL` | Optional absolute `http` or `https` URL with no userinfo. The value reaches Boto3 unchanged; Boto3 owns any narrower SDK compatibility. |
| `INFRAHUB_SYNC_S3_REGION` | Optional region passed to Boto3. |
| `INFRAHUB_SYNC_S3_ADDRESSING_STYLE` | Optional: `path` puts the bucket in the request path, `virtual` in the host name. Unset, it is `path` when an endpoint URL is set, and Boto3 chooses when none is. Any other value stops the process. |
| `INFRAHUB_SYNC_CA_DIRECTORY` | Optional directory of PEM CA certificate files, named `*.pem` or `*.crt`, that the process trusts next to the public roots of `certifi`. A file that holds a private key or is not a readable certificate stops the process. See [Trust a private certificate authority](../compose-deployment.mdx#trust-a-private-certificate-authority). |
| `INFRAHUB_SYNC_SERVICE_WORK_POOL` | Name of the existing Prefect pool used by the deployment, worker, and API reconciliation. It is never returned by the API. |
| `INFRAHUB_SYNC_RUN_ADMISSION_TTL_SECONDS` | Optional decimal integer from 1 through 86400; defaults to 300. An unclaimed execution becomes abandoned at this inclusive deadline. |
| `PREFECT_WORKER_QUERY_SECONDS` | Prefect worker polling interval. It must be a finite positive decimal no greater than 3600; the API derives its liveness thresholds from the same value. |
| Adapter credential variables | The environment variables that the `credentials` entries of a registered package name, for example `INFRAHUB_SYNC_CREDENTIAL_NETBOX_TOKEN`. A registered run reads only these credential values from the worker environment; adapter URL variables such as `NETBOX_URL` do not replace the declared URLs. |

The service flow accepts exactly eight bounded parameters:

| Parameter | Type | Purpose |
| --- | --- | --- |
| `run_id` | `str` | API-created Sync run identity. |
| `stage` | `plan`, `verify`, `apply`, or `sync` | Execution stage accepted by the API. |
| `config_id` | `str` or `null` | Registered configuration identity. |
| `registry_version` | `int` or `null` | Immutable version of the registered configuration. |
| `package_checksum` | `str` or `null` | Checksum bound to the registered configuration package. |
| `branch` | `str` or `null` | Optional Infrahub branch. |
| `expected_checksum` | SHA-256 string or `null` | Reviewed checksum required by `apply`. |
| `confirm_writes` | `bool` | Required for `apply` and composed `sync`. |

`config_id`, `registry_version`, and `package_checksum` must all be present. The worker
refuses an execution when any of them is `null`, and it refuses a run that has no registered
configuration, before it reads the source or the destination.

The API rejects configured secret values in flow-bound request fields. Credentials,
endpoints, adapter instances, and filesystem paths are never flow parameters.

## Start the API

Set the same durable-store contract used by the worker and start Uvicorn through the packaged
entry point:

```bash
export PREFECT_API_URL="http://127.0.0.1:4200/api"
export INFRAHUB_SYNC_DATABASE_URL="postgresql://sync:replace-me@postgres/infrahub_sync"
export INFRAHUB_SYNC_S3_BUCKET="infrahub-sync-artifacts"
export INFRAHUB_SYNC_S3_PREFIX="infrahub-sync"
export INFRAHUB_SYNC_SERVICE_HOST="127.0.0.1"
export INFRAHUB_SYNC_SERVICE_WORK_POOL="sync-process-pool"
python -m infrahub_sync.service.serve
```

:::warning A product database created by an earlier version is not upgraded

Startup creates the tables, indexes and constraints of the product database when they are
missing. It does not add a column to a table that already exists, so a table that an earlier
version created keeps the columns of that version.

Start this version on an empty database. On a database that an earlier version created,
startup fails, or a later request fails, when it reaches a missing column. The runs,
configurations and audit events in the earlier database are not copied to the new one.

Several processes can start at the same time on the same database, whether it is empty or
already has the tables.

:::

Also export `INFRAHUB_SYNC_ADMIN_ACCOUNT_PASSWORD`, and optionally
`INFRAHUB_SYNC_ADMIN_ACCOUNT_TOKEN`, as [Accounts and API tokens](#accounts-and-api-tokens)
describes. Without the password, the API does not start.

The server listens on port `8000`. Its host defaults to `127.0.0.1`. Put TLS and any
network access controls at your ingress boundary. Accounts and tokens authenticate the callers
of the application. They do not replace transport security.

Open `http://127.0.0.1:8000/api/docs`, select **Authorize**, and enter an API token or a
session token without the `Bearer` prefix. Swagger UI adds the complete `Authorization` header.

## Discovery and health

`GET /health` and `GET /version` are the two unauthenticated lifecycle and
server-discovery routes. They disclose neither a configured work-pool
name, run identity, credential, nor Prefect endpoint. All run and
configuration routes remain bearer-authenticated.

`GET /version` returns the installed server version, the currently supported
unstable API identifier, and the installed Infrahub SDK version:

```json
{"server_version":"<installed version>","api_versions":["v3-unstable"],"stability":"unstable","sdk_version":"<installed infrahub-sdk version>"}
```

`sdk_version` is the version of the `infrahub-sdk` package installed in the `sync-api`
container. It is `null` when the service cannot read that package's metadata, or when
the metadata does not hold a valid version. A Sync API
older than this field does not return it.

It is a discovery resource only. This server does not yet reject clients based on a
claimed compatibility range.

### `GET /health`

`GET /health` reports whether the Sync API can serve requests: it checks the four components
that the Sync API depends on and reads the work pool. It takes no parameter, no body and no
token. `GET /api` and `GET /api/` redirect to it with `307`.

| Status | When |
| --- | --- |
| `200` | `status` is `healthy`: every component is `up`, the work pool was read, and at least `INFRAHUB_SYNC_HEALTH_MIN_WORKERS` workers are live. |
| `503` | `status` is `unhealthy`: any other case. |

Both answers carry the same JSON body, `Content-Type: application/json` and
`Cache-Control: no-store`. The body never contains a host name, an IP address, a credential
name or value, an error message or the Sync version. If the route itself fails, the answer is
the `503` `service-unavailable` error envelope instead of a report.

`HEAD /health` answers the same status code and headers as `GET /health`, without a body. It
runs the same checks, so a monitoring tool that only reads the status code can use it. The
OpenAPI document lists only `GET`.

```json
{
  "status": "healthy",
  "dependencies": [
    {"name": "database", "status": "up", "error": "none"},
    {"name": "object_store", "status": "up", "error": "none"},
    {"name": "task_manager", "status": "up", "error": "none"},
    {"name": "task_manager_db", "status": "up", "error": "none"}
  ],
  "workers": {
    "state": "known",
    "minimum": 1,
    "live_workers": 1,
    "queue_depth": 0,
    "items": [
      {
        "name": "infrahub-sync-service-3f0c2a9e-6a1b-4c55-9d3e-2b7c1e0f4a11",
        "state": "live",
        "last_heartbeat": "2026-11-23T10:15:02Z"
      },
      {
        "name": "infrahub-sync-service-8b1d7e40-2c9f-4e0a-a6b3-5f2e9c7d1b08",
        "state": "stale",
        "last_heartbeat": "2026-11-23T09:41:57Z"
      }
    ]
  },
  "timestamp": "2026-11-23T10:15:09Z"
}
```

In this example the second worker is the record of a worker that ran before a restart. A
stale worker is listed and does not change `status`.

The fields of the report:

| Field | Meaning |
| --- | --- |
| `status` | `healthy` or `unhealthy`, as the table of status codes above describes. |
| `dependencies` | Exactly four entries, always in this order: `database` (the product database in PostgreSQL), `object_store` (the S3-compatible bucket), `task_manager` (the Prefect server) and `task_manager_db` (the database of the Prefect server, as the Prefect server reports it). |
| `dependencies[].status` | `up`, or `down` when the check failed or did not end within `INFRAHUB_SYNC_HEALTH_CHECK_TIMEOUT` seconds. |
| `dependencies[].error` | `none` when the component is `up`; otherwise one of the error categories below. |
| `workers.state` | `known` when the work pool was read; `unknown` when it could not be read within the time limit. `unknown` makes the answer `503`. |
| `workers.minimum` | The value of `INFRAHUB_SYNC_HEALTH_MIN_WORKERS`. |
| `workers.live_workers` | The number of listed workers whose state is `live`. `null` when `workers.state` is `unknown`. |
| `workers.queue_depth` | The number of runs that are due and that no worker has claimed. `null` when `workers.state` is `unknown`. |
| `workers.items` | The workers of the pool that sent a heartbeat in the last 24 hours, newest heartbeat first, then by name. Empty when `workers.state` is `unknown`. |
| `workers.items[].name` | The worker name `infrahub-sync-service-<uuid>` that the Sync worker registers at each start, or `other` for a worker of the pool with any other name. |
| `workers.items[].state` | `live` when the Prefect server reports the worker online and its last heartbeat is no older than `max(3 × heartbeat interval, 30 seconds)`; `stale` otherwise. |
| `workers.items[].last_heartbeat` | The time of the worker's last heartbeat. |
| `timestamp` | When the round of checks started. |

The error categories of `dependencies[].error`:

| Category | Meaning |
| --- | --- |
| `none` | The component is up. |
| `timeout` | No answer within `INFRAHUB_SYNC_HEALTH_CHECK_TIMEOUT` seconds. A paused container gives this. |
| `connection_refused` | The address was reached, but nothing listens on the port. |
| `connection_closed` | The connection was opened and then closed by the other side. |
| `name_resolution_failed` | The host name does not resolve. A stopped Compose container gives this. |
| `unavailable` | The component answered but cannot serve requests: a Prefect `503`, a missing bucket, refused object-store credentials or a refused database login. |
| `unknown_error` | Any other failure. |

Two settings of the API process control the checks. A value outside its range stops the Sync
API at start with a message that names the variable.

| Variable | Default | Rule |
| --- | --- | --- |
| `INFRAHUB_SYNC_HEALTH_CHECK_TIMEOUT` | `3` | The number of seconds that each component check and the read of the work pool may take. A whole number from 1 to 60. |
| `INFRAHUB_SYNC_HEALTH_MIN_WORKERS` | `1` | The answer is `503` when fewer workers than this number are live. A whole number from 1 to 999999999. |

All checks of one round run at the same time, so a round takes at most about
`INFRAHUB_SYNC_HEALTH_CHECK_TIMEOUT` seconds. Each API process reuses the result of a round for
one second after the round ended, so many callers that poll at the same time cause at most one
round per second.

Use `GET /health` as a readiness signal for monitoring and alerting, not as a liveness probe
that restarts the Sync API. The components are shared: when PostgreSQL or the Prefect server
stops, every Sync API process answers `503`, and a liveness probe would restart all of them
without fixing the cause. Set the probe's own timeout above
`INFRAHUB_SYNC_HEALTH_CHECK_TIMEOUT`, so that a slow component is reported as `down` in the
body instead of as a probe timeout. The `sync-api` container health check of the Compose
deployment uses `GET /version` for this reason.

A monitoring check needs only the status code. With `curl`, `-f` makes the command fail on
`503`:

```bash
curl -fsS --max-time 10 "$INFRAHUB_SYNC_API_URL/api/health" > /dev/null
```

In Uptime Kuma, add an HTTP monitor on `<Sync API address>/api/health` with the accepted status
codes `200-299` and a request timeout above `INFRAHUB_SYNC_HEALTH_CHECK_TIMEOUT`. With the
Prometheus blackbox exporter, use an `http` module that accepts only `200`:

```yaml
modules:
  sync_health:
    prober: http
    timeout: 10s
    http:
      valid_status_codes: [200]
```

The 10-second timeout in these examples fits the default `INFRAHUB_SYNC_HEALTH_CHECK_TIMEOUT` of
3 seconds. The setting accepts up to 60 seconds; when you raise it, raise the probe timeout
above the new value.

To find the cause of a `503`, read the body: the component with `status` `down` and its
`error`, or the `workers` section.

### Run liveness and cancellation

Each submitted Prefect execution is claimed by its worker before it resolves a
configuration or builds adapters. The API derives the stall threshold as
`max(3 × PREFECT_WORKER_QUERY_SECONDS, 30 seconds)`, and reconciles no less often
than that threshold permits (at most five seconds, with a 0.25-second lower bound).
An unclaimed execution is marked stalled at that threshold and becomes abandoned at
the admission TTL. A claimed execution whose exact owner is no longer fresh becomes
`interrupted` with an `ambiguous` outcome; it is not retried automatically.

Cancellation is also bounded. Sync persists cancellation intent before contacting
Prefect. A successful Prefect acknowledgement is recorded separately. Until the
same liveness threshold expires, that intent fences claim, abandonment, and orphan
adjudication. At the inclusive deadline, an unconfirmed cancellation settles as
unavailable and the execution becomes abandoned or interrupted/ambiguous according
to whether it was claimed. An acknowledged request retains its accepted response,
but still reaches that terminal verdict unless Prefect is durably observed as
terminally cancelled first.

A terminal execution is immutable, so its summary is served from the retained record
and carries no live provider detail: `detail_available` is `false` and
`unavailable_reason` is `live-detail-not-requested`. Once an execution has a recorded
`terminal_state`, its `state` is that terminal state, in every response, even when a live
or retained Prefect observation reports an earlier state such as `running`.
`terminal_state` and `terminal_outcome` are the authoritative fields for how an
execution ended. Only the response that records an execution's terminal
verdict still carries that execution's live detail.

Each orchestration entry also carries `prefect_flow_run_url`: the address of the flow
run's page in the Prefect UI, `<INFRAHUB_SYNC_PREFECT_UI_URL>/runs/flow-run/<flow_run_id>`.
It is `null` when `INFRAHUB_SYNC_PREFECT_UI_URL` is unset or empty. The Sync API reads that
setting at start-up and refuses to start when it is not an absolute `http` or `https` URL
with a host, or when it holds credentials, a query or a fragment. The refusal message names
the setting and does not repeat its value. A client from an earlier release accepts a
response that holds the field.

### Read state of each side

Each orchestration entry also carries `reads`: the state of the source read and the
destination read of a `plan` or `sync` execution. Read the run while the stage runs to follow
each side, and after it ends to find which side failed or did not start. Every route whose
response holds orchestration entries returns it: `POST /runs`, `GET /runs/{run_id}`,
`POST /runs/{run_id}/verify`, `POST /runs/{run_id}/apply` and `POST /runs/{run_id}/cancel`.
`GET /runs` does not return it, because its items hold no orchestration entries.

```json
"reads": {
  "source": {
    "state": "succeeded",
    "started_at": "2026-11-09T10:00:01Z",
    "ended_at": "2026-11-09T10:00:13Z",
    "read_mode": "full",
    "nodes_by_kind": {"DcimDevice": 3, "LocationSite": 2},
    "error_class": null
  },
  "destination": {
    "state": "reading",
    "started_at": "2026-11-09T10:00:01Z",
    "ended_at": null,
    "read_mode": null,
    "nodes_by_kind": {},
    "error_class": null
  }
}
```

`reads` is `null` in four cases:

- For a `verify` or `apply` execution, which reads neither side.
- For an execution recorded before the Sync API stored the read state.
- For a `plan` or `sync` execution that the worker has not started yet.
- For a `plan` or `sync` execution in which the worker could not store the read state of
  either side. The worker logs a warning when a write fails and continues the stage, so
  `reads` can stay `null` after the stage has started.

When the worker starts a `plan` or `sync` stage, it records both sides as `waiting` before
it reads the destination schema and, for a `sync`, before it waits for the configuration's
write guard. When that write succeeds, `source` and `destination` are both present from that
moment, so a stage that fails before either read returns both sides as `not_started`. When
`reads` is not `null`, `source` or `destination` is `null` when the worker could not store
that side's read state, and in the cases that the list after the table describes.

| `state` | Meaning |
| --- | --- |
| `waiting` | The worker started the stage and has not started reading this side. |
| `reading` | The read of this side has started and has not ended. `started_at` is set. |
| `succeeded` | The read ended without an error. `ended_at`, `read_mode` and `nodes_by_kind` are set. |
| `failed` | The read ended with an error. `ended_at` and `error_class` are set. |
| `not_started` | The execution ended without completing before this side's read started. |
| `interrupted` | The execution ended without completing while this side was being read. |

The Sync API stores only `waiting`, `reading`, `succeeded` and `failed`. It derives the
returned state from the stored state, the execution's `terminal_state`, and the flow run
state it last observed in Prefect:

- When `terminal_state` is set to anything other than `completed`, a side stored as `waiting`
  is returned as `not_started`, and a side stored as `reading` is returned as `interrupted`.
  `ended_at` is `null` for both.
- When `terminal_state` is not set yet, but Prefect reports the flow run as `failed`,
  `crashed` or `cancelled`, the Sync API returns the sides the same way. This covers a worker
  that stopped before the service recorded its execution's verdict.
- When `terminal_state` is `completed`, a side still stored as `waiting` or `reading` is
  returned as `null`, because the end of its read was not recorded. The Sync API logs a
  warning.
- A stored state that does not parse, or that holds a state or read mode the Sync API does
  not store, is returned as `null`, and the Sync API logs a warning.

`state` and `read_mode` are strings in the client model, so a client from this release
reads a run response that holds a state or a read mode added by a later release.

`read_mode` is `full` when the worker extracted every top-level kind of the side in full,
and `incremental` otherwise, including for a side that mixes kinds extracted in full and
kinds read incrementally. `nodes_by_kind` counts the nodes read for each
top-level kind of the side and each other kind the side holds, sorted by kind name; a
top-level kind with no node counts `0`. It is `{}` for every state other than `succeeded`,
and for a succeeded read whose nodes could not be counted, in which case the worker logs a
warning. `error_class` is the class name of the error that
ended the read, such as `ConnectionError`, and is `null` for every state other than `failed`.
No field holds an exception message, an address, a secret or configuration content.

A run can hold `plan`, `verify` and `apply` entries in order. To show one read state for a
run, use the latest entry whose `purpose` is `plan` or `sync`. The change is additive:
existing fields keep their meaning and order.

### Timings of the plan step

Each orchestration entry also carries `plan_step`: the start and the end of each part of the
plan step of a `plan` or `sync` execution. Read it to find which part of a plan takes the
time, or which part was running when a plan stopped. The routes that return `reads` return
`plan_step` too; `GET /runs` does not.

`plan_step` and each of its parts are subject to change in a later release.

```json
"plan_step": {
  "running": null,
  "parts": {
    "waiting":   {"started_at": "2026-11-16T10:00:00Z", "ended_at": "2026-11-16T10:00:04Z", "stopped_at": null},
    "preparing": {"started_at": "2026-11-16T10:00:04Z", "ended_at": "2026-11-16T10:00:09Z", "stopped_at": null},
    "comparing": {"started_at": "2026-11-16T10:00:41Z", "ended_at": "2026-11-16T10:01:13Z", "stopped_at": null},
    "checking":  {"started_at": "2026-11-16T10:01:13Z", "ended_at": "2026-11-16T10:01:15Z", "stopped_at": null},
    "saving":    {"started_at": "2026-11-16T10:01:15Z", "ended_at": "2026-11-16T10:01:16Z", "stopped_at": null}
  }
}
```

`parts` holds one entry per part that started, in the order the plan step runs them:

| Part | Period |
| --- | --- |
| `waiting` | From the submission of the execution (`submitted_at`) to the moment a worker takes it (`claimed_at`). Subject to change. |
| `preparing` | From `claimed_at` to the start of the earlier of the two reads. Subject to change. |
| `comparing` | Deriving the operations from the two reads. Subject to change. |
| `checking` | The checks that run on the derived plan before it is saved, which build the plan report. Subject to change. |
| `saving` | Writing the plan and publishing it, up to the moment the run returns its plan. Subject to change. |

The two reads run between `preparing` and `comparing`. Their times stay in `reads` and are not
repeated in `plan_step`.

Each entry holds three times:

- `started_at` is the start of the part.
- `ended_at` is the end of the part, and is `null` while the part runs.
- `stopped_at` is set only for the part that was running when the execution failed, was
  cancelled or was interrupted. It is the execution's `terminal_at`. When Prefect reports the
  flow run as `failed`, `crashed` or `cancelled` and the execution has no `terminal_state`
  yet, that part is returned with `started_at` only.

`running` names the part that runs, and is `null` once the execution has a verdict. A part
that did not start has no entry, so no part holds a duration that was not measured. A
`waiting` entry is returned only when `claimed_at` is not before `submitted_at`. When an
execution completed and the stored timings still name a running part, that part has no entry,
because its end was not recorded; the Sync API logs a warning.

`plan_step` is `null` for a `verify` or `apply` execution, for an execution recorded before the
Sync API stored these timings, and for a `plan` or `sync` execution that the worker has not
started yet. When the worker cannot store a timing, it logs a warning with the error class and
continues the plan. No field holds an error message or a value from the source or destination
data.

`running` and the part names are strings in the client model, so a client from this release
reads a run response that holds a part added by a later release.

## Routes

Every route below requires `Authorization: Bearer <token>`. Every `POST` route that writes or
requests a change also requires a non-empty `Idempotency-Key` header and a JSON body;
`POST /configs/{config_id}/versions/{registry_version}/validate`, `POST /configs/validate` and
`POST /schedules/next-starts` are the exceptions, since they store nothing. The first re-checks an
already-registered version and takes no body. The second takes a JSON body but no
`Idempotency-Key` and no `reason`. The third computes start times and takes no `Idempotency-Key`.

In the body of every `POST` route that requires an `Idempotency-Key`, `reason` is optional.
When present, it must be non-empty, and the service records it in the audit history. When it is
absent or `null`, the service records the request without a reason. For idempotency, an absent
reason and a `null` reason are the same value, and both differ from any text.

`POST /configs` and `POST /configs/{config_id}/versions` also accept
`registered_without_validation`, `false` by default. When it is `true`, the service marks the
created version as registered without validation. The service records the value that the request
sends and does not check it. The web interface sends `true` when the destination could not be
reached during validation; the CLI never sends it. For idempotency, an absent value and `false`
are the same value, and both differ from `true`. When the package is identical to a version
already stored for the configuration (`created: false`), the field is ignored and that version is
returned unchanged.

| --- | --- |
| `POST /configs` | Register a new configuration package as version 1. Administrator only. Both or neither gets 400 `request`. The CLI sends `package`; the web interface sends `document`, so the stored package and its checksum are those of the file that was checked. For idempotency, a `document` is compared as text, and it differs from any `package`. The response names the version by `config_id`, `registry_version`, `package_checksum`, `created_at` and `registered_without_validation`, without its package content. ### List runs and configurations

`GET /runs`, `GET /configs` and `GET /configs/{config_id}/versions` return one page at a time
in the same envelope:

```json
{"items": [], "next_cursor": null}
```

| Query parameter | Applies to | Rule |
| --- | --- | --- |
| `limit` | all three lists | Items per page, from 1 to 200. Defaults to 50. A value outside that range returns `422 request-invalid`. |
| `cursor` | all three lists | The `next_cursor` of the previous page, sent with the same filters. A cursor that does not decode, or that was issued for another list or for other filters, returns `422 invalid-cursor`. |
| `config_id` | `GET /runs` | Only runs of this configuration. A malformed configuration ID returns `422 request-invalid`; an unknown configuration returns `404 configuration-not-found`. |
| `registry_version` | `GET /runs` | Only runs of this configuration version. Requires `config_id`, otherwise `422 request-invalid`. An unknown version returns `404 configuration-version-not-found`. |
| `trigger_type` | `GET /runs` | Only runs that a person or another system started (`manual`) or that a schedule started (`scheduled`). Another value returns `422 request-invalid`. |
| `schedule_id` | `GET /runs` | Only runs that this schedule started. A malformed identifier returns `422 request-invalid`; an unknown schedule returns an empty list. |
| `name` | `GET /configs` | Only configurations with exactly this name. |

`next_cursor` is `null` on the last page. The lists return no total count.

- `GET /runs` orders runs by `started_at`, newest first. A list item has the same fields as the
  `run` object that `GET /runs/{run_id}` returns, except that `artifact_refs` and
  `prefect_executions` are always empty. The list has no `orchestration` field. Read the run
  itself for those values. `destination_branch` is the branch the run writes to. It is
  `null` for runs created before the field existed. Without filters, the list also includes
  legacy runs that have no `config_id`. `approval` is the run's approval, or `null` when the
  run has none; see [Approve the reviewed plan](#approve-the-reviewed-plan).
  `trigger_type` is `scheduled` for a run that a schedule started, with its `schedule_id` and
  `scheduled_start_at`, the start time of the cadence in UTC. It is `manual` for every other run,
  and `schedule_id` and `scheduled_start_at` are then `null`. A scheduled run records the
  schedule's owner as its `actor`; its `started_at` is later than `scheduled_start_at` when the
  run started late or waited for another run.
- `GET /configs` orders configurations by `created_at`, newest first. Each item carries
  `config_id`, `name`, `latest_version` and `created_at`.
- `GET /configs/{config_id}/versions` orders versions by `registry_version`, newest first. Each
  item carries `config_id`, `registry_version`, `package_checksum`, `created_at`,
  `registered_by`, `registration_reason`, `registered_without_validation`, `latest_run` and
  `latest_applied_run`, and no package content. `registered_without_validation` is `true` for a
  version registered with that field set to `true`, and `false` for every other version. `latest_run` is the version's newest run by `started_at`.
  `latest_applied_run` is the most recently applied run, ordered by the time its apply
  finished. An apply updates the plan run, so its `started_at` is the time the plan was
  created and its `finished_at` is the time the apply finished. Each run reference carries
  `run_id`, `phase`, `outcome`, `started_at` and `finished_at`; `finished_at` is `null` for a
  run that has not finished. `registered_by` and `registration_reason` are `null` for versions
  registered before they were recorded. Read
  `GET /configs/{config_id}/versions/{registry_version}` for the package content.

Both configuration lists previously returned a bare array and accepted `offset`. They now
return the envelope above. `offset` is removed: the service ignores it, so a client that
pages with `offset` reads the first page again.

`GET /me` returns the actor that the token authenticates as:

```json
{"actor": "automation@example.com", "administrator": false, "approval_required": true}
```

`approval_required` is `true` when the service runs with `INFRAHUB_SYNC_REQUIRE_APPROVAL` on;
see [Require an approved plan](#require-an-approved-plan). It performs no other action. Use it
to check a token, and whether `apply` needs an approval, before you submit a run.

### Find a run's flow runs in Prefect

Each flow run that Sync submits to Prefect carries tags that identify its run, its stage and,
for a registered run, its configuration version. Sync creates the flow run with these tags,
and Prefect adds the deployment's tags, including any tag you added to the deployment:

| Tag | Example |
| --- | --- |
| `run:<run_id>` | `run:20260810T1500-0123abcd` |
| `stage:<stage>` | `stage:apply` |
| `config:<config_id>` | `config:cfg-netbox` |
| `config-version:<config_id>@<registry_version>` | `config-version:cfg-netbox@2` |

Filter flow runs by one of these tags in the Prefect UI or API to list every stage of one run,
or every run of one configuration version.

### Read a run's log

`GET /runs/{run_id}/logs` returns the lines that Sync wrote while it ran the run's stages. The
Sync API reads them from every flow run that the run record names, one or more per stage. It
returns only the lines that Sync's own code wrote, and leaves out the lines that the engine
and the worker of the orchestrator wrote, such as the flow run's final state.

| Query parameter | Rule |
| --- | --- |
| `stage` | Only the lines of this stage: `plan`, `verify`, `apply` or `sync`. |
| `limit` | Lines per page, from 1 to 1000. Defaults to 200. |
| `offset` | The number of lines to skip. Defaults to 0. |

A value outside these rules returns `422 request-invalid`.

```json
{
  "run_id": "20261106T1015-0123abcd",
  "items": [
    {
      "stage": "plan",
      "attempt": 1,
      "timestamp": "2026-11-06T10:15:01Z",
      "level": "ERROR",
      "source": "infrahub_sync.service.flow",
      "message": "Branch `demo-test` does not exist in Infrahub. Next step: Create it, or start the run with `--branch <existing branch>`."
    }
  ],
  "limit": 200,
  "offset": 0,
  "has_more": false,
  "run_phase": "plan-failed"
}
```

- `stage` and `attempt` name the flow run that wrote the line. `source` is the name of the
  Sync logger that wrote it.
- `level` is `DEBUG`, `INFO`, `WARNING`, `ERROR` or `CRITICAL`.
- Lines are ordered by flow run, in the order the run record lists them, then by time.
- Control characters other than line breaks and tabs are removed from `message`, and a message
  is cut at 4,096 characters.
- `run_phase` is the run's phase when the page was read.
- A run that has no flow run yet returns an empty `items` list.

To read new lines while a run is in progress, send `offset` equal to the number of lines
already read: the response holds only the newer lines. `run_phase` alone does not show that
a stage ended: a verify or an apply of a planned run keeps the phase `planned` while it runs,
and a verify does not change the phase when it ends. Read `GET /runs/{run_id}` and check the
`terminal_state` of the latest `orchestration` entry instead. The orchestrator stores the
last lines of a flow run a moment after it ends, so read again for a few seconds after that
before you stop. `infrahub-sync runs logs RUN_ID --follow` reads every 2 seconds this way and
exits after three reads in a row return no new line once the run has ended.

The orchestrator keeps the log of a flow run for as long as it keeps the flow run. When it no
longer holds a flow run that the run record names, the route returns `410 log-expired`. When
it cannot be reached, the route returns `503 log-unavailable`; `GET /runs/{run_id}`,
`GET /runs/{run_id}/results` and `GET /events` keep answering. The deployment page explains
[how long Prefect keeps flow runs](../compose-deployment.mdx#how-long-run-logs-are-kept).

### List events

`GET /events` lists what happened to runs, configurations and schedules: each decision the Sync
API made on a request, each stage result the worker recorded, and each decision the worker made
on a start of a schedule. An event is saved in the same
database transaction as the decision or result it records, so neither is saved without the
other. An event that records a refusal is saved on its own.

| Query parameter | Rule |
| --- | --- |
| `run_id` | Only events about this run. |
| `config_id` | Only events about this configuration, or that name it as a related resource. |
| `event_type` | Only events of this type. Repeat it for several types. |
| `related` | Only events with this related resource, written `<kind>:<id>`, for example `account:alice`, `branch:main` or `schedule:<schedule_id>`. Repeat it for several. |
| `since` | Only events at or after this time. A date and time with a time zone. |
| `until` | Only events before this time. A date and time with a time zone. |
| `limit` | Events per page, from 1 to 200. Defaults to 50. |
| `offset` | The number of matching events to skip. Defaults to 0. |
| `order` | `asc`, the default, lists events oldest first. `desc` lists them newest first. |

A value outside these rules returns `422 request-invalid`. Events are ordered by
`occurred_at`, then `event_id`: both ascending with `order=asc` or without `order`, both
descending with `order=desc`. A request without `order` gets the same answer as before `order`
existed.

With `order=asc`, read new events by sending `offset` equal to the number of events already read;
`infrahub-sync events --follow` reads every 2 seconds this way until you stop it. An event saved
late with an earlier `occurred_at` than events already read takes a position among them and moves
the later events down by one, so a reader that pages this way can skip one event or read one
event twice.

With `order=desc`, a new event takes the first position and moves every older event down by one.
To read older pages while new events are saved, read the first page without `until`, then
send with every older page `until` set to just after the `occurred_at` of the first page's newest
event, and read the newest events again with a request without `until`. `until` keeps only events
saved before it, so take it from an event the Sync API returned rather than from the reader's
clock, which can differ from the Sync API's clock. An event saved after the newest event but
less than a millisecond after it still falls before `until`, moves the older events down by one
and can make an older page repeat one event: leave out an event whose `event_id` you have already
read. The schedule page of the web interface reads a schedule's history this way, with `until` one
millisecond after that event, and leaves out repeats by `event_id`:

```text
GET /events?related=schedule:<schedule_id>&order=desc&limit=50&offset=0
GET /events?related=schedule:<schedule_id>&order=desc&until=<until>&limit=50&offset=<n>
```

```json
{
  "items": [
    {
      "event_id": "a-3f0c9d2e5b7a4c1e8f6d0b2a4c6e8f01",
      "event_type": "infrahub_sync.run.planned",
      "occurred_at": "2026-11-06T10:15:02Z",
      "actor": "alice",
      "operation": "plan",
      "outcome": "succeeded",
      "reason": null,
      "primary_resource": {"kind": "run", "id": "20261106T1015-0123abcd"},
      "related": [
        {"kind": "account", "id": "alice"},
        {"kind": "config", "id": "cfg-netbox"},
        {"kind": "config_version", "id": "cfg-netbox@3"},
        {"kind": "branch", "id": "main"}
      ]
    }
  ],
  "limit": 50,
  "offset": 0,
  "has_more": false
}
```

`primary_resource` is the run that the event is about, else the schedule, else the
configuration. It is `null` when the event names none of them. `related` holds
the actor's account and, when they are known, the configuration, its version, the
destination branch and the schedule. Every event of a run that a schedule started names that
schedule, so `related=schedule:<schedule_id>` returns the history of a schedule and of its runs.

An event can also hold `details`, the facts of the event, under a closed set of keys. A key
that the event does not use is `null`, and an event that records no fact has `details: null`:

| Key | Holds | Used by |
| --- | --- | --- |
| `start_at` | The start time of the cadence. | Every event of one start of a schedule. The one event that records the older missed starts and `infrahub_sync.schedule.stopped` do not hold it. |
| `starts`, `first_start_at`, `last_start_at` | The count, the first and the last of the missed starts. | The one event that records the missed starts older than the 500 most recent. |
| `left_out` | The plan's count of records left out. | `infrahub_sync.run.synced` and `infrahub_sync.run.failed` of a scheduled run. |
| `branch`, `proposed_change_id` | The branch and the proposed change of a run with branch review. | The events of a proposed change. |
| `replaced_run_id` | The earlier run whose proposed change or branch was replaced. | `infrahub_sync.schedule.proposed_change_replaced`. |
| `cause` | A refusal code or a failure class, never text from Infrahub. | `start_failed` and `proposed_change_failed`. |
| `changes` | The settings whose stored value the change altered: one `{field, before, after}` entry per setting, described below. | `infrahub_sync.schedule.changed`. An event recorded before this key existed has `changes: null`. |

Each entry of `changes` names a setting by its field of `POST /schedules/{schedule_id}/change`
(`registry_version`, `cron`, `timezone`, `write_target`, `write_when_left_out`, `overlap_policy` or
`start_late_by_at_most_seconds`) and holds its stored value before and after the change: a version
number, a cron expression, a time zone name, a write target, `true` or `false`, an overlap policy,
or a number of seconds. The entries follow the order of that list. A setting that the request sent
with the value it already had is not listed, and a setting that the change altered without the
request naming it is listed: a change to `branch-review` turns `write_when_left_out` off. When no
stored value changed, `changes` is an empty list. A request repeated with the same
`Idempotency-Key` receives the stored answer and records no second change event:

```json
"details": {
  "changes": [
    {"field": "registry_version", "before": 2, "after": 3},
    {"field": "start_late_by_at_most_seconds", "before": 1800, "after": 2700}
  ]
}
```

The event types are:

| Event type | Recorded when |
| --- | --- |
| `infrahub_sync.run.accepted` | The Sync API accepted a plan, sync, verify, approve or apply request, or a cancel request. For a cancel request, `operation` is `cancel`; for a cancel that withdrew a finished plan, `outcome` is `accepted-withdrawn`. |
| `infrahub_sync.run.replayed` | A retry with the same idempotency key received the stored answer. |
| `infrahub_sync.run.refused` | The Sync API refused a run request. `outcome` names the reason, for example `refused-checksum`. |
| `infrahub_sync.run.unavailable` | The orchestrator could not confirm a submission or a cancellation request. |
| `infrahub_sync.run.planned` | A plan stage succeeded. |
| `infrahub_sync.run.verified` | A verify stage succeeded. |
| `infrahub_sync.run.applied` | An apply stage succeeded. |
| `infrahub_sync.run.resumed` | A resume stage succeeded: the rest of the saved plan was applied. |
| `infrahub_sync.run.synced` | A sync stage succeeded. |
| `infrahub_sync.run.failed` | A stage failed, or was interrupted. `outcome` is `failed`, or `ambiguous` when the stage may have written to the destination. The Sync API records this event, with `outcome` `ambiguous`, when it ends an execution whose worker stopped without recording a result. |
| `infrahub_sync.run.cancelled` | An execution that a cancel request stopped ended cancelled, or a cancel request withdrew a finished plan. `actor` and `reason` come from the cancel request. For a withdrawal, the Sync API records this event itself, with the `run.accepted` event of the request. |
| `infrahub_sync.config.registered` | A configuration was registered as version 1. |
| `infrahub_sync.config.version_registered` | A new version of a configuration was registered. |
| `infrahub_sync.config.version_retrieved` | A version request had the same content as an existing version of the configuration, and the Sync API returned that version with status 200. No version was created. |
| `infrahub_sync.config.refused`, `.replayed`, `.unavailable` | The same decisions as for a run, on a configuration request. |
| `infrahub_sync.schedule.created`, `.changed`, `.paused`, `.resumed`, `.deleted`, `.taken_over` | The Sync API accepted a request on a schedule. `operation` is `schedule-create`, `schedule-change`, `schedule-pause`, `schedule-resume`, `schedule-delete` or `schedule-take-over`. |
| `infrahub_sync.schedule.refused`, `.replayed` | The Sync API refused a request on a schedule, or a retry with the same idempotency key received the stored answer. `outcome` names the cause of a refusal. |
| `infrahub_sync.schedule.start_skipped` | A start created no run, because a run of the configuration was in progress, a proposed change of the schedule was approved and not merged, another start was waiting, the schedule writes to the default branch while the worker's `INFRAHUB_SYNC_REQUIRE_APPROVAL` is on, or the owner's account is disabled or deleted. `outcome` is `skipped-run-in-progress`, `skipped-approved-change-open`, `skipped-start-waiting`, `skipped-approval-required` or `skipped-owner-not-found`; `run_id` names the run in progress, or the run that opened the approved proposed change. After `skipped-approval-required` or `skipped-owner-not-found`, the schedule is stopped. |
| `infrahub_sync.schedule.start_queued` | A start waits for the run in progress to end, under the `queue` policy. `outcome` is `queued`. |
| `infrahub_sync.schedule.start_missed` | A start passed while the worker or the task manager was not running. `outcome` is `missed-started-late` when a late run started, with its `run_id`, and `missed-skipped` otherwise. |
| `infrahub_sync.schedule.start_failed` | A start created no run, for example because the configuration version can no longer be run. `outcome` is `failed` and `details.cause` holds the reason. |
| `infrahub_sync.schedule.stopped` | A schedule moved to the state `stopped`. `outcome` is the reason: `owner-not-found`, `approval-required` or `repeated-failures`. Recorded when the Sync API starts, by a resume or a take-over that found the reason, by the worker when it handles a start of a schedule that writes to the default branch while approval is required or whose owner's account is disabled or deleted, or with the end of the fifth failed run in a row, whose `run_id` it names. |
| `infrahub_sync.schedule.proposed_change_opened` | A run with branch review opened its proposed change. `outcome` is `opened`. |
| `infrahub_sync.schedule.proposed_change_replaced` | A run closed an earlier proposed change of the schedule, or deleted an earlier branch that had none. One event for each. `outcome` is `replaced`. |
| `infrahub_sync.schedule.proposed_change_kept` | An earlier proposed change was left in place because a person merged, closed, deleted or approved it. `outcome` is `kept-merged`, `kept-closed`, `kept-missing` or `kept-approved`. |
| `infrahub_sync.schedule.proposed_change_failed` | Opening the proposed change, or replacing an earlier one, failed. `outcome` is `failed` and `details.cause` holds the failure class. The result of the write does not change. |

A start that creates a run on time records no schedule event: the run's own events name the
schedule. The actor of an event of a start or of a proposed change is the schedule's owner. No
event holds a credential, source data, or text from Infrahub other than identifiers and branch
names.

A request refused for a missing or invalid token is not an event, and `GET /events` never
returns it.

### Read why a stage failed

When a stage fails with an error that Sync knows, the run records a `cause` and a
`next_action` under `plan_failure`, `verify_failure`, `apply_failure` or `sync_failure` in
`GET /runs/{run_id}/results`. The worker writes one `ERROR` line to the run's log,
`<cause> Next step: <next_action>`, without a Python traceback, and the stage ends failed. For
example, when the destination branch does not exist:

```text
Branch `demo-test` does not exist in Infrahub. Next step: Create it, or start the run with `--branch <existing branch>`.
```

A failure to read the destination schema also records a cause and a next action, for example a
refused token or a missing permission. An error that Sync does not know records its class name
only.

A failure record written by this release also holds these fields. A field that does not apply
is `null` or absent:

- `failure_type`: one of these types, grouped by what failed:
    - a credential or the connection to a source or the destination: `system_unreachable`,
      `system_timeout`, `token_rejected`, `permission_missing`, `tls_certificate_rejected`,
      `credential_missing`;
    - reading a source record: `record_load_failed`, `transform_failed`;
    - the destination's answer: `destination_rejected_write`, `destination_peer_missing`,
      `destination_peer_ambiguous`, `lineage_refused`, `destination_schema_unavailable`;
    - the checks of a saved plan: `verification_failed`, `apply_refused`;
    - a `sync` that stopped after its plan for a review of the left-out records:
      `left_out_review_required`;
    - the branch and the proposed change of a scheduled run that writes to a branch for review:
      `destination_default_branch_not_main`, `branch_list_failed`, `branch_create_failed`,
      `branch_delete_failed`, `proposed_change_open_failed`, `proposed_change_read_failed`,
      `proposed_change_close_failed`;
    - any other error: `internal_error`.
- `system`: `{"role": "source" or "destination", "adapter": <name>}`.
- `error_code`, `node_kind`, `attribute` and `infrahub_message`: Infrahub's error code, node
  kind, field name and message of a rejected write. `infrahub_message` is set only for
  `destination_rejected_write`.
- `record` and `field`: the source record (`kind`, `identity`, `source_id`) and the field that a
  load or transform failure names.
- `operations_total` and `failed_operation_detail`: for a stopped apply, the number of
  operations in the plan, and the `action`, `kind` and `identity` of the failed operation.

The record never holds the text of another error, so no credential reaches it. A record
written by an earlier release has none of these fields.

A `sync` that stops after its plan because the plan leaves out records records no stage
failure. Its stage result in `GET /runs/{run_id}/results` holds a `failure` object instead,
with `failure_type: left_out_review_required`, `stage: sync`, the `left_out` count and the
`next_action`. The run ends with phase `planned` and outcome `left-out-review-required`.

When `verify` or `apply` fails on a check that runs before the first write, `verify_failure` or
`apply_failure` also holds `failed_checks`: the name of each check that failed, such as
`destination_schema`. Both stages record the same name for the same problem.

### Create a plan

Address the exact registered configuration revision by its `config_id` and
`registry_version`:

```bash
curl --request POST http://127.0.0.1:8000/api/runs \
  --header "Authorization: Bearer $SYNC_API_TOKEN" \
  --header "Idempotency-Key: plan-inventory-2026-08-10" \
  --header "Content-Type: application/json" \
  --data '{
    "operation": "plan",
    "config_id": "<config_id>",
    "registry_version": 1,
    "reason": "review inventory changes"
  }'
```

`branch` and `confirm_writes` are also accepted. `POST /runs` accepts only this registered
form — `config_id`, `registry_version`, `branch`, `confirm_writes`, and `reason` — and
forbids extra fields; it does not accept a `sync_name` or `configuration_reference` form.
A legacy, directory-resolved configuration runs through the
[direct Prefect deployment](./prefect-remote-run.mdx) instead.

Acceptance returns `202` with the durable `ProductRun` and its first orchestration link.
The `run_id` in that response is the identity for every later stage, result, artifact, and
Prefect execution link.

Read the plan after the worker publishes it:

```bash
curl --header "Authorization: Bearer $SYNC_API_TOKEN" \
  http://127.0.0.1:8000/api/runs/20260810T1500-0123abcd/plan
```

The plan response includes its checksum, checksum verification state, summary, verification
notes, per-object operations, and `schema_fingerprint`. For a registered plan,
`schema_fingerprint` is the 64-character SHA-256 digest of the destination-schema
semantics consumed by that configuration. It is `null` only for a legacy unregistered
plan.

### Review the problems of a plan

The plan `summary` also holds the counts of the plan's problem check:

- `left_out`, `left_out_with_problem`, `left_out_dependent` and `left_out_by_kind`: the records
  the plan does not write, because they have a problem or depend on a left-out record through a
  required relationship.
- `problems` and `problems_by_type`: the problems found.
- `kept`: the records written without one optional relationship.
- `deletes_withheld_by_kind`: the kinds for which the plan computes no delete.
- `dropdown_values_checked`: `false` when the run had no destination schema snapshot.

Three routes list the entries, in the order of the saved plan:

```bash
curl --header "Authorization: Bearer $SYNC_API_TOKEN" \
  "http://127.0.0.1:8000/api/runs/20260810T1500-0123abcd/plan/problems?offset=0&limit=500&problem_type=dropdown_value_not_in_choices"
```

`GET /runs/{run_id}/plan/problems`, `/plan/left-out` and `/plan/kept` take `offset` and `limit`
(1 to 500) and the filter `kind`; `/plan/problems` also takes `problem_type`. Each returns the
`run_id`, the `plan_checksum`, the `entries`, `offset`, `limit`, `total` and `next_offset`,
which is `null` on the last page. A problem entry holds the `problem_type`, the source `record`
(`kind`, `identity`, `source_id`), the `field`, the source `value`, the Dropdown choices in
`allowed`, the `peer`, the `other_records` and a `reason`. It never holds the expression of a
transform or a filter. A plan saved in format 2 or 3 returns empty lists. An unknown
`problem_type` is `422`.

### Verify the reviewed plan

Verification runs, against the destination, every check that `apply` runs before its first
write, and writes nothing. The worker reads the live destination schema for it, with the
credentials and network access that `apply` uses, and the service passes the run's
`destination_branch` as the branch. Verification does not take the configuration's write
guard, does not change the run's phase, and does not approve the plan. It does not check the
confirmation that the left-out records were reviewed: only an apply request carries it
(`confirm_left_out`, described under the apply request):

```bash
curl --request POST \
  http://127.0.0.1:8000/api/runs/20260810T1500-0123abcd/verify \
  --header "Authorization: Bearer $SYNC_API_TOKEN" \
  --header "Idempotency-Key: verify-20260810T1500-0123abcd" \
  --header "Content-Type: application/json" \
  --data '{"reason":"verify the reviewed plan"}'
```

The checks, in the order they run and are reported:

| Check | What it compares |
| --- | --- |
| `checkpoint` | The plan this run saved can be read back whole and unaltered. |
| `run_binding` | The plan belongs to this run. |
| `plan_checksum` | The plan checksum is unchanged. |
| `source_snapshot` | The saved source snapshot is unchanged. |
| `config_version` | The configuration version is the one the plan was created with. |
| `format_version` | The plan format is one this release can apply. |
| `destination_schema` | The live destination schema matches the plan's `schema_fingerprint`. |
| `destination_binding` | The destination URL and branch match the ones the plan recorded. |
| `write_surface` | The destination adapter can apply a saved plan. |
| `planned_fields` | Every planned field exists in the destination schema and can be written. Reported only for an Infrahub destination. |
| `lineage` | The plan records an import account, the apply would run with that same import account, and the `source` and `owner` nodes the package names exist in the destination. Reported only for a destination that records lineage, such as Infrahub. |

On success, `GET /runs/{run_id}/results` holds the result under `verification`, with `checks`
listing every check that passed, in order, and `destination_checked: true`.

When a check fails, the verification stage fails, and `GET /runs/{run_id}` reports the failure
with the name of the check, what was expected and what was found, as for a refused `apply`.
Two failures of the saved plan files have names of their own, and both belong to
`plan_checksum`: `torn_operations` when the operations file is missing or incomplete, and
`last_changes` when the last-changes file does not match the manifest.
When the destination cannot be reached, the stage fails with the destination error, and no
check after it is reported as passed.

A verification is also accepted on an interrupted run whose write may have reached the
destination; see [Resume an interrupted run](#resume-an-interrupted-run). After every check
passes, it reads the node of each uncertain operation from the destination and stores
`results.verification.operations`, one `{operation_id, kind, action, state}` entry for each,
with `state` one of `matches`, `differs` and `missing`. A create whose key more than one node
at the destination holds is reported as `differs`. Recorded deletes are never listed, because
they are never written. It never stores a value. When more than
2,000 operations are uncertain, it reports the first 2,000 and stores the count of the others
in `results.verification.operations_truncated`. The states never make the verification fail. A
failed read of those nodes does: the failure record names its cause by the error's class, such
as an unreachable destination or a refused token. For a failure that names a system or a
credential, the record's `next_action` ends with running `verify` again, then `runs resume`.

### Approve the reviewed plan

Approval records that the reviewed plan is accepted, bound to its checksum. It writes nothing
to the destination and submits no execution:

```bash
curl --request POST \
  http://127.0.0.1:8000/api/runs/20260810T1500-0123abcd/approve \
  --header "Authorization: Bearer $SYNC_API_TOKEN" \
  --header "Idempotency-Key: approve-20260810T1500-0123abcd" \
  --header "Content-Type: application/json" \
  --data '{
    "expected_checksum": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
    "reason": "reviewed by the network team"
  }'
```

`reason` is optional. Only the actor who created the run, or an administrator, can approve it.
The service evaluates the request in this order:

1. Authorization (`403 forbidden`), then a replay of the same idempotency key.
2. A run in phase `cancelled` is refused with `409 run-cancelled`. A run that is neither in
   phase `planned` nor resumable, or that has an execution in progress, is refused with
   `409 run-not-approvable`; the message names the phase or the stage that is running. A run
   is resumable when its write stopped part-way; see
   [Resume an interrupted run](#resume-an-interrupted-run). The store checks this again when it
   stores the approval, so no approval is stored while a verification or a resume runs.
3. The saved plan is read as for `GET /runs/{run_id}/plan` (`404 run-not-found`,
   `410 artifact-expired`, `503 plan-unavailable`).
4. A plan whose checksum could not be confirmed is refused with `409 plan-checksum-unverified`.
5. An `expected_checksum` that differs from the plan's checksum is refused with
   `409 checksum-mismatch`; the message shows both checksums.
6. A run that already has an approval is refused with `409 already-approved`. The error's
   `details` carry the existing approval.

A refused approval stores no approval on the run. The service records the refusal in the
audit history as an `infrahub_sync.run.refused` event. On success, the service answers `200` with the run
resource, which now carries `approval`, and `plan_summary` with the counts of the plan
approved: `creates`, `updates` and `deletes_recorded`. The response is stored with the
mutation receipt, so a retry with the same key returns it unchanged. The run's `approval` is:

```json
"approval": {
  "approved_by": "alice",
  "approved_at": "2026-11-10T14:03:11Z",
  "plan_checksum": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "reason": "reviewed by the network team"
}
```

Approval is not a phase: an approved run stays in the phase it was in. Approval does not run the
destination checks; `apply` runs them, and `verify` reports their result beforehand.

### Apply the reviewed plan

Apply requires the exact retained checksum and explicit write confirmation:

```bash
curl --request POST \
  http://127.0.0.1:8000/api/runs/20260810T1500-0123abcd/apply \
  --header "Authorization: Bearer $SYNC_API_TOKEN" \
  --header "Idempotency-Key: apply-20260810T1500-0123abcd" \
  --header "Content-Type: application/json" \
  --data '{
    "expected_checksum": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
    "confirm_writes": true,
    "reason": "change approved"
  }'
```

The worker verifies the saved plan again before its first destination write. Destination
deletes remain disabled.

When the plan leaves out records (`summary.left_out` greater than 0), the request must also
hold `"confirm_left_out": true`, the confirmation that the person reviewed the left-out
records. Without it, the service answers `409 left-out-confirmation-required` before any
write, with the count in the error's `left_out` field and a message such as `this plan leaves
out 6 records; confirm with confirm_left_out=true`, where 6 is the plan's count. The worker checks the confirmation again.
`confirm_left_out` must be a JSON boolean; any other value is `422`. On a plan that leaves out
nothing, it has no effect.

A `sync` run that stopped after its plan because the plan leaves out records is applied the
same way, once, with its plan checksum and `confirm_left_out: true`.

A plan saved in format 2 or 3 by an earlier release is refused before any write with
`PlanFormatApplyUnsupportedError`: create a new plan and apply that one.

`PlanSchemaChangedError` means the live destination-schema semantics no longer match the
reviewed plan's `schema_fingerprint`. The worker refuses the retained plan before any
destination write. Create a new plan against the current schema, review its
`schema_fingerprint`, operations, and checksum, then apply that new plan. There is no
schema-drift override.

The service refuses to apply a run in phase `cancelled` with `409 run-cancelled`, whatever the
approval setting, before it reserves the mutation receipt. The store's write admission refuses
it too, so a cancel and an apply of the same run cannot both succeed. This applies to every
cancelled run, including a run whose `verify` stage was cancelled while it ran.

### Resume an interrupted run

An apply, a `sync` and a resume save a progress marker while they write: the position, in the
saved plan's order, of the last operation committed. Positions count from 0 and include
recorded deletes. They save it after every 500 committed creates and updates, at the first
commit after 30 seconds, when the write stops, and after the plan's last operation. They do not
save when the kind changes: the plan is sorted by tier and then by operation ID, so the kinds of
one tier are mixed. When the marker cannot be saved for 5 minutes, the write stops and the run
is interrupted.

`GET /runs/{run_id}` returns how far the write got under `apply_progress`, and each resume under
`resumes`. `apply_progress` is `null` when the run has no `apply`, `sync` or `resume` execution.
A `sync` killed while it was still planning has a `sync` execution, so it returns an object
whose `position` is `null`:

```json
"apply_progress": {
  "position": 5999,
  "saved_at": "2026-11-12T10:15:00Z",
  "resumable": true,
  "verify_required": true,
  "by_kind": [
    {"kind": "DcimDevice", "committed": 1200, "uncertain": 0, "not_reached": 0},
    {"kind": "DcimInterface", "committed": 4800, "uncertain": 4000, "not_reached": 0}
  ]
},
"resumes": []
```

In this example, the worker was killed after it saved position 5999, the 6,000th operation, and
the plan holds no recorded delete. `position` is the highest saved position over all the run's
write executions. The counts of `by_kind` are over the plan's positions, so a recorded delete
is counted as `committed` at or before `position`, as `uncertain` inside the uncertain
operations, and as `not_reached` after them. `uncertain` counts the operations after `position`
that may have reached the destination:

- through the failed operation, when the failure record of the latest write execution names it;
- through the next 500 creates and updates and the recorded deletes between them, when the last
  save is known to have succeeded, for example while a resume still runs;
- through the end of the plan in every other case, for example when the worker was killed.

While the first apply or `sync` of a run still runs, `reconciliation_required` is `false` and no
operation is counted as `uncertain`.

A failure record stores the `flow_run_id` of the execution that wrote it, and only a record of
the latest write execution names the failed operation. A record stored before this field existed
names none, so every remaining operation is uncertain.

After a resume that succeeded, `apply_progress.resumable` is `false`, every operation is
`committed`, and `resumes` holds one entry:

```json
"resumes": [
  {"actor": "alice", "requested_at": "2026-11-12T11:02:00Z", "reason": null, "start_after": 5999, "outcome": "succeeded", "operations_written": 4000}
]
```

Each entry of `resumes` holds `operations_written`: the creates and updates that resume wrote,
after its `start_after`. For a resume that succeeded, the count runs to the end of the plan; for
a resume that was stopped, it runs to its own last saved position. When a resume or an apply
succeeds, the run's summary counts the whole plan. The `operations_written` of a failure record
counts the creates and updates at or before the position the execution started after, plus the
ones the execution wrote. After a kill, operations an earlier execution wrote past its last
saved position are counted only once a later execution writes them again.

A run is `resumable` when `reconciliation_required` is `true`, the run is not
cancelled, its plan is saved, and no execution of it is unfinished. `verify_required` is `true`
until a verification passes after the latest interruption.

When the worker of a `sync` run is killed while it is still planning, the run requires
reconciliation but saved no plan, so it wrote nothing. Its `apply_progress` has `position: null`,
`resumable: false`, `verify_required: false` and an empty `by_kind`. A verification of that run
is refused with `409 run-execution-conflict`, and a resume with `409 run-not-resumable`; both
refusals are recorded in the run's audit history. Start a new `plan` or `sync` run instead.

The service reads the kind and action of each operation from the saved plan once per run, and
keeps them in memory, so polling `GET /runs/{run_id}` does not read the whole plan on every
request. When the plan expired or cannot be read, `by_kind` is empty, and the service logs a
warning that names the run, the error class and the error code, without the error message.

A resume applies the run's saved plan from the operation after `position`, in a new execution
of purpose `resume` on the same run. It does not read the source or create a plan, for an
apply run and for a `sync` run. It requires the saved plan's checksum and explicit write
confirmation:

```bash
curl --request POST \
  http://127.0.0.1:8000/api/runs/20260810T1500-0123abcd/resume \
  --header "Authorization: Bearer $SYNC_API_TOKEN" \
  --header "Idempotency-Key: resume-20260810T1500-0123abcd" \
  --header "Content-Type: application/json" \
  --data '{
    "expected_checksum": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
    "confirm_writes": true,
    "reason": "resume after the worker restart"
  }'
```

`reason` is optional, and `confirm_left_out` works as for `apply`. Only the actor who created the
run, or an administrator, can resume it (`403 forbidden`). The service answers `202` with the
run. It refuses a resume before any write:

| Status | Code | When |
| --- | --- | --- |
| 409 | `confirmation-required` | `confirm_writes` is not `true`. |
| 409 | `run-not-resumable` | The run is not interrupted, is cancelled, saved no plan, or has an unfinished execution. This includes an applied run, a run whose apply failed before its first write, a run that was never applied, a `sync` run that stopped after its plan, and a `sync` run whose worker was killed before it saved its plan. The message says which; for a run that saved no plan, it says that a new `plan` or `sync` run is the next step. |
| 409 | `checksum-conflict` | `expected_checksum` differs from the saved plan's checksum. |
| 409 | `left-out-confirmation-required` | The plan leaves out records and `confirm_left_out` is not `true`. |
| 409 | `approval-required` / `approval-checksum-mismatch` | The service requires approval and the run has none for this checksum. The `approval-required` message names `infrahub-sync approve RUN_ID --expected-checksum CHECKSUM`; an interrupted run can be approved. |
| 409 | `verify-required` | No verification passed on the run after its latest interruption. |
| 409 | `run-execution-conflict` | Another resume of the run is unfinished. |
| 410 / 503 | `artifact-expired` / `plan-unavailable` | The saved plan expired or cannot be read. |

Every resume request, accepted or refused, is recorded in the run's audit history and event
list with the operation `resume`. The worker runs every pre-write check again before its first
write. When a resume ends `succeeded`, the run's phase becomes `applied` and
`reconciliation_required` becomes `false`. When a resume is interrupted, the run stays
resumable, and the next resume needs a new verification. A resume writes the plan's values over
every node that the verification reported as `differs`.

### Require an approved plan

When the service runs with `INFRAHUB_SYNC_REQUIRE_APPROVAL` set to `true`, `1`, `yes` or `on`
(in any case), it adds these refusals. The setting is off by default, and any value other than
those and `false`, `0`, `no` or `off` stops the service at startup.

- `POST /runs/{run_id}/apply` on a run with no approval: `409 approval-required`. The message
  says to approve the plan with `approve RUN_ID --expected-checksum ...`.
- `POST /runs/{run_id}/apply` with an `expected_checksum` that differs from the approved
  checksum: `409 approval-checksum-mismatch`. The message shows both checksums.
- `POST /runs` with `operation: sync`: `409 approval-required-for-sync`, before the run record
  is created. The message says to run `plan`, `approve` and `apply` instead. `operation: plan`
  is not affected.
- `POST /schedules`, or `POST /schedules/{schedule_id}/change`, with `write_target:
  default-branch`: `409 approval-required-for-schedule`. The message names
  `INFRAHUB_SYNC_REQUIRE_APPROVAL`. A schedule with branch review is not affected: its runs write
  to a branch that Sync created for the run, and need no approval.

When the service starts with the setting on, it stops each active schedule that writes to the
default branch, with the reason `approval-required`; see [Schedules](#schedules).

The apply refusals are evaluated after authorization and idempotency replay, and before the
mutation receipt is reserved. The service reads the setting for each request. When the
setting is off, `apply` does not read approvals, and approvals stay recorded on their runs.
`GET /me` reports the setting as `approval_required`.

### Withdraw a plan by cancelling its run

`POST /runs/{run_id}/cancel` takes the same request as before: an optional `reason` and a
required `Idempotency-Key`. After authorization and a replay of the same key:

1. A run with an active execution: the service asks Prefect to cancel that execution and
   answers `202`, as before. Cancelling a write can answer `409 cancellation-ambiguous`.
2. A run with no active execution in phase `planned`: the service withdraws the plan. In one
   store transaction it checks again that no write was admitted and no other stage is
   reserved or running, sets the phase and the outcome to `cancelled`, and completes the
   receipt. It answers `200` with the run resource, which keeps its `approval`, if any. Nothing
   is sent to Prefect. When the check fails, it answers `409 run-execution-conflict`.
3. A run with no active execution in phase `cancelled`: `409 run-already-cancelled`.
4. A run with no active execution in any other phase, such as `applied` or `plan-failed`:
   `409 execution-terminal`, as before.

After a withdrawal, `approve` and `apply` refuse the run with `409 run-cancelled`. Create a new
plan run to try again.

### Schedules

A schedule starts a `sync` run of one configuration version on a cron cadence, with the
schedule's owner as the run's actor. [Schedule sync runs](../orchestration.mdx) describes how a
team uses it. Both write targets are turned on in this build: the default `branch-review`, and
`default-branch` on a Sync API that does not require approval.

`POST /schedules` takes these fields:

| Field | Required | Default | Rule |
| --- | --- | --- | --- |
| `name` | yes | | Unique among the schedules that are not deleted. |
| `config_id`, `registry_version` | yes | | A registered configuration version. A configuration has at most one schedule that is not deleted. |
| `cron` | yes | | A cron expression with five fields. |
| `timezone` | no | `UTC` | A time zone name, such as `Europe/Paris`. |
| `write_target` | no | `branch-review` | `branch-review` or `default-branch`. |
| `write_when_left_out` | no | `false` | `true` is accepted only with `default-branch`. |
| `overlap_policy` | no | `reject` | `reject` or `queue`. |
| `start_late_by_at_most_seconds` | no | `3600` | From 60 to 604800. |
| `reason` | no | | |

`POST /schedules/{schedule_id}/change` takes the same fields except `name` and `config_id`, and
at least one of them. A field that is absent keeps its value. `pause`, `resume`, `delete` and
`take-over` take only an optional `reason`. A pause of a paused schedule, a resume of an active
schedule and a second deletion answer `200` and change nothing.

Each route answers with the schedule resource:

```json
{
  "schedule_id": "s-3f2a9c0d1e2b4a5c6d7e8f9a0b1c2d3e",
  "name": "from-netbox-nightly",
  "config_id": "from-netbox",
  "registry_version": 3,
  "newer_version": null,
  "cron": "0 2 * * *",
  "timezone": "Europe/Paris",
  "write_target": "branch-review",
  "write_when_left_out": false,
  "left_out_set_by": null,
  "left_out_set_at": null,
  "overlap_policy": "reject",
  "start_late_by_at_most_seconds": 3600,
  "state": "active",
  "state_reason": null,
  "owner": "operator",
  "next_start_at": "2026-11-18T01:00:00Z",
  "waiting_start_at": null,
  "last_run_id": null,
  "prefect_synced": true,
  "consecutive_failures": 0,
  "open_branch": null,
  "created_at": "2026-11-17T09:12:00Z",
  "updated_at": "2026-11-17T09:12:00Z"
}
```

- `newer_version` is the highest registered version of the configuration when it is higher than
  `registry_version`, else `null`. The schedule still runs `registry_version`.
- `left_out_set_by` and `left_out_set_at` name the actor who last turned `write_when_left_out`
  on, and when.
- `state` is `active`, `paused`, `stopped` or `deleted`. `state_reason` is `owner-not-found`,
  `approval-required` or `repeated-failures` for a stopped schedule, else `null`.
- `next_start_at` is computed from `cron` and `timezone` each time the schedule is returned. It
  is `null` when the schedule is not active.
- `waiting_start_at` is the start that waits for a run in progress, under the `queue` policy.
- `last_run_id` is the schedule's most recent run. `GET /runs/{run_id}` holds its outcome.
- `prefect_synced` is `false` while the Sync API has not confirmed that the task manager matches the schedule as it is stored; for a deleted schedule, that the task manager holds no schedule for it. The task manager may then still hold the schedule as it was before the last change, and starts runs with what it holds.
- `consecutive_failures` is the count of runs in a row that failed, were interrupted or ended
  ambiguous. At 5, the schedule stops with the reason `repeated-failures`.
- `open_branch` is the schedule's most recent branch whose proposed change is open, with
  `run_id`, `branch` and `proposed_change_id`, else `null`. A deletion, or a change of the write
  target to `default-branch`, leaves that branch and proposed change in Infrahub and names them
  here.
- All times are in UTC.

`GET /schedules` lists schedules newest first, by `created_at`, in the envelope of
[List runs and configurations](#list-runs-and-configurations), with `limit` and `cursor`. Filter by
`config_id` and by `state`; without `state`, deleted schedules are left out. An unknown state
returns `422 request-invalid`. `GET /schedules/{schedule_id}` also returns a deleted schedule.

The schedule routes answer these refusals:

| Status | Code | When |
| --- | --- | --- |
| 403 | `forbidden` | The caller is neither the owner nor an administrator, or is not an administrator for a take-over. |
| 404 | `schedule-not-found` | No schedule has that identifier. |
| 404 | `configuration-version-not-found` | The configuration or the version is not registered. |
| 409 | `schedule-name-in-use` | A schedule that is not deleted has that name. |
| 409 | `schedule-exists-for-configuration` | The configuration already has a schedule that is not deleted. The message names it. |
| 409 | `approval-required-for-schedule` | `write_target` is `default-branch` and the Sync API requires approval. |
| 409 | `schedule-branch-declared` | `write_target` is `branch-review` and the configuration version declares its own destination branch. |
| 409 | `schedule-deleted` | A change, pause, resume or take-over of a deleted schedule. |
| 409 | `schedule-stopped` | A resume of a stopped schedule whose reason still holds, or of a paused or stopped schedule that the resume stopped for another reason. The message names the reason and the action it needs. |
| 409 | `schedule-changed` | Another request changed the schedule during each of three attempts to save this one. Send the request again. |
| 409 | `idempotency-conflict`, `idempotency-in-progress` | As for the other routes; see [Idempotency and retries](#idempotency-and-retries). |
| 422 | `schedule-cron-invalid` | The cron expression is not valid or does not have five fields. |
| 422 | `schedule-timezone-invalid` | The time zone name is not known. |
| 422 | `schedule-left-out-not-applicable` | `write_when_left_out` is `true` and `write_target` is `branch-review`. |
| 422 | `schedule-setting-not-available` | The write target is not turned on in this build. |
| 422 | `secret-parameter-refused` | A request field holds a credential. |
| 422 | `request-invalid` | The body does not match the schema, names `name`, `config_id` or `owner` in a change, or changes nothing. |
| 503 | `configuration-version-invalid` | The registered configuration version cannot be read. |
| 503 | `orchestration-unavailable` | The schedule is stored, and either the task manager could not be reached or the product database failed while the Sync API matched the task manager to the stored schedules; the message says which. The task manager may then still hold the schedule as it was before the change, also after a deletion, and starts runs with what it holds. The next change to any schedule, or a restart of the Sync API, matches the task manager to the stored schedules again, which removes the task manager's schedule of a deleted schedule, and records the match. |

A resume of a paused schedule, or of a stopped schedule whose reason no longer holds (also
`repeated-failures`), whose owner's account is disabled or deleted, or that writes to the default branch
while the service requires approval, stores the schedule as stopped with that reason and answers
`409 schedule-stopped`. A take-over of a schedule stopped for
`owner-not-found` makes it active, unless it writes to the default branch while the service
requires approval: it then stays stopped with the reason `approval-required`.

#### Next start times of a cron expression

`POST /schedules/next-starts` returns the next start times of a cron expression in a time zone,
computed by the code that computes a schedule's `next_start_at`. The schedule forms of the web
interface call it while a person types a cadence. Any authenticated account can call it. It
stores nothing, records no event, also when it refuses a request, and takes no
`Idempotency-Key`. The values travel in a JSON body, not in the query string, so a credential
typed into a field by mistake does not reach the access log.

| Field | Required | Default | Rule |
| --- | --- | --- | --- |
| `cron` | yes | | A cron expression with five fields. |
| `timezone` | no | `UTC` | A time zone name, such as `Europe/Paris`. |
| `count` | no | `5` | The number of start times, from 1 to 20. |

```json
{
  "cron": "0 2 * * *",
  "timezone": "Europe/Paris",
  "starts": ["2026-11-20T01:00:00Z", "2026-11-21T01:00:00Z"],
  "searched_until": "2031-11-23T21:40:00Z"
}
```

- `starts` are in UTC, in increasing order, and later than the time of the request.
- The search ends 1830 days (five years of 366 days) after the time of the request, at
  `searched_until`. The example answers a request made at 2026-11-19T21:40:00Z. `starts` holds
  fewer than `count` times when the expression has fewer starts before then, for example
  `0 0 29 2 *`.
- An expression that has no start at all, for example `0 0 30 2 *`, is refused with
  `422 schedule-cron-invalid`, as `POST /schedules` refuses it.

The route answers these refusals:

| Status | Code | When |
| --- | --- | --- |
| 422 | `schedule-cron-invalid` | The cron expression is not valid, does not have five fields or has no start. Same message as `POST /schedules`. |
| 422 | `schedule-timezone-invalid` | The time zone name is not known. Same message as `POST /schedules`. |
| 422 | `secret-parameter-refused` | `cron` or `timezone` holds a credential. The message names the field and does not repeat its value. |
| 422 | `request-invalid` | `cron` is absent, or `count` is not an integer from 1 to 20. |

#### Scheduled runs and the run routes

`POST /runs/{run_id}/verify`, `/apply` and `/resume` refuse a scheduled run with branch review
with `409 scheduled-run-not-appliable`. The schedule's next run replaces it. Its plan and its
results stay readable.

## Idempotency and retries

An exact retry by the same actor with the same `Idempotency-Key`, target, and JSON body
returns the stored status and body. A different request using that actor and key returns
`409 idempotency-conflict`.

Sync stores a SHA-256 digest of the client key, never the raw key. Before dispatch, it
atomically reserves a durable mutation receipt; run creation reserves the receipt and
product run in one transaction. The receipt owns a separate opaque key passed to Prefect's
native idempotency field. If an HTTP or Prefect response is lost after submission, retry the
exact request. The retry reuses the receipt, opaque Prefect key, Sync run ID, and Prefect
flow-run ID.

Do not change the request body, including `reason`, while retrying. Use a new idempotency key
for a new intent.

The first confirmed composed `sync` or reviewed `apply` permanently consumes that run's
single write admission, including when the execution later fails, crashes, or is cancelled.
Retry an uncertain request with its original idempotency key. To make another write attempt
after a terminal failure or cancellation, create and review a new plan run. One case releases
the admission: a `sync` that stops after its plan because the plan leaves out records
dispatched no operation, so the service releases its write admission when the stop is
recorded. That run then admits one confirmed apply, and every later submission is refused as
below.

A run admits its one write only while nothing else is in flight on it: no other write
admission, no other unresolved plan, verify, apply, or sync submission, and no unfinished
execution. Whichever request wins is decided before either competitor is submitted to
Prefect, so the loser never starts work. It is answered with `409 run-execution-conflict`
stored on its own receipt, and replaying that idempotency key replays the refusal. Once a
run has admitted its write, every later plan, verify, apply, and sync submission on that run
gets the same refusal — including after the write becomes terminal, because terminal write
evidence is not reopened.

A submission stays unresolved until it has a stored response, a stored refusal included. If
a client abandons one — the process dies before it reads the reply, and the key is never
replayed — that run cannot admit another stage. There is no receipt-expiry mechanism; create
a new plan or sync run instead.

## Write safety and reconciliation

A managed apply or sync holds one PostgreSQL advisory guard for the registered configuration
it writes, so two workers cannot write the same configuration at once. The guard is held
across the destination-sensitive checks and the whole write loop, and its release is
confirmed before any success is published.

Public run resources carry `reconciliation_required`. It is `false` on every new run and
becomes `true` only when a write execution ends without proving what reached the
destination. Only a resume that ends `succeeded` sets it back to `false`; see
[Resume an interrupted run](#resume-an-interrupted-run).

| What happened | Durable outcome | Your next step |
| --- | --- | --- |
| Another writer held the guard for the whole deadline | `failed`; no destination was contacted and nothing was written | Create a new plan: the other writer may have changed the destination |
| A destination-sensitive check failed under the guard | The existing specific refusal; nothing was written | Fix the cause and create a new plan |
| The adapter failed after the first operation was dispatched | `interrupted` / `ambiguous`, `reconciliation_required: true`, with the partial `ApplyRecord` in the retained results | Verify the run, then resume it or create a new plan |
| You cancelled a run whose worker already held the write | `interrupted` / `ambiguous`, `reconciliation_required: true`; the cancel request answers `409 cancellation-ambiguous` | Verify the run, then resume it or create a new plan |
| You cancelled a finished plan before applying it | `cancelled` / `cancelled`; nothing was written, and `approve` and `apply` now answer `409 run-cancelled` | Create a new plan run if you still want the change |
| The worker or its guard session was lost | `interrupted` / `ambiguous`, `reconciliation_required: true` | Verify the run, then resume it or create a new plan |
| The run completed normally | The existing succeeded result | Nothing; this run accepts no further write |

Cancellation is not a clean-stop guarantee for a write. A worker that has already begun
dispatching may have changed the destination before the cancellation reached it, so Sync
records the conservative answer rather than a cancelled one — unless the normal completion
path won first.

### Reconcile an uncertain write

Sync never retries a write by itself after an uncertain result. There are two ways to
reconcile an interrupted run.

Resume it on the same run, as [Resume an interrupted run](#resume-an-interrupted-run)
describes: run `POST /runs/{run_id}/verify`, read the state of each uncertain operation in
`results.verification.operations`, then call `POST /runs/{run_id}/resume`. A successful resume
is the only request that clears `reconciliation_required`.

Or plan again, for example when a node reported as `differs` holds a change that must stay:

1. create a new plan run on the same registered configuration;
2. read its summary. A plan with no operations means the destination currently matches the desired
   state; it does not prove which run made the changes; and
3. otherwise review the remaining operations and apply that new plan.

## Errors and retained state

Every error uses the same envelope:

```json
{
  "error": {
    "code": "checksum-conflict",
    "message": "expected_checksum does not match the retained reviewed plan",
    "status": 409,
    "run_id": "20260810T1500-0123abcd",
    "mutation_id": null
  }
}
```

A refusal that has structured context also carries `details`, such as the existing approval
of `already-approved`, or the `config_id` and `name` of the configuration that already has the
name of a package in `configuration-name-in-use`. Other errors have no `details` field.

| Status | Meaning |
| --- | --- |
| `401` | Missing or invalid authentication. |
| `403` | The actor does not own the mutation or the schedule and is not an administrator. |
| `404` | The Sync run, schedule (`schedule-not-found`) or run-owned artifact does not exist, or a list filter names an unknown configuration (`configuration-not-found`) or configuration version (`configuration-version-not-found`). |
| `409` | Idempotency conflict, missing confirmation, an apply of a plan that leaves out records without `confirm_left_out` (`left-out-confirmation-required`), stale checksum, non-cancellable execution, a run that cannot admit another stage (`run-execution-conflict`), or a cancelled write whose outcome is uncertain (`cancellation-ambiguous`). For a registration or a new version: a package whose name another configuration already has (`configuration-name-in-use`). For approval: a run that cannot be approved (`run-not-approvable`), a plan whose checksum is unconfirmed (`plan-checksum-unverified`), a checksum that differs from the plan's (`checksum-mismatch`), or a second approval (`already-approved`). When the service requires approval: an apply without an approval (`approval-required`) or with a different checksum (`approval-checksum-mismatch`), or a `sync` (`approval-required-for-sync`). For a cancelled run: an `approve` or `apply` (`run-cancelled`), or a second cancel (`run-already-cancelled`). A verify, apply or resume of a scheduled run with branch review (`scheduled-run-not-appliable`). The refusals of a schedule request are listed in [Schedules](#schedules). |
| `410` | The retained plan or artifact has expired, or the orchestrator no longer holds a flow run whose log `GET /runs/{run_id}/logs` reads (`log-expired`). |
| `422` | Invalid request schema or query parameter (`request-invalid`), a list cursor that does not decode or was issued for another list or other filters (`invalid-cursor`), missing idempotency key, or a secret-bearing flow parameter. |
| `503` | Submission, live orchestration detail, or retained data cannot be confirmed or retrieved, or the orchestrator cannot be reached to read a run's log (`log-unavailable`). For the account routes: a password check or hash that waited more than 5 seconds for a place, or for another check of the same account name (`sign-in-busy`). |

Error messages name "the orchestrator", not Prefect, and never hold its address.

Prefect detail can expire or become unavailable while the durable Sync record, results,
and published artifacts remain readable. Cancellation never deletes the product record or
its execution history. The API adds no retry policy and no recovery state machine. A schedule
has its own overlap policy, which applies only to its starts; see [Schedules](#schedules).
